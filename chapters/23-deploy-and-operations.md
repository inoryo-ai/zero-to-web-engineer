# 第23章 デプロイと運用（環境・ログ・監視・障害対応・Docker入門）

> **この章のゴール**：作ったアプリを「自分のPCの外で、動かし続ける」ために必要な考え方と道具を身につけます。デプロイの流れ、Docker、ログと監視、障害対応、本番の DB を安全に変える方法を学びます。
> **目安時間**：読む 3.5時間 ＋ 演習 8時間
> **前提**：第22章まで

## この章で学ぶこと

- 開発・ステージング・本番の環境の違いと、環境変数で設定を切り替える理由を説明できる
- デプロイの流れ（ビルド・リリース・起動・切り替え・確認）と、PaaS・Kamal の違いを説明できる
- Docker のイメージ・コンテナ・Dockerfile・compose を説明し、ループバック限定でコンテナを動かせる
- ログ・メトリクス・アラートの役割の違いを説明し、自分のアプリで見るべき指標を決められる
- 障害が起きたときに、一次対応・報告・ポストモーテムの流れで動ける
- 本番の DB マイグレーションを安全に流す手順と、バックアップの取り方・戻し方を説明できる

## 「動いた」の先にある仕事

ここまでの演習は、すべて自分の PC の上で、`127.0.0.1` で待ち受けて動かしてきました。これは第10章で決めた安全のためのルールです。

実際のサービスは、インターネット上のサーバで、24時間365日動き続けます。そこには、PC の上では考えなくてよかった仕事がたくさんあります。

- 新しいコードを、利用者を止めずに届ける（デプロイ）
- 本番だけで使う設定や秘密情報を、安全に渡す（環境と環境変数）
- 今、正常に動いているかを知る（ログ・メトリクス・アラート）
- 壊れたときに、早く気づいて、早く戻す（障害対応）
- 消えたら困るデータを守る（バックアップ）

この仕事全体を **運用** と呼びます。ソフトウェアの一生のうち、作っている期間より、動かしている期間の方がずっと長いものです。ジュニアのうちから運用の考え方を知っておくと、「運用しやすいコード」が書けるようになります。

## 環境：開発・ステージング・本番

### 3つの環境

アプリを動かす場所と目的によって、環境を分けます。

- **開発環境**（development）：自分の PC で、作りながら動かす環境。エラーの詳細が見え、コードを変えるとすぐ反映されます。
- **ステージング環境**（staging）：本番とほぼ同じ構成で、本番に出す前の最終確認をする環境。チームの人だけが使います。
- **本番環境**（production）：利用者が実際に使う環境。

これに加えて、Rails にはテストを実行するための **テスト環境**（test）があります。

たとえるなら、演劇です。開発環境は稽古場、ステージング環境は本番と同じ舞台で行う通し稽古（ゲネプロ）、本番環境は観客の入った本番の舞台です。稽古場でうまくいっても、本番の舞台の照明や音響で問題が出ることがあります。だから通し稽古をします。

### Rails の環境の切り替え

Rails では、環境変数 `RAILS_ENV` で環境を切り替えます。何も指定しなければ `development` です。環境ごとの設定は `config/environments/` の下にあります。

- `development.rb`：コードの再読み込みを有効にする、エラーの詳細を表示する、など
- `test.rb`：メールを実際に送らない、など
- `production.rb`：エラーの詳細を隠す（第20章）、HTTPS を強制する、ログを標準出力に出す、など

ステージングには、`production.rb` の設定をそのまま使い、接続先や秘密情報だけを環境変数で変える方法がよく使われます。本番と設定の違いが少ないほど、「ステージングでは動いたのに本番で壊れた」が起きにくくなるからです。

### ステージングのデータ

ステージングでは、本番のデータをそのままコピーして使ってはいけません。ステージングは本番より守りが弱いことが多く、触れる人も多いからです。第10章のルールどおり、ダミーデータか、個人情報を取り除いて加工したデータを使います。

### 環境変数で設定を渡す

環境ごとに違う値（DB の接続先、外部 API のキー、ログの詳しさなど）は、コードに書かずに環境変数で渡します。第20章で秘密情報について学んだのと同じ仕組みです。

この「コードは同じで、設定だけを環境から渡す」という考え方は、**Twelve-Factor App**（12要素のアプリ）という有名な設計指針の一つとしても知られています。同じコード（同じイメージ）を、ステージングにも本番にも、設定だけ変えて置けるようになります。

数値の設定を環境変数で受け取るときは、型の変換に注意します。環境変数の値は、いつも文字列だからです。

```ruby
max_threads = Integer(ENV.fetch("RAILS_MAX_THREADS", "3"))
log_level   = ENV.fetch("RAILS_LOG_LEVEL", "info")
puts "スレッド数: #{max_threads} / ログレベル: #{log_level}"
```

```text
$ ruby threads.rb
スレッド数: 3 / ログレベル: info

$ RAILS_MAX_THREADS=5 RAILS_LOG_LEVEL=debug ruby threads.rb
スレッド数: 5 / ログレベル: debug

$ RAILS_MAX_THREADS=five ruby threads.rb
threads.rb:1:in `Integer': invalid value for Integer(): "five" (ArgumentError)
```

`Integer()` は、数字として読めない文字列を渡すと例外を発生させます。`"five".to_i` のように書くと、黙って `0` になってしまいます。設定の間違いは、起動時に大きな音を立てて止まる方が、後で原因の分からない不具合になるより、ずっとましです。

Rails アプリでよく使われる環境変数を挙げておきます。

| 環境変数 | 役割 |
|---|---|
| `RAILS_ENV` | 環境の名前（`production` など） |
| `RAILS_MASTER_KEY` | credentials を開く鍵（第20章） |
| `DATABASE_URL` | DB の接続先（PostgreSQL などを使う場合） |
| `RAILS_MAX_THREADS` | Puma のスレッド数 |
| `WEB_CONCURRENCY` | Puma のプロセス数 |
| `RAILS_LOG_LEVEL` | ログの詳しさ |

どの変数が実際に使われるかは、Rails のバージョンと、`config/puma.rb`・`config/database.yml`・`config/environments/production.rb` の書き方によります。自分のアプリのファイルを `ENV` で検索して確かめてください。

## デプロイの流れ

### デプロイとは

**デプロイ**は、新しいバージョンのアプリを、本番などの環境に配置して動かすことです。引っ越しにたとえると、荷造り（ビルド）、新居への搬入（リリース）、入居（起動）、住所変更の届け出（切り替え）、のような段階があります。

一般的なデプロイの流れは次のとおりです。

```text
1. CI でテストと静的解析が通る（第22章）
2. ビルド：実行に必要なものをまとめる（gem のインストール、アセットの準備、Docker イメージの作成など）
3. リリース：設定（環境変数）と組み合わせ、DB マイグレーションを実行する
4. 起動：新しいバージョンのプロセスを立ち上げる
5. ヘルスチェック：新しいプロセスが正常に応答するか確かめる
6. 切り替え：利用者のリクエストを、古いプロセスから新しいプロセスへ移す
7. 確認：エラーが増えていないか、ログとメトリクスを見る
```

5 の **ヘルスチェック** は、「アプリが生きているか」を確かめる簡単なリクエストです。Rails 7.1 以降の新しいアプリには、`/up` というヘルスチェック用の URL が最初からあります。正常なら 200、起動に失敗していれば 500 を返します。

5 と 6 を組み合わせると、「新しいプロセスが正常だと確かめてから切り替える」ことができます。こうすると、利用者から見てサービスが止まらないデプロイ（**ゼロダウンタイムデプロイ**）になります。新しいバージョンが起動に失敗したら、切り替えずに古いものを動かし続ければよいからです。

### ロールバック

デプロイした後で問題が見つかったら、一つ前のバージョンに戻します。これを **ロールバック** と呼びます。障害対応で最初に考える手段の一つです。

ただし、コードは戻せても、DB の変更は簡単には戻せないことがあります。列を削除するマイグレーションを流した後で、コードだけ戻しても、消えたデータは返ってきません。これが、後の節「DB マイグレーションを本番で安全に流す」につながります。

### デプロイ先の選び方：PaaS と Kamal

デプロイ先には、大きく分けて2つの選択肢があります。

**PaaS**（Platform as a Service）は、サーバの管理をサービス側に任せる方法です。GitHub のリポジトリをつなぐか、コマンドを1つ実行すると、ビルドから起動まで面倒を見てくれます。Rails でよく使われるものに、Render や Fly.io があります。

- **Render**：管理画面で GitHub のリポジトリをつなぎ、ビルドのコマンドと起動のコマンドを設定します。設定をファイル（`render.yaml`）に書いて管理することもできます。
- **Fly.io**：`fly` というコマンドラインツールを使います。`fly launch` でアプリの設定ファイル（`fly.toml`）を作り、`fly deploy` でデプロイします。秘密情報は `fly secrets set` で設定します。

どちらも、環境変数は管理画面やコマンドで設定し、リポジトリには入れません。料金や無料で使える範囲はサービスごとに違い、よく変わります。使う前に、必ず各サービスの公式の料金ページで確認してください。

**Kamal** は、自分で用意したサーバに、Docker を使ってアプリを配置する道具です。Rails 8 の新しいアプリには、Kamal の設定ファイル（`config/deploy.yml`）が最初から入っています。`kamal setup` で初回の準備を、`kamal deploy` でデプロイを、`kamal rollback` でロールバックを行います。秘密情報は `.kamal/secrets` というファイルを通して渡します。このファイルには秘密情報そのものではなく、環境変数やパスワード管理ツールから値を読み出す指示を書くのが基本です。

PaaS と Kamal の違いは、「どこまで自分で面倒を見るか」です。

| | PaaS | Kamal（自分のサーバ） |
|---|---|---|
| サーバの OS の更新・ファイアウォール | サービス側 | 自分 |
| 自由度 | サービスの決まりの範囲 | 高い |
| 最初の手間 | 少ない | 多い |
| 学べること | アプリのデプロイ | サーバ運用まで含めた全体 |

初めてデプロイするなら、サーバの守りをサービス側に任せられる PaaS から始めるのがおすすめです。自分のサーバを持つと、OS のセキュリティ更新やファイアウォールの設定まで、すべて自分の責任になります。

## Docker入門

### なぜ Docker を学ぶのか

「自分の PC では動くのに、サーバでは動かない」。その原因の多くは、環境の違いです。Ruby のバージョン、OS、インストールされているライブラリが少しずつ違うのです。

**Docker** は、アプリと、それを動かすのに必要なもの（OS の一部、Ruby、gem など）を、まとめて一つの箱に詰める道具です。同じ箱なら、どこで開けても同じように動きます。

たとえるなら、引っ越しで家具をバラバラに運ぶのではなく、部屋ごとコンテナに詰めて運ぶようなものです。運んだ先で組み立て直す必要がありません。Kamal も、多くの PaaS も、裏側でこの仕組みを使っています。

Docker を使うには、macOS では Docker Desktop などをインストールします。Windows では WSL と組み合わせて使います。導入方法は公式のドキュメントに従ってください。

### イメージとコンテナ

Docker の一番大事な2つの言葉です。

- **イメージ**：アプリと実行環境を詰めた、読み取り専用のひな形。
- **コンテナ**：イメージから作られた、実際に動いている実体。

第5章で学んだ、Ruby のクラスとインスタンスの関係に似ています。イメージがクラス、コンテナがインスタンスです。1つのイメージから、いくつでもコンテナを作れます。コンテナの中で何かを変えても、元のイメージは変わりません。コンテナを消せば、中で変えたものも消えます。

コンテナが消えると中身も消える、という性質は大切です。DB のデータやアップロードされたファイルのような「消えては困るもの」は、コンテナの外（**ボリューム** と呼ばれる保存場所など）に置く必要があります。

### Dockerfile

イメージの作り方を書いたファイルが **Dockerfile** です。小さな Ruby のプログラムを動かすだけの、学習用の例を見てみます。

```dockerfile
# 土台になるイメージ（Ruby 3.3 入りの小さな Linux）
FROM ruby:3.3-slim

# コンテナの中の作業フォルダ
WORKDIR /app

# PC のファイルをイメージの中にコピーする
COPY hello.rb .

# コンテナを起動したときに実行するコマンド
CMD ["ruby", "hello.rb"]
```

主な命令の意味は次のとおりです。

- `FROM`：土台にするイメージ。公式の Ruby イメージなど、既にあるものを使います。
- `WORKDIR`：以降の命令を実行するフォルダ。
- `COPY`：PC のファイルをイメージにコピーします。
- `RUN`：イメージを作るときにコマンドを実行します（gem のインストールなど）。
- `EXPOSE`：コンテナが待ち受けるポートの番号を記録します。これだけでは外から接続できるようにはなりません。
- `CMD`：コンテナを起動したときに実行するコマンド。

イメージを作り（ビルド）、コンテナとして動かすコマンドは次のとおりです。

```bash
docker build -t hello-ruby .
docker run --rm hello-ruby
```

`-t` はイメージに名前を付ける指定、`--rm` は終わったコンテナを自動で消す指定です。

Rails 7.1 以降の `rails new` では、本番用の Dockerfile が最初から作られます。gem のインストール、アセットの準備、実行用のユーザーの作成などが、もっと細かく書かれています。上の小さな例を理解してから読むと、各行の意味が追いやすくなります。

### .dockerignore：鍵を箱に入れない

`COPY . .` のようにフォルダ全体をコピーすると、`.gitignore` で除外していたファイルまでイメージに入ってしまいます。`.gitignore` は Git のための設定で、Docker は読まないからです。

Docker には **.dockerignore** という別の除外ファイルがあります。ここに `config/master.key` や `.env` を書いておかないと、秘密情報がイメージの中に焼き込まれます。イメージは他のサーバや人に配られることがあるので、これは秘密情報の漏えいです。Rails が作る `.dockerignore` には、最初から `master.key` などが入っています。自分で編集するときは消さないように注意します。

### ポートの公開：ここは要注意

コンテナの中で動くサーバに PC から接続するには、ポートを **公開** します。

```bash
docker run --rm -p 127.0.0.1:3000:3000 myapp
```

`-p 127.0.0.1:3000:3000` は、「PC の `127.0.0.1` の 3000番」を「コンテナの 3000番」につなぐ、という意味です。

ここで、とても大事な注意があります。`-p 3000:3000` のように PC 側のアドレスを省略すると、Docker は **全部のネットワークインターフェース（`0.0.0.0`）** で待ち受けます。第10章で禁止した状態です。しかも Linux では、Docker のポート公開が、OS のファイアウォールの設定より優先されてしまう場合があります。「ファイアウォールで閉じているから大丈夫」と思っていても、外から接続できてしまうのです。**ポートを公開するときは、必ず `127.0.0.1:` を先頭に付けてください。**

一方で、コンテナの **中の** サーバは `0.0.0.0` で待ち受ける必要があります。コンテナはそれぞれ自分専用のネットワークを持っていて、コンテナの中の `127.0.0.1` は、コンテナ自身しか指さないからです。外（PC）から届いたリクエストは、コンテナの中では別のネットワークインターフェースに届きます。

整理すると、次のとおりです。

- コンテナの中：`0.0.0.0` で待ち受ける（コンテナの外からの入口を作るため）
- PC 側の公開：`127.0.0.1:` を必ず付ける（PC の外には出さないため）

確かめ方も、これまでと同じです。

```bash
docker ps                                  # PORTS 欄が 127.0.0.1:3000->3000/tcp になっているか
lsof -nP -iTCP:3000 -sTCP:LISTEN           # 127.0.0.1:3000 で待ち受けているか
```

`0.0.0.0:3000->...` や `*:3000` と表示されたら、すぐにコンテナを止めて、`-p` の指定を直します。

### docker compose：複数のコンテナをまとめて動かす

アプリが DB サーバ（PostgreSQL など）や Redis（第21章）を使う場合、コンテナが複数になります。それらをまとめて定義し、一度に起動する道具が **docker compose** です。設定は `compose.yaml`（古い名前は `docker-compose.yml`）に書きます。

開発用に PostgreSQL を動かす例です。

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: local-dummy-password
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:
```

- `image: postgres:17`：PostgreSQL 17 の公式イメージを使います。データの保存先のパスは、イメージのメジャーバージョンによって変わることがあります。バージョンを上げるときは、イメージの公式の説明を確認してください。
- `POSTGRES_PASSWORD`：この PC の中だけで使う、ダミーのパスワードです。本番のパスワードをここに書いてはいけません。
- `ports`：ここでも `127.0.0.1:` を付けています。
- `volumes`：DB のデータを、コンテナの外のボリュームに保存します。コンテナを作り直しても、データが残ります。

```bash
docker compose up -d      # 裏で起動する
docker compose ps         # 状態を見る
docker compose down       # 止めて片付ける（ボリュームは残る）
```

## ログ・メトリクス・アラート

### 3つの役割

本番で何が起きているかを知る手段は、主に3つあります。

- **ログ**：一つ一つの出来事の記録。「12:03:15 に、このリクエストが来て、500 エラーになった」。
- **メトリクス**：数値の時系列。「1分あたりのリクエスト数」「エラーの割合」「応答時間」。
- **アラート**：メトリクスなどが決めた条件を超えたときに、人に知らせる仕組み。

たとえるなら、健康管理です。ログは日記、メトリクスは毎日測る体温や血圧のグラフ、アラートは「体温が38度を超えたら連絡して」という取り決めです。グラフで異変に気づき、日記を読んで原因を探します。

### ログ

Rails の本番環境では、ログを **標準出力**（プログラムが普通に文字を出力する先）に書くのが一般的です。PaaS や Docker は、標準出力をまとめて集め、検索できるようにしてくれます。Rails のバージョンによって、この設定が最初から有効になっているか、環境変数で有効にするかが違います。`production.rb` を確認してください。

ログで大切なことを3つ挙げます。

1. **リクエスト ID を付ける**：同時に多くのリクエストが来ると、ログの行が混ざります。各行にリクエストごとの ID を付けると、一つのリクエストの流れを追えます。Rails では `config.log_tags = [:request_id]` で設定でき、新しいアプリの `production.rb` には最初から入っていることが多いです。第20章で「エラー画面には問い合わせ用の番号だけ出す」と書いたのは、この ID を想定しています。
2. **ログレベルを使い分ける**：`debug`（開発時の細かい情報）、`info`（通常の出来事）、`warn`（注意が必要）、`error`（失敗）、`fatal`（致命的）。本番では普通 `info` 以上を記録します。
3. **個人情報と秘密情報を出さない**：第20章のとおりです。本番のログは、開発のログよりずっと多くの人や仕組みを通ります。

### メトリクス

最低限見ておきたいメトリクスは、次の4つです。

- **リクエスト数**：どれだけ使われているか。急に増えた（攻撃や話題）、急に減った（どこかで止まっている）を知る。
- **エラーの割合**：5xx を返した割合。
- **応答時間**：リクエストを受けてから返すまでの時間。
- **リソースの使用量**：CPU、メモリ、DB の接続数、ジョブのキューに溜まっている数（第21章）。

応答時間は、平均だけを見てはいけません。100人中99人が0.1秒でも、1人が30秒待たされていると、平均はそれほど悪く見えません。そこで **パーセンタイル** を使います。「p95 が 0.8秒」は「遅い方から5%を除くと、全員0.8秒以内に返っている」という意味です。p50（中央値）、p95、p99 をよく見ます。

### アラート

アラートの設計で一番大切なのは、「鳴ったら、人が何かをする必要がある」ものだけを鳴らすことです。

- **良いアラート**：「5分間、エラーの割合が5%を超えている」。利用者が困っている、という症状に基づいている。
- **悪いアラート**：「CPU 使用率が一瞬70%を超えた」。利用者は困っていないかもしれず、何をすればよいか分からない。

意味の薄いアラートが多いと、人は慣れて無視するようになります（**アラート疲れ**）。第22章の flaky テストと同じ構図です。アラートごとに「鳴ったら最初に何を見るか、何をするか」を書いた手順書（**ランブック**）を用意しておくと、慌てずに動けます。

エラーの記録・通知に特化した外部サービス（エラートラッキングサービス）もよく使われます。例外が起きると、スタックトレースと発生回数をまとめて知らせてくれます。そこに送る情報にも、個人情報を含めないように設定します。

## 障害対応

### 障害は起きるものとして備える

どれだけ気をつけても、障害は起きます。大切なのは、起きないことより、**早く気づいて、早く戻して、同じことを繰り返さない** ことです。

障害対応は、大きく3つの段階に分かれます。

1. **一次対応**：被害の拡大を止め、サービスを戻す
2. **報告**：関係者に、分かっていることを伝え続ける
3. **ポストモーテム**：落ち着いてから振り返り、再発を防ぐ

### 一次対応：まず止血する

一次対応の目的は、**原因を突き止めることではなく、利用者への影響を止めること** です。怪我をしたら、原因を考える前にまず止血するのと同じです。

よく使う手段は、次のとおりです。

- 直前のデプロイが怪しければ、**ロールバック** する
- 問題のある機能だけを **止める**（機能を切り替えるフラグや設定で無効にする）
- 外部サービスの障害なら、その部分を **諦める** 表示に切り替える（第21章の「失敗時の扱い」）
- 負荷が原因なら、プロセスを **増やす**

ジュニアとして最初に障害に出会ったときに大切なのは、次の3つです。

- **すぐに声を上げる**：「エラーが増えているように見えます」と、確信がなくてもチームに伝えます。黙って一人で調べ続けるのが、一番被害を大きくします。
- **本番で勝手に直さない**：本番のサーバやDBを、相談なしに操作しません。よかれと思った操作が、被害を広げることがあります。
- **やったことを時刻付きでメモする**：「14:05 エラー率の上昇に気づいた」「14:08 チャンネルに報告」。後の報告とポストモーテムで必ず役に立ちます。

### 報告：事実と推測を分ける

障害の間は、決まった間隔で状況を伝えます。報告では、事実と推測をはっきり分けます。

```text
【障害報告 第1報】14:20 時点
・事象：14:02 頃から、投稿の作成で一部エラーが発生（事実：エラー率 約30%）
・影響：投稿の作成ができない利用者がいる。閲覧は正常（事実）
・原因：14:00 のデプロイの変更が関係している可能性（推測、調査中）
・対応：14:25 にロールバック予定
・次回の報告：14:40 または状況が変わったとき
```

「いつ」「何が」「誰に影響が」「今何をしているか」「次にいつ報告するか」を入れます。「原因が分かってから報告しよう」と待つと、関係者は何も分からないまま不安になります。分かっていないことは「分かっていない」と書けば十分です。

### ポストモーテム：人ではなく仕組みを直す

サービスが戻った後、**ポストモーテム**（事後の振り返り）を書きます。目的は、同じ障害を繰り返さないことです。

ポストモーテムで最も大切な約束は、**個人を責めない**（ブレームレス）ことです。「Aさんが確認を怠った」で終わると、次は別の人が同じミスをします。それに、責められると人は失敗を隠すようになり、次の障害の発見が遅れます。「なぜ、確認しなくても本番に出せる仕組みになっていたのか」と、仕組みに目を向けます。

ポストモーテムには、たとえば次の項目を書きます。

- **概要**：何が起きたか、数行で
- **影響**：誰が、どのくらいの時間、何に困ったか
- **時系列**：検知、報告、一次対応、復旧までを時刻付きで
- **原因**：直接の原因と、それを許した背景。「なぜ」を何度か繰り返して掘り下げる
- **うまくいったこと・うまくいかなかったこと**
- **再発防止策**：具体的な作業として、担当者と期限を付ける。「気をつける」は対策になりません。テストの追加、CI のチェックの追加、アラートの追加などの、仕組みの変更にします。

## DB マイグレーションを本番で安全に流す

### なぜ本番のマイグレーションは怖いのか

開発環境では、マイグレーションを気軽に流し、失敗したら DB を作り直せました。本番ではそうはいきません。理由は3つあります。

1. **データがある**：消えたデータは、バックアップからしか戻せません。
2. **大きい**：何百万行もあるテーブルの変更は時間がかかり、その間テーブルが **ロック**（他の処理が待たされる状態）されることがあります。ロック中は、利用者の操作が止まります。
3. **古いコードと新しいコードが同時に動く**：デプロイの途中では、古いバージョンのプロセスと新しいバージョンのプロセスが並んで動きます。マイグレーションは、両方から見て問題ない形でなければなりません。

### 広げてから、縮める

3つ目の問題に対する基本の型が、**拡張と縮小**（expand and contract）です。一度に変えず、「新しいものを足す」と「古いものを消す」を、別々のデプロイに分けます。

列の名前を `body` から `content` に変えたい場合を考えます。`rename_column` で一度に変えると、デプロイの途中で古いコードが `body` を探して失敗します。代わりに、次のように段階を分けます。

```text
1回目のデプロイ：content 列を追加する。コードは body と content の両方に書き込み、body から読む
（データの移行）：既存の行の body を content にコピーする（少しずつ）
2回目のデプロイ：コードを content から読むように変える。body にはもう書かない
3回目のデプロイ：コードから body を使わないことを Rails に伝える（ignored_columns）
4回目のデプロイ：body 列を削除する
```

手間はかかりますが、どの時点でも、古いコードと新しいコードの両方が正しく動きます。どの段階でも、一つ前に戻せます。

### 安全に流すためのコツ

- **列の削除は、まずコードから使わなくする**：Rails はモデルの列の一覧を覚えています。いきなり列を消すと、動いているプロセスが混乱します。先に `self.ignored_columns += ["body"]` で無視させてデプロイし、その後で削除します。
- **データの移行は少しずつ**：何百万行を一度に更新すると、長いロックが発生します。`in_batches` で、たとえば1,000行ずつ更新します。データの移行は、構造を変えるマイグレーションとは分けて実行するのが一般的です。
- **大きなテーブルへのインデックス追加に注意する**：PostgreSQL では、`algorithm: :concurrently` を指定すると、書き込みを止めずにインデックスを作れます。このときマイグレーションに `disable_ddl_transaction!` も必要です。これは PostgreSQL の機能で、DB の種類によって使えるかどうかが違います。
- **`NOT NULL` の追加は段階を分ける**：既存の行に値が入っていない列に、いきなり `NOT NULL` を付けると失敗します。値を埋めてから制約を付けます。
- **流す前にバックアップを確認する**：最新のバックアップがあり、そこから戻せることを確かめてから流します。
- **戻せるか試しておく**：開発環境で `bin/rails db:migrate` の後に `bin/rails db:rollback` を実行し、元に戻せることを確かめます。戻せないマイグレーション（データを消すものなど）は、レビューで特に慎重に見てもらいます。
- **道具の助けを借りる**：`strong_migrations` という gem は、本番で危険なマイグレーションを書くと警告してくれます。

SQLite は `ALTER TABLE` でできることが限られていて、Rails はテーブルを作り直すことで列の変更を実現する場合があります。大きなテーブルではこれも時間がかかります。どの DB を使っていても、「本番と同じくらいの量のダミーデータで、かかる時間を測る」のが確実な方法です。

## バックアップ

### バックアップは「戻せて」初めて意味がある

**バックアップ**は、データの写しを別の場所に保存しておくことです。間違った操作、バグ、ハードウェアの故障、攻撃などでデータが失われたときに、そこから戻します。

運用の世界には、「戻したことのないバックアップは、バックアップではない」という言葉があります。いざ戻そうとしたら、ファイルが壊れていた、必要なテーブルが入っていなかった、戻し方を誰も知らなかった、という事故がよく起きるからです。定期的に、実際に戻す練習（**リストア訓練**）をします。

### 何を、どこに、どのくらい

- **何を**：DB だけでなく、アップロードされたファイル（Active Storage など）も対象です。credentials を開く鍵も、別の安全な場所に保管が必要です。鍵がなければ、暗号化された設定を復元できません。
- **どこに**：本番と同じ場所だけに置くと、その場所ごと失われたら終わりです。よく知られた目安に **3-2-1 ルール** があります。データのコピーを3つ持ち、2種類の保存先を使い、1つは離れた場所に置く、という考え方です。
- **どのくらい**：「どの時点まで戻せればよいか」（**RPO**、目標復旧時点）と、「どのくらいの時間で戻せればよいか」（**RTO**、目標復旧時間）を決めます。1日1回のバックアップなら、最悪で1日分のデータを失います。それで困るなら、もっと頻繁に取る仕組みが必要です。

バックアップには、本番と同じ個人情報が入っています。本番と同じかそれ以上に、暗号化と、見られる人の制限が必要です。

### SQLite でのバックアップの例

SQLite の DB は1つのファイルですが、アプリが書き込んでいる最中にファイルをそのままコピーすると、壊れた写しができることがあります。SQLite のコマンドラインツールの `.backup` を使うと、整合性の取れた写しを作れます。

```text
$ sqlite3 demo.sqlite3 "CREATE TABLE posts(id INTEGER PRIMARY KEY, title TEXT); INSERT INTO posts(title) VALUES ('テスト投稿1'),('テスト投稿2');"
$ sqlite3 demo.sqlite3 ".backup backup-20261001.sqlite3"
$ sqlite3 demo.sqlite3 "DELETE FROM posts;"
$ sqlite3 demo.sqlite3 "SELECT count(*) FROM posts;"
0
$ sqlite3 backup-20261001.sqlite3 "PRAGMA integrity_check; SELECT count(*) FROM posts;"
ok
2
```

間違って全部消した後でも、バックアップには2件が残っています。`PRAGMA integrity_check` は、DB ファイルが壊れていないかを確かめる命令で、問題がなければ `ok` と表示されます。

本番で SQLite を使う場合は、変更を継続的に別の場所へ送る Litestream のような道具を使うこともあります。PostgreSQL なら `pg_dump` で写しを作り、`pg_restore` などで戻します。クラウドの管理された DB サービスには、自動バックアップや「ある時点に戻す」機能があることが多いです。どの方法でも、戻す練習が必要なことは変わりません。

## インターネットに公開する前に

ここまでのすべての演習は、ループバック（`127.0.0.1`）限定で行ってきました。この章の演習でも、最後の「発展」以外はループバック限定です。

アプリをインターネットに公開すると、世界中の誰でも、もちろん攻撃者も、アクセスできるようになります。公開されたサーバには、数分のうちに自動の攻撃ツールからリクエストが届き始めます。だから、公開は次の条件をすべて満たしてからにします。

- **認証と認可**：第19章の認証が全画面に効いていて、第20章の IDOR などのテストがすべて通っている。
- **秘密情報**：`master.key`・`.env`・秘密鍵がリポジトリにもイメージにも入っていない。本番用の値は、デプロイ先の環境変数（または Secrets の仕組み）で渡している。開発で使った値を使い回さない。
- **ダミーデータのみ**：本物の個人情報（自分や知人のものを含む）を入れない。新規登録を誰でもできる状態なら、他人が個人情報を入力する可能性があるので、登録を自分だけに制限するなどの対策をする。
- **本番設定**：エラーの詳細が表示されない（第20章）。HTTPS が強制されている。
- **自動検査**：CI（第22章）で、テスト・RuboCop・Brakeman・bundler-audit がすべて通っている。
- **上限**：ログインのレート制限や、一覧の最大件数などが入っている（第20章）。
- **片付けの予定**：いつ公開をやめて、アプリとデータを削除するかを決めている。

一つでも満たせないなら、公開しません。「ちょっとだけ」「URL を知っている人しか来ない」は、理由になりません。URL は推測され、自動で探されます。

## 実務ではこうなる

- **デプロイはボタン一つ、またはマージで自動**：多くのチームでは、`main` にマージすると CI を経て自動でステージングにデプロイされ、確認後に本番へ出す、という流れになっています。ジュニアが最初にデプロイを任されるときは、必ず先輩と一緒に、手順書を見ながら行います。
- **デプロイの後は見守る**：デプロイして終わりではありません。10〜30分は、エラーの割合と応答時間を見守ります。「金曜の夕方にデプロイしない」という習慣のチームもあります。問題が出たときに、対応できる人が少ないからです。
- **当番制**：障害の連絡を受ける当番（オンコール）を、交代で担当するチームが多いです。ジュニアは最初、先輩の当番に付いて学びます。
- **マイグレーションはレビューの重点項目**：本番の DB に触る変更は、普通のコードより慎重にレビューされます。大きなテーブルへの変更は、流す時間帯まで相談して決めます。

ジュニアがやりがちな失敗も挙げておきます。

- 本番の DB に、確認のつもりで手で接続し、誤って更新してしまう。本番での手作業は、必ず手順を書いて、もう一人に見てもらいながら行います。
- 障害に気づいたのに、自分のせいだと思って言い出せず、一人で調べ続ける。
- `rename_column` や `remove_column` を一度のデプロイで流し、デプロイの途中でエラーが大量に出る。
- `docker run -p 3000:3000` で、開発中のアプリを同じネットワークの全員に公開してしまう。
- バックアップは取っていたが、一度も戻したことがなく、いざというときに戻し方が分からない。

## 演習

第22章のアプリをコピーして使います。

```bash
cp -R ~/workspace/ch22-ci ~/workspace/ch23-deploy
cd ~/workspace/ch23-deploy
```

演習23-1〜23-3は、すべて自分の PC の中で、ループバック限定で行います。サーバやコンテナを起動したら、毎回 `lsof -nP -iTCP:<ポート> -sTCP:LISTEN` で `127.0.0.1` になっていることを確かめます。データはダミーのみです。

### 演習23-1：環境変数で設定し、Docker で本番モードを動かす

- やること
  1. アプリの中で、環境によって変えたい設定を1つ選ぶ（例：一覧の最大件数、第21章の天気 API の接続先）。`ENV.fetch` で読むように変え、必須なら初期値を付けない。数値なら `Integer()` で変換する。
  2. その設定を読む部分のテストを書く（TDD）。「環境変数があればその値を使う」「数値として読めない値なら起動時に例外になる」などを確かめる。
  3. `.env.example` に、その環境変数の名前を追記する。
  4. `.dockerignore` を開き、`config/master.key` と `.env` が含まれていることを確かめる。なければ追加する。
  5. Rails が作った `Dockerfile` を読み、各行が何をしているかを `docs/operations.md` に自分の言葉で書く。特に、`EXPOSE` の行でコンテナが何番で待ち受けるかを確かめる。
  6. イメージをビルドし、本番モードのコンテナを起動する。`<コンテナのポート>` は手順5で確かめた番号にする。
     ```bash
     docker build -t ch23-app .
     docker run -d --name ch23-app -p 127.0.0.1:3000:<コンテナのポート> -e RAILS_MASTER_KEY="$(cat config/master.key)" ch23-app
     ```
  7. `docker ps` と `lsof` で待ち受け先を確かめ、ヘルスチェックの URL に接続する。確認が終わったら `docker stop ch23-app` と `docker rm ch23-app` で片付ける。
- **完了条件**
  - 手順2のテストが成功する。
  - `docker ps` の PORTS 欄が `127.0.0.1:3000->...` になっている。`0.0.0.0` や `[::]` が含まれない。
  - `curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3000/up` の出力が `200` になる。
  - `docker run --rm ch23-app ls config` の出力に `master.key` が含まれない（イメージに鍵が入っていない）。
- ヒント
  - Rails のバージョンによって、Dockerfile のコンテナ側のポートは 3000 の場合と 80 の場合があります。
  - 本番モードでは HTTPS を前提にした設定（`assume_ssl` や `force_ssl`）が有効なことがあり、ブラウザでの画面操作がうまくいかない場合があります。この演習のゴールは、本番モードで起動し、ヘルスチェックが通ることの確認です。画面の動作確認は開発モードで行ってください。
  - コンテナの起動に失敗したら、`docker logs ch23-app` でログを読みます。第7章のエラーの読み方がそのまま使えます。
  - `RAILS_MASTER_KEY` を渡すコマンドは、シェルの履歴に残ります。この演習の鍵はローカルのダミー用なので許容しますが、本番の鍵では同じことをしないでください。

### 演習23-2：ログを読み、障害対応を練習する

外部 API の障害を、自分の PC の中で再現して、障害対応の流れを練習します。

- やること
  1. `production.rb` と `development.rb` のログの設定を読み、開発環境でもログにリクエスト ID が付くように設定する（`config.log_tags`）。
  2. 開発サーバを `127.0.0.1` で起動する。第21章の天気 API の接続先を、誰も待ち受けていないポート（例：`http://127.0.0.1:9`）に変えて、外部 API の障害を再現する。
  3. 天気を表示する画面を何度か開き、ログを観察する。1つのリクエスト ID を選び、そのリクエストの最初から最後までのログ行を `grep` で抜き出す。
  4. 「この障害に気づいてから10分後」の想定で、本文の例にならって障害報告の第1報を書く。
  5. 接続先を元に戻して「復旧」させ、ポストモーテムを書く。概要・影響・時系列・原因・うまくいったこと／いかなかったこと・再発防止策の項目を必ず入れる。
  6. 自分のアプリで見るべきメトリクスを4つと、アラートの条件を2つ決める。アラートには、鳴ったら最初に何をするかのランブックを付ける。
  7. 4〜6を `docs/operations.md` にまとめる。
- **完了条件**
  - 手順3で抜き出したログに、同じリクエスト ID の行が複数あり、そこに個人情報（メールアドレスなど）と API キーが含まれていない。
  - 障害報告に「事象」「影響」「原因（事実か推測かを明記）」「対応」「次回の報告予定」がある。
  - ポストモーテムの再発防止策が、「気をつける」ではなく、テスト・設定・アラートなどの具体的な変更になっていて、それぞれに期限が書かれている。
  - アラートの条件が、利用者への影響（症状）に基づいている。
- ヒント
  - 外部 API が失敗しても、画面全体が 500 エラーにならないことを確かめてください。もし 500 になるなら、第21章の「失敗時の扱い」が不十分です。それを再発防止策に入れて、テストを追加して直すところまでやると、さらに良い練習になります。
  - ポストモーテムで、自分を責める書き方になっていないか読み直してください。「確認を忘れた」ではなく「確認しなくても通る仕組みだった」と書けるか考えます。

### 演習23-3：安全なマイグレーションとバックアップ・リストア訓練

投稿の `body` 列を `content` に名前変更する作業を、拡張と縮小の型で行います。自分のアプリの列名に読み替えてかまいません。

- やること
  1. 始める前に、開発用の DB のバックアップを取る。SQLite の `.backup` を使い、バックアップファイルは `.gitignore` で除外した場所（例：`tmp/backups/`）に置く。
  2. 投稿のダミーデータを、少なくとも1,000件作る（`db/seeds.rb` やタスクで。中身はダミーのみ）。
  3. 次の段階を、それぞれ別のコミットにする。各コミットの時点で `bin/rails test` が成功すること。
     - コミット1：`content` 列を追加する。保存のときに `body` と `content` の両方に書く。読むのは `body` から。
     - コミット2：既存の行の `body` を `content` にコピーする処理を作る。`in_batches` を使い、一度に全部を更新しない。
     - コミット3：読む側を `content` に切り替え、`body` には書かない。モデルで `body` を `ignored_columns` に入れる。
     - コミット4：`body` 列を削除するマイグレーションを作る。
  4. 各マイグレーションについて、`bin/rails db:migrate` の後に `bin/rails db:rollback` を実行し、元に戻せるか確かめる。戻せないものがあれば、理由を `docs/operations.md` に書く。
  5. リストア訓練をする。手順1のバックアップを別のファイル名にコピーして開き、`PRAGMA integrity_check` が `ok` になること、投稿の件数がバックアップを取った時点と同じであることを確かめる。手順を `docs/operations.md` に書く。
- **完了条件**
  - `git log --oneline` で、段階ごとのコミットが4つ以上確認できる。
  - 各コミットをチェックアウトして `bin/rails test` を実行すると、どれも成功する（少なくともコミット1と3で確認する）。
  - リストアしたファイルで、`PRAGMA integrity_check` の結果が `ok`、件数がバックアップ時点と一致する。
  - `git ls-files tmp/backups` で何も表示されない（バックアップがコミットされていない）。
- ヒント
  - 「両方に書く」処理をどこに書くか（モデルのコールバック、属性の代入メソッドなど）を考えてみてください。それぞれの利点と欠点を比べるのも良い学習です。
  - コミット2のデータ移行を、マイグレーションの中に書くか、別のタスクにするかは、現場によって流派があります。どちらにしたか、理由を書いてください。
  - バックアップを戻す練習は、開発用 DB を直接上書きせず、別のファイルで行います。

### 演習23-4（発展）：条件を満たしたうえで、インターネットに公開する

この演習は任意です。**次の条件をすべて満たせない場合は、行わないでください。** 行わなくても、この教材の修了に影響はありません。

- やること
  1. 本文「インターネットに公開する前に」の条件を、チェックリストとして `docs/release-checklist.md` に書き写す。各項目に、満たしていることの根拠（テストの名前、コマンドの出力、設定ファイルの行）を書く。根拠が書けない項目が一つでもあれば、ここで中止する。
  2. デプロイ先（Render・Fly.io などの PaaS、または Kamal）を一つ選ぶ。選ぶ前に、公式サイトで料金と、無料で使える範囲があるかを自分で確認する。支払いの設定が必要な場合は、上限を設定できるかも確認する。
  3. 本番用の秘密情報は、デプロイ先の環境変数（または Secrets）の機能で設定する。開発で使った値は使わない。
  4. デプロイし、HTTPS の URL でヘルスチェックが 200 を返すこと、ログインしないと投稿の操作ができないことを確かめる。
  5. ログとメトリクスを確認できる画面を開き、自分のリクエストが記録されていることを確かめる。
  6. 決めておいた日に、アプリとデータを削除する。削除したことを確かめる。
- **完了条件**
  - `docs/release-checklist.md` のすべての項目に根拠が書かれている。
  - HTTPS の URL で `/up` が 200 を返す。ログインせずに投稿の作成・編集・削除の URL にアクセスすると、ログイン画面に飛ばされるか 401・404 などになる。
  - 公開を終える日付が記録され、その日に削除したことが記録されている。
- ヒント
  - 公開中は、本物の個人情報を一切入れません。自分の名前やメールアドレスも、ダミーに置き換えます。
  - 公開した URL を、SNS などに投稿しないでください。必要な相手にだけ伝えます。
  - 不審なアクセスがログに見えたら、それは正常な状態です（自動の攻撃ツールは常に来ています）。ただし、ログインの成功や想定外のデータの変化が見えたら、すぐに公開を止め、第20章のローテーションの手順に進みます。

## 確認クイズ

**Q1.** ステージング環境で、本番のデータベースをそのままコピーして使ってよいか。

**Q2.** `docker run -p 3000:3000 myapp` で起動した。何が問題か。どう直すか。

**Q3.** コンテナの中の Rails サーバは `0.0.0.0` で待ち受けている。これは第10章のルール違反か。

**Q4.** 本番で障害が起きた。原因はまだ分からない。報告は原因が分かってからにすべきか。

**Q5.** 列の名前を変えるのに、`rename_column` を一つのマイグレーションで流すと、何が起きうるか。

**Q6.** 毎日バックアップを自動で取っている。これで安心と言えるか。

### 解答と解説

1. **使ってはいけません。** ステージングは本番より守りが弱く、触れる人も多いことが多いです。ダミーデータか、個人情報を取り除いて加工したデータを使います。
2. **PC の全部のネットワークインターフェース（`0.0.0.0`）で公開されます。** 同じネットワークの他人が接続でき、Linux では OS のファイアウォールを素通りすることもあります。`-p 127.0.0.1:3000:3000` のように、必ず `127.0.0.1:` を付け、`docker ps` と `lsof` で確かめます。
3. **ルール違反ではありません。** コンテナは自分専用のネットワークを持ち、中の `127.0.0.1` はコンテナ自身しか指しません。外からの入口を作るために、中では `0.0.0.0` で待ち受けます。PC の外に出さないための制限は、ポートを公開するときの `127.0.0.1:` で行います。
4. **原因が分からなくても、すぐに報告します。** 事実（いつから、何が、誰に影響が）と推測（原因の候補）を分けて書き、次にいつ報告するかを伝えます。黙って調べ続けると、関係者が判断できず、被害が大きくなります。
5. **デプロイの途中で、古いコードが古い列名を探してエラーになります。** デプロイ中は古いコードと新しいコードが同時に動くからです。新しい列を足す、両方に書く、データを移す、読む先を変える、古い列を無視させる、消す、のように段階を分けます（拡張と縮小）。
6. **言えません。** 実際に戻せることを確かめていなければ、いざというときに使えないかもしれません。定期的にリストア訓練をし、DB 以外（アップロードファイル、鍵）も対象になっているか、別の場所に保存されているか、暗号化とアクセスの制限があるかも確かめます。

## AIの使い方（この章）

推奨する聞き方の例：

- 「Rails が生成した Dockerfile の各行について、自分の理解を書きました（ファイルの中身と自分のメモを貼る）。間違っている所や、理解が浅い所を指摘してください」
- 「列の名前を変える作業を、次の段階に分けました（段階を書く）。デプロイの途中で古いコードと新しいコードが同時に動くとき、各段階で問題が起きないか確認してください」
- 「自分が書いたポストモーテムです（ダミーの内容）。個人を責める書き方になっている所と、再発防止策が具体的でない所を指摘してください」

やってはいけない使い方：

- 本番のログ、環境変数の一覧、デプロイ先の設定画面のスクリーンショットを、そのまま AI に貼り付ける。秘密情報や利用者の個人情報が含まれていることがあります。
- 障害の最中に、AI が提案したコマンドを、意味を理解しないまま本番で実行する。本番での操作は、必ず意味を説明できる状態で、チームの合意のもとで行います。

## まとめ

- 開発・ステージング・本番は目的が違う環境です。同じコードを、環境変数で設定だけ変えて動かします。
- デプロイは、ビルド・リリース・起動・ヘルスチェック・切り替え・確認の流れで行い、問題があればロールバックします。
- Docker は、アプリと実行環境を箱に詰める道具です。ポートを公開するときは、必ず `127.0.0.1:` を付けます。
- ログ・メトリクス・アラートで状態を知り、障害は「止血・報告・ポストモーテム」の流れで、人ではなく仕組みを直します。
- 本番の DB は拡張と縮小の型で段階的に変え、バックアップは戻す練習をして初めて意味を持ちます。インターネットへの公開は、すべての条件を満たしてからです。

## 用語

| 用語 | 意味 |
|---|---|
| 運用 | アプリを本番で動かし続けるための仕事全体 |
| ステージング環境 | 本番とほぼ同じ構成で、公開前の最終確認をする環境 |
| デプロイ | 新しいバージョンのアプリを環境に配置して動かすこと |
| ヘルスチェック | アプリが正常に応答するかを確かめる簡単なリクエスト |
| ロールバック | 問題のあるバージョンから、一つ前のバージョンに戻すこと |
| PaaS | サーバの管理をサービス側に任せて、アプリを動かせるサービス |
| Kamal | 自分のサーバに Docker でアプリを配置する道具。Rails 8 の標準 |
| Docker | アプリと実行環境をまとめて箱に詰め、どこでも同じように動かす道具 |
| イメージ・コンテナ | 箱のひな形と、そこから作られて動いている実体 |
| ボリューム | コンテナが消えても残る、データの保存場所 |
| メトリクス | リクエスト数やエラー率などの数値の時系列 |
| パーセンタイル | 「遅い方から何%を除くと、全員この値以内」を表す指標。p95 など |
| ポストモーテム | 障害の後に行う、個人を責めない振り返り |
| 拡張と縮小 | 新しいものを足してから古いものを消す、段階的な変更の型 |
| RPO・RTO | どの時点まで戻せればよいか、どのくらいの時間で戻せればよいかの目標 |
