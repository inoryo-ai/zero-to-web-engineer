# 第24章 チーム開発（Issue・ブランチ・PR・コードレビュー・見積もり・報連相）

> **この章のゴール**：チームの一員として、作業を受け取り、変更を小さく分けて提出し、レビューを経てマージするまでの流れを一人で回せるようになる。困ったときに、適切なタイミングと形で周りに伝えられるようになる。
> **目安時間**：読む 3時間 ＋ 演習 5時間
> **前提**：第23章まで

## この章で学ぶこと

- 他人が読んで作業を始められる Issue を書ける
- GitHub Flow に沿ってブランチを切り、適切な粒度でコミットできる
- PR の説明を書き、出す前にセルフレビューできる
- コードレビューを受ける側・する側として、観点と言い方を説明できる
- コンフリクトを落ち着いて解消できる
- 見積もりを立て、遅れそうなときに早めに報告できる

## なぜチーム開発の作法を学ぶのか

ここまでの章では、ほとんどの作業を一人で進めてきました。
自分で考え、自分で書き、自分で確かめれば済みました。
しかし仕事のソフトウェア開発は、ほぼ必ずチームで行います。

チームで作るとき、コードを書く時間は仕事の一部にすぎません。
残りは「何を作るか決める」「作ったものを伝える」「確かめ合う」時間です。
ジュニアエンジニアが最初に評価されるのは、実はこちらの部分です。

たとえば、技術力が同じ二人のジュニアがいるとします。
一人は、3日黙って作業し、最終日に「終わりませんでした」と言います。
もう一人は、半日で詰まった時点で相談し、2日目に遅れを報告します。
チームにとって助かるのは、明らかに後者です。
問題が早く見えれば、仕事を分け直したり、手伝ったりできるからです。

この章で学ぶ作法は、すべて「チームの状況を見えるようにする」ための道具です。
Issue は「やること」を見えるようにします。
ブランチと PR は「変更の中身」を見えるようにします。
レビューは「品質」を、報連相は「進み具合」を見えるようにします。
そう考えると、ばらばらに見える作法が一つにつながります。

## Issue の書き方

### Issue とは何か

**Issue**（イシュー）は、GitHub 上の「やることリストの1枚のカード」です。
バグ報告、機能の追加、調査の依頼などを1件ずつ書きます。
番号が自動で振られ、`#12` のように書くと他の場所から参照できます。

Issue の目的は、書いた人がいなくても作業を始められるようにすることです。
口頭で「ログインのあれ、直しておいて」と頼まれても、翌週には内容を忘れます。
文字で残しておけば、誰が担当しても同じ情報から始められます。

### よい Issue の型

迷ったら、次の5つを書きます。

```markdown
## 背景（なぜやるのか）
投稿一覧のページで、他人の下書きが見えてしまっている。

## やること
- 一覧には公開済みの投稿だけを表示する
- 自分の下書きは「マイページ」でだけ見られるようにする

## 完了条件
- [ ] ログアウト状態で一覧を開いても下書きが表示されない
- [ ] 上記を確かめるシステムテストがある

## 再現手順（バグの場合）
1. ユーザーAでログインし、下書きを1件作る
2. ログアウトして /posts を開く
3. Aの下書きが表示される（期待：表示されない）

## 参考
- 関連: #8（下書き機能の追加）
```

特に大事なのは「背景」と「完了条件」です。
背景がないと、作業者は目的を知らないまま作ることになります。
目的が分からないと、細かい判断のたびに迷うか、ずれた判断をします。
完了条件がないと、どこまでやれば終わりなのかが人によって変わります。
完了条件は、第6章で学んだテストのように「確かめられる形」で書きます。

### 大きすぎる Issue は分ける

「ユーザー機能を作る」のような Issue は大きすぎます。
登録、ログイン、ログアウト、プロフィール編集と、中身が多すぎるからです。
目安は「1〜2日で終わり、PR 1つで出せる大きさ」です。
それを超えそうなら、親の Issue からいくつかの子の Issue に分けます。
分けることで、進み具合が見え、レビューもしやすくなります。

## ブランチ戦略：GitHub Flow

### ブランチ戦略とは

第2章で、ブランチは「作業用の分かれ道」だと学びました。
チームでは、ブランチの使い方に決まりを作ります。
これを**ブランチ戦略**と呼びます。
決まりがないと、誰がどのブランチに何を入れたのか分からなくなるからです。

### GitHub Flow の流れ

多くのWeb開発チームで使われる、単純な戦略が **GitHub Flow** です。
ルールは次のとおりです。

1. `main` ブランチは、いつでもリリースできる状態に保つ
2. 作業を始めるときは、`main` から新しいブランチを作る
3. ブランチ上で作業し、こまめにコミットして push する
4. 準備ができたら PR（プルリクエスト）を出す
5. レビューと CI が通ったら `main` にマージする
6. マージしたら、そのブランチは削除する

コマンドにすると、1回の作業は次のようになります。

```bash
git switch main
git pull                        # 最新の main を取ってくる
git switch -c fix/hide-drafts   # 作業用ブランチを作る
# ……編集とテスト……
git add app/controllers/posts_controller.rb test/system/posts_test.rb
git commit -m "Hide draft posts from the public index"
git push -u origin fix/hide-drafts
```

最後の push のあと、GitHub の画面に「Compare & pull request」ボタンが出ます。
そこから PR を作ります。

### ブランチ名の付け方

ブランチ名は、中身が一目で分かるようにします。
`feature/`（機能追加）、`fix/`（バグ修正）、`docs/`（文書）などの接頭辞をよく使います。
Issue 番号を入れるチームもあります（例：`fix/12-hide-drafts`）。
チームに決まりがあれば、必ずそれに従います。

### なぜ main を直接触らないのか

`main` に直接コミットすると、レビューを通らない変更が本番に混ざります。
また、複数人が同時に `main` を書き換えると、壊れた状態が他人に伝わります。
ブランチを分けることで、未完成の作業を隔離できます。
多くのチームでは、GitHub の設定で `main` への直接 push を禁止しています。
これを「ブランチ保護」と呼びます。

## コミットの粒度とメッセージ

### 1コミット1つの意図

**コミットの粒度**とは、1回のコミットにどれだけの変更を入れるかです。
基本は「1コミットに1つの意図」です。

悪い例は、次のようなコミットです。

```text
fix
いろいろ修正
WIP
```

これでは、あとから履歴を見ても何をしたのか分かりません。
さらに、バグを直す変更と、無関係な整形が同じコミットに混ざっていると、
問題が起きたときに「どの変更が原因か」を切り分けられません。

よい例は、たとえば次の並びです。

```text
Add published scope to Post
Show only published posts on index
Add system test for hiding drafts
```

一つひとつが小さく、名前を読めば中身が分かります。

### メッセージの書き方

コミットメッセージは、1行目に「何をしたか」を短く書きます。
英語で命令形（Add, Fix, Remove など）にする習慣が広く使われています。
日本語で書くチームもあります。これもチームの決まりに合わせます。

理由まで書きたいときは、1行空けて本文を書きます。

```text
Show only published posts on index

下書きが一覧に表示され、他人に見えていた (#12)。
一覧の取得を Post.published に限定した。
```

本文には「なぜ」を書きます。
「何を変えたか」は差分を見れば分かりますが、理由は差分には残らないからです。

### 意図しないファイルを入れない

`git add .` は便利ですが、関係のないファイルまで入る危険があります。
特に、`.env`、`config/master.key`、ログ、DBファイルは絶対に入れません。
これは第20章で学んだ秘密情報の扱いそのものです。
コミット前に `git status` と `git diff --staged` で中身を確かめる癖をつけます。

```bash
git status
git diff --staged    # これからコミットする差分だけを表示する
```

## PR の説明とテンプレート

### PR とは何か

**PR**（プルリクエスト）は、「このブランチの変更を main に取り込んでください」というお願いです。
同時に、レビューの場でもあります。
差分の各行にコメントを付けて、議論できます。

### PR の説明に書くこと

PR の説明は、レビューする人への手紙です。
レビュアーはあなたの頭の中を知りません。
「何を、なぜ、どう確かめたか」を書きます。

多くのチームでは、リポジトリに PR のテンプレートを置いています。
`.github/pull_request_template.md` というファイルを作ると、PR 作成時に自動で入力されます。
例を示します。

```markdown
## 概要
閉じる Issue: #12
公開一覧から下書きを除外しました。

## 変更内容
- Post に published スコープを追加
- PostsController#index で published のみ取得
- システムテストを追加

## 確認方法
- [ ] bin/rails test が通る
- [ ] ローカルでユーザーAの下書きがログアウト状態で見えないことを確認

## スクリーンショット（画面の変更がある場合）

## レビューで特に見てほしい点
スコープ名を published にしたが、visible の方がよいか迷っている。

## 影響範囲・注意点
マイページの表示には影響しない（別のクエリを使っているため）。
```

「閉じる Issue: #12」の代わりに `Closes #12` と書くと、マージ時に Issue が自動で閉じます。

「レビューで特に見てほしい点」は、とても役に立つ欄です。
自分が迷った所を正直に書くと、レビュアーはそこに時間を使えます。
迷いを隠すより、見せた方が早く良い結果になります。

### PR は小さく

PR は小さい方がよいとされます。
差分が数百行を超えると、レビュアーの集中力が続きません。
すると見落としが増え、レビューも遅れます。
目安は「レビューに30分以上かからない大きさ」です。
大きくなりそうなら、Issue の段階で分けます。

## セルフレビュー

### PR を出す前に自分で読む

**セルフレビュー**とは、PR を出す前に、自分の差分をレビュアーの目で読むことです。
GitHub の「Files changed」タブで、他人のコードのつもりで読みます。
エディタで見るのとは見え方が変わり、不思議なほど問題が見つかります。

### セルフレビューのチェックリスト

- [ ] 差分に、デバッグ用の `puts` や `binding.irb` が残っていない
- [ ] 関係のないファイル、整形だけの変更が混ざっていない
- [ ] 秘密情報（鍵・トークン・パスワード・実データ）が入っていない
- [ ] テストを追加・更新し、ローカルですべて通った
- [ ] CI が通っている
- [ ] 変数名やメソッド名から、意図が読み取れる
- [ ] エラー時や空の入力など、正常系以外を考えた
- [ ] 第20章のセキュリティの観点（認可・エスケープ・バインド）を確認した
- [ ] PR の説明を読めば、何をなぜ変えたか分かる

セルフレビューの目的は、レビュアーの時間を「本当に議論すべき点」に使ってもらうことです。
`puts` の消し忘れを指摘するために、先輩の時間を使わせるのはもったいないことです。

## コードレビューを受ける

### レビューは「人」ではなく「コード」への意見

**コードレビュー**とは、他の人の変更を読んで、問題や改善点を伝えることです。
初めてレビューを受けると、たくさんの指摘に落ち込むことがあります。
しかし指摘は、あなたの人格や能力への評価ではありません。
コードをよくするための意見です。
指摘が多いのは、ジュニアの最初の数か月ではごく普通のことです。

### 受け方の作法

1. まず全部読み、指摘の意図を理解する
2. 分からない指摘は、遠慮せず質問する（「〜という理解で合っていますか？」）
3. 直したら、どのコミットで直したかを返信する（例：「a1b2c3d で修正しました」）
4. 同意できない点は、理由を添えて意見を返す
5. 同じ種類の指摘を2回受けないよう、メモに残す

4つ目は大事です。
レビュアーが常に正しいわけではありません。
「この形にしたのは〜という理由です。それでも変えた方がよいでしょうか？」と書けば、
議論になり、どちらかが新しいことを学べます。
黙って従うのも、感情的に反論するのも、どちらも学びの機会を逃します。

## コードレビューをする

### ジュニアもレビューしてよい

「自分はまだ新人だからレビューできない」と思うかもしれません。
しかし、ジュニアのレビューにも価値があります。
「この部分が読んで分からなかった」という感想は、それ自体が貴重な情報です。
新しく入った人に分からないコードは、将来の誰かにも分かりにくいからです。
また、他人のコードを読むことは、第12章で学んだ「読む力」の一番よい練習になります。

### レビューの観点

上から順に、重要度が高いものです。

| 観点 | 確認すること |
|---|---|
| 目的 | Issue の完了条件を満たしているか |
| 正しさ | バグはないか。空・nil・境界の値で壊れないか |
| セキュリティ | 認可漏れ、エスケープ漏れ、SQL の文字列埋め込み、秘密情報がないか |
| テスト | 変更を守るテストがあるか。失敗するべき場面のテストもあるか |
| 設計 | 責務が適切な層（Model / Controller / View）に置かれているか |
| 読みやすさ | 名前は意図を表しているか。複雑すぎないか |
| 細かい好み | 書き方の好み。直さなくてもよいことが多い |

細かい好みから先にコメントすると、大事な指摘が埋もれます。
大きな観点から見るようにします。

### 言い方

レビューコメントは文字だけで届くため、口頭より冷たく伝わります。
次のような工夫をします。

- 断定より質問の形にする：「ここは nil になりませんか？」
- 理由を添える：「〜なので、`find_by` の方が安全だと思います」
- 重要度を示す：「必須」「提案」「nits（細かい点・任意）」などの印を付ける
- よい所も伝える：「このテスト名、分かりやすいです」

たとえば次の2つを比べてください。

```text
悪い例：これは間違い。find を使うべき。
よい例：[必須] ここで他人の投稿IDを指定すると、他人の投稿を編集できてしまいそうです。
        current_user.posts.find(params[:id]) にすると防げると思いますが、どうでしょう？
```

よい例は、問題、理由、案、相手の判断の余地の4つがそろっています。

## コンフリクトの解消

### コンフリクトとは

**コンフリクト**（衝突）とは、二つのブランチが同じ場所を別々に変えたため、
Git がどちらを採るか決められない状態です。
チーム開発では日常的に起きます。壊れたわけではないので、落ち着いて対処します。

### 実際に起こしてみる

次は、手元で実際に衝突を起こしたときの出力です。
`feature/greeting-a` ブランチで `hello.rb` を変え、同時に `main` でも同じ行を変えました。
その後、作業ブランチに `main` を取り込もうとしています。

```text
$ git merge main
Auto-merging hello.rb
CONFLICT (content): Merge conflict in hello.rb
Automatic merge failed; fix conflicts and then commit the result.
$ git status
On branch feature/greeting-a
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   hello.rb
```

ファイルの中身は次のようになっています。

```text
<<<<<<< HEAD
puts "Hello, Alice"
=======
puts "Hello, world"
>>>>>>> main
```

`<<<<<<< HEAD` から `=======` までが今いるブランチの内容です。
`=======` から `>>>>>>> main` までが取り込もうとした `main` の内容です。

### 解消の手順

1. 衝突したファイルを開き、両方の変更の**意図**を理解する
2. 正しい最終形に書き直し、`<<<<<<<` `=======` `>>>>>>>` の記号をすべて消す
3. テストを実行して、壊れていないことを確かめる
4. `git add hello.rb` で解消済みとして登録する
5. `git commit` でマージを完了する

迷ったら `git merge --abort` で、マージ前の状態に戻れます。

一番の注意点は、1つ目です。
「自分の方を残せばいい」と機械的に選ぶと、相手の修正を消してしまいます。
どちらを残すべきか分からないときは、相手の変更を書いた人に聞きます。
それが一番速く、安全です。

### コンフリクトを減らすには

- ブランチを長く放置しない（数日以内にマージする）
- こまめに `main` を取り込む
- PR を小さくする
- 同じファイルを触りそうなら、事前に声をかける

## 見積もりと遅れの報告

### 見積もりはなぜ難しいか

**見積もり**とは、作業にかかる時間を事前に予測することです。
正直に言うと、見積もりはベテランでも難しい作業です。
ジュニアの見積もりは、実際の2〜3倍ずれることも珍しくありません。
知らないことが、どれだけ出てくるか予測できないからです。

### 見積もりの立て方

1. 作業を細かく分ける（半日以下の単位まで）
2. 分けた一つひとつに時間を付ける
3. 「分からない部分」を書き出し、調査の時間を別に足す
4. テスト、セルフレビュー、レビュー対応の時間を足す
5. 合計に余裕（1.5倍程度）を持たせる

例を示します。

```text
Issue #12 下書きを一覧から隠す
- Post に published スコープを追加＋モデルテスト    1h
- index の取得を変更                               0.5h
- システムテストを書く（書き方を調べる必要あり）   2h
- セルフレビュー・PR 作成                          0.5h
- レビュー対応                                     1h
合計 5h → 余裕を見て 1日
```

4つ目の「レビュー対応」を忘れる人が多いです。
コードを書き終えた時点では、作業は終わっていません。
マージされて、初めて終わりです。

### 遅れは早く報告する

見積もりがずれるのは、恥ずかしいことではありません。
問題なのは、ずれたことを報告しないことです。

遅れが分かったら、その時点で伝えます。
伝えるときは、次の3点をそろえます。

```text
#12 の件で報告です。
状況：システムテストの書き方で詰まっており、予定より半日遅れそうです。
原因：ログイン状態をテストで作る方法が分かっていません。
見通し：明日の午前に誰かに15分相談できれば、明日中に PR を出せる見込みです。
```

「状況」「原因」「見通し（または相談したいこと）」です。
見通しまで書くと、受け取った人は次の行動を決められます。

## 報連相

**報連相**（ほうれんそう）は、報告・連絡・相談の略です。
日本の職場でよく使われる言葉です。

| 種類 | 意味 | 例 |
|---|---|---|
| 報告 | 頼まれた仕事の進み具合や結果を伝える | 「#12 の PR を出しました」 |
| 連絡 | 関係者に事実を共有する | 「明日は午後から休みます」 |
| 相談 | 判断に迷うことを一緒に考えてもらう | 「A案とB案、どちらがよいでしょう？」 |

### 結論から書く

チャットで伝えるときは、結論を最初に書きます。
読む人は忙しく、最後まで読まないかもしれないからです。

```text
悪い例：昨日から調べていて、まず〜を試して、次に〜を見て、……なので、今日中は無理そうです。
よい例：#12 は今日中に終わらない見込みです。原因は〜です。明日の昼に PR を出します。
```

### 毎日の報告

多くのチームでは、毎朝短いミーティングや、チャットでの日報があります。
「昨日やったこと」「今日やること」「困っていること」を短く伝えます。
3つ目の「困っていること」を空欄にし続けるジュニアは、要注意です。
困っていないのではなく、困っていると言えていないことが多いからです。

## 質問の仕方：15〜30分ルール

### 自分で考える時間と、聞くタイミング

第7章で、エラーの読み方と質問の仕方を学びました。
チームではさらに「いつ聞くか」が大事になります。

よく使われるのが **15〜30分ルール** です。
詰まったら、まず15〜30分は自分で調べます。
それでも進まなければ、質問します。

自分で全く調べずに聞くと、相手の時間を奪い、自分も学べません。
逆に、半日以上一人で抱えると、チームの時間を失います。
先輩が5分で解決できることに、ジュニアが3時間かけるのは、チーム全体では損です。
15〜30分は、その間のちょうどよい区切りです。
チームによって時間は違うので、最初に「何分詰まったら聞けばよいですか」と確認しましょう。

### 質問の型

```text
【やりたいこと】ログイン済みユーザーとしてシステムテストを動かしたい
【やったこと】
- Rails ガイドの System Testing の節を読んだ
- sign_in メソッドを書いたが、NoMethodError になった
【エラー全文】（そのまま貼る）
【仮説】Devise を使っていないので sign_in ヘルパーがない？
【聞きたいこと】このプロジェクトで、テストでログインする標準的な方法はありますか？
```

「やったこと」と「仮説」があると、相手はあなたの理解の段階に合わせて答えられます。
エラー文やログを貼るときは、秘密情報や実データが含まれていないか必ず確かめます。

## ペアプログラミング

**ペアプログラミング**（ペアプロ）は、二人で一台の画面を見ながら書く方法です。
キーボードを持つ人を「ドライバー」、全体を見て方向を考える人を「ナビゲーター」と呼びます。
運転手と地図を見る助手席の人のような関係です。
15〜30分ごとに役割を交代するのが一般的です。

ジュニアにとってペアプロは、先輩の「考え方」を直接見られる貴重な機会です。
ドキュメントには書かれない、調べ方、ショートカット、判断の順番が見えます。
ドライバーのときは、何を考えているか声に出しながら書きます。
黙って書くと、ナビゲーターはあなたの意図が分からないからです。

リモートでは、画面共有でペアプロします。
このとき、通知や他のタブ、ターミナルの環境変数が映らないよう気をつけます。

## 議事録とドキュメント

### 議事録

会議で決まったことは、文字にしないと消えます。
**議事録**は、会議の内容と決定事項の記録です。
新人が議事録を担当することはよくあり、議論を理解する練習にもなります。

```markdown
# 2026-10-01 投稿機能の仕様相談
参加：Aさん、Bさん、自分

## 決まったこと
- 下書きは本人だけが見られる
- 公開後の編集は可能。編集履歴は残さない

## 決まっていないこと（宿題）
- 下書きの保存期限 → Aさんが来週までに確認

## 次のアクション
- 自分：#12 を今週中に実装する
```

「決まったこと」「決まっていないこと」「誰が何をいつまでに」の3つが核です。
議論の経過を全部書く必要はありません。

### ドキュメント

チームの知識は、README や Wiki などのドキュメントに残します。
特にジュニアが貢献しやすいのは、セットアップ手順です。
入社して最初に環境を作るとき、手順書の古い所や抜けに必ず気づきます。
それを直す PR は、初めての貢献として最適です。
「新しい人が困った所」は、次の新しい人も必ず困るからです。

## 実務ではこうなる

現場では、Issue を受け取ってからマージまでを、毎日のように繰り返します。
Slack などのチャット、GitHub、カレンダーを行き来しながら進めます。
チームによっては Issue の代わりに Jira や Linear などのツールを使いますが、考え方は同じです。

ジュニアがやりがちな失敗を挙げます。

- **巨大な PR を出す**：1週間分の変更を一度に出し、レビューが何日も止まる。
- **黙って詰まる**：「聞いたら迷惑だ」と思い、半日以上一人で抱える。
- **レビュー指摘に何も返さずに直す**：レビュアーは何が直ったか分からず、もう一度全部読むことになる。
- **コンフリクトで相手の変更を消す**：自分の側だけを残し、他人の修正を巻き戻してしまう。
- **見積もりに「レビュー対応」と「テスト」を入れない**：書き終わった日を完了日として報告してしまう。
- **`git add .` で秘密情報を入れる**：`.env` や鍵を push してしまう。push したものは、履歴から消しても漏れたものとして扱い、すぐに上長へ報告し、鍵を無効化する必要があります。

どれも、技術力ではなく習慣で防げる失敗です。

## 演習

演習用のリポジトリは `~/workspace/ch24-team/` に作ります。
第18章以降で作った Rails アプリを使ってもかまいません。
その場合は、そのリポジトリで作業し、フォルダ名を読み替えてください。
GitHub のリポジトリは非公開（Private）で作ることを推奨します。

### 演習24-1：Issue を3つ書く

- 自分のアプリに対して、追加したい機能1つ、直したいバグ1つ、改善したい点1つを考える。
- それぞれを GitHub の Issue に、本章の型（背景・やること・完了条件など）で書く。
- 1つは「大きすぎる Issue」をわざと書き、子の Issue 2つ以上に分割する。
- **完了条件**：Issue が4つ以上あり、すべてに「背景」と、チェックボックス形式の「完了条件」がある。親 Issue に子 Issue の番号（`#数字`）が書かれている。
- ヒント：完了条件は「誰が確かめても同じ結果になるか」を基準に書きます。

### 演習24-2：PR を作り、セルフレビューする（一人でできる形）

- 演習24-1 の Issue から1つ選び、`main` から作業ブランチを作る。
- TDD で実装する。まず失敗するテストをコミットし（RED）、通す実装をコミットし（GREEN）、整理をコミットする（REFACTOR）。
- `.github/pull_request_template.md` を作り、本章の例を参考に自分用のテンプレートを用意する。
- PR を出し、「Files changed」タブでセルフレビューする。気づいた点を、自分で行コメントとして3つ以上残す。
- 指摘を直し、それぞれのコメントに「どのコミットで直したか」を返信する。
- **完了条件**：PR に3つ以上のコミットがあり、メッセージから順序（テスト→実装→整理）が分かる。PR の説明に `Closes #番号` がある。セルフレビューコメントが3つ以上あり、すべてに修正コミットのハッシュ付き返信がある。CI が通った状態でマージされ、Issue が自動で閉じている。
- ヒント：コメントが見つからないときは、本章のセルフレビューのチェックリストを上から1つずつ当てはめてみましょう。

### 演習24-3：コンフリクトを起こして解消する

- `~/workspace/ch24-team/conflict-practice/` に新しいリポジトリを作る。
- 本章の例と同じように、2つのブランチで同じ行を別々に変え、マージしてコンフリクトを起こす。
- 一度 `git merge --abort` で戻ることを試し、もう一度マージして、今度は両方の意図を活かす形で解消する。
- **完了条件**：`git log --oneline --graph` でマージコミットが確認できる。ファイルに `<<<<<<<` などの記号が残っていない（`grep -n '<<<<<<<' -r .` で何も出ない）。
- ヒント：「両方の意図を活かす」とは、どちらかを選ぶのではなく、両方の変更の目的を満たす新しい形を考えることです。

### 演習24-4：見積もりと振り返り

- 演習24-2 に着手する前に、本章の形式で見積もりを書き、Issue のコメントに残す。
- 作業後、実際にかかった時間を同じ表に書き足し、ずれた理由を3行で書く。
- 途中で遅れが分かった場合は、「状況・原因・見通し」の形式の報告文も Issue に残す。
- **完了条件**：Issue に「見積もり」と「実績」の両方の表があり、ずれた理由が書かれている。

### 演習24-5（発展・仲間がいる場合）：相互レビューとペアプロ

- 学習仲間と、お互いのリポジトリに Collaborator として招待し合う。
- 相手の PR を1つレビューする。重要度の印（必須・提案・nits）を付け、よい所も1つ以上書く。
- 自分の PR へのレビューに返信し、同意できない点が1つでもあれば理由を添えて議論する。
- 30分のペアプロを1回行い、15分で役割を交代する。終わったら議事録の形式で「決まったこと・宿題」を残す。
- **完了条件**：相手の PR に、重要度の印付きコメントが3つ以上ある。自分の PR のすべてのコメントに返信がある。ペアプロの議事録がリポジトリかIssueにある。
- 一人の場合の代わり：1週間前に自分が書いた PR を、他人のコードのつもりでもう一度レビューし、同じ形式でコメントを残します。

## 確認クイズ

**Q1**：Issue に「背景（なぜやるのか）」を書く理由を説明してください。

**Q2**：GitHub Flow で、`main` ブランチはどういう状態に保つべきですか。

**Q3**：次のコミットメッセージの問題点を挙げてください。「修正」

**Q4**：コンフリクトの解消で、一番注意すべきことは何ですか。

**Q5**：作業が予定より遅れそうだと分かりました。いつ、何を伝えるべきですか。

### 解答と解説

**A1**：作業者が目的を知ることで、細かい判断を正しくできるからです。仕様に書かれていない場面に出会ったとき、目的が分かっていれば「目的に合う方」を選べます。

**A2**：いつでもリリースできる状態です。だから直接コミットせず、ブランチと PR を通し、レビューと CI を経てからマージします。

**A3**：何を、なぜ修正したのかが分かりません。あとから履歴を見ても役に立たず、問題の原因を探すときに手がかりになりません。「Fix nil error when post has no title」のように、何をしたかを具体的に書きます。

**A4**：両方の変更の意図を理解してから解消することです。機械的に自分の側だけを残すと、相手の修正を消してしまいます。分からなければ、相手に聞きます。

**A5**：分かった時点ですぐに伝えます。内容は「状況・原因・見通し（または相談したいこと）」の3点です。遅れそのものより、遅れが見えないことの方がチームにとって困ります。

## AIの使い方（この章）

推奨する聞き方の例：

- 「次の PR の説明文を書きました。レビュアーの立場で、分かりにくい所や足りない情報を指摘してください」（自分で書いた文章を見直してもらう）
- 「このレビューコメントを受けました。指摘の意図が分かりません。どういう問題を心配しているのか、例を挙げて解説してください」
- 「コンフリクトの両側の差分です。それぞれの変更が何を目的にしているか説明してください。解消後のコードは自分で書きます」

この章でやってはいけない使い方：

- PR の説明、Issue、報告文を AI に丸ごと書かせ、自分で読み直さずに出すこと。自分の作業を自分の言葉で説明することが、この章の練習の中心です。
- 会社や他人のリポジトリのコード、チャットのログ、議事録を、許可なく外部の AI サービスに貼ること。社内の情報には、外部に出してよいかのルールがあります（第25章で詳しく扱います）。

## まとめ

チーム開発の作法は、すべて「状況を見えるようにする」ための道具です。
Issue で目的と完了条件を、小さなコミットと PR で変更の中身を、レビューで品質を見えるようにします。
遅れや詰まりは、早く、結論から、状況・原因・見通しをそろえて伝えます。
これらは技術力ではなく習慣です。今日から一人のリポジトリでも練習できます。

## 用語

| 用語 | 意味 |
|---|---|
| Issue | やることを1件ずつ書く GitHub 上のカード。番号で参照できる |
| 完了条件 | どうなったら作業が終わりかを、確かめられる形で書いたもの |
| ブランチ戦略 | チームでのブランチの作り方・使い方の決まり |
| GitHub Flow | main から作業ブランチを切り、PR とレビューを経てマージする単純な戦略 |
| ブランチ保護 | main への直接 push などを禁止する GitHub の設定 |
| コミットの粒度 | 1回のコミットに含める変更の大きさ。基本は1コミット1意図 |
| PR（プルリクエスト） | ブランチの変更を取り込むよう依頼し、レビューする場 |
| PR テンプレート | PR の説明に自動で入る雛形。`.github/pull_request_template.md` |
| セルフレビュー | PR を出す前に、自分の差分をレビュアーの目で読むこと |
| コードレビュー | 他人の変更を読み、問題や改善点を伝えること |
| nits | レビューで「細かい点・直さなくてもよい」ことを示す印 |
| コンフリクト | 同じ場所への別々の変更を、Git が自動で統合できない状態 |
| 見積もり | 作業にかかる時間を事前に予測すること |
| 報連相 | 報告・連絡・相談 |
| ペアプログラミング | 二人で一つの画面を見ながら書く方法。ドライバーとナビゲーターに分かれる |
