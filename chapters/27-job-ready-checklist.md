# 第27章 業務レディ・チェックリストと次の学習

> **この章のゴール**：自分が「ジュニアエンジニアとして業務に参加できる」状態にあるかを、チェックリストで確かめ、足りない所を該当章に戻って埋められる。ポートフォリオと面接で自分の力を自分の言葉で伝え、入社後も学び続ける計画を立てられる。
> **目安時間**：読む 1.5時間 ＋ 演習 4時間
> **前提**：第26章まで

## この章で学ぶこと

- 技術・チーム・セキュリティ・AI の4領域で、自分の「できる」を確かめられる
- 足りない項目を、該当する章に戻って埋める計画を立てられる
- ポートフォリオで、作ったものと考えたことを伝えられる
- 面接でよく聞かれることに、自分の言葉で答える練習ができる
- 入社後最初の3か月の過ごし方と、次に学ぶ分野を説明できる

## ここまで来たあなたへ

第1章で、ターミナルを初めて開いたことを覚えているでしょうか。
そこから、Socket で HTTP サーバを作り、フレームワークと ORM を自作し、
Rails で認証・認可のあるアプリを作り、テストと CI を整え、発表までしてきました。
これは、決して小さな道のりではありません。

この章では、ここまでの学びを点検します。
そして、正直に一つのことを伝えます。

> **この教材を終えても、学びは終わりません。**

この教材のゴールは「ジュニアエンジニアとして業務に参加できる」ことです。
「一人前のエンジニア」ではありません。
現場には、この教材で扱わなかった技術、知らない設計、独自の決まりが必ずあります。
入社後も、毎日のように「知らないこと」に出会います。
それは、あなたの準備が足りなかったからではありません。
どのエンジニアも、ずっと学び続けているからです。

ただし、この教材で身につけたものは、その学びを支える土台になります。
「抽象を降りて、また登る」経験をした人は、新しい技術に出会っても、
「これは裏で何をしているのか」と考えられます。
その姿勢こそが、学び続けるための一番の道具です。

## 業務レディ・チェックリスト

### 使い方

各項目を読み、次の3段階で自己評価します。

- **○**：何も見ずに、できる・説明できる
- **△**：資料や過去のコードを見れば、できる
- **×**：まだできない・説明できない

ジュニアとして業務に参加する時点では、すべてが ○ である必要はありません。
目安は「× がなく、△ が半分以下」です。
× の項目は、リンク先の章に戻って埋めます。
△ の項目は、入社前後に繰り返し使って ○ にしていきます。

「説明できる」は、声に出して1分間話せるか、で確かめます。
頭の中で「分かっている気がする」だけでは、面接やレビューで言葉になりません。

### チェックの結果をどう使うか

チェックの結果は、そのまま次の学習計画になります。
× の項目を、該当する章の演習からやり直します。
読むだけではなく、演習の完了条件をもう一度満たすところまで行います。

1回のチェックで終わらせず、2〜4週間ごとに繰り返すのがおすすめです。
日付を入れて保存しておくと、○ が増えていく様子が見え、自信になります。

## ポートフォリオの見せ方

### ポートフォリオとは

**ポートフォリオ**とは、自分の力を示す作品集です。
エンジニアの場合は、GitHub のリポジトリと、その説明が中心になります。
採用担当者は、短い時間で多くの応募者を見ます。
「何を作ったか」が数秒で分かり、「どう考えたか」に興味を持ってもらう工夫が要ります。

### 何を載せるか

最終課題（第26章）のアプリを、ポートフォリオの中心にします。
加えて、第14章の自作フレームワークや第16章の自作 ORM も、強い材料になります。
「Rails を使える」だけでなく「Rails の裏側を理解している」ことを示せるからです。

### README に書くこと

リポジトリの README は、ポートフォリオの表紙です。
次の内容を、上から順に書きます。

1. アプリ名と1文の説明（誰の、どんな困りごとを解決するか）
2. 画面のスクリーンショット（ダミーデータのもの）
3. 主な機能
4. 使った技術（Ruby・Rails・SQLite・GitHub Actions など）
5. 設計で工夫した点（ER図、認可表、設計判断とその理由）
6. テストとセキュリティ（何をテストしたか、残る不足をどう記録したか）
7. 今後の改善
8. ローカルでの起動手順

5と6が、他の応募者と差がつく所です。
機能の多さより、「なぜそう作ったか」が書かれていることの方が評価されます。
第26章の発表スライドの内容を、文章に直すと書きやすくなります。

### 公開する前の確認

リポジトリを公開する前に、第10章・第20章の確認を必ず行います。

- [ ] Git の履歴全体に、鍵・トークン・`.env`・`config/master.key` が含まれていない
- [ ] スクリーンショットや DB の中身に、実在の個人情報が含まれていない
- [ ] コミットに使ったメールアドレスを公開してよいか確認した（GitHub の非公開メール設定を使う方法もある）
- [ ] 元教材や他人のコードを使った部分は、ライセンスに従って出典を書いた
- [ ] 自作サーバ・自作フレームワークは「学習用・本番利用不可」と README に明記した

過去のコミットに秘密情報が含まれていた場合、最新のファイルから消すだけでは足りません。
履歴に残っているからです。
その鍵は漏れたものとして無効化し、公開するのは新しく作り直したリポジトリにするのが安全です。

## 面接で聞かれやすいこと

### 自分の言葉で話す

面接で見られるのは、知識の量よりも「自分で考え、自分の言葉で説明できるか」です。
暗記した模範解答は、一つ深く質問されると崩れます。
自分が実際にやったことを材料に話せば、深掘りされても答えられます。

次の質問に、声に出して答える練習をしてください。
1問あたり1〜2分で話すのが目安です。

### 技術の理解を問う質問

- 「ブラウザで URL を入力してから画面が表示されるまで、何が起きていますか？」
- 「Rails の MVC について、それぞれの役割と、分ける理由を説明してください」
- 「N+1 問題とは何ですか？ どう気づき、どう直しますか？」
- 「認証と認可の違いは何ですか？ あなたのアプリではどう実装しましたか？」
- 「テストは何のために書きますか？ どの層で何をテストしましたか？」

1つ目の質問は、この教材で最も得意な質問になっているはずです。
Socket、HTTP、Rack、ルーター、コントローラ、ORM、ビューを自分で作ったからです。
「自分でサーバを作ったときに、ここで〜が起きていると分かりました」と話せると、強い印象を残します。

### 経験を問う質問

- 「一番苦労したことと、どう乗り越えたかを教えてください」
- 「作ったアプリで、もし作り直すなら何を変えますか？」
- 「分からないことがあったとき、どうやって調べますか？」
- 「AI をどう使っていますか？」

最後の質問は、近年よく聞かれます。
第25章の内容を、自分の経験で話せるようにしておきます。
「AI に完成コードを書かせず、解説させて、公式ドキュメントで裏を取っていました。
たとえば〜のとき、AI の説明に〜という誤りがあり、ドキュメントで気づきました」
のように、具体例があると説得力が増します。

### 答えられないとき

知らないことを聞かれたら、正直に「分かりません」と言ってかまいません。
そのうえで、「知っている範囲ではこう考えます」「調べるなら、まず〜を見ます」と続けます。
知ったかぶりは、深掘りされるとすぐに分かります。
現場で一番困るのは、分からないことを分からないと言えない人です。
面接でも、それは同じです。

### 逆質問

面接の最後に「何か質問はありますか？」と聞かれることがよくあります。
これは、あなたがその会社で働く姿を考えているかを示す機会です。
たとえば次のような質問ができます。

- 「新しく入ったジュニアエンジニアは、最初の数か月でどんな仕事を担当していますか？」
- 「コードレビューは、どのように進めていますか？」
- 「AI ツールの利用について、チームの決まりはありますか？」

## 入社後最初の3か月の過ごし方

### 最初の1か月：環境と人に慣れる

新しく入った人がチームに慣れるまでの期間を、**オンボーディング**と呼びます。
多くの会社では、教育担当の先輩や、決まった手順が用意されています。
最初の1か月は、成果を出すことより、慣れることが目標です。

- 開発環境を作る。手順書の古い所を見つけたら、直す PR を出す（第24章）
- チームのリポジトリの構成、ブランチ戦略、PR の決まり、レビューの流れを確認する
- 社内のセキュリティと AI 利用のルールを確認する（第25章の質問リスト）
- 小さなバグ修正や文言の変更など、「最初の Issue」を1つマージまで運ぶ
- 「何分詰まったら聞けばよいか」を、最初にチームに確認する

最初は、知らない言葉や略語が大量に出てきます。
自分用の用語メモを作り、分かったことを書き足していきます。
この教材の各章の「用語」の表と同じ形です。

### 2か月目：小さな機能を任される

- 設計済みの小さな Issue を、見積もりから PR まで一人で運ぶ
- レビューで受けた指摘をメモし、同じ指摘を2回受けないようにする
- 他の人の PR を読み、分からない所を質問する（レビューの練習になる）
- 第12章のように、プロジェクトのコードを入口から読み、リクエストの流れを追う

### 3か月目：自分から動く

- 自分の担当範囲で、気になる所を Issue にして提案する
- ペアプロや障害対応に同席し、先輩の調べ方を観察する
- 3か月の振り返りを書き、次の3か月の学習目標を上長と相談する

### 気をつけたいこと

入社後しばらくは、「自分だけができていない」と感じやすい時期です。
周りの先輩は、何年もその仕事をしている人たちです。
比べる相手は先輩ではなく、1か月前の自分です。
本章のチェックリストを月に1回やり直すと、成長が見えます。

体調と生活のリズムも大切です。
夜遅くまで一人で抱えるより、翌朝に相談した方が、ほとんどの場合早く解決します。

## 次の学習

この教材で扱えなかった分野は、たくさんあります。
ここでは、ジュニアの次の一歩として価値が高いものを挙げます。
すべてを一度に学ぶ必要はありません。
仕事で必要になったもの、興味を持ったものから選びます。

### フロントエンド

第9章では、フォームを中心に最低限の HTML・CSS・JavaScript を学びました。
実際の Web アプリでは、画面の動きを JavaScript で作る場面が多くあります。
Rails では Hotwire（Turbo・Stimulus）が標準です。
React や Vue などのフレームワークを使うチームもあります。
まず JavaScript そのもの（非同期処理、DOM の操作）を固めるのがおすすめです。

### クラウドとインフラ

第23章では、デプロイと運用の入り口を学びました。
次は、AWS・Google Cloud などのクラウドの基本（サーバ、DB、ストレージ、ネットワーク、権限）です。
Docker をより深く使い、コンテナで動かす仕組みも学ぶ価値があります。
ここでも「抽象を降りる」考え方が役に立ちます。
クラウドのサービスも、裏ではこの教材で学んだ HTTP・Socket・DB が動いています。

### 設計

コードが大きくなると、「どこに何を書くか」の判断が難しくなります。
オブジェクト指向設計、リファクタリング、ドメインモデリングなどを学ぶと、判断の引き出しが増えます。
第14章で抽象化の判断をした経験は、ここで生きてきます。
本を読むときは、自分のコードに当てはめて試しながら読むのが効果的です。

### パフォーマンス

アプリが使われるほど、遅さが問題になります。
SQL の実行計画とインデックス、N+1 の解消、キャッシュ、バックグラウンド処理などがテーマです。
大事なのは、推測ではなく計測から始めることです。
「遅い気がする」ではなく、ログや計測ツールで「どこが何秒かかっているか」を確かめます。

### セキュリティ

第10・20章で基礎を学びましたが、セキュリティは学びが終わらない分野です。
OWASP の資料を読み進め、新しい攻撃の手口と対策を追い続けます。
自分が使っている gem や Rails のセキュリティ情報を、定期的に確認する習慣をつけます。

### その他

- **Ruby をより深く**：メタプログラミング、Ruby 自体のソースコードを読む
- **データベース**：PostgreSQL や MySQL、トランザクションと排他制御
- **コンピュータサイエンスの基礎**：データ構造、アルゴリズム、OS、ネットワークの理論
- **英語**：公式ドキュメント、エラーメッセージ、Issue の議論の多くは英語です。読む量を少しずつ増やします

### 学び続ける方法

- 毎日少しでも、コードを読むか書く
- 学んだことを、短い文章にしてまとめる（人に説明できるかの確認になる）
- 公式ドキュメントとリリースノートを読む習慣をつける
- 勉強会やコミュニティで、他のエンジニアと話す
- 分からないことに出会ったら、「抽象を降りて」裏で何が起きているかを確かめる

## 実務ではこうなる

現場の先輩エンジニアも、毎日新しいことを調べています。
違うのは、知識の量だけでなく、「調べ方」と「確かめ方」を知っていることです。
この教材で身につけた、エラーを読む、コードを読む、テストで確かめる、
一次情報に当たる、という習慣は、そのまま現場で通用します。

ジュニアがやりがちな失敗を挙げます。

- **教材を終えたことで、学びを止めてしまう**：半年後、新しい技術についていけなくなる。
- **チェックリストを ○ で埋めることが目的になる**：本当にできるかを、演習で確かめていない。
- **ポートフォリオで機能の数を競う**：「なぜそう作ったか」が書かれていない。
- **面接で暗記した答えを話す**：深掘りされると、自分の経験と結びつかない。
- **入社後、詰まっても聞かずに抱え込む**：第24章の15〜30分ルールを忘れる。

## 演習

演習のファイルは `~/workspace/ch27-ready/` に作ります。

### 演習27-1：業務レディ・チェック

- 本章の40項目のチェックリストを、ファイルに写す。ファイル名は `~/workspace/ch27-ready/checklist-YYYY-MM-DD.md`（日付は実施日）。
- 各項目を ○△× で自己評価する。
- ○ を付けた項目から5つを選び、声に出して1分で説明する。説明できなかったら △ に直す。
- × と △ の項目について、戻る章と、やり直す演習の番号を書く。
- **完了条件**：40項目すべてに ○△× のいずれかがあり、× と △ のすべてに「戻る章と演習番号」が書かれている。
- ヒント：自己評価が甘くなりがちな人は、○ の基準を「何も見ずに、他人に教えられる」に上げてみましょう。

### 演習27-2：やり直しと再チェック

- 演習27-1 で × を付けた項目のうち、最大3つについて、該当章の演習をやり直し、完了条件を満たす。× がない場合は △ から選ぶ。
- 2週間後に、新しい日付のファイルでチェックリストをやり直す。
- **完了条件**：やり直した演習の完了条件を満たした証拠（テストの成功出力、PR の URL など）がファイルに記録されている。2回分のチェックのファイルがあり、× の数が減っている。

### 演習27-3：ポートフォリオの README

- 第26章の最終課題のリポジトリの README を、本章の8項目の構成で書き直す。
- 公開前の確認リストをすべて実行し、結果を `~/workspace/ch27-ready/publish-check.md` に記録する。
- 公開するかどうかは、確認の結果を見て自分で判断する（非公開のままでもよい）。
- **完了条件**：README に8項目がすべてある。「設計で工夫した点」に、設計判断とその理由が少なくとも2つ書かれている。公開前の確認リストの全項目に、実行したコマンドまたは確認方法と結果がある。

### 演習27-4（発展）：模擬面接

- 本章の「面接で聞かれやすいこと」から5問以上を選び、自分の答えを声に出して録音する。
- 録音を聞き直し、「自分の経験に基づいているか」「1〜2分に収まっているか」を確かめ、改善した答えをもう一度録音する。
- 仲間がいる場合は、お互いに面接官役をし、答えに対して「なぜ？」を2回深掘りする。
- **完了条件**：5問以上について、1回目と2回目の録音があり、改善点を各1行でメモしている。録音やメモに、実在の企業の機密情報や他人の個人情報が含まれていない。

## 確認クイズ

**Q1**：この教材を終えた時点で、チェックリストのすべてが ○ である必要がないのはなぜですか。

**Q2**：ポートフォリオの README で、他の応募者と差がつきやすいのはどの部分ですか。理由も答えてください。

**Q3**：面接で知らないことを聞かれました。どう答えるのがよいですか。

**Q4**：過去のコミットに API キーが含まれていたリポジトリを公開したいです。どうすべきですか。

**Q5**：「この教材を終えても学び続ける必要がある」理由を、自分の言葉で説明してください。

### 解答と解説

**A1**：この教材のゴールは「ジュニアとして業務に参加できる」ことで、一人前ではないからです。△ の項目は、業務で繰り返し使ううちに ○ になります。大事なのは × をなくし、足りない所を自分で把握していることです。

**A2**：「設計で工夫した点」と「テストとセキュリティ」です。機能の一覧は多くの応募者が書きますが、なぜそう作ったか、何を確かめ、何が残っているかを書ける人は少ないからです。それは、自分で考えて作った証拠になります。

**A3**：正直に「分かりません」と言い、そのうえで知っている範囲での考えや、どう調べるかを話します。知ったかぶりは深掘りで分かりますし、現場で一番困るのは分からないと言えない人だからです。

**A4**：最新のファイルから消すだけでは、履歴に残るため不十分です。その API キーは漏れたものとして無効化し、新しいキーを作ります。公開するのは、秘密情報を含まない形で作り直したリポジトリにするのが安全です。

**A5**：解答例：現場には、教材で扱わなかった技術や独自の決まりが必ずあり、技術そのものも変わり続けるからです。この教材で得たのは完成した知識ではなく、裏で何が起きているかを確かめる姿勢と、調べ方・確かめ方です。それを使って学び続けることが、エンジニアの仕事の一部です。

## AIの使い方（この章）

推奨する聞き方の例：

- 「私は面接の練習をしています。Rails の MVC について説明するので、面接官として『なぜ？』を2回深掘りする質問をしてください」
- 「ポートフォリオの README を書きました。採用担当者の立場で、分かりにくい所と、もっと知りたくなる所を指摘してください。書き直しはしないでください」
- 「チェックリストで × だった『N+1 に気づける』について、確認のための小さな問題を3つ出してください」

この章でやってはいけない使い方：

- 面接の答えや README を AI に書かせ、自分の経験と結びつかない文章をそのまま使うこと。深掘りされたときに答えられません。
- 実在の企業の選考情報や、他の応募者の情報をプロンプトに入れること。

## まとめ

40項目のチェックリストで、技術・チーム・セキュリティ・AI の4領域の「できる」を点検し、足りない所は該当章の演習に戻って埋めます。
ポートフォリオと面接では、機能の多さより「なぜそう作ったか」を自分の言葉で伝えます。
入社後は、慣れる・任される・自分から動くの順で3か月を過ごします。
この教材を終えても、学びは終わりません。ここで身につけた「抽象を降りて確かめる」姿勢で、学び続けてください。

## 用語

| 用語 | 意味 |
|---|---|
| 業務レディ | ジュニアとして、チームの業務に参加できる状態 |
| ポートフォリオ | 自分の力を示す作品集。エンジニアの場合は主に GitHub のリポジトリと説明 |
| README | リポジトリの説明書。ポートフォリオの表紙になる |
| 模擬面接 | 本番の前に、面接の形式で受け答えを練習すること |
| 逆質問 | 面接の最後に、応募者から会社へ質問すること |
| オンボーディング | 新しく入った人が、チームや仕事に慣れるまでの期間とその支援 |
| Hotwire | Rails 標準の、JavaScript を書く量を抑えて画面を動かす仕組み（Turbo・Stimulus） |
| クラウド | インターネット経由で借りて使うサーバ・DB・ストレージなどのサービス |
| 実行計画 | DB が SQL をどの手順で実行するかの計画。遅いクエリの調査に使う |
| リリースノート | ソフトウェアの新しい版で何が変わったかをまとめた文書 |
