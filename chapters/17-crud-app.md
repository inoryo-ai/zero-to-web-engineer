# 第17章 自作部品でCRUDアプリを作る

> **この章のゴール**：第11〜16章で自作したサーバ・フレームワーク・ORMを組み合わせ、作成・表示・更新・削除ができる小さなWebアプリを完成させます。CSRF対策とエラーページを実装し、残っている防御の不足を記録できるようになります。
> **目安時間**：読む 3時間 ＋ 演習 20時間
> **前提**：第16章まで

## この章で学ぶこと

- アプリのテーマを決め、テーブル・バリデーション・URLを設計できる
- 自作の Router / Controller / View / Model を統合し、CRUD一式を TDD で実装できる
- CSRF攻撃の仕組みを説明し、セッションに結び付いたトークンで防御し、攻撃が失敗するテストを書ける
- 404・403・422・500 のエラーページを、内部情報を漏らさずに返せる
- 「テストが通る」ことと「本番で安全」の違いを、防御の不足の記録表で説明できる

## これまでの部品を1つにする

ここまでで、Webアプリに必要な部品を1つずつ作ってきました。

| 部品 | 作った章 | 役割 |
|---|---|---|
| HTTPサーバ / Rack | 第11章・第13章 | ソケットでリクエストを受け、レスポンスを返す |
| Router | 第14章 | URLとHTTPメソッドから、呼ぶ Controller を決める |
| Controller | 第14章 | リクエストを受けて、何をするか決める |
| View（ERB） | 第14章 | HTMLを組み立てる。出力はエスケープする |
| 共通処理（before_action 的な仕組み） | 第14章 | 全アクションの前に共通のチェックを行う |
| Model / BaseModel | 第16章 | DBの読み書きとデータの正しさを受け持つ |
| Console | 第16章 | Model を対話的に試す |

この章では、これらをつなげて1つのアプリにします。1つのリクエストが、次の順に流れていきます。

```text
ブラウザ
  → HTTPリクエスト
  → サーバ（Rack）
  → Router（どの Controller のどのアクションか）
  → 共通処理（CSRFトークンの確認など）
  → Controller（何をするか決める）
  → Model（DBを読み書きし、正しさを確かめる）
  → DB
  → View（HTMLを組み立てる）
  → HTTPレスポンス
  → ブラウザ
```

部品をただつなげるだけなら、意外と早く動きます。でも、この章の目標は「動く」ことではありません。「どの部品が何に責任を持っているか説明できる」ことです。たとえば、入力チェックは Controller の仕事でしょうか、Model の仕事でしょうか。CSRFトークンの確認は、各アクションに書くべきでしょうか、共通処理に書くべきでしょうか。迷ったら、各部品の責任に立ち返って考えます。

## テーマを決める

最初に、何を作るかを決めます。条件は次の3つです。

- 作成・一覧・詳細・更新・削除（CRUD）が自然に成り立つこと
- テーブルは1つで足りること（関連は第18章で扱います）
- 1日で説明できるくらい小さいこと

CRUD は Create（作成）、Read（読み取り）、Update（更新）、Delete（削除）の頭文字です。ほとんどの業務アプリは、この4つの操作の組み合わせでできています。

例として、メモ帳、タスク管理、読書記録、ひとこと掲示板などが考えられます。この章の説明では「投稿（Post）」を管理するアプリを例にします。投稿はタイトルと本文を持ちます。自分のテーマに合わせて読み替えてください。

テーマ選びでやりがちな失敗は、欲張ることです。「ログイン機能も」「画像も」「タグも」と広げると、統合の学びに集中できません。ログインは第19章、関連は第18章で、Rails を使って学びます。この章では、あえて小さく作ります。

## データを設計する

### テーブルとカラム

テーマが決まったら、テーブルを設計します。第15章で学んだとおり、カラムごとに型と制約を決めます。

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | INTEGER | PRIMARY KEY | DBが自動で振る番号 |
| title | TEXT | NOT NULL | タイトル |
| body | TEXT | NOT NULL | 本文 |
| created_at | TEXT | NOT NULL | 作成日時（ISO 8601形式の文字列） |

SQLite には日時の専用の型がないので、文字列で保存するのが一般的です。`2026-10-01T10:00:00+09:00` のような ISO 8601 形式にしておくと、文字列のまま並べ替えても時刻順になります。

テーブルを作るSQLは `db/schema.sql` に書きます。開発用DBへは `sqlite3 db/development.sqlite3 < db/schema.sql` で流し込み、テストでは同じファイルをメモリDBに流し込みます。開発とテストで同じ定義を使うことで、「テストでは動くのに本番では動かない」というずれを防げます。

### バリデーションを決める

次に、Model で守るルールを決めます。

- title は空にできない。100文字以内
- body は空にできない。2000文字以内

DBの NOT NULL 制約と Model のバリデーションは、役割が違いました（第16章）。DB制約は最後の砦、バリデーションは利用者に分かりやすいエラーを返すためのものです。両方を設定します。

文字数の上限は、見た目の都合だけではありません。上限がないと、巨大な文字列を送りつけられたときに、DBもメモリも圧迫されます。小さな防御の1つです。

## URLとルーティングを設計する

### REST の考え方

URLの設計には、REST（レスト）と呼ばれる考え方がよく使われます。「操作の対象（リソース）」をURLで表し、「何をするか」をHTTPメソッドで表す、というものです。Rails もこの考え方を採用しています。投稿の場合、次の7つが基本の形です。

| HTTPメソッド | URL | アクション | 何をするか |
|---|---|---|---|
| GET | /posts | index | 一覧を表示する |
| GET | /posts/new | new | 作成フォームを表示する |
| POST | /posts | create | 作成する |
| GET | /posts/:id | show | 1件を表示する |
| GET | /posts/:id/edit | edit | 編集フォームを表示する |
| PATCH | /posts/:id | update | 更新する |
| DELETE | /posts/:id | destroy | 削除する |

ここで大事な約束があります。**GET では、データを変更してはいけません。** GET は「見るだけ」の操作です。ブラウザは、リンクの先読みや再読み込みで GET を勝手に送ることがあります。検索エンジンのロボットも GET でページを巡回します。もし `GET /posts/3/delete` で削除できたら、誰かがリンクをたどっただけでデータが消えます。

### HTML フォームは GET と POST しか送れない

表の PATCH と DELETE には、1つ問題があります。HTMLの `<form>` は、`method` に GET と POST しか指定できません（第9章）。解決策は2つあります。

1つ目は、URLで区別する方法です。`POST /posts/:id/update`、`POST /posts/:id/destroy` のようにします。仕組みが単純で、自作フレームワークでも作りやすいです。

2つ目は、フォームに隠しフィールド `_method` を入れ、サーバ側で「POST だが、本当は PATCH として扱う」と読み替える方法です。

```html
<form action="/posts/3" method="post">
  <input type="hidden" name="_method" value="patch">
  ...
</form>
```

Rails はこの2つ目の方法を使っています。Rack には、これを行う `Rack::MethodOverride` というミドルウェアがあります（第13章）。どちらを選んでもかまいません。選んだ理由を設計メモに残してください。どちらの方法でも、状態を変える操作は POST で送られるという点が、後の CSRF 対策に関係します。

## CRUD を TDD で作る

### Controller の責任

Controller の仕事は、リクエストを受けて「何をするか」を決め、Model と View に仕事を割り振ることです。SQL は書きません。チェックのルールも書きません。それぞれ Model の仕事です。

`create` アクションの流れを日本語で書くと、次のようになります。

1. フォームから送られた値を取り出す
2. 値から Post オブジェクトを作り、`save` する
3. 成功したら、詳細ページへリダイレクトする
4. 失敗したら、入力値とエラーを付けて、フォームをもう一度表示する

### 成功したらリダイレクトする（PRG パターン）

作成に成功したとき、そのまま詳細画面のHTMLを返すこともできます。でも、それには問題があります。利用者がブラウザの再読み込みボタンを押すと、ブラウザは直前の POST をもう一度送ります。同じ投稿が2つできてしまいます。

そこで、POST が成功したら「この URL を GET で見に行ってください」というリダイレクトを返します。ブラウザは詳細ページを GET で取り直すので、再読み込みしても GET が繰り返されるだけです。この流れを、POST → Redirect → GET の頭文字を取って PRG パターンと呼びます。

リダイレクトのステータスコードは、303 See Other を使うと意図が明確です。303 は「次は GET で取りに行ってください」という意味です。レスポンスヘッダの `location` に行き先のURLを入れます。

### 失敗したら入力を残してフォームを再表示する

バリデーションで失敗したときは、リダイレクトしません。入力した値とエラーメッセージを付けて、フォームをもう一度表示します。リダイレクトすると、入力した内容が消えてしまうからです。長い本文を書いた後に全部消えたら、利用者はがっかりします。

このときのステータスコードは 422 Unprocessable Content（以前の名前は Unprocessable Entity）が適切です。「リクエストの形は正しいが、内容が受け付けられない」という意味です。200 を返すと、テストやプログラムから「成功」と区別しにくくなります。

### 存在しない id

`/posts/999` のように存在しない id が来たら、404 を返します。第16章で `find` が見つからないときの振る舞い（nil か例外か）を決めたはずです。それを Controller でどう 404 に変換するかを決めます。各アクションで `if post.nil?` と書くか、例外を共通処理でまとめて 404 にするか。後者のほうが書き忘れが起きにくいです。

### テストの順番

元教材と同じく、1つずつ RED → GREEN で進めます。おすすめの順番は次のとおりです。

1. 一覧（index）：投稿が2件あれば、両方のタイトルが表示される
2. 詳細（show）：本文が表示される。存在しない id なら 404
3. 作成フォーム（new）：フォームが表示される
4. 作成（create）：正しい値なら件数が1増え、303 で詳細へ。不正な値なら件数は増えず、422 で入力値とエラーが表示される
5. 編集・更新（edit / update）：値が変わる。不正な値なら変わらず 422
6. 削除（destroy）：件数が1減り、303 で一覧へ。対象以外の投稿は残る
7. GET では作成・更新・削除が起きない

第16章のSQLインジェクションのテストは、統合した後も通る状態を保ちます。検索機能を付けるなら、`' OR '1'='1` で全件が返らないテストを足します。

## View と XSS 対策

第14章で、ERB の出力をエスケープして XSS を防ぎました。統合したアプリでは、エスケープが必要な場所が増えます。特にフォームの再表示が要注意です。

フォームを再表示するとき、入力された値を `value` 属性に入れて返します。ここでエスケープを忘れると、属性の外に抜け出す攻撃ができてしまいます。たとえばタイトルに `"><script>alert(1)</script>` と入力されると、`value="` の引用符が閉じられ、その後ろの `<script>` がHTMLとして実行されます。

Ruby 標準の `ERB::Util.html_escape` は、属性の中で危険な引用符も変換します。

```ruby
require "erb"
puts ERB::Util.html_escape(%q{<script>alert("x")</script> & 'quote'})
```

```text
&lt;script&gt;alert(&quot;x&quot;)&lt;/script&gt; &amp; &#39;quote&#39;
```

`<` と `>` だけでなく、`"` と `'` も変換されています。属性値は必ず引用符で囲み（`value="..."`）、中身はエスケープする。この2つを守れば、属性からの脱出は防げます。

保存されている投稿を一覧・詳細・編集画面に表示するときも、同じです。DBに入っている値は「一度チェックを通った安全な値」ではありません。利用者が入力した文字列そのものです。出力するたびにエスケープします。

完了条件として、`<script>` を含む投稿を保存し、一覧・詳細・編集の3画面で、生の `<script>` が出力されず `&lt;script&gt;` になっていることをテストで確かめます。

## CSRF 対策

この章で一番難しいところです。ゆっくり読んでください。

### CSRF とは何か

CSRF（シーサーフ、Cross-Site Request Forgery）は、「別のサイトから、利用者のブラウザに、意図しないリクエストを送らせる」攻撃です。

具体例で考えます。あなたは自分のPCで、自作アプリを `http://127.0.0.1:3000` で動かしています。そのまま別のタブで、悪意のあるWebサイトを開いてしまいました。そのページには、次のようなHTMLが隠されています。

```html
<form action="http://127.0.0.1:3000/posts/1" method="post" id="f">
  <input type="hidden" name="_method" value="delete">
</form>
<script>document.getElementById("f").submit();</script>
```

ページを開いた瞬間、フォームが自動で送信されます。送信しているのはあなたのブラウザです。あなたのブラウザからは `127.0.0.1:3000` に届きます。サーバから見ると、あなたが自分で削除ボタンを押したのと区別がつきません。投稿1が消えます。

たとえるなら、あなたの家の郵便受けに、あなたの筆跡を真似た「預金を全部引き出してください」という依頼書を、他人が入れるようなものです。銀行の窓口は、筆跡と印鑑が本物に見えれば応じてしまいます。

### よくある誤解

次の対策は、どれも CSRF を防げません。

- **サーバを 127.0.0.1 で待ち受ける**：リクエストを送っているのは利用者自身のブラウザです。ブラウザは同じPCで動いているので、ループバックに届きます
- **GET をやめて POST にする**：上の例のとおり、別サイトのフォームからも POST は送れます。ただし「GET でデータを変えない」こと自体は前提として必要です
- **HTTPS にする**：通信は暗号化されますが、送信者が誰かは変わりません
- **ログイン機能がないから関係ない**：この章のアプリには認証がありませんが、別サイトからデータを消されるという被害は同じように起きます

ログインがあるアプリでは、事態はもっと深刻です。ブラウザは、そのサイトのCookie（ログイン状態）を自動で付けて送るからです。攻撃者は、あなたのログイン状態を勝手に使えます。Cookie については第19章で詳しく学びます。

### トークンで防ぐ

基本の対策は「CSRFトークン」です。考え方はこうです。

1. サーバは、利用者ごとに推測できないランダムな文字列（トークン）を作り、サーバ側に覚えておく
2. フォームを表示するとき、そのトークンを隠しフィールドに埋め込む
3. フォームが送信されたら、送られてきたトークンが、その利用者のために覚えておいたものと一致するか確かめる
4. 欠けている、または一致しなければ、DBを変更する**前に** 403 などで拒否する

悪意のあるサイトは、あなたのブラウザにリクエストを送らせることはできます。でも、あなたのフォームに埋め込まれたトークンを読むことはできません。ブラウザは、別のサイトのページの中身を読ませない仕組み（同一オリジンポリシー）を持っているからです。だから、正しいトークンを付けたリクエストを偽造できません。

### 「利用者ごと」をどう実現するか：最小のセッション

トークンを「その利用者のために覚えておく」には、リクエストをまたいで利用者を見分ける仕組みが必要です。これがセッションです。この章では、最小限のセッションを自作します。

- 初めて来たブラウザに、推測できないセッションID を発行し、Cookie で渡す
- サーバは、セッションID をキーにしたハッシュ（メモリ上の保管場所）に、そのセッションのトークンを保存する
- 次のリクエストからは、ブラウザが送ってくる Cookie のセッションID で、保管場所を引く

推測できないランダムな文字列は、Ruby 標準の `SecureRandom` で作れます。

```ruby
require "securerandom"
p SecureRandom.hex(32).size
p SecureRandom.urlsafe_base64(32).size
```

```text
64
43
```

`SecureRandom.hex(32)` は 32 バイト（256 ビット）の乱数を、64文字の16進数で返します。`rand` は推測できる可能性があるので、セキュリティの用途には使いません。セッションID もトークンも `SecureRandom` で作ります。

守るべき点をまとめます。

- 全利用者で共通の固定値をトークンにしない。1人のトークンが分かれば全員に使えてしまう
- トークンを URL のクエリ文字列に入れない。URL はログや閲覧履歴、他サイトへの参照元情報に残る
- トークンやセッションID をログに出力しない
- セッションID の Cookie には `HttpOnly` と `SameSite=Lax` を付ける（意味は第19章で学びます）
- 比較は、文字列の一致にかかる時間から中身を推測されないよう、`Rack::Utils.secure_compare` のような比較用のメソッドを使う

### 検証は共通処理に置く

トークンの検証を、各アクション（create / update / destroy）に書くと、いつか書き忘れます。第14章で作った before_action 的な共通処理に置き、「GET 以外のリクエストはすべて検証する」形にしましょう。新しいアクションを足しても、自動で守られます。この「安全なほうが既定値」という設計は、Rails も採用しています。

### 攻撃が失敗するテストを書く

完了条件は「トークンがない、または違うリクエストで、DBが変わらない」ことをテストで示すことです。テストでは、フォームの送信に当たるリクエストを自分で組み立てます。次の補助メソッドは、Rack の環境ハッシュを組み立ててアプリを呼ぶ例です。`App` は自分のアプリの入り口に読み替えてください。

```ruby
require "stringio"
require "uri"

def post_form(path, params, session_id: nil)
  body = URI.encode_www_form(params)
  env = {
    "REQUEST_METHOD" => "POST",
    "PATH_INFO" => path,
    "CONTENT_TYPE" => "application/x-www-form-urlencoded",
    "CONTENT_LENGTH" => body.bytesize.to_s,
    "rack.input" => StringIO.new(body)
  }
  env["HTTP_COOKIE"] = "session_id=#{session_id}" if session_id
  App.call(env)
end
```

これを使った最初のテストは、たとえば次の形です。テストの準備で、セッションとそのトークンを作っておく必要があります。その方法は、自分のセッションの設計に合わせて考えてください。

```ruby
def test_rejects_create_without_token
  status, _headers, _body = post_form("/posts", { "title" => "攻撃", "body" => "x" },
                                      session_id: @session_id)

  assert_equal 403, status
  assert_equal 0, Post.all.size
end
```

同じ形で、少なくとも次のパターンをテストします。

- トークンなし
- 改ざんしたトークン（1文字変えたもの）
- 別のセッションのトークン（セッションAの Cookie に、セッションBのトークンを付ける）
- セッションの Cookie そのものがない

これを、作成・更新・削除の**すべて**の状態変更ルートで確かめます。もちろん、正しいセッションとトークンの組み合わせなら成功するテストも必要です。そうでないと「全部拒否する」だけの壊れた実装でも通ってしまいます。

### 追加の防御

Cookie の `SameSite` 属性や、リクエストの `Origin` ヘッダを確かめる方法も、CSRF の防御に役立ちます。ただし、これらは追加の防御として学び、属性を設定しただけで完了にはしません。古いブラウザや設定によって効かない場合があるからです。トークンが基本、その他は重ねて守るための層です。

ここで作ったセッションとトークンは、あくまで学習用の最小実装です。セッションの有効期限、サーバ再起動時の扱い、複数スレッドからの同時アクセスなど、本番に必要な検討はしていません。本番のログインやセッション管理には使わないでください。

## エラーページ

### どの層で何を返すか

エラーには種類があり、ステータスコードで区別します。

| 状況 | ステータス | どこで判断するか | 画面に出すもの |
|---|---|---|---|
| URLに合うルートがない | 404 Not Found | Router | 「ページが見つかりません」 |
| id の投稿が存在しない | 404 Not Found | Controller（Model の結果を見て） | 同上 |
| CSRFトークンが不正 | 403 Forbidden | 共通処理 | 「リクエストを処理できません」 |
| バリデーションエラー | 422 | Controller（Model の結果を見て） | 入力フォームとエラー |
| 想定外の例外 | 500 Internal Server Error | 一番外側（ミドルウェアなど） | 「エラーが発生しました」 |

### 内部情報を漏らさない

500 エラーの画面に、例外のメッセージや、どのファイルの何行目で起きたかの情報（スタックトレース）を表示してはいけません。開発中は便利ですが、攻撃者にとっては「使っているライブラリ」「ファイルの配置」「SQLの形」を知る手がかりになります。

画面には短い一般的なメッセージだけを出し、詳しい情報はサーバのログ（ターミナルの出力など）に書きます。ログにも、トークンやパスワードのような秘密は書きません。

テストでは、わざと例外を起こすルートを作り、ステータスが 500 であること、レスポンス本文に例外のメッセージが含まれないことを確かめます。例外を握りつぶして何も記録しない（`rescue` して何もしない）のも、障害の原因を追えなくなるので避けます。

## 防御の不足を記録する

最後に、とても大事な作業があります。「このアプリに、まだ何が足りないか」を書き出すことです。

この章のテストがすべて通っても、このアプリは本番で使える安全さを持っていません。テストは、学習の範囲で決めた完了条件を確かめているだけです。テストが確かめていない領域が、まだたくさん残っています。副教材「安全上の注意」で示された5つの領域を、自分のアプリについて記録します。

| 領域 | 放置すると起きること | 状態 | 根拠（コード・テスト） |
|---|---|---|---|
| 資源の上限（接続数・スレッド数・リクエスト行／ヘッダ／ボディ長・メモリ・CPU） | 巨大なリクエストや大量接続でサーバが落ちる | 未確認 | |
| タイムアウト（読み取り・書き込み・TLSハンドシェイク、遅いクライアント） | 少しずつ送ってくる接続にスレッドを占有される | 未確認 | |
| 資源の回収（例外・切断時のソケットclose、スレッド・DB接続） | ファイル記述子や接続が漏れ続け、いずれ停止する | 未確認 | |
| HTTPの厳密な検証（構文・メッセージ境界・不正入力の拒否） | 解釈のずれを突かれ、リクエストを密輸される | 未確認 | |
| 運用上の防御（認証・認可、セッション管理、機密を漏らさないログ・エラー応答、依存の更新） | 誰でも操作でき、エラー画面から内部情報が漏れる | 未確認 | |

「状態」は「実装済み」「一部」「未実装」「未確認」のどれかで書きます。確かめていないものを「実装済み」にしてはいけません。「一部」なら、何ができていて何ができていないかを根拠欄に書きます。たとえば、本文の文字数上限を付けたなら、ボディ長の上限は「一部」かもしれません。でも、HTTPリクエスト全体の大きさに上限がなければ、巨大なリクエストは本文のチェックの前にメモリを使い切ります。

この表は、第26章の最終課題でもう一度埋め直します。今の時点で正直に書いておくと、後で自分の成長を比べられます。

Rails のようなフレームワークは、この表のかなりの部分を、目に見えないところで引き受けています。次の第18章では、自作した部品が Rails の何に当たり、何が自動化されているのかを対応づけていきます。

> さらに深く：[Phase 6.1: 統合 — 自作コンポーネントでWebアプリケーションを構築する](https://github.com/speee/training-web-app/blob/main/phase-6-1.md)、[最終成果物課題](https://github.com/speee/training-web-app/blob/main/goal.md)

## 実務ではこうなる

現場では、フレームワークがCRUDの骨組みを用意してくれます。Rails なら、次の章で見るように数行でルーティングとフォームが揃います。それでも、この章で考えたことは、そのまま実務の判断になります。

- 「GET でデータを変えない」は、レビューで必ず確認される原則です。「ワンクリックで既読にする」機能を GET のリンクで作ってしまうのは、ジュニアがやりがちな失敗です
- 保存に失敗したときに 200 を返す、入力を消してしまう、という失敗もよくあります。Rails でも、失敗時のステータスを正しく返さないと画面が更新されないことがあります（第18章）
- 本番環境のエラー画面に、スタックトレースを出してしまう事故は実際に起きます。開発用の設定のまま公開したときです
- CSRF対策は Rails では既定で有効です。ところが「API を作るから」「外部サービスからの通知を受けるから」と、理由を十分に考えずに無効化する人がいます。無効化するなら、代わりの防御があるかを必ず確かめます

また、「何がまだ足りないか」を記録する習慣は、そのまま実務のリスク管理です。「全部大丈夫です」と言うエンジニアより、「ここまでは確かめました。ここは未確認です」と言えるエンジニアのほうが信頼されます。

すべて `~/workspace/ch17-crud-app/` で行います。テーマは自分で決めてかまいません。説明では投稿（Post）を例にします。サーバは必ず `127.0.0.1` で起動し、データはダミーだけを使います。

### 演習17-1：設計をまとめる

- やること
  1. `docs/design.md` を作り、次の5項目を書く：テーマと理由、テーブル定義（カラム・型・制約）、バリデーションのルール、ルート表（メソッド・URL・アクション・何をするか）、PATCH / DELETE をどう送るか（URLで区別するか `_method` か）とその理由

  3. Model を BaseModel から作り、バリデーションのテストを書いて通す
- **完了条件**
  - `docs/design.md` に5項目すべてがある
  - `sqlite3 db/development.sqlite3 ".schema"` の出力に、設計どおりのテーブルが表示される
  - 空のタイトル・上限を超える本文で `save` が false になるテストが通る
  - `git check-ignore -v db/development.sqlite3` で無視の設定が表示される
- ヒント
  - ルート表に「GET でデータを変えない」が守られているかを、自分でチェックしてから先に進みましょう

### 演習17-2：CRUD 一式を TDD で作る

- やること
  1. 本文の「テストの順番」の1〜7を、RED → GREEN → REFACTOR で実装する
  2. 作成・更新の成功時は 303 でリダイレクトし、失敗時は 422 で入力値を残したフォームを表示する
  3. 存在しない id では 404 を返す
  4. 第16章の SQLインジェクションのテストが通ったままであることを確認する
- **完了条件**
  - すべてのアクションのテストが通る
  - 作成に失敗したとき、件数が変わらず、ステータスが 422 で、入力したタイトルがフォームに残っているテストが通る
  - GET で `/posts/1/edit` などを呼んでも件数と内容が変わらないテストが通る
  - `grep -rn 'execute' app/controllers/` が0件である（Controller に SQL がない）
- ヒント
  - 303 のテストでは、ステータスに加えて `location` ヘッダの値も確かめましょう
  - 1つのテストで1つのことだけを確かめると、失敗したときに原因が分かりやすくなります

### 演習17-3：CSRF・XSS・エラーページ

- やること
  1. 最小のセッション（推測できないセッションID を Cookie で渡し、サーバ側でトークンを保持する）を作る
  2. 状態を変えるフォームすべてに、トークンの隠しフィールドを埋め込む
  3. GET 以外のリクエストで、DB更新の前にトークンを検証する共通処理を作る。欠落・不一致は 403
  4. `<script>` を含む投稿が、一覧・詳細・編集画面で文字列として表示されるようにする
  5. 404 / 403 / 422 / 500 のエラー応答を作る。500 では内部情報を画面に出さない
- **完了条件**（すべてテストで確かめる）
  - トークンなし・改ざん済み・別セッションのトークン・Cookie なし、の4パターンで、作成・更新・削除のすべてが 403 になり、DBの件数と内容が変わらない
  - 正しいセッションとトークンの組み合わせでは、作成・更新・削除が成功する
  - `<script>alert(1)</script>` を本文に持つ投稿を表示すると、レスポンスに `<script>alert(1)` が含まれず、`&lt;script&gt;` が含まれる（一覧・詳細・編集の3画面）
  - 例外を起こすルートで 500 が返り、本文に例外のメッセージが含まれない
- ヒント
  - 「別セッションのトークン」のテストのために、テストの準備で2つのセッションを作っておきます
  - フォームにトークンを埋め込む部分は、全フォームで共通の部品（ヘルパーメソッド）にすると、埋め込み忘れが減ります

- やること

  4. 1つのリクエスト（例：投稿の更新）が、どの部品をどの順で通るかを `docs/design.md` に追記する
  5. 自分のPCで、ダミーデータを使ってCRUDを一通り操作するデモを行う。人に見せるなら画面共有か録画にする
  6. 発展（任意）：Rails がどの部分を自動化していそうか、予想を `docs/design.md` に書いておく。第18章で答え合わせをする
- **完了条件**

  - `git ls-files` の結果が空である

  - 公開URLを作るサービス（トンネル）やポート転送は使いません。デモは自分のPCの中で完結させます

## 確認クイズ

**Q1.** 投稿の作成に成功した後、詳細画面のHTMLをそのまま返さず、303 でリダイレクトするのはなぜですか。

**Q2.** 「このアプリは 127.0.0.1 でしか待ち受けていないし、ログイン機能もない。だから CSRF 対策は不要だ」という意見は正しいですか。

**Q3.** CSRFトークンを「全利用者で共通の、推測しにくい長い文字列」にしました。何が問題ですか。

**Q4.** バリデーションに失敗したとき、ステータス 200 でフォームを返すと、何が困りますか。

**Q5.** 演習のテストがすべて通りました。このアプリを、社内の共有サーバで同僚に使ってもらってよいですか。

### 解答と解説

**A1.** 再読み込みで二重に作成されるのを防ぐためです。POST の結果のページで再読み込みすると、ブラウザは同じ POST をもう一度送ります。リダイレクトして GET で詳細を表示すれば、再読み込みしても GET が繰り返されるだけです。これを PRG パターンと呼びます。

**A2.** 正しくありません。CSRF のリクエストを送るのは利用者自身のブラウザで、同じPC上にあるので 127.0.0.1 に届きます。ログインがなくても、別サイトから投稿を消されるなどの被害は起きます。トークンによる防御が必要です。

**A3.** 1人がそのトークンを知れば、全員分のリクエストを偽造できます。トークンは利用者（セッション）ごとに別の値にし、そのセッションに結び付けて検証します。また、ソースコードやログに固定値が残る危険もあります。

**A4.** プログラムやテストから「成功」と「失敗」を区別しにくくなります。422 を返せば、ステータスだけで「内容が受け付けられなかった」ことが分かります。Rails と Turbo の組み合わせでは、失敗時に 422 を返さないと画面が正しく更新されないこともあります（第18章）。

**A5.** いけません。テストは学習の範囲の完了条件を確かめただけです。資源の上限、タイムアウト、認証・認可などは未実装か未確認で、防御の不足の表に記録したとおりです。社内のネットワークも、信頼できないネットワークとして扱います。

## AIの使い方（この章）

この章では、AIを「設計のレビュー役」と「攻撃パターンを一緒に考える相手」として使います。

推奨する聞き方の例です。

- 「私のアプリのルート表です（表を貼る）。REST の考え方や『GET で状態を変えない』原則から見て、問題があれば指摘してください。修正したコードは書かないでください」
- 「CSRF トークンの検証で、私はトークンなし・改ざん・別セッション・Cookie なしの4パターンをテストしています。他に考えるべきパターンはありますか」
- 「防御の不足の表の『タイムアウト』の行を、私のサーバのコード（該当部分を貼る）について『一部』としました。この判断が妥当か、確かめる方法を教えてください」

やってはいけない使い方です。

- CSRF 対策やセッションのコードをAIに書かせて、そのまま貼ること。セキュリティの仕組みこそ、自分で理解して書かないと、どこに穴があるか説明できません
- 防御の不足の表を、自分のコードを確かめずにAIに埋めさせること。「実装済み」の根拠は、自分のコードとテストでしか示せません

## まとめ

- Webアプリは、責任の分かれた部品（Router・Controller・Model・View）が協力して動いている。統合では、各部品の責任に立ち返って判断する
- GET でデータを変えない。成功したら 303 でリダイレクトし、失敗したら 422 で入力を残して再表示する
- CSRF はループバック・POST・HTTPS では防げない。セッションに結び付けたトークンを、DB更新の前に、共通処理で検証する
- テストが通っても本番で安全とは限らない。足りない防御を正直に記録することが、安全への第一歩になる

## 用語

| 用語 | 意味 |
|---|---|
| CRUD | Create・Read・Update・Delete。データに対する基本の4操作 |
| REST | リソースをURLで、操作をHTTPメソッドで表すURL設計の考え方 |
| リソース | URLで表される操作の対象。この章では投稿（Post） |
| PRG パターン | POST の成功後にリダイレクトし、GET で結果を表示する流れ。二重送信を防ぐ |
| 303 See Other | 「次は GET で指定のURLを取りに行って」という意味のリダイレクト |
| 422 Unprocessable Content | 形式は正しいが内容を受け付けられない、という意味のステータス |
| メソッドオーバーライド | フォームの隠しフィールド `_method` で、POST を PATCH や DELETE として扱う仕組み |
| CSRF | 別サイトから利用者のブラウザに、意図しない状態変更リクエストを送らせる攻撃 |
| CSRFトークン | セッションごとに発行する推測できない値。フォームに埋め込み、送信時に照合する |
| セッション | 複数のリクエストをまたいで、同じ利用者だと見分けるための仕組み |
| SecureRandom | 推測できない乱数を作る Ruby 標準のライブラリ |
| 同一オリジンポリシー | 別のサイトのページの中身を読ませない、ブラウザの安全の仕組み |
| スタックトレース | 例外が起きるまでに呼ばれたメソッドとファイル・行の一覧 |
