# 第20章 セキュリティ実践（OWASP Top 10・秘密情報・依存関係）

> **この章のゴール**：Railsアプリを「動く」から「攻撃されても壊れにくい」へ一段引き上げます。代表的な脆弱性の型を知り、自分のアプリで対策とテストを書けるようになります。
> **目安時間**：読む 3時間 ＋ 演習 6時間
> **前提**：第19章まで

## この章で学ぶこと

- OWASP Top 10（2021年版）の10項目を、自分のRailsアプリの具体的な場所と結びつけて説明できる
- APIキーやパスワードなどの秘密情報を、環境変数や Rails の credentials で管理できる
- 秘密情報が漏れたときに「消す」ではなく「ローテーションする」理由を説明できる
- bundler-audit・Dependabot・Brakeman で、依存関係とコードの既知の問題を見つけられる
- ログとエラー画面から個人情報や内部情報が漏れないように設定できる
- リソースの上限とタイムアウトを決め、それをテストで確かめられる

## セキュリティは「最後に足すもの」ではない

第10章で、Webセキュリティの基本を学びました。第11〜17章では、パストラバーサル・XSS・CSRF・SQLインジェクションの対策を自分で実装し、攻撃が失敗するテストを書きました。第18章からは Rails に乗り換え、第19章で認証と認可を作りました。

ここで一度、立ち止まって考えます。Rails を使えば、もう安全なのでしょうか。

答えは「半分だけ安全」です。Rails は、ERB の自動エスケープや CSRF トークン、SQL のプレースホルダなど、多くの防御を最初から持っています。副教材「安全上の注意（本編）」の言い方を借りると、フレームワークは「見えない仕事」を引き受けてくれます。

しかし、Rails が引き受けられない仕事もあります。

- 「この投稿を、この人が編集してよいか」という判断（認可）
- API キーをどこに置くかという判断（秘密情報の管理）
- 使っている gem に穴が見つかったときの更新（依存関係の管理）
- 何をログに残し、何を残さないかの判断（ログ設計）

これらはアプリごとに答えが違うので、フレームワークには決められません。この章は、その「アプリを作る人が決めること」を扱います。

副教材の「最小実装に残る防御の不足」の表を覚えているでしょうか。資源の上限、タイムアウト、資源の回収、HTTPの厳密な検証、運用上の防御の5つでした。自作サーバでは全部が自分の責任でした。Rails と Puma（Railsが使うWebサーバ）に乗り換えると、このうち「資源の回収」や「HTTPの厳密な検証」の多くは任せられます。一方で「運用上の防御」と、上限・タイムアウトの一部は、依然としてあなたの仕事です。この章の最後の演習で、あの表を Rails 版として埋め直します。

## OWASP Top 10 とは何か

**OWASP**（オワスプ）は、Webアプリのセキュリティについて情報を公開している非営利の団体です。**OWASP Top 10** は、その団体がまとめた「Webアプリで特に多く、影響の大きい問題」のランキングです。数年ごとに改訂されます。

たとえるなら、交通安全の「事故の多い交差点マップ」です。全部の危険を網羅してはいません。しかし、まずどこに気をつけるべきかを教えてくれます。業界の共通語なので、レビューや脆弱性の報告で「これは A01 ですね」のように使われます。

この章では、**2021年版**の項目名で説明します。2025年版の公開も進んでいて、項目名や順位が一部変わっています。最新の内容は、OWASP の公式サイト（https://owasp.org/www-project-top-ten/ ）で確認してください。順位が入れ替わっても、それぞれの考え方はそのまま役に立ちます。

### A01 アクセス制御の不備（Broken Access Control）

「ログインしているか」ではなく、「その人がその操作をしてよいか」の確認漏れです。2021年版で1位になった、最も多い問題です。

典型例は、URL の数字を書き換えるだけで他人のデータが見えてしまうケースです。`/posts/12/edit` を開ける人が、`/posts/13/edit` も開けてしまう。これを **IDOR**（Insecure Direct Object Reference、直接オブジェクト参照の不備）と呼びます。

Rails でよくある原因は、次のような書き方です。

```ruby
# 危ない：ID さえ合えば誰の投稿でも見つかる
@post = Post.find(params[:id])

# 安全側：ログイン中のユーザーの投稿の中から探す
@post = current_user.posts.find(params[:id])
```

下の書き方では、他人の投稿の ID を指定すると `ActiveRecord::RecordNotFound` が発生します。Rails はこれを 404 Not Found として返します。「存在しない」と答えるので、他人の投稿が存在するかどうかも漏れません。

第19章で作った認可の仕組みが、すべてのアクションに漏れなく効いているか。これを確かめる手段はテストしかありません。演習20-1で書きます。

### A02 暗号化の失敗（Cryptographic Failures）

守るべきデータを、暗号化せずに送ったり保存したりする問題です。パスワードを平文でDBに保存する、HTTP（暗号化なし）でログインさせる、などが該当します。

Rails では次の道具がそろっています。

- パスワードは `has_secure_password`（bcrypt によるハッシュ化）で保存する。第19章で使いました。
- 本番では `config.force_ssl = true` で HTTPS を強制する。
- 特に機密性の高い列は、Active Record Encryption（Rails 7 以降）で暗号化できる。

ポイントは「暗号を自作しない」ことです。暗号は、正しく見えても簡単に破れる作り方がたくさんあります。実績のある仕組みを、決められた使い方で使います。

### A03 インジェクション（Injection）

外から来た文字列が、データではなく命令として解釈される問題です。SQLインジェクションが代表で、2021年版では XSS もここに含まれます。第14〜16章で自作しながら対策を学びました。

Rails では、次のように書けば値は安全にバインドされます。

```ruby
Post.where(title: params[:q])
Post.where("title LIKE ?", "%#{Post.sanitize_sql_like(params[:q])}%")
```

危ないのは、文字列の中に直接埋め込む書き方です。

```ruby
# 危ない：params[:q] がそのまま SQL 文になる
Post.where("title = '#{params[:q]}'")
```

XSS も同じ構造です。ERB の `<%= %>` は自動でエスケープします。しかし `raw` や `html_safe` を付けると、そのエスケープを自分で外すことになります。これらを見かけたら「本当に必要か」を疑ってください。

### A04 安全でない設計（Insecure Design）

実装のミスではなく、設計の段階で守りが抜けている問題です。たとえば「パスワード再設定のメールに、新しいパスワードそのものを書いて送る」設計は、実装がどれだけ正確でも危険です。

対策は、作り始める前に「この機能を悪用するなら、どうするか」を考える習慣です。これを **脅威モデリング** と呼びます。大げさな手法を使わなくても、「誰が」「何を」「どうやって悪用できるか」を3行書くだけで効果があります。

### A05 セキュリティの設定ミス（Security Misconfiguration）

本番環境なのに開発用の設定のまま動いている、という問題です。次のような例があります。

- 本番でエラー時に詳細なスタックトレース（エラーの発生経路）を表示している
- 管理画面が初期パスワードのまま公開されている
- 不要なポートやサービスが外から見える

Rails は `config/environments/production.rb` に本番向けの安全な初期値を持っています。このファイルを理由なく書き換えないこと、書き換えるならレビューを通すことが大切です。後の節「エラー画面で内部情報を出さない」で詳しく見ます。

### A06 脆弱で古いコンポーネント（Vulnerable and Outdated Components）

使っているライブラリ（gem）に、既知の脆弱性があるのに更新していない問題です。あなたのコードが完璧でも、土台の gem に穴があれば攻撃されます。

Rails アプリは、たいてい数十から百を超える gem に依存しています。手作業で全部を追うのは不可能です。そこで、後の節で bundler-audit と Dependabot を使って自動化します。

### A07 識別と認証の失敗（Identification and Authentication Failures）

ログインまわりの弱さです。パスワードの総当たりを止めない、セッションIDをログアウト後も使える、推測しやすいパスワードを許す、などが該当します。

第19章で、ログイン時に `reset_session` でセッションを作り直す理由を学びました。この章では、ログインの試行回数に上限を付けます（後の節「リソース上限とタイムアウト」）。

### A08 ソフトウェアとデータの整合性の不備（Software and Data Integrity Failures）

「信頼できるはず」のものを、確かめずに信じてしまう問題です。たとえば、どこから来たか分からないスクリプトをCIで実行する、署名を確かめずに外部からの通知（Webhook）を受け入れる、などです。

Webhook の署名検証は、第21章で実装します。

### A09 セキュリティログとモニタリングの不備（Security Logging and Monitoring Failures）

攻撃を受けても、記録がなくて気づけない問題です。ログインの失敗が1分間に1万回あっても、誰も見ていなければ止められません。

ただし、ログに「何でも書けばよい」わけではありません。パスワードや個人情報をログに書くと、今度はログが漏えいの原因になります。この両立を後の節で扱います。監視とアラートは第23章で学びます。

### A10 サーバーサイドリクエストフォージェリ（SSRF）

利用者が指定した URL に、サーバがリクエストを送る機能を悪用される問題です。

たとえば「画像の URL を入力すると、サーバが取り込んでくれる」機能があるとします。攻撃者が `http://127.0.0.1:...` や、クラウドの内部管理用アドレスを入力すると、サーバは外からは届かない内部へリクエストを送ってしまいます。サーバが「内側からの使い走り」にされるわけです。

対策は、アクセスしてよいホストを許可リストで決めることです。「危ないものを拒否する」より「安全なものだけ許可する」方が漏れにくくなります。第16章で、`ORDER BY` のカラム名を許可リストで制限したのと同じ考え方です。

### 10項目に共通すること

並べてみると、10項目は大きく3つに分けられます。

1. **信頼してはいけないものを信頼した**：A03、A08、A10。外からの入力や、出どころの分からないデータ。
2. **確認すべきことを確認しなかった**：A01、A07。誰が何をしてよいか、本人かどうか。
3. **作った後の管理が足りない**：A02、A05、A06、A09。設定、更新、記録。

1と2はコードを書くときに、3は運用するときに効いてきます。この章の残りの節は、主に3を扱います。

## 秘密情報の管理

**秘密情報**とは、知られると他人があなたやあなたのサービスになりすませる情報です。APIキー、DBのパスワード、署名用の鍵、Rails の `secret_key_base` などが該当します。

第10章のルールを思い出してください。「秘密鍵・トークン・パスワードはコミットしない。`.gitignore` を先に」。ここではその理由をもう一歩深く見て、Rails での具体的な置き場所を学びます。

### なぜコードに書いてはいけないのか

コードに直接書いた秘密情報は、次の経路で漏れます。

- GitHub に push した瞬間、リポジトリを見られる全員に見える。公開リポジトリなら、自動収集ボットが数分で見つけるとも言われます。
- 後で削除しても、Git の履歴に残る。
- コードをコピーした人、画面共有を見た人、AIに貼り付けた先にも渡る。

もう一つの理由は「環境ごとに値を変えたい」からです。開発ではダミーのキー、本番では本物のキーを使います。値がコードに埋め込まれていると、環境ごとに書き換えが必要になります。

### 環境変数

**環境変数**は、プログラムの外から値を渡す仕組みです。OS がプロセス（動いているプログラム）を起動するときに、名前と値の組を一緒に渡します。たとえるなら、コードという「レシピ」に対して、環境変数は「今日の材料メモ」です。レシピは同じでも、材料メモを差し替えれば別の料理になります。

Ruby では `ENV` で読みます。`ENV["名前"]` は、値がないと `nil` を返します。`ENV.fetch("名前")` は、値がないと例外を発生させます。必須の設定には `fetch` を使うと、設定漏れにすぐ気づけます。

```ruby
puts ENV.fetch("APP_GREETING", "こんにちは（既定値）")
api_key = ENV.fetch("WEATHER_API_KEY")
puts "キーの長さ: #{api_key.length}"
```

```text
$ ruby env_fetch.rb
こんにちは（既定値）
env_fetch.rb:2:in `fetch': key not found: "WEATHER_API_KEY" (KeyError)
	from env_fetch.rb:2:in `<main>'

$ WEATHER_API_KEY=dummy-1234 APP_GREETING=やあ ruby env_fetch.rb
やあ
キーの長さ: 10
```

コマンドの前に `名前=値` を書くと、そのコマンドにだけ環境変数を渡せます。キーそのものではなく「長さ」だけを表示している点にも注目してください。秘密情報は、確認のためでも画面に出さない習慣をつけます。

### `.env` ファイルは commit しない

環境変数を毎回コマンドに書くのは面倒です。そこで、開発環境では `.env` というファイルに書いておき、`dotenv` という gem で読み込む方法がよく使われます。

```text
# .env（コミットしない）
WEATHER_API_KEY=dummy-1234
```

このとき、次の2つを必ず守ります。

1. `.env` を作る **前に** `.gitignore` に `.env` を追加する。
2. 値を空にした見本 `.env.example` を作り、こちらはコミットする。チームの他の人が「どの変数が必要か」を知るためです。

```text
# .env.example（コミットする。値は書かない）
WEATHER_API_KEY=
```

追加した後、本当に無視されるかを確かめます。

```bash
git check-ignore -v .env      # .gitignore の該当行が表示されればOK
git ls-files -- .env          # 何も表示されなければOK
```

`.gitignore` は、既に追跡しているファイルには効きません。うっかり先にコミットしていたら、`git rm --cached -- .env` で追跡から外します。ただし、これだけでは履歴に残った値は消えません。その場合の対応は、後の「漏れたらローテーション」で説明します。

### Rails の credentials

Rails には、秘密情報を **暗号化した状態でリポジトリに置く** 仕組みがあります。これを **credentials** と呼びます。

- `config/credentials.yml.enc`：暗号化された秘密情報。コミットしてよい。
- `config/master.key`：それを開く鍵。**絶対にコミットしない**。`rails new` が作る `.gitignore` に最初から入っています。

たとえるなら、`credentials.yml.enc` は金庫、`master.key` は金庫の鍵です。金庫は会社の廊下に置いてもよいですが、鍵は持ち歩かない、という分け方です。

編集は専用のコマンドで行います。保存すると自動で暗号化されます。

```bash
EDITOR="code --wait" bin/rails credentials:edit
```

`--wait` は、エディタでファイルを閉じるまでコマンドを待たせる指定です。これがないと、エディタが開いた瞬間に保存処理が終わってしまいます。開いたファイルには YAML 形式で書きます。

```yaml
weather_api:
  key: dummy-1234
```

アプリからは次のように読みます。

```ruby
Rails.application.credentials.dig(:weather_api, :key)
```

本番サーバには `master.key` のファイルを置く代わりに、環境変数 `RAILS_MASTER_KEY` に鍵の中身を設定するのが一般的です。環境ごとに別の鍵を使いたい場合は `bin/rails credentials:edit --environment production` で、本番専用のファイルと鍵を作れます。

### 環境変数と credentials の使い分け

どちらを使うかはチームで決めます。目安は次のとおりです。

- **credentials**：値の変更をコードと一緒に管理したい場合。誰がいつ変えたかが Git に残ります。
- **環境変数**：デプロイ先のサービス（第23章）の管理画面で設定する場合や、環境ごとに値が違う場合。

どちらの場合も、「鍵となる値（`master.key` や環境変数の中身）はリポジトリの外」という原則は同じです。

### 漏れたらローテーション

ここが最も大切です。秘密情報をコミットしたり、どこかに貼り付けたりしてしまったら、**漏えいしたものとして扱い、ローテーションします**。

**ローテーション**とは、古い値を無効にして新しい値に取り替えることです。家の合鍵を落としたら、鍵を探すより先に錠前を交換するのと同じです。

手順は次のとおりです。

1. 発行元（外部サービスの管理画面など）で、新しいキーを発行する。
2. アプリの設定（credentials や環境変数）を新しい値に更新し、デプロイする。
3. 古いキーを発行元で **無効化** する。
4. 古いキーで実際に失敗することを確かめる。
5. 漏れていた期間に、不審な利用がなかったか発行元の記録を確認する。
6. チームに報告する。隠すと、対応が遅れて被害が大きくなります。

「削除コミットを入れたから大丈夫」「非公開リポジトリだから大丈夫」は、どちらも間違いです。履歴は残り、複製は既に誰かの手元にあるかもしれません。履歴から消す道具（`git filter-repo` など）もありますが、それは後片付けです。ローテーションの代わりにはなりません。

なお、`secret_key_base` を取り替えると、それで署名したセッションの Cookie がすべて無効になります。つまり全員がログアウトされます。影響があるので、本番での実施はチームで相談して行います。

GitHub には、既知の形式のトークンを push 前に検出して止める **secret scanning（push protection）** という機能もあります。有効にしておくと安心ですが、すべての形式を見つけられるわけではありません。最後の砦は、あなたの `.gitignore` とコミット前の確認です。

## 依存関係の脆弱性を見つける

### なぜ依存関係が狙われるのか

あなたの `Gemfile` に書かれた gem は、さらに別の gem に依存しています。`Gemfile.lock` を開くと、その全体が書かれています。このうち一つにでも既知の脆弱性があれば、攻撃の入口になります。

既知の脆弱性には **CVE** という番号が付き、公開データベースに登録されます。攻撃者もこのデータベースを読みます。つまり「公開された脆弱性を放置する」ことは、「鍵が壊れていると貼り紙のある家に住み続ける」のに近い状態です。

### bundler-audit：Gemfile.lock を調べる

**bundler-audit** は、`Gemfile.lock` に書かれた gem のバージョンを、公開されている脆弱性データベース（ruby-advisory-db）と照らし合わせる道具です。

`Gemfile` の開発用グループに追加します。

```ruby
group :development, :test do
  gem "bundler-audit", require: false
end
```

```bash
bundle install
bundle exec bundle-audit check --update
```

`--update` は、照合に使うデータベースを最新にする指定です。問題がなければ次のように表示されます。

```text
No vulnerabilities found
```

問題があれば、gem の名前、バージョン、CVE 番号、直し方（どのバージョンに上げればよいか）が表示されます。Rails のバージョンによっては、新しいアプリに `bin/bundler-audit` が最初から用意されています。あればそれを使ってください。

### Dependabot：更新の提案を自動で受け取る

**Dependabot** は GitHub の機能です。依存関係に新しいバージョンや脆弱性の修正が出ると、更新のプルリクエストを自動で作ってくれます。

リポジトリに `.github/dependabot.yml` を置くと有効になります。

```yaml
version: 2
updates:
  - package-ecosystem: "bundler"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 10
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
```

Rails 7.2 以降の `rails new` では、このファイルが最初から作られます。2つ目の `github-actions` は、第22章で書く CI の設定で使う部品の更新を見張る設定です。

届いたプルリクエストを、何も考えずにマージしてはいけません。CI（第22章）が通ることを確認し、変更履歴（CHANGELOG）で大きな変更がないか見てから取り込みます。逆に、放置し続けるのも危険です。溜まるほど一度の更新が大きくなり、怖くて上げられなくなるからです。

### Brakeman：自分のコードを調べる

bundler-audit と Dependabot は「他人のコード（gem）」を調べます。**Brakeman** は「自分のコード」を調べる静的解析ツールです。**静的解析**とは、プログラムを動かさずに、ソースコードを読んで問題を探すことです。

Rails 7.2 以降の新しいアプリには、Brakeman が最初から入っていて `bin/brakeman` で実行できます。入っていなければ `Gemfile` の開発用グループに `gem "brakeman", require: false` を足します。

```bash
bin/brakeman --no-pager
```

文字列を埋め込んだ SQL、`html_safe` の危ない使い方、許可していないパラメータの一括代入などを見つけると、警告が出ます。警告には確からしさ（Confidence：High / Medium / Weak）が付きます。

Brakeman はコードを読むだけなので、誤検知もあります。誤検知と判断したら、理由を説明できる状態にしたうえで、`bin/brakeman -I` で無視リスト（`config/brakeman.ignore`）に登録します。登録時には必ず理由を書きます。「よく分からないから無視」は、一番やってはいけない使い方です。

## ログに個人情報を出さない

### ログは思ったより多くの人に読まれる

**ログ**は、アプリが動いた記録です。障害の調査に欠かせません。一方で、ログはたいてい多くの人が読めます。開発者全員、運用担当、ログ保存サービスの事業者、障害調査の協力先などです。保存期間も長いことが多いです。

だから、ログに個人情報やパスワードが含まれると、それ自体が漏えいになります。実際に、大きなサービスで「パスワードが平文でログに残っていた」という事故が何度も起きています。

### `filter_parameters` で隠す

Rails は、リクエストのパラメータをログに記録します。そのとき、指定した名前のパラメータを `[FILTERED]` に置き換えます。設定は `config/initializers/filter_parameter_logging.rb` にあります。

```ruby
Rails.application.config.filter_parameters += [
  :passw, :email, :secret, :token, :_key, :crypt, :salt, :certificate, :otp, :ssn
]
```

上は新しい Rails アプリの初期値の一例です。中身はバージョンによって少し違うので、自分のファイルを開いて確認してください。名前は部分一致で効きます。`:passw` は `password` にも `password_confirmation` にも効きます。

ログインフォームを送ると、ログは次のようになります。

```text
Parameters: {"authenticity_token"=>"[FILTERED]", "email"=>"[FILTERED]", "password"=>"[FILTERED]"}
```

この設定は、Active Record のオブジェクトを `inspect` したときの表示にも使われます（Rails 6 以降）。コンソールで `User.first` を表示しても、`password_digest` は `[FILTERED]` になります。

自分のアプリに独自の個人情報（電話番号、住所など）を追加したら、ここにも追加します。設定が効いているかは、テストで確かめられます。演習20-2で書きます。

### 自分で書くログに注意する

`filter_parameters` が守るのは、Rails が自動で書くログだけです。自分で書くログは守ってくれません。

```ruby
# 危ない：メールアドレスがそのままログに残る
Rails.logger.info("ログイン失敗: #{params[:email]}")

# 安全側：個人を特定する情報の代わりにIDなどを使う
Rails.logger.info("ログイン失敗: user_id=#{user&.id || 'unknown'}")
```

どうしても値の一部が必要なら、マスク（一部を伏せ字にすること）します。

```ruby
def mask_email(email)
  name, domain = email.split("@", 2)
  return "[不正な形式]" if domain.nil?
  "#{name[0]}***@#{domain}"
end

puts mask_email("user1@example.com")
puts mask_email("not-an-email")
```

```text
u***@example.com
[不正な形式]
```

ログに何を出すかを判断する目安は「このログ行が社外に流出したら、誰かが困るか」です。困るなら、出さないか、マスクします。

## エラー画面で内部情報を出さない

### 開発用のエラー画面は本番では危険

開発中、Rails はエラーが起きると詳しい画面を出します。エラーの種類、スタックトレース、リクエストのパラメータ、実行中のSQLなどです。開発には便利ですが、本番でこれを出すと、攻撃者に地図を渡すことになります。使っているライブラリ、ファイルの配置、DBのテーブル名などが分かってしまうからです。

Rails は環境ごとに設定を持っていて、本番では詳細を出しません。

```ruby
# config/environments/production.rb（抜粋）
config.consider_all_requests_local = false
```

`false` のとき、Rails はエラーの詳細を隠し、`public/404.html` や `public/500.html` のような静的なページを返します。これらのページには、内部情報を書かないようにします。

### 自分でエラーメッセージを返すときの注意

自分で例外を捕まえて画面に出すときも、同じ注意が必要です。

```ruby
# 危ない：例外のメッセージには内部情報が含まれることがある
rescue => e
  render plain: "エラー: #{e.message}", status: :internal_server_error
```

例外のメッセージには、SQL 文やファイルのパスが含まれることがあります。利用者には「問題が発生しました」のような一般的な文言と、問い合わせ用の番号（リクエストIDなど）だけを返します。詳しい内容はログに残し、開発者がそちらを見て調べます。

この「利用者向けの文言」と「開発者向けの記録」を分ける考え方は、第21章の JSON API のエラー応答や、第23章の障害対応でも使います。

## リソース上限とタイムアウト

### なぜ上限が必要なのか

副教材の表で「資源の上限」と「タイムアウト」が最初の2行にあったのを思い出してください。サーバの CPU、メモリ、DB 接続、スレッドは、どれも有限です。上限を決めないと、一人の利用者（または攻撃者）がそれを使い切り、他の全員が使えなくなります。これを **DoS**（Denial of Service、サービス妨害）と呼びます。

悪意がなくても起きます。たとえば「全件表示」のURLに10万件のデータがあれば、それだけでサーバは苦しくなります。

### 上限を決める場所

Rails アプリで、上限を考えるべき場所を挙げます。

- **一覧の件数**：一度に返す件数の最大値を決める。`?per=100000` のような指定は、上限で切り詰める。
- **アップロードの大きさ**：ファイルサイズの上限を決め、モデルのバリデーションで確かめる。前段のプロキシ（第23章）やデプロイ先でも上限を設定する。
- **入力の長さ**：タイトルや本文に `length: { maximum: ... }` のバリデーションを付ける。DBの列にも制限を付けると、二重の守りになります。
- **試行回数**：ログインやパスワード再設定に、一定時間あたりの回数制限を付ける。これを **レート制限** と呼びます。

レート制限は、Rails 7.2 以降ならコントローラに1行で書けます。

```ruby
class SessionsController < ApplicationController
  rate_limit to: 10, within: 3.minutes, only: :create
end
```

これで、同じ接続元から3分間に11回目のログイン試行が来ると、Rails は 429 Too Many Requests を返します。回数の記録には Rails のキャッシュを使います。Rails 7.2 より前のバージョンでは、`rack-attack` という gem がよく使われます。

### タイムアウトを決める場所

**タイムアウト**は「これ以上は待たない」という時間の上限です。待ち続けると、その間スレッドやDB接続を握ったままになります。少しずつ溜まると、最後は全部が埋まって止まります。

- **外部APIの呼び出し**：接続と応答待ちのそれぞれに上限を付ける。第21章で詳しく扱います。
- **DBのクエリ**：PostgreSQL なら `statement_timeout` で、遅すぎるクエリを打ち切れる。
- **リクエスト全体**：Puma の前に置くプロキシや、デプロイ先のサービスで上限を設定する（第23章）。

どの値が正しいかは、アプリによって違います。大切なのは「上限がない」状態をなくすことと、その値を決めた理由を説明できることです。

## 実務ではこうなる

現場では、セキュリティ専任の人がいても、日々のコードを書くのは開発者です。ジュニアに最初に期待されるのは、高度な攻撃手法の知識ではありません。「基本を外さない」ことです。

- **プルリクエストのレビューで指摘される定番**：`Post.find(params[:id])` で他人のデータが取れる、`permit` に `user_id` や `admin` を入れている、`html_safe` の理由が説明できない、ログに `params` を丸ごと出している、など。
- **CI で自動チェック**：Brakeman、bundler-audit、RuboCop（第22章）を CI で毎回動かし、警告が出たらマージできないようにするチームが多いです。
- **依存関係の更新は「当番制」**：Dependabot のプルリクエストを週に一度まとめて見る、という運用がよくあります。
- **脆弱性の報告窓口**：外部から脆弱性の報告を受けたら、ジュニアが一人で判断せず、すぐに上長やセキュリティ担当に共有します。

ジュニアがやりがちな失敗も挙げておきます。

- 動作確認のために、本物のAPIキーをコードに直書きし、そのままコミットしてしまう。
- `.env` を作ってから `.gitignore` に追加しようとして、先に `git add .` してしまう。
- 秘密情報を含むエラーログを、そのまま Slack や AI に貼り付けて質問する。
- エラーを消したい一心で、`rescue => e` で例外を握りつぶし、何も記録しない。
- Brakeman の警告を「誤検知っぽい」という理由だけで無視リストに入れる。

どれも、悪意ではなく「急いでいた」「知らなかった」から起きます。この章のチェックを、手が覚えるまで繰り返してください。

## 演習

演習は、第19章で認証と認可を付けた Rails アプリを使います。作業用にコピーしてから始めます。

```bash
cp -R ~/workspace/ch19-auth ~/workspace/ch20-security
cd ~/workspace/ch20-security
```

第19章のフォルダ名が違う場合は、自分のフォルダ名に読み替えてください。以下では、ログインユーザーが自分の投稿を管理するリソースを `Post` として説明します。自分のアプリのリソース名に読み替えてください。

開発サーバを起動するときは、これまでどおり `bin/rails server -b 127.0.0.1` で起動します。起動後に `lsof -nP -iTCP:3000 -sTCP:LISTEN` を実行し、`127.0.0.1:3000` で待ち受けていることを確かめます。データはすべてダミー（`user1@example.com` など）を使います。

### 演習20-1：攻撃が失敗することをテストで示す

自分のアプリに対して、代表的な攻撃が失敗することを結合テスト（`test/integration/` 配下のテスト）で示します。進め方は TDD です。まずテストを書いて実行し、対策済みならそのまま GREEN、穴があれば RED になります。RED になったら対策を実装して GREEN にします。

- やること
  1. `test/integration/security_test.rb` を作る。
  2. 次の4つのテストを書く。
     - **IDOR**：ユーザーAでログインし、ユーザーBの投稿の詳細・編集・更新・削除にアクセスする。どれも 404 が返り、Bの投稿がDB上で変わっていない。
     - **一括代入**：投稿の更新リクエストに `user_id`（他人のID）を混ぜて送る。投稿の持ち主が変わっていない。
     - **XSS**：本文に `<script>alert(1)</script>` を含む投稿を作り、表示ページを取得する。レスポンスに生の `<script>alert(1)` が含まれず、エスケープされた `&lt;script&gt;` が含まれる。
     - **SQLインジェクション**：検索機能があれば、`' OR '1'='1` で検索し、全件が返らない。検索機能がなければ、このテストの代わりに Brakeman の結果（演習20-3）で SQL の警告がないことを確かめる。
  3. `bin/rails test test/integration/security_test.rb` で実行する。RED のテストがあれば、コントローラを直して GREEN にする。
  4. OWASP Top 10（2021年版）の10項目それぞれについて、自分のアプリで「該当する箇所」「対策済みか」「根拠となるテストや設定」を表にまとめ、`docs/security-checklist.md` に書く。
- **完了条件**
  - `bin/rails test test/integration/security_test.rb` がすべて成功する。
  - 対策のコードを一時的に元に戻すと（たとえば `current_user.posts.find` を `Post.find` に戻すと）、IDOR のテストが失敗することを確認した。確認後は元に戻す。
  - `docs/security-checklist.md` に10項目すべての行がある。「未対応」や「該当なし」の行には理由が書かれている。
- ヒント
  - 一括代入のテストでは、リクエストを送った後に `post.reload` してから持ち主を確かめます。`reload` しないと、テストの中の古いオブジェクトを見てしまいます。
  - 「攻撃が失敗するテスト」は、対策を外したら失敗しなければ意味がありません。完了条件の2つ目は、そのための確認です。

### 演習20-2：秘密情報とログを守る

外部APIのキー（ダミー）を credentials で管理し、ログにパスワードやメールアドレスが残らないことをテストで確かめます。

- やること
  1. `git check-ignore -v config/master.key` を実行し、`master.key` が無視されていることを確かめる。
  2. `bin/rails credentials:edit` で `weather_api: key:` にダミーの値（`dummy-` で始まる文字列）を入れる。アプリ内のどこか（たとえば設定を読む小さなクラス）から `Rails.application.credentials.dig(:weather_api, :key)` で読めるようにする。
  3. `.gitignore` に `.env` を追加し、`.env.example` を作ってコミットする。
  4. 次のテストを書く（TDD で、先にテストを書いて RED を確認する）。
     - `ActiveSupport::ParameterFilter.new(Rails.application.config.filter_parameters)` を使い、`password`・`password_confirmation`・`email` が `[FILTERED]` に置き換わること。
     - 自分のアプリ独自の個人情報（たとえば `phone`）も置き換わること。最初は RED になるはずなので、設定に追加して GREEN にする。
  5. 開発サーバでログインし、`log/development.log` を `grep` して、入力したパスワードの文字列が含まれないことを確かめる。
- **完了条件**
  - 追加したテストがすべて成功する。
  - `git ls-files -- config/master.key .env` を実行して何も表示されない。
  - `grep -c "<ログインに使ったダミーパスワード>" log/development.log` の結果が `0` になる。
- ヒント
  - `ParameterFilter#filter` はハッシュを受け取り、置き換え済みのハッシュを返します。
  - 自分で `Rails.logger` に書いている箇所があれば、`grep -rn "logger" app/` で探して、個人情報を出していないか見直します。

### 演習20-3：依存関係とコードを自動で検査する

- やること
  1. bundler-audit を導入し、`bundle exec bundle-audit check --update` を実行する。
  2. Brakeman を実行する（`bin/brakeman --no-pager`、なければ導入する）。
  3. 警告が出たら、1件ずつ「何が問題か」「直したか、誤検知として理由付きで無視したか」を `docs/security-checklist.md` に追記する。
  4. `.github/dependabot.yml` を作る（なければ）。`bundler` と `github-actions` の2つを週1回チェックする設定にする。
- **完了条件**
  - `bundle exec bundle-audit check --update` の出力が `No vulnerabilities found` になる。脆弱性が残る場合は、更新できない理由と回避策が記録されている。
  - `bin/brakeman --no-pager` の結果で、未対応の警告が0件になる（無視リストに入れたものは理由が記録されている）。
  - `.github/dependabot.yml` が `ruby -ryaml -e 'p YAML.load_file(".github/dependabot.yml")'` でエラーなく読める。
- ヒント
  - 古い gem を上げると、テストが壊れることがあります。そのときは一度に全部を上げず、`bundle update <gem名>` で一つずつ上げ、そのたびにテストを実行します。
  - わざと危ないコード（文字列埋め込みの `where` など）を一時的に書いて Brakeman を実行すると、警告がどう見えるかが分かります。確認したら必ず元に戻します。

### 演習20-4（発展）：上限を決めて、テストで確かめる

- やること
  1. 投稿一覧にページ分割を入れ、1ページの最大件数を決める（例：50件）。`?per=100000` を指定しても最大件数を超えないことをテストで示す。
  2. ログインの `create` アクションにレート制限を付ける（Rails 7.2 以降なら `rate_limit`）。上限を超えた試行に 429 が返るテストを書く。
  3. 投稿のタイトルと本文に、長さの上限のバリデーションを付ける。上限を1文字超えた入力が保存されないテストを書く。
  4. `config/environments/production.rb` を読み、`consider_all_requests_local`・`force_ssl`・ログ関係の設定がそれぞれ何をしているかを `docs/security-checklist.md` に説明する。
  5. 副教材の「最小実装に残る防御の不足」の表を、このアプリ用に埋め直す。「状態」と「根拠」を必ず書く。
- **完了条件**
  - 1〜3のテストがすべて成功する。
  - 防御の不足の表に5行すべてがあり、「実装済み」とした行には根拠（テスト名や設定ファイルの行）が書かれている。
- ヒント
  - `rate_limit` は回数の記録にキャッシュを使います。テスト環境のキャッシュは初期設定で何も保存しない（`:null_store`）ため、そのままでは制限がかかりません。`rate_limit` の `store:` オプションにテスト用のメモリ上のキャッシュを渡す方法などを、Rails ガイドや API ドキュメントで調べてください。
  - 確かめていないものを「実装済み」にしないでください。分からなければ「未確認」と書くのが正しい答えです。

## 確認クイズ

**Q1.** `/posts/5/edit` を開いたとき、ログインしていない人はログイン画面に飛ばされる。これでアクセス制御は十分か。

**Q2.** APIキーを誤ってコミットし、GitHub に push してしまった。すぐに削除するコミットを push した。他にやるべきことは何か。

**Q3.** `config/credentials.yml.enc` と `config/master.key` のうち、Git にコミットしてよいのはどちらか。理由も答えよ。

**Q4.** bundler-audit と Brakeman は、それぞれ何を調べる道具か。

**Q5.** 本番環境で、エラーの原因を利用者に伝えるために `e.message` をそのまま画面に出したい。問題はあるか。

**Q6.** Rails の `filter_parameters` を設定した。これで、ログに個人情報が出る心配はなくなったか。

### 解答と解説

1. **十分ではない。** それは「ログインしているか」の確認（認証）だけです。ログインしたユーザーAが、ユーザーBの投稿の編集画面を開けないかも確かめる必要があります（認可、A01）。`current_user.posts.find` のように、自分のデータの中から探す書き方にし、他人の ID で 404 になるテストを書きます。
2. **ローテーションです。** 発行元で新しいキーを発行し、アプリの設定を更新し、古いキーを無効化します。削除コミットを入れても履歴に残り、既に複製されているかもしれません。漏れていた期間の利用記録を確認し、チームに報告します。
3. **`credentials.yml.enc` です。** これは暗号化されているので、鍵がなければ読めません。`master.key` はそれを開く鍵なので、コミットすると暗号化の意味がなくなります。
4. **bundler-audit は「使っている gem」の既知の脆弱性を、Brakeman は「自分が書いたコード」の危ない書き方を調べます。** 前者は `Gemfile.lock` と脆弱性データベースを照合し、後者はソースコードを静的解析します。調べる対象が違うので、両方使います。
5. **問題があります。** 例外のメッセージには SQL 文やファイルパスなどの内部情報が含まれることがあり、攻撃の手がかりになります（A05）。利用者には一般的な文言と問い合わせ用のIDだけを返し、詳細はログに残します。
6. **なくなっていません。** `filter_parameters` が守るのは、Rails が自動で記録するパラメータと、Active Record の `inspect` の表示です。自分で `Rails.logger.info` に書いた文字列は守られません。自分で書くログは、出す内容を自分で判断し、必要ならマスクします。

## AIの使い方（この章）

推奨する聞き方の例：

- 「Rails で `Post.find(params[:id])` と `current_user.posts.find(params[:id])` の違いを、発行される SQL の違いから説明してください。自分の理解は〇〇です。合っていますか」
- 「Brakeman で次の警告が出ました（警告文を貼る。ファイルパスやアプリ固有の名前は伏せる）。この警告が想定している攻撃のシナリオを、初心者向けに説明してください。直し方は自分で考えたいので、まだ教えないでください」
- 「OWASP Top 10 の A01 と A07 の違いを、ログイン機能を例に説明してください」

やってはいけない使い方：

- 秘密情報やログをそのまま AI に貼り付ける。`master.key` の中身、`.env` の値、本物のメールアドレスが入ったログは、AI のサービスに送った時点で「自分の管理外に出た」ことになります。貼る前に必ずダミーに置き換えるか、伏せ字にします。もし貼ってしまったら、ローテーションの対象です。
- 「このアプリのセキュリティ対策を全部書いて」と依頼し、生成されたコードを理解せずに取り込む。対策は、なぜ効くのかを説明できて初めて保守できます。テストも自分で書きます。

## まとめ

- Rails は多くの防御を持っていますが、認可・秘密情報・依存関係・ログの判断はアプリを作る人の仕事です。
- OWASP Top 10 は「どこに気をつけるか」の地図です。この章では2021年版の項目で、自分のアプリの具体的な場所と結びつけました。
- 秘密情報はリポジトリの外（環境変数・`master.key`）に置き、漏れたら消すのではなくローテーションします。
- bundler-audit・Dependabot・Brakeman で、既知の問題の発見を自動化します。
- ログとエラー画面は「漏れたら困る情報を出さない」、リソースには「上限とタイムアウトを必ず付ける」。どちらもテストや設定の根拠で確かめます。

## 用語

| 用語 | 意味 |
|---|---|
| OWASP Top 10 | Webアプリの代表的なセキュリティ上の問題をまとめたランキング。数年ごとに改訂される |
| IDOR | URL などのIDを書き換えるだけで、他人のデータに触れてしまう問題。アクセス制御の不備の典型 |
| 脅威モデリング | 作る前に「誰が、何を、どうやって悪用できるか」を考える作業 |
| SSRF | 利用者が指定したURLにサーバがアクセスする機能を悪用し、内部ネットワークへリクエストを送らせる攻撃 |
| 秘密情報 | APIキー、パスワード、署名用の鍵など、知られるとなりすましができる情報 |
| 環境変数 | プログラムの外から、起動時に名前と値の組を渡す仕組み |
| credentials | Rails の、秘密情報を暗号化してリポジトリに置く仕組み。鍵は `master.key` |
| ローテーション | 漏れた（または古くなった）秘密情報を無効にし、新しい値に取り替えること |
| CVE | 公開された脆弱性に付けられる識別番号 |
| bundler-audit | `Gemfile.lock` の gem を脆弱性データベースと照合する道具 |
| Dependabot | 依存関係の更新プルリクエストを自動で作る GitHub の機能 |
| Brakeman | Rails アプリのソースコードを読んで、危ない書き方を探す静的解析ツール |
| 静的解析 | プログラムを実行せずに、ソースコードを読んで問題を探すこと |
| レート制限 | 一定時間あたりの操作回数に上限を設けること |
| タイムアウト | 処理を待つ時間の上限。超えたら打ち切る |
