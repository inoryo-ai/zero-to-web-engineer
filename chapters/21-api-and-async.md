## API とは何か

ここまで作ってきたアプリは、ブラウザに HTML を返していました。人間が画面を見て操作する前提です。

**API**（Application Programming Interface）は、プログラムがプログラムを呼び出すための窓口です。Web の世界で「API」と言うと、たいてい「HTTP でリクエストを送ると、JSON などのデータが返ってくる窓口」を指します。

たとえるなら、HTML を返すアプリはレストランの「客席」、API は「業者用の搬入口」です。客席では盛り付けた料理（見た目つきの画面）を出しますが、搬入口では食材（データ）をそのままやり取りします。

API が使われる場面は、たとえば次のとおりです。

- スマートフォンのアプリが、サーバからデータを取ってくる
- ブラウザ上の JavaScript が、画面を再読み込みせずにデータを更新する
- 自分のサーバが、天気・決済・地図などの外部サービスを呼ぶ
- 外部サービスが、何かが起きたことを自分のサーバに知らせてくる（Webhook）

この章では、作る側（自分の API）と使う側（外部の API）の両方を扱います。

## REST の考え方で URL を設計する

### リソースとメソッド

**REST** は、Web API を設計するときの代表的な考え方です。中心にあるのは次の2つです。

- URL は「もの（リソース）」を表す名詞にする。例：`/posts`、`/posts/12`
- そのものに「何をするか」は HTTP メソッドで表す。例：`GET`（取得）、`POST`（作成）

第8章で学んだ HTTP メソッドが、そのまま「動詞」の役割を持ちます。URL に動詞を入れない、というのが基本の形です。

```text
良い例                      避けたい例
GET    /posts               GET  /getAllPosts
GET    /posts/12            GET  /showPost?id=12
POST   /posts               POST /createPost
PATCH  /posts/12            POST /posts/12/update
DELETE /posts/12            GET  /deletePost?id=12
```

右下の `GET /deletePost` は特に危険です。`GET` は「取得するだけ」と約束されたメソッドなので、ブラウザや検索エンジンのクローラ、プリフェッチ（先読み）機能が気軽にアクセスします。それで削除が起きてしまうのです。

第18章で使った Rails の `resources :posts` は、この REST の形をそのまま作ってくれる仕組みでした。`bin/rails routes` を実行すると、メソッドと URL とアクションの対応を確認できます。

### 関連するリソースとバージョン

「投稿12についたコメント」のように、リソースが親子関係を持つこともあります。その場合は `/posts/12/comments` のように入れ子にします。ただし、入れ子は1段までにとどめるのが一般的です。`/users/3/posts/12/comments/5` のような長い URL は、扱いにくくなるからです。

API は、一度公開すると使う側のプログラムが依存します。勝手に形を変えると、相手のプログラムが壊れます。そのため、URL に `/api/v1/` のようなバージョンを入れておき、大きく変えるときは `/api/v2/` を新しく作る、という方法がよく使われます。

```ruby
# config/routes.rb（抜粋）
namespace :api do
  namespace :v1 do
    resources :posts, only: [:index, :show, :create]
  end
end
```

`namespace` を使うと、URL が `/api/v1/posts` になり、コントローラは `app/controllers/api/v1/posts_controller.rb` に置く決まりになります。

## JSON を返す

### JSON の形

**JSON**（JavaScript Object Notation）は、データを文字で表すための書式です。もとは JavaScript の書き方から生まれましたが、今ではほとんどの言語で読み書きできます。

Ruby では標準ライブラリの `json` で扱えます。

```ruby
require "json"

post = { id: 1, title: "はじめての投稿", published: true, tags: ["ruby", "rails"], deleted_at: nil }
text = JSON.generate(post)
puts text

data = JSON.parse(text)
puts data["title"]
puts data[:title].inspect
puts JSON.pretty_generate(data)
```

```text
{"id":1,"title":"はじめての投稿","published":true,"tags":["ruby","rails"],"deleted_at":null}
はじめての投稿
nil
{
  "id": 1,
  "title": "はじめての投稿",
  "published": true,
  "tags": [
    "ruby",
    "rails"
  ],
  "deleted_at": null
}
```

3行目の `nil` に注目してください。`JSON.parse` は、キーを文字列として読み込みます。Ruby のシンボル `:title` では取り出せません。初心者が何度もつまずく所です。また、Ruby の `nil` は JSON では `null` になります。

### Rails で JSON を返す

Rails のコントローラでは、`render json:` で JSON を返せます。

```ruby
render json: { id: post.id, title: post.title }, status: :ok
```

ここで、セキュリティ上の大事な注意があります。モデルをそのまま `render json: user` のように渡すと、**全部の列が JSON に入ります**。`password_digest` や、内部で使っているフラグ、メールアドレスまで外に出てしまいます。第20章で設定した `filter_parameters` は、ここでは効きません。

だから、API で返す項目は「出してよいもの」を明示的に選びます。方法はいくつかあります。

- `as_json(only: [:id, :title, :body])` のように、出す列を指定する
- Jbuilder（Rails 標準のテンプレート）で、返す形を書く
- 返す形を作る専用のクラスを用意する

どれを使っても、考え方は第20章の許可リストと同じです。「出してはいけないものを除く」ではなく「出してよいものだけを選ぶ」ようにします。新しい列を追加したときに、うっかり外へ出ることがなくなるからです。

### ステータスコードを使い分ける

API では、ステータスコードが「結果の要約」になります。使う側のプログラムは、まずステータスコードを見て成功か失敗かを判断するからです。エラーなのに `200 OK` を返し、本文に `{"error": ...}` と書く API は、使う側を混乱させます。

よく使うものを、使う場面と一緒に挙げます。

| コード | 名前 | 使う場面 |
|---|---|---|
| 200 | OK | 取得や更新が成功した |
| 201 | Created | 作成が成功した。作ったものを本文で返すことが多い |
| 204 | No Content | 成功したが、返す本文がない（削除の成功など） |
| 400 | Bad Request | リクエストの形が壊れている（JSON として読めない、必須の項目がない） |
| 401 | Unauthorized | 認証されていない（トークンがない、間違っている） |
| 403 | Forbidden | 認証はされたが、その操作の権限がない |
| 404 | Not Found | そのリソースがない（または、あることを知らせたくない） |
| 409 | Conflict | 今の状態と衝突する（同じものを二重に作ろうとした、など） |
| 422 | Unprocessable Content | 形は正しいが、内容がバリデーションを通らない |
| 429 | Too Many Requests | 回数制限を超えた（第20章のレート制限） |
| 500 | Internal Server Error | サーバ側のバグなど、想定外のエラー |
| 503 | Service Unavailable | 一時的に処理できない（メンテナンス中、混雑中） |

迷いやすい組み合わせを2つ説明します。

**401 と 403**：401 は「あなたが誰か分からない」、403 は「あなたが誰かは分かったが、それは許されていない」です。ただし、第20章で見たように、他人のリソースについては 403 ではなく 404 を返すことがよくあります。403 を返すと「そのIDのものは存在する」と教えてしまうからです。

**400 と 422**：400 は「手紙が読めない」、422 は「手紙は読めたが、書かれた内容を受け付けられない」です。タイトルが空、のような入力ミスは 422 にします。

Rails では、ステータスコードをシンボルでも書けます。`:created` は 201、`:not_found` は 404 です。422 は Rails やその下で動く Rack のバージョンによってシンボル名が違います。古い名前は `:unprocessable_entity`、新しい名前は `:unprocessable_content` です。迷ったら、数字の `422` で書いても問題ありません。

### エラーの本文も形をそろえる

エラーのときも、本文の形をそろえておくと、使う側が扱いやすくなります。

```json
{
  "error": {
    "code": "validation_failed",
    "message": "入力内容に誤りがあります",
    "details": { "title": ["を入力してください"] }
  }
}
```

第20章で学んだとおり、500 のときに例外のメッセージをそのまま入れてはいけません。「問題が発生しました」という文言と、ログと照合するための ID だけを返します。

### API の認証

ブラウザ向けの画面では、第19章のセッション Cookie でログイン状態を保ちました。スマートフォンのアプリや他のサーバから呼ばれる API では、**トークン**を使う方法が一般的です。トークンは「この API を使ってよい」という合言葉の文字列で、リクエストのヘッダに入れて送ります。

```text
Authorization: Bearer <トークン>
```

Rails では `authenticate_with_http_token` というメソッドで、このヘッダからトークンを取り出せます。トークンは秘密情報なので、第20章のルールがそのまま当てはまります。ログに出さない、コードに書かない、漏れたら作り直す、です。

なお、Cookie で認証するAPIは、ブラウザから勝手に Cookie が送られるので CSRF 対策が必要です。トークンをヘッダで送る方式なら、ブラウザが自動で付けることはありません。どちらの方式を選んだかで、必要な対策が変わる点を覚えておいてください。

## 外部 API を呼ぶ

### 外部は「いつか必ず失敗する」

自分のサーバから外部のサービスを呼ぶとき、最初に持つべき前提は「相手はいつか必ず遅くなるし、失敗する」です。ネットワークの瞬断、相手のメンテナンス、相手側の障害、回数制限。どれも、自分ではどうにもできません。

だから、外部 API を呼ぶコードでは次の3つを必ず決めます。

1. **どれだけ待つか**（タイムアウト）
2. **失敗したら、もう一度試すか**（リトライ）
3. **最終的に失敗したら、どうするか**（失敗時の扱い）

### タイムアウトを付ける

Ruby の標準ライブラリ `Net::HTTP` を例に、タイムアウトの効果を見てみます。次のプログラムは、わざと5秒間黙る「遅い外部 API」の代わりのサーバを `127.0.0.1` で立て、それを呼びます。

```ruby
require "socket"
require "net/http"

# 応答が遅い「外部API」の代わり。必ず 127.0.0.1 で待ち受ける
server = TCPServer.new("127.0.0.1", 0)
port = server.addr[1]
Thread.new do
  loop do
    client = server.accept
    sleep 5 # わざと5秒黙る
    client.close
  end
end

http = Net::HTTP.new("127.0.0.1", port)
http.open_timeout = 2 # 接続確立までの上限（秒）
http.read_timeout = 1 # 応答を待つ上限（秒）
http.max_retries = 0 # Net::HTTP の自動再試行を止める（Ruby 2.5 以降）

started = Time.now
begin
  http.get("/weather")
rescue Net::ReadTimeout => e
  puts "タイムアウト: #{e.class}（#{(Time.now - started).round(1)}秒で諦めた）"
end
```

```text
$ ruby slow_server_timeout.rb
タイムアウト: Net::ReadTimeout（1.0秒で諦めた）
```

`TCPServer.new("127.0.0.1", 0)` のポート番号 `0` は、「空いているポートを OS に選ばせる」という意味です。第11章で学んだとおり、待ち受けは必ず `127.0.0.1` にしています。

タイムアウトには、性質の違う2種類があります。

- **open_timeout**：相手とつながるまでの上限。相手のサーバが落ちているときに効きます。
- **read_timeout**：つながった後、応答を待つ上限。相手が重くて返事が遅いときに効きます。

`Net::HTTP` の初期値は、どちらも60秒です。60秒待つ間、あなたのサーバのスレッドは何もできません。利用者もそれだけ待たされます。外部 API を呼ぶときは、必ず自分で短めの値を設定してください。

ここで一つ、面白い発見があります。上のコードから `http.max_retries = 0` の行を消して実行すると、表示は「2.0秒で諦めた」になります。`Net::HTTP` は、`GET` のような冪等なリクエストがタイムアウトすると、**黙って1回だけやり直す**のです（Ruby 2.5 以降）。ライブラリが見えないところでリトライしていることがある。これは、次のリトライの節の大事な伏線です。

実務では、`Net::HTTP` を直接使わず、Faraday などの HTTP クライアントの gem を使うことも多いです。どの道具でも、タイムアウトの設定項目を探して値を決める、という作業は同じです。

### リトライする・しないを決める

失敗したとき、もう一度試せば成功することがあります。一時的なネットワークの問題などです。しかし、何でもリトライすればよいわけではありません。

**リトライしてよい失敗**の例：

- タイムアウト、接続できない
- 502、503、504（相手側が一時的に不調）
- 429（回数制限）。相手が `Retry-After` ヘッダで待つ時間を教えてくれたら、それに従う

**リトライしても無駄な失敗**の例：

- 400、401、403、404、422。リクエスト自体が間違っているので、何度送っても同じ結果になる

リトライするときは、すぐに連打せず、待ち時間を少しずつ伸ばします。これを **指数バックオフ** と呼びます。さらに、待ち時間に小さな乱数（**ジッター**）を足します。多くのサーバが同時にリトライすると、復旧しかけた相手に一斉に押し寄せてまた倒してしまうからです。

```ruby
class TemporaryError < StandardError; end

# 待ち時間を 0.1, 0.2, 0.4 ... と倍々にし、ゆらぎ（ジッター）を足す
def with_retry(max_attempts: 3, base: 0.1)
  attempt = 0
  begin
    attempt += 1
    yield attempt
  rescue TemporaryError => e
    raise if attempt >= max_attempts
    wait = base * (2**(attempt - 1)) + rand * 0.05
    puts "  #{attempt}回目失敗（#{e.message}）。#{wait.round(2)}秒待って再試行"
    sleep wait
    retry
  end
end

results = [:fail, :fail, :ok]
answer = with_retry do |attempt|
  raise TemporaryError, "503が返った" if results[attempt - 1] == :fail
  "#{attempt}回目で成功"
end
puts answer

begin
  with_retry { raise TemporaryError, "ずっと503" }
rescue TemporaryError => e
  puts "諦めた: #{e.message}"
end
```

```text
$ ruby retry_demo.rb
  1回目失敗（503が返った）。0.11秒待って再試行
  2回目失敗（503が返った）。0.24秒待って再試行
3回目で成功
  1回目失敗（ずっと503）。0.12秒待って再試行
  2回目失敗（ずっと503）。0.21秒待って再試行
諦めた: ずっと503
```

待ち時間の数字は乱数を含むので、実行するたびに少し変わります。`retry` は、`begin` の先頭からやり直す Ruby の構文です。回数の上限を必ず付けている点に注目してください。上限のないリトライは、無限ループと同じです。

そして、リトライには大きな落とし穴があります。**「失敗した」と思った処理が、実は相手側では成功していた**場合です。たとえば決済 API に「1,000円請求して」と送り、応答待ちでタイムアウトしたとします。相手は請求を済ませたけれど、返事が届かなかっただけかもしれません。ここでリトライすると、二重請求になります。これを防ぐ考え方が、章の後半で扱う「冪等性」です。

### 最終的に失敗したときの扱い

リトライしても失敗したら、どうするかを決めておきます。選択肢はいくつかあります。

- **利用者に正直に伝える**：「天気情報を取得できませんでした。時間をおいて再度お試しください」。画面全体をエラーにせず、その部分だけを諦める。
- **前回の結果を使う**：少し古くても困らない情報なら、保存しておいた前回の値を表示する。
- **後でやり直す**：後で説明する非同期処理に回し、時間をおいて再実行する。
- **記録して知らせる**：ログに残し、失敗が続くならアラートを出す（第23章）。

どれを選ぶかは、機能によって違います。天気予報なら「表示しない」で済みますが、決済なら「成功したかどうか分からない」状態を必ず確認しに行く必要があります。

また、外部 API を呼ぶ処理は、専用のクラスにまとめておくのがおすすめです。タイムアウトやリトライの設定が1か所に集まり、テストのときに偽物と差し替えやすくなるからです。テストでの差し替え方は、第22章の「モックとスタブ」で詳しく扱います。

## Webhook を受け取る

### 呼ぶのではなく、呼ばれる

**Webhook** は、外部サービスの側から、あなたのサーバに HTTP リクエストを送ってくる仕組みです。「決済が完了した」「リポジトリに push された」のような出来事を知らせてくれます。

たとえるなら、外部 API を呼ぶのは「こちらから電話して聞く」、Webhook は「何かあったら向こうから電話をもらう」です。何度も「終わりましたか」と聞きに行かずに済みます。

便利な反面、Webhook には固有の難しさがあります。

1. **誰でも送れる**：あなたの Webhook の URL を知っていれば、誰でも偽の通知を送れます。
2. **同じ通知が複数回届く**：送り側は、あなたから成功の応答が返らなければ再送します。応答が遅れただけでも再送されます。
3. **順番が入れ替わる**：「更新」が「作成」より先に届くことがあります。
4. **すぐ返事をしないと失敗扱いになる**：多くのサービスは、数秒以内に 2xx の応答を求めます。

### 署名で本物か確かめる

1つ目の問題には、**署名**で対処します。送り側とあなたは、事前に共有の秘密の文字列（Webhook シークレット）を持っておきます。送り側は、本文とシークレットから **HMAC** という方式で署名を計算し、ヘッダに付けて送ります。あなたも同じ計算をして、署名が一致すれば本物と判断します。

```ruby
require "openssl"

secret  = "dummy-webhook-secret" # 本物は credentials に置く
payload = '{"id":"evt_001","type":"payment.succeeded"}'

signature = OpenSSL::HMAC.hexdigest("SHA256", secret, payload)
puts signature

# 1文字でも本文が変わると、署名はまったく別物になる
tampered = payload.sub("succeeded", "refunded")
puts OpenSSL::HMAC.hexdigest("SHA256", secret, tampered)
```

```text
$ ruby hmac_demo.rb
4f98a2e8c2ba94ebb5b5a3f9c4c1b6643201c933efaf1d024134c6ba38aa2166
f705afe0f75ce765c16d2048fc70c1128286df3416aaf2e659d6d2c38a7712af
```

シークレットを知らない攻撃者は、正しい署名を作れません。本文を書き換えても、署名が合わなくなります。第20章の A08「整合性の不備」への対策そのものです。

Rails で実装するときの注意点を挙げます。

- 署名の計算には、パース前の生の本文（`request.raw_post`）を使う。JSON をパースしてから作り直すと、空白やキーの順番が変わり、署名が合わなくなります。
- 署名の比較には `==` ではなく `ActiveSupport::SecurityUtils.secure_compare` を使う。`==` は先頭から比べて違う所ですぐ終わるので、かかる時間の差から正しい署名を推測される恐れがあります。
- 署名が合わなければ、何も処理せず 401 などを返す。
- Webhook のコントローラでは、CSRF 対策のトークン確認を外す必要があります（`skip_forgery_protection`）。外部サービスは CSRF トークンを持っていないからです。その代わりに、署名検証が守りの役目を果たします。署名検証なしで CSRF だけ外すのは、玄関の鍵を外したまま出かけるのと同じです。

多くのサービスは、署名の対象に送信時刻も含めています。古い時刻の通知を拒否すれば、盗み見た通知をそのまま再送する攻撃（リプレイ攻撃）も防げます。署名の方式やヘッダ名はサービスごとに違うので、必ず相手のドキュメントに従います。

### 開発中の Webhook は「自分で送って」試す

外部サービスから自分の PC に Webhook を届けるには、PC をインターネットから見える状態にする必要があります。そのための公開トンネルのツールもありますが、**この教材では使いません**。第10章のルールどおり、演習のサーバはループバック限定です。

代わりに、署名付きのリクエストを自分で作り、`curl` で `127.0.0.1` に送って試します。テストでも同じリクエストを作れるので、困ることはありません。

### すぐに返事をして、処理は後で

4つ目の問題（すぐ返事が必要）と、2つ目の問題（重複）には、次の形で対処します。

1. 署名を確かめる
2. 通知の ID（イベント ID）を DB に保存する。既に保存済みなら「処理済み」として 200 を返して終わる
3. 実際の処理は非同期のジョブに任せ、すぐに 200 を返す

2と3を実現するのが、次の節の「非同期処理」と、その次の「冪等性」です。

## 非同期処理

### なぜ非同期にするのか

利用者がボタンを押してから画面が返るまでの処理を、**同期処理**と呼びます。メールの送信、画像の変換、外部 API の呼び出しなど、時間のかかる処理を同期処理の中でやると、利用者はその間ずっと待たされます。外部が遅ければ、第20章で見たようにサーバのスレッドも埋まっていきます。

**非同期処理**は、時間のかかる仕事を「後でやる」リストに入れて、利用者にはすぐに返事をする方法です。リストの仕事は、別のプロセス（**ワーカー**）が順番に片付けます。

たとえるなら、クリーニング店の受付です。受付係（Webサーバ）は服を預かって引換券を渡し、すぐに次の客の対応に移ります。洗濯は奥の作業場（ワーカー）がやります。受付で洗い終わるまで客を待たせたりはしません。

この「後でやる」リストを **キュー**、リストに入った1件の仕事を **ジョブ** と呼びます。

### Active Job

Rails には、ジョブを書くための共通の仕組み **Active Job** があります。ジョブのクラスを生成します。

```bash
bin/rails generate job FetchWeather
```

`app/jobs/fetch_weather_job.rb` ができます。`perform` メソッドの中に、後でやりたい処理を書きます。

```ruby
class FetchWeatherJob < ApplicationJob
  queue_as :default

  def perform(city_id)
    # ここに時間のかかる処理を書く
  end
end
```

ジョブをキューに入れるには `perform_later` を呼びます。

```ruby
FetchWeatherJob.perform_later(city.id)
```

`perform_later` はすぐに戻ってきます。処理そのものは、ワーカーが後で実行します。

### キューの実装：Solid Queue と Sidekiq

Active Job は「ジョブの書き方」を決めるだけで、実際にキューを保存して実行する部分は別の仕組み（**キューアダプタ**）に任せます。代表的なものを2つ紹介します。

- **Solid Queue**：キューを DB に保存します。Rails 8 では、本番の初期設定がこれです。追加のサーバが要らないのが利点です。ワーカーは `bin/jobs` で起動します。
- **Sidekiq**：キューを Redis（メモリ上で動く高速なデータストア）に保存します。長く使われてきた実績があり、大量のジョブを速くさばくのが得意です。Redis のサーバが別に必要です。

どちらを使っても、`perform_later` で入れて `perform` で処理する、というジョブの書き方は同じです。これが Active Job という共通の仕組みがある理由です。

開発環境では、Rails のバージョンによって、ジョブを同じプロセスの中で実行する簡易的なアダプタが使われることがあります。自分のアプリで何が使われているかは、`config/environments/` の各ファイルで `queue_adapter` を検索して確かめてください。

### ジョブを書くときの注意

**引数は小さく、IDを渡す**：ジョブの引数は、キューに保存するために文字に変換されます。Active Record のオブジェクトを渡すと、Rails は内部的に「どのモデルの何番か」を保存し、実行時に DB から読み直します。そのため、実行までの間にレコードが削除されると、ジョブは失敗します。この性質を理解したうえで、ID などの小さな値を渡すのが基本です。

**失敗したらどうするかを書く**：Active Job には、失敗時のふるまいを宣言する仕組みがあります。

```ruby
class FetchWeatherJob < ApplicationJob
  retry_on Net::ReadTimeout, wait: :polynomially_longer, attempts: 5
  discard_on ActiveJob::DeserializationError
end
```

`retry_on` は、指定した例外が起きたら、待ち時間を伸ばしながら決めた回数まで再実行します。`:polynomially_longer` は Rails 7.1 以降の名前で、それより前は `:exponentially_longer` でした。`discard_on` は、その例外が起きたらジョブを捨てます。上の例では、レコードが既に削除されていて読み直せない場合に捨てています。

**ジョブは2回以上実行されることがある**：これが一番大事な注意です。ワーカーがジョブを実行し終えた直後、完了を記録する前に落ちたら、どうなるでしょうか。キューから見ると「未完了」なので、そのジョブはもう一度実行されます。多くのキューの仕組みは「少なくとも1回は実行する」ことは保証しますが、「ちょうど1回」は保証しません。だから、ジョブは何度実行されても結果が変わらないように書く必要があります。

### ジョブのテスト

Rails のテストでは、ジョブ用のテスト補助メソッドが最初から使えます。

```ruby
assert_enqueued_with(job: FetchWeatherJob, args: [city.id]) do
  post "/cities/#{city.id}/refresh"
end
```

これは「ブロックの中の処理で、指定したジョブが、指定した引数でキューに入ったか」を確かめます。ジョブを実際に実行して結果まで確かめたいときは、`perform_enqueued_jobs` を使います。テストでは、キューに入れることと、ジョブの中身の処理を、別々にテストするのが基本です。

## 冪等性

### 何度やっても同じ結果になること

**冪等性**（べきとうせい）とは、同じ操作を1回やっても、何回やっても、結果が同じになる性質です。

身近な例では、エレベーターの「閉」ボタンは冪等です。1回押しても10回押しても、扉が閉まるという結果は同じです。一方、自動販売機のボタンは冪等ではありません。お金があるかぎり、押した回数だけ飲み物が出てきます。

HTTP のメソッドにも、この性質が決められています。`GET`、`PUT`、`DELETE` は冪等とされています。「12番を削除する」は、何回やっても「12番がない」という結果は同じです（2回目以降の応答が 404 になることはあります）。`POST` は冪等ではありません。「投稿を作る」を2回送れば、投稿が2つできます。先ほど `Net::HTTP` が `GET` だけを黙ってリトライしていたのは、この区別に基づいています。

### なぜ外部連携と非同期処理で必要なのか

この章で出てきた「同じことが2回起きる」場面を集めてみます。

- 外部 API の呼び出しがタイムアウトし、リトライした（相手側では1回目が成功していたかもしれない）
- Webhook が再送された
- ジョブが2回実行された
- 利用者がボタンを2回押した

ネットワーク越しの処理では、「確実にちょうど1回だけ実行する」ことは、とても難しいです。だから発想を逆にして、「2回実行されても困らないように作る」のです。

次のプログラムで違いを見てみます。

```ruby
# 冪等でない処理と、冪等な処理の違い
balance = 1000
add_point = ->(amount) { balance += amount }
add_point.call(100)
add_point.call(100) # 同じ通知が2回届いた
puts "冪等でない: #{balance}"

processed = {}
balance = 1000
handle = lambda do |event_id, amount|
  next "#{event_id} は処理済み" if processed[event_id]
  processed[event_id] = true
  balance += amount
  "#{event_id} を処理"
end
puts handle.call("evt_001", 100)
puts handle.call("evt_001", 100)
puts "冪等: #{balance}"
```

```text
$ ruby idempotency_demo.rb
冪等でない: 1200
evt_001 を処理
evt_001 は処理済み
冪等: 1100
```

ポイントは、通知ごとに一意な ID（`evt_001`）があり、「処理済みの ID」を覚えていることです。これが、冪等にするための基本の型です。

### Rails で冪等にする方法

上の例では Hash に覚えていましたが、実際のアプリでは DB を使います。

**ユニーク制約を使う**：処理済みのイベント ID を保存するテーブルを作り、その列に **ユニークインデックス**（同じ値を2回入れられない制約）を付けます。アプリ側で「既にあるか確認してから保存」するだけだと、2つのリクエストがほぼ同時に来たとき、両方が「まだない」と判断してしまいます。DB の制約なら、2つ目の保存を確実に失敗させられます。第15章で学んだ制約が、ここで生きてきます。

**状態を確認する**：「注文が既に支払い済みなら何もしない」のように、処理の前に現在の状態を確かめます。ジョブの先頭で `return if order.paid?` のように書くのが典型です。

**Idempotency-Key を使う**：自分が API を提供する側なら、`POST` のリクエストに、使う側が一意なキーをヘッダで付けてくる方式を受け付けられます。同じキーで2回目のリクエストが来たら、新しく作らずに1回目の結果を返します。決済サービスの API などでよく使われる方式で、ヘッダ名には `Idempotency-Key` がよく使われます。逆に、自分が外部の API を呼ぶ側で、相手がこの方式に対応していれば、リトライのときに同じキーを付けることで二重実行を防げます。

## 実務ではこうなる

API と外部連携は、ジュニアが最初に任されやすく、同時に事故も起きやすい分野です。

- **API の仕様書**：チームで API を作るときは、OpenAPI という形式で仕様書を書き、それをもとにレビューすることが多いです。URL・パラメータ・レスポンスの形・ステータスコードを、実装の前に合意します。
- **外部 API のクライアントはレビューの重点項目**：タイムアウトの値、リトライの条件、失敗時の扱いは、レビューで必ず聞かれます。「初期値のままです」は通りません。
- **ジョブの監視**：本番では、キューに溜まっているジョブの数や、失敗し続けているジョブを監視します（第23章）。Solid Queue なら Mission Control、Sidekiq なら付属の管理画面で、失敗したジョブを確認・再実行できます。
- **Webhook のログ**：外部サービスの管理画面には、たいてい「送った Webhook の履歴と、あなたのサーバの応答」が残っています。障害調査では、自分のログと突き合わせて見ます。

ジュニアがやりがちな失敗も挙げておきます。

- `render json: @user` で、`password_digest` やメールアドレスを API で公開してしまう。
- 外部 API の呼び出しにタイムアウトを付けず、相手の障害に巻き込まれて自分のサービスも止まる。
- エラーなら何でもリトライする設定にして、422 を無限に送り続け、相手から回数制限を受ける。
- Webhook のコントローラで CSRF チェックを外したが、署名検証を入れ忘れる。
- ジョブが2回実行される可能性を考えず、メールが二重に届く、ポイントが二重に付く。
- 決済などのテストで、本物の API キーと本物の API を使ってしまう。外部サービスが用意しているテスト用の環境とキーを使います。

### 演習21-3：署名付き Webhook を受け取り、ジョブで処理する

架空の決済サービスから「支払い完了」の Webhook を受け取る、という想定で実装します。

- やること

  2. 先にテストを書く。
     - 正しい署名なら 200 を返し、ジョブがキューに入る（`assert_enqueued_with`）。
     - 署名がない、または間違っているなら 401 を返し、ジョブは入らず、DB も変わらない。

     - 同じイベント ID の通知を2回送ると、2回とも 200 を返すが、ジョブは1回しか入らない。

  3. イベント ID を保存するテーブルを作り、イベント ID の列にユニークインデックスを付ける。

- **完了条件**
  - 上のテストがすべて成功する。
  - 署名検証の処理を一時的に外すと、署名が間違っているケースのテストが失敗することを確認した（確認後は元に戻す）。
  - マイグレーションのファイルに、イベント ID のユニークインデックスがある。
- ヒント
  - 署名の計算には `request.raw_post` を使います。
  - 比較には `ActiveSupport::SecurityUtils.secure_compare` を使います。
  - ユニークインデックスに引っかかると `ActiveRecord::RecordNotUnique` が発生します。これを「既に処理済み」として扱えば、同時に2つ届いた場合にも対応できます。

  - 「同じキーで2回送っても投稿は1件しか増えない」「キーがなければ従来どおり毎回作られる」「別のユーザーが同じキーを使っても互いに影響しない」の3つのテストが成功する。
- ヒント
  - キーの保存先のテーブルには「ユーザー」と「キー」の組み合わせでユニーク制約を付けます。

## 確認クイズ

**Q1.** `GET /posts/12/delete` で投稿を削除する設計は、なぜ避けるべきか。

**Q2.** ログインしていないユーザーが投稿作成 API を呼んだときと、ログインしたユーザーが他人の投稿を更新しようとしたときに返すステータスコードを、それぞれ答えよ。

**Q3.** 外部 API の呼び出しで 422 が返ってきた。リトライすべきか。

**Q4.** Webhook のコントローラで CSRF のチェックを外した。他に必ず入れるべき対策は何か。

**Q5.** ジョブの中で「ユーザーにポイントを100付与する」処理を書く。注意すべきことは何か。

**Q6.** `render json: @user` と書いた。何が問題になりうるか。

### 解答と解説

1. **`GET` は「取得するだけ」と約束されたメソッドだからです。** ブラウザの先読み、クローラ、リンクのプレビュー機能などが気軽に `GET` を送ります。それだけで削除が起きてしまいます。削除は `DELETE` メソッドで表し、CSRF 対策で守ります。
2. **前者は 401、後者は 404（または 403）です。** 401 は「誰か分からない」、403 は「誰かは分かったが許されない」です。他人のリソースの存在を知らせたくないときは 404 を返すことが多いです（第20章の IDOR 対策）。
3. **リトライすべきではありません。** 422 は「リクエストの内容が受け付けられない」という意味で、同じリクエストを何度送っても結果は変わりません。リトライするのは、タイムアウトや 503 のような一時的な失敗だけです。
4. **署名の検証です。** CSRF トークンの代わりに、共有シークレットによる HMAC 署名で「本物の送り主からの通知か」を確かめます。比較は `secure_compare` で行い、可能なら送信時刻も確かめてリプレイ攻撃を防ぎます。
5. **ジョブは2回以上実行されることがあるので、冪等にする必要があります。** そのままでは二重にポイントが付くかもしれません。「どの理由で付与したか」を一意な ID で記録し、ユニーク制約で二重の付与を防ぐなどの工夫をします。
6. **User の全部の列が JSON に入ります。** `password_digest` やメールアドレスなど、外に出してはいけない情報が漏れます。返す項目は許可リストで明示的に選びます。

## AIの使い方（この章）

推奨する聞き方の例：

- 「API の設計をレビューしてください。次の URL とメソッドとステータスコードの一覧（自分で考えたもの）について、REST の考え方から見て不自然な所と、その理由を指摘してください」
- 「Webhook の署名検証で、`==` ではなく `secure_compare` を使う理由を、タイミング攻撃の仕組みから説明してください」
- 「自分のリトライの方針はこうです（方針を書く）。二重実行が起きるシナリオがあれば、具体的な時系列で挙げてください」

やってはいけない使い方：

- 外部サービスの本物の API キーや Webhook シークレットを含むコードや設定を貼り付ける。貼る前にダミーに置き換えます。
- 「Webhook の受信処理を書いて」と依頼して、署名検証と冪等性の仕組みを理解しないまま取り込む。ここはお金や個人情報に直結する部分です。テストも含めて、自分で書いて説明できる状態にします。

## まとめ

- REST では、URL でリソース（名詞）を、HTTP メソッドで操作（動詞）を表します。ステータスコードは、結果の要約として正しく使い分けます。
- JSON API で返す項目は許可リストで選びます。モデルをそのまま返すと、秘密の列まで漏れます。
- 外部 API は「いつか必ず失敗する」前提で、タイムアウト・リトライの条件・失敗時の扱いを決めます。
- Webhook は署名で本物か確かめ、すぐに返事をして処理はジョブに回します。
- ネットワーク越しの処理では「ちょうど1回」は難しいので、何度実行されても困らない冪等な作りにします。

## 用語

| 用語 | 意味 |
|---|---|
| API | プログラムから別のプログラムの機能を呼び出すための窓口 |
| REST | URL でリソースを、HTTP メソッドで操作を表す、Web API の設計の考え方 |
| JSON | データを文字で表す書式。多くの言語で読み書きできる |
| ステータスコード | HTTP の応答に付く3桁の数字。結果の種類を表す |
| トークン | API の利用を許可するための合言葉の文字列。ヘッダで送る |
| タイムアウト | 待つ時間の上限。接続までと応答までの2種類がある |
| リトライ | 失敗した処理をもう一度試すこと |
| 指数バックオフ | リトライの待ち時間を倍々に伸ばしていく方法 |
| ジッター | 待ち時間に足す小さな乱数。一斉リトライを避ける |
| Webhook | 外部サービスが、出来事をHTTPリクエストで知らせてくる仕組み |
| HMAC | 共有の秘密と本文から署名を計算する方式。改ざんやなりすましを検出できる |
| 非同期処理 | 時間のかかる仕事を後回しにして、利用者にはすぐ返事をする方法 |
| キュー・ジョブ・ワーカー | 後でやる仕事のリスト、その1件、それを処理するプロセス |
| Active Job | Rails でジョブを書くための共通の仕組み |
| 冪等性 | 同じ操作を何回やっても結果が同じになる性質 |
