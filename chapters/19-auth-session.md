# 第19章 Cookie・セッション・認証・認可

> **この章のゴール**：Cookie とセッションの仕組みを理解し、Rails アプリにパスワードによるログイン・ログアウトと「自分のデータだけを操作できる」認可を、攻撃が失敗するテスト付きで実装できるようになります。
> **目安時間**：読む 4時間 ＋ 演習 16時間
> **前提**：第18章まで

## この章で学ぶこと

- 認証と認可の違いを、例を挙げて説明できる
- Cookie の送られ方と、HttpOnly・Secure・SameSite などの属性の意味を説明できる
- パスワードをそのまま保存してはいけない理由と、bcrypt によるハッシュ化の仕組みを説明できる
- `has_secure_password` と `reset_session` を使って、ログイン・ログアウトを実装できる
- 他人のデータを見る・変える操作が失敗することを、テストで示せる
- Devise などのライブラリを使うか自作するかを、根拠を挙げて判断できる

## 認証と認可

この章の主役は、似た名前の2つの言葉です。

- **認証（Authentication）**：相手が「誰か」を確かめること。ログインがその代表
- **認可（Authorization）**：その人に「何をしてよいか」を決めること。自分の投稿は編集できるが、他人の投稿は編集できない、など

会社のビルにたとえます。受付で社員証を見せて本人だと確かめてもらうのが認証です。社員証で入れる部屋が、所属部署によって違うのが認可です。受付を通ったからといって、社長室に入れるわけではありません。

Webアプリの事故で多いのは、認証はしているのに認可が抜けているケースです。ログインさえすれば、URLの数字を変えるだけで他人のデータが見えてしまう。この章では、両方を作り、両方をテストで確かめます。

## Cookie の仕組み

### HTTP は「覚えていない」

第8章で学んだとおり、HTTP はステートレス（状態を持たない）な仕組みです。サーバは、1つ前のリクエストが誰から来たかを覚えていません。毎回が初対面です。これでは、ログインしても次のページで「あなたは誰？」となってしまいます。

そこで使うのが Cookie（クッキー）です。Cookie は、サーバがブラウザに預ける小さなメモです。

1. サーバがレスポンスに `Set-Cookie` ヘッダを付ける：「このメモを持っておいて」
2. ブラウザはメモを保存する
3. 以後、同じサイトへのリクエストには、ブラウザが自動で `Cookie` ヘッダにメモを付けて送る

コートを預けたときにもらう番号札に似ています。番号札（Cookie）を見せれば、係の人（サーバ）はどのコートか分かります。

### 実際に見てみる

第18章のアプリを起動し、別のターミナルでフォームのあるページにアクセスします。`-i` はレスポンスヘッダも表示するオプションです。

```bash
curl -i http://127.0.0.1:3000/posts/new
```

ヘッダの中に、次のような行があるはずです（値は毎回変わります。長いので途中を省略しています）。

```text
set-cookie: _post_app_session=Wk1x...--3f0a...; path=/; httponly; samesite=lax
```

`_post_app_session` が Cookie の名前、`=` の後ろが値です。その後ろの `path=/; httponly; samesite=lax` が属性です。ヘッダ名が小文字なのは、Rails 8 が使う Rack 3 の決まりです。HTTP のヘッダ名は大文字・小文字を区別しないので、`Set-Cookie` と同じ意味です。

なぜフォームのページで Cookie が発行されたのでしょう。第18章で見た CSRF トークンを、セッションに保存したからです。

### Cookie の属性

属性は、Cookie の扱い方をブラウザに指示するものです。セキュリティに関わる重要な属性を表にまとめます。

| 属性 | 意味 | 付けないと何が起きうるか |
|---|---|---|
| `HttpOnly` | JavaScript から `document.cookie` で読めなくする | XSS が起きたとき、セッションの Cookie を盗まれて送られる |
| `Secure` | HTTPS の通信のときだけ送る | HTTP の通信で Cookie が平文で流れ、盗み見られる |
| `SameSite` | 別サイトから始まったリクエストに Cookie を付けるかを決める | CSRF の被害を受けやすくなる |
| `Path` / `Domain` | どのURL・どのドメインに送るか | 広すぎると、関係ない場所にも送られる |
| `Expires` / `Max-Age` | いつまで保存するか | 付けなければ、ブラウザを閉じるまで（セッションCookie） |

`SameSite` には3つの値があります。

- `Strict`：別サイトから来たリクエストには、一切 Cookie を付けない。安全だが、他サイトのリンクから来たときもログインしていない扱いになる
- `Lax`：別サイトからのリンクで移動する GET には付けるが、別サイトからの POST などには付けない。多くのブラウザの既定値
- `None`：常に付ける。`Secure` と一緒でないとブラウザが受け付けない

Rails のセッション Cookie は、既定で `HttpOnly` と `SameSite=Lax` が付きます。`Secure` は、本番環境で HTTPS を強制する設定（`config.force_ssl = true`。Rails 8 の本番用設定では既定で有効）にすると付きます。開発環境は HTTP なので付きません。第13章で学んだ HTTPS が、Cookie を守る前提になっているわけです。

大事な注意があります。`HttpOnly` は XSS を防ぐものではありません。XSS が起きても、セッションの Cookie を盗まれにくくするだけです。`SameSite` も、CSRF トークンの代わりではありません。古いブラウザや例外的な条件では効かないことがあります。どちらも「重ねて守る」ための層です。第17章でトークンを基本にしたのは、このためです。

## セッション

### Cookie にそのまま「ログイン中のユーザーID」を入れてはいけない

ログインに成功したら、Cookie に `user_id=5` と書けばよいでしょうか。いけません。Cookie はブラウザに保存されたメモなので、利用者が自由に書き換えられます。開発者ツールで `user_id=1` に書き換えれば、ユーザー1になりすませます。

そこで、セッションという仕組みを使います。セッションは「サーバが信頼できる形で、利用者ごとのデータを覚えておく仕組み」です。実現方法は大きく2つあります。

| 方式 | Cookie に入るもの | データの置き場所 | 特徴 |
|---|---|---|---|
| サーバ側に保存 | 推測できないセッションID だけ | サーバ（DB・メモリなど） | サーバ側で削除すれば、その場で無効にできる |
| Cookie に保存（Rails の既定） | 暗号化・署名したデータそのもの | ブラウザ | サーバに保存領域がいらない。大きさは約4KBまで |

第17章で自作したのは、前者のサーバ側に保存する方式でした。Rails の既定は後者の CookieStore です。セッションのデータを暗号化し、改ざんを検出する署名を付けて、Cookie に丸ごと入れます。暗号化の鍵は `secret_key_base` という秘密の値から作られます。利用者は中身を読めず、書き換えると署名が合わなくなって無視されます。

`secret_key_base` が漏れると、攻撃者が好きなセッションを作れてしまいます。本番の `secret_key_base` は、`config/credentials.yml.enc` に暗号化して保存され、それを開く鍵が `config/master.key` です。`master.key` は `.gitignore` で Git から除外されています。絶対にコミットしたり、チャットに貼ったりしないでください。詳しくは第20章で扱います。

### Rails でセッションを使う

Controller からは `session` というハッシュのようなものを読み書きできます。

```ruby
session[:user_id] = user.id   # 書き込み
session[:user_id]             # 読み出し
reset_session                 # セッションを丸ごと捨てて作り直す
```

暗号化や署名、Cookie の発行は、Rails のミドルウェア（第18章の `bin/rails middleware` に並んでいたもの）が裏で行います。

### CookieStore の弱点

CookieStore には、知っておくべき弱点が1つあります。ログアウトで `reset_session` すると、ブラウザの Cookie は新しいものに置き換わります。でも、もし攻撃者が古い Cookie の値をこっそりコピーしていたら、その値はサーバから見て「正しく署名されたセッション」のままです。サーバ側に「このセッションは無効」と記録する場所がないからです。

この問題を避けるため、ログイン中の状態をDBのテーブル（セッションの一覧）で管理する方法もあります。ログアウト時にはその行を削除するので、コピーされた Cookie も使えなくなります。Rails 8 の認証ジェネレーター（後で紹介します）は、この方式を採用しています。この章の演習では、まず仕組みが見えやすい CookieStore で作り、違いを理解します。

## パスワードを安全に保存する

### 平文で保存してはいけない

パスワードを、入力されたまま（平文）DBに保存してはいけません。DBの中身が漏れたとき、全員のパスワードがそのまま知られます。多くの人は同じパスワードを他のサービスでも使っているので、被害は自分のサービスだけでは済みません。DBの中身は、バックアップの紛失、SQLインジェクション、内部の人の不正など、さまざまな経路で漏れます。

### ハッシュ化すればよい？

ハッシュ関数は、入力から決まった長さの値（ハッシュ値）を作る関数です。同じ入力からは同じ値が出ますが、値から入力を逆算することはできません（第13章の TLS でも登場しました）。パスワードの代わりにハッシュ値を保存し、ログイン時は入力をハッシュ化して比べれば、パスワードそのものを保存せずに済みます。

ただし、ハッシュ関数なら何でもよいわけではありません。よく知られた SHA-256 で試してみます。

```ruby
require "digest"

alice = Digest::SHA256.hexdigest("password123")
bob   = Digest::SHA256.hexdigest("password123")
puts alice
puts alice == bob

started = Time.now
100_000.times { |i| Digest::SHA256.hexdigest("guess#{i}") }
puts "10万回: #{(Time.now - started).round(2)}秒"
```

```text
ef92b778bafe771e89245b89ecbc08a44a4e166c06659911881f383d4473e94f
true
10万回: 0.14秒
```

問題が2つ見えます。

1つ目は、同じパスワードからは同じハッシュ値が出ることです。Alice と Bob が同じパスワードなら、DBを見ただけで分かります。よく使われるパスワードのハッシュ値の一覧（レインボーテーブル）を用意しておけば、照らし合わせるだけで元のパスワードが分かります。

2つ目は、速すぎることです。手元のPCでは、10万回の計算が0.14秒で終わりました（時間は環境で変わります）。専用の機械を使えば、1秒に何十億回も試せます。短いパスワードなら、総当たりですぐに見つかります。SHA-256 は「大量のデータを速く処理する」ための関数で、パスワードの保存には向いていません。

### bcrypt：ソルトと「わざと遅く」

パスワードの保存には、bcrypt のような専用の方式を使います。bcrypt は次の2つの工夫を持っています。

- **ソルト**：パスワードごとにランダムな値（ソルト）を混ぜてからハッシュ化する。同じパスワードでも、人ごとに違うハッシュ値になる。レインボーテーブルが使えなくなる
- **コスト（ストレッチング）**：計算をわざと何千回も繰り返し、1回の計算を遅くする。正しい利用者のログインは一瞬の遅れで済むが、総当たりで何十億回も試す攻撃者には致命的に遅くなる

Ruby の bcrypt gem で作ったハッシュ値は、次のような60文字の文字列になります。

```text
$2a$12$（ソルト22文字）（ハッシュ値31文字）
```

`2a` は bcrypt の版、`12` はコストです。コスト12は、2の12乗（4096）回の繰り返しを意味します。bcrypt gem の既定値は12です。ソルトがハッシュ値の中に入っているので、ソルトを別に保存する必要はありません。

なお、bcrypt は先頭の72バイトまでしか使いません。日本語のパスワードでは、1文字が3バイトになることが多いので、24文字ほどで上限になります。Rails の `has_secure_password` は、72バイトを超えるパスワードをバリデーションで拒否します。

### has_secure_password

Rails では、`has_secure_password` を使えば、bcrypt によるパスワードの保存と照合を数行で書けます。まず `Gemfile` の bcrypt の行を有効にします。`rails new` で作った `Gemfile` には、`# gem "bcrypt", "~> 3.1.7"` という行がコメントアウトされて入っています。先頭の `#` を外して `bundle install` します。

次に、ユーザーのモデルを作ります。

```bash
bin/rails generate model User email:string:uniq password:digest
```

`password:digest` と書くと、`password_digest` カラムが作られ、モデルに `has_secure_password` が書き込まれます。`email:string:uniq` は、メールアドレスに一意（重複しない）のインデックスを付けます。マイグレーションに `null: false` を足してから `bin/rails db:migrate` します。

`has_secure_password` は、モデルに次の機能を足します。

- `password=`：平文のパスワードを受け取り、bcrypt でハッシュ化して `password_digest` に入れる。平文は保存されない
- `password_confirmation`：確認用の入力。値があれば `password` と一致するかを確かめる
- `authenticate(平文)`：パスワードが正しければユーザー自身を、違えば `false` を返す
- バリデーション：新規作成時にパスワードが必須、72バイトまで

Rails 7.1 以降では、クラスメソッドの `authenticate_by` も使えます。

```ruby
User.authenticate_by(email: "user1@example.com", password: "password-for-test-1")
# 正しければ User のインスタンス、違えば nil
```

`authenticate_by` は、メールアドレスが存在しない場合も、存在する場合とほぼ同じ時間がかかるように作られています。「存在しないメールアドレスだと速く返ってくる」と、応答時間の差から登録の有無を推測されるからです。`find_by(email:)` してから `authenticate` を呼ぶ書き方より、こちらを使いましょう。

メールアドレスは、大文字・小文字や前後の空白の違いで「別人」として登録されないよう、保存前にそろえます。Rails 7.1 以降なら `normalizes :email, with: ->(email) { email.strip.downcase }` と書けます。

## ログインとログアウト

### ルートと流れ

ログインは「セッションを作る」、ログアウトは「セッションを消す」操作と考えると、REST の形にできます。ユーザーにとってセッションは1つなので、単数形の `resource` を使います。

```ruby
resource :session, only: [:new, :create, :destroy]
```

これで `GET /session/new`（ログインフォーム）、`POST /session`（ログイン）、`DELETE /session`（ログアウト）ができます。ユーザー登録は `resources :users, only: [:new, :create]` のように別に作ります。

ログインの流れは次のとおりです。

1. フォームからメールアドレスとパスワードを受け取る
2. `User.authenticate_by` で照合する
3. 成功したら、**セッションを作り直してから**、ユーザーの id をセッションに入れ、リダイレクトする
4. 失敗したら、エラーメッセージを付けてフォームを 422 で再表示する

3の部分は、たとえば次の2行になります。

```ruby
reset_session
session[:user_id] = user.id
```

`reset_session` がなぜ必要かは、次の節で説明します。ログアウトでも `reset_session` を呼び、ログインページなどへ 303 でリダイレクトします。

### 「今ログインしているのは誰か」

各 Controller から「今のユーザー」を取り出せるように、`ApplicationController` に小さなメソッドを用意するのが定番です。考え方だけ示します。

- `current_user`：`session[:user_id]` があれば、その id のユーザーを返す。なければ nil。1回のリクエストの中で何度も DB を引かないよう、インスタンス変数に覚えておく
- `require_login`：`current_user` が nil なら、ログインページへリダイレクトする。`before_action` で使う
- ビューからも `current_user` を使えるよう、`helper_method` で公開する

ログインが必要なのは、ほとんどのページです。だから、`ApplicationController` で全体に `before_action :require_login` をかけ、ログインページや登録ページだけ `skip_before_action` で外す形にします。第17章の CSRF の検証と同じ「安全なほうが既定値」の考え方です。逆に、必要なページに1つずつ付ける形だと、付け忘れたページが誰でも見られるページになります。

### 失敗メッセージは区別しない

ログインに失敗したとき、「そのメールアドレスは登録されていません」「パスワードが違います」と分けて表示したくなります。親切に見えますが、攻撃者にとっても親切です。どのメールアドレスが登録されているかを調べられてしまいます（アカウント列挙）。メッセージは「メールアドレスまたはパスワードが違います」の1種類にします。

また、パスワードを総当たりで試す攻撃を防ぐには、試行回数の制限が必要です。Rails 7.2 以降には `rate_limit` という仕組みがあります。第20章で実装します。

## セッション固定攻撃

ログインの直前に `reset_session` を呼ぶ理由を説明します。ここは少し難しいところです。

セッション固定攻撃（Session Fixation）は、次の手順で行われます。

1. 攻撃者が、自分でサイトにアクセスし、セッションの Cookie を手に入れる（まだログインしていない状態）
2. 何らかの方法で、その Cookie を被害者のブラウザに仕込む（脆弱な別のサブドメインから Cookie を設定するなど）
3. 被害者が、その Cookie のままログインする
4. サーバが、セッションを作り直さずに「このセッションはユーザーAのもの」と記録すると、攻撃者の手元にある同じ Cookie も、ユーザーAとしてログイン済みになる

たとえるなら、攻撃者が用意した番号札を、被害者に持たせてコートを預けさせるようなものです。攻撃者は同じ番号の札の控えを持っているので、後からコートを受け取れます。

対策は、ログインに成功した瞬間に、セッションを新しく作り直すことです。`reset_session` は古いセッションを捨て、新しいセッションを始めます。攻撃者が持っている古い Cookie は、ログイン状態と結び付きません。番号札を、預けた瞬間に新しいものと交換するわけです。

ログアウトでも `reset_session` を呼びます。共有のPCで、次に使う人に前の人のセッションが残らないようにするためです。

Rails の既定の CookieStore では、セッションのデータが Cookie そのものに入っているので、サーバ側に保存する方式ほど攻撃の形はそのままでは当てはまりません。それでも、ログイン前のセッションに入っていたデータ（攻撃者が仕込んだ値かもしれません）を持ち越さないという意味で、`reset_session` は必ず呼びます。セッションの保存方式を後で変えても安全なままでいられるよう、「ログインしたら作り直す」を習慣にしてください。

## 認可：自分のデータだけを操作できるようにする

### 投稿に持ち主を付ける

投稿（Post）に、持ち主のユーザーを結び付けます。

```bash
bin/rails generate migration AddUserToPosts user:references
```

生成されたマイグレーションには `add_reference :posts, :user, null: false, foreign_key: true` が書かれています。既に持ち主のない投稿がDBにあると、`null: false` の制約を満たせず、マイグレーションが失敗します。開発用のデータはダミーなので、先に消してから適用します。

```bash
bin/rails runner "Comment.delete_all; Post.delete_all"
bin/rails db:migrate
```

モデルには `Post` に `belongs_to :user`、`User` に `has_many :posts, dependent: :destroy` を足します。テスト用のフィクスチャ（`test/fixtures/posts.yml`）にも `user: one` のように持ち主を書き足します。

### 「誰のデータか」で絞って探す

このアプリでは、投稿を「持ち主だけが見られる個人用のメモ」として設計します。一覧・詳細・編集・更新・削除のすべてで、ログイン中のユーザーの投稿だけを対象にします。

認可の抜けで最も多いのは、次の形です。

```ruby
# 危険：URL の id に一致する投稿を、誰のものかに関係なく探す
@post = Post.find(params[:id])
```

ユーザーAが `/posts/12/edit` を開けるなら、URL の数字を変えて `/posts/13/edit` も開けます。投稿13がユーザーBのものでも関係ありません。これを IDOR（直接オブジェクト参照の不備）と呼びます。

正しい形は、ログイン中のユーザーの投稿の中から探すことです。

```ruby
@post = current_user.posts.find(params[:id])
```

発行される SQL は `WHERE "posts"."user_id" = ? AND "posts"."id" = ?` のようになります。他人の投稿の id を指定すると、条件に合う行がないので `RecordNotFound` になり、404 が返ります。作成するときも、`current_user.posts.build(post_params)` のように、持ち主を自動で付けます。

### 403 ではなく 404 を返す理由

他人の投稿にアクセスされたとき、「権限がありません（403）」と返す方法もあります。でもそれは「その id の投稿は存在する」と教えることになります。404 を返せば、存在するかどうかも分かりません。誰のものかで絞って探す書き方なら、自然に 404 になります。

### ボタンを隠すだけでは認可にならない

一覧で、他人の投稿の「編集」ボタンを表示しないようにしても、それは見た目の工夫にすぎません。攻撃者はボタンを使わず、URL を直接入力したり、`curl` でリクエストを送ったりします。認可のチェックは、必ずサーバ側（Controller）で行います。

### 持ち主を変えさせない

Strong Parameters の許可リストに `user_id` を入れてはいけません。入れると、更新のリクエストに `post[user_id]=2` を混ぜて、投稿を他人のものに付け替えたり、他人の名前で投稿したりできてしまいます（第18章の一括代入）。持ち主は、必ずサーバ側で `current_user` から決めます。

### 認可をテストで確かめる

認可は、テストで確かめないと、必ずどこかで抜けます。アクションが増えたとき、1つだけ `Post.find` のまま、ということが起きるからです。テストでは、ユーザーAでログインしてから、ユーザーBの投稿に対して詳細・編集・更新・削除のリクエストを送り、次のことを確かめます。

- すべて 404 になる
- ユーザーBの投稿のタイトルと本文が変わっていない（`reload` して確かめる）
- ユーザーBの投稿が削除されていない

ログインの操作をテストごとに書くのは大変なので、`test/test_helper.rb` に補助メソッドを作っておくと便利です。たとえば `sign_in_as(user)` という名前で、ログインのリクエストを送るメソッドです。フィクスチャのユーザーのパスワードは、次のように ERB で作れます。

```yaml
# test/fixtures/users.yml
one:
  email: user1@example.com
  password_digest: <%= BCrypt::Password.create("password-for-test-1") %>
two:
  email: user2@example.com
  password_digest: <%= BCrypt::Password.create("password-for-test-2") %>
```

テスト環境では、`has_secure_password` が bcrypt のコストを最小にするので、テストが遅くなりすぎることはありません。

## ライブラリを使うか、自作するか

この章ではログインを手で書きました。仕組みを理解するためです。実際のプロジェクトでは、次のような選択肢があります。

| 選択肢 | 概要 | 向いている場面 | 気をつけること |
|---|---|---|---|
| 自作（この章の方法） | `has_secure_password` とセッションで書く | 学習。要件がごく単純 | パスワード再設定・試行回数制限・メール確認などを全部自分で作り、検証する必要がある |
| Rails の認証ジェネレーター | `bin/rails generate authentication`（Rails 8.0 以降）。読めるコードが生成される | 新規の Rails アプリで、要件が標準的 | 利用者の登録画面は含まれない。生成されたコードは自分のコードとして保守する |
| Devise | Rails で長く使われている認証の gem。登録・確認メール・ロックなどが揃う | 既存の多くの現場。機能を一通り揃えたい | 設定と規約が多い。中身を知らずに使うと、カスタマイズで迷う |
| 外部の認証サービス・OAuth | Google などでのログイン、認証専用の外部サービス | 社内システムのシングルサインオン、多要素認証が必須 | 外部サービスへの依存、設定ミス、費用 |

Rails 8 の認証ジェネレーターが作るコードを読むと、この章で学んだことがそのまま出てきます。DBのテーブルでログイン状態を管理し、その id を署名付きの Cookie に入れています。Cookie には `httponly: true` と `same_site: :lax` が明示されています。ログインには `User.authenticate_by` を使い、ログインの試行には `rate_limit` が付いています。

判断の基準をまとめます。

- 認証は、間違えたときの被害がとても大きい。実績があり、多くの人に検証されたものを使うのが基本
- ただし「ライブラリを使ったから安全」ではない。設定や使い方を誤れば穴が開く。中身の仕組みを理解していることが前提
- 既存の現場では、すでに使われているもの（Devise であることが多い）に合わせる。新しく入れ替える判断は、ジュニア1人ではしない

なお、認可にもライブラリがあります。Pundit や Action Policy などは、「誰が何をしてよいか」のルールを1か所にまとめる仕組みを提供します。この章の `current_user.posts.find` は、その最も単純な形です。

## 実務ではこうなる

認証・認可は、セキュリティ事故の原因として最も多い領域の1つです。OWASP Top 10（第20章）でも、アクセス制御の不備が最上位に置かれています。

現場での仕事は、ほとんどの場合、既存の認証の仕組みの上に機能を足すことです。そのときにジュニアがやりがちな失敗を挙げます。

- 新しい Controller を作り、`before_action` でのログインチェックや、`current_user` での絞り込みを入れ忘れる
- 一覧は `current_user.posts` で絞ったのに、詳細や削除では `Post.find` のままにする
- 管理画面を作るときに、「管理者かどうか」のチェックをビューのボタンの表示だけで行う
- デバッグのために、パスワードやセッションの中身をログに出力する
- テスト用のアカウントに、自分が普段使っているパスワードを設定する

コードレビューでは、「この操作は、誰ができるべきか」「他人の id を指定したらどうなるか」を必ず問われます。新しいアクションを作るたびに、自分で同じ問いを立て、テストで答えを固定してください。

## 確認クイズ

**Q1.** 「認証」と「認可」の違いを、この章のアプリを例に説明してください。

**Q2.** ログインに成功したら、Cookie に `user_id=5` と直接書いて、次からはその値でユーザーを判断することにしました。何が問題ですか。

**Q3.** パスワードを SHA-256 でハッシュ化して保存しています。平文よりは安全ですが、何が足りませんか。

**Q4.** ログインの処理で、`session[:user_id] = user.id` の前に `reset_session` を呼ぶのはなぜですか。

**Q5.** 投稿の編集画面で、他人の投稿には「編集」ボタンを表示しないようにしました。これで認可は十分ですか。

### 解答と解説

**A1.** 認証は「相手が誰かを確かめる」ことで、メールアドレスとパスワードでのログインがそれです。認可は「その人に何をしてよいかを決める」ことで、ログイン中のユーザーが自分の投稿だけを見たり編集したりできるようにする部分です。ログインしていても、他人の投稿は操作できません。

**A2.** Cookie は利用者が自由に書き換えられるので、`user_id=1` にすれば他人になりすませます。ログイン状態はセッション（暗号化・署名された Cookie、またはサーバ側の保存）で管理し、利用者が改ざんできないようにします。

**A3.** ソルトがないので、同じパスワードが同じハッシュ値になり、レインボーテーブルで元のパスワードを調べられます。また、計算が速すぎるので、総当たりで試されやすいです。bcrypt のように、ソルトを使い、わざと遅く計算する専用の方式を使います。Rails なら `has_secure_password` です。

**A4.** セッション固定攻撃を防ぐためです。攻撃者が事前に用意したセッションを被害者に使わせ、そのままログインさせると、攻撃者も同じセッションでログイン済みになってしまいます。ログインの瞬間にセッションを作り直せば、古いセッションはログイン状態と結び付きません。

**A5.** 十分ではありません。ボタンを隠しても、攻撃者は URL を直接入力したり `curl` で送ったりできます。認可のチェックはサーバ側で行い、`current_user.posts.find(params[:id])` のように、自分のデータの中から探します。他人の id では 404 になることをテストで確かめます。

## AIの使い方（この章）

認証・認可は、間違いが大きな被害につながる領域です。AIの説明は便利ですが、必ず公式のドキュメント（Rails ガイドや API ドキュメント）で裏を取ってください。

推奨する聞き方の例です。

- 「Rails の `has_secure_password` が、パスワードを保存するときと照合するときに、内部で何をしているか説明してください。Rails 8.1 のソースのどのファイルを読めばよいかも教えてください」
- 「私の認可のテスト（貼る）は、詳細・編集・更新・削除で他人の投稿が 404 になることを確かめています。抜けている攻撃パターンがあれば指摘してください」
- 「セッション固定攻撃を、Cookie に保存する方式とサーバ側に保存する方式で、それぞれどう考えればよいか比べてください」

やってはいけない使い方です。

- ログイン機能や `current_user` の実装を丸ごとAIに書かせ、理解しないまま使うこと。どこで認可が抜けているかを自分で説明できなくなります
- 本物のパスワード、本番の `secret_key_base`、`master.key` の中身、実際の利用者のデータをAIに貼ること。AIのサービスに送った情報は、自分の手を離れます

## まとめ

- 認証は「誰か」、認可は「何をしてよいか」。ログインがあっても、認可が抜けていれば他人のデータを操作される
- Cookie は利用者が書き換えられるメモ。ログイン状態は署名・暗号化されたセッションで管理し、HttpOnly・Secure・SameSite で重ねて守る
- パスワードは平文でも単純なハッシュでもなく、ソルトとコストを持つ bcrypt（`has_secure_password`）で保存する
- ログイン・ログアウトでは `reset_session` でセッションを作り直す。データは `current_user.posts.find` のように持ち主で絞って探し、他人の id では 404 になることをテストで示す
- 認証は実績のある仕組みを使うのが基本。ただし仕組みを理解したうえで使う

## 用語

| 用語 | 意味 |
|---|---|
| 認証（Authentication） | 相手が誰かを確かめること。ログイン |
| 認可（Authorization） | その人に何をしてよいかを決めること |
| Cookie | サーバがブラウザに預ける小さなデータ。以後のリクエストに自動で付けて送られる |
| HttpOnly | JavaScript から Cookie を読めなくする属性 |
| Secure | HTTPS の通信のときだけ Cookie を送る属性 |
| SameSite | 別サイトから始まったリクエストに Cookie を付けるかを決める属性 |
| セッション | 複数のリクエストをまたいで、利用者ごとのデータを信頼できる形で覚えておく仕組み |
| CookieStore | セッションのデータを暗号化・署名して Cookie に入れる、Rails の既定の方式 |
| `secret_key_base` | Rails がセッションの暗号化や署名に使う秘密の値 |
| ソルト | パスワードごとに混ぜるランダムな値。同じパスワードでも別のハッシュ値になる |
| bcrypt | ソルトとコストを持つ、パスワード保存のためのハッシュ方式 |
| `has_secure_password` | bcrypt によるパスワードの保存と照合を提供する Rails の機能 |
| セッション固定攻撃 | 攻撃者が用意したセッションで被害者をログインさせ、そのセッションを乗っ取る攻撃 |
| IDOR | URL の id を変えるだけで他人のデータにアクセスできてしまう、認可の不備 |
| アカウント列挙 | ログインの失敗メッセージなどから、登録済みのメールアドレスを調べられてしまうこと |
