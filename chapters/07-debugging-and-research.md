# 第7章 エラーの読み方・デバッグ・調べ方・質問の仕方

> **この章のゴール**：エラーが出ても慌てずに、メッセージとスタックトレースから原因の場所を絞り込めるようになる。仮説と検証で直し、自力で解けないときは相手に伝わる質問ができるようになる。
> **目安時間**：読む 2.5時間 ＋ 演習 4時間
> **前提**：第6章まで

## この章で学ぶこと

- エラーメッセージから「種類・内容・場所」を読み取れる
- スタックトレースを読み、自分のコードのどこから問題が始まったかを特定できる
- `p`・`pp`・`binding.irb` を使って、実行中の値を確かめられる
- 公式ドキュメント（docs.ruby-lang.org）でメソッドの使い方を調べられる
- 問題を小さく切り出した「最小再現」を作れる
- 必要な情報がそろった質問文を書ける

## エラーは敵ではなく、手がかり

プログラミングを始めたばかりの人は、赤い文字のエラーを見ると「失敗した」と感じます。しかし、現場のエンジニアも毎日エラーを見ています。違いは、エラーを「何が起きたかを教えてくれる報告書」として読めるかどうかです。

病院の問診にたとえます。「なんとなく調子が悪い」とだけ言われても、医者は困ります。「昨日の夜から、右のお腹が、歩くと痛む」と言われれば、原因の見当がつきます。Ruby のエラーメッセージは、この「いつ・どこが・どう痛むか」を、毎回きちんと書いてくれる患者のようなものです。

正直に言うと、エラーを読めるようになるには慣れが必要です。最初のうちは英語の文章に圧倒されると思います。この章では、どこから読めばよいかの「型」を身につけます。型があれば、知らないエラーでも手がかりを拾えるようになります。

## エラーメッセージの3つの要素

次のプログラムを `nil_error.rb` として実行してみます。

```ruby
user = { "name" => "テスト太郎", "email" => "user1@example.com" }
puts user[:name].upcase
```

```console
$ ruby nil_error.rb
nil_error.rb:2:in `<main>': undefined method `upcase' for nil:NilClass (NoMethodError)
Did you mean?  case
```

1行のメッセージを、3つの部分に分けて読みます。

| 部分 | この例では | 意味 |
|---|---|---|
| 場所 | `nil_error.rb:2:in `<main>'` | `nil_error.rb` の2行目。`<main>` はメソッドの外（ファイルの一番外側）という意味 |
| 内容 | `undefined method `upcase' for nil:NilClass` | nil に対して `upcase` を呼んだが、そんなメソッドはない |
| 種類 | `(NoMethodError)` | 例外のクラス名。第5章で学んだ例外の種類 |

読む順番のおすすめは、**種類 → 内容 → 場所** です。種類で大まかな分類をつかみ、内容で何が起きたかを知り、場所でどこを見ればよいかを決めます。

この例の内容を日本語にすると、「nil には `upcase` というメソッドがない」です。つまり、`user[:name]` が nil だったということです。なぜ nil なのでしょうか。Hash のキーは `"name"`（文字列）なのに、`:name`（シンボル）で取り出そうとしたからです。第4章で学んだとおり、文字列とシンボルは別のキーです。

### 「Did you mean?」を信じすぎない

2行目の `Did you mean?  case` は、Ruby が出してくれる「もしかして」の候補です。名前の打ち間違いを見つけるのに役立ちます。

ただし、この例の候補 `case` はまったく見当違いです。`upcase` と綴りが似ているメソッドを機械的に探しているだけだからです。候補は参考程度にして、本当の原因はメッセージの内容から考えてください。

### NoMethodError for nil は「nil がどこから来たか」の問題

`undefined method `○○' for nil` は、初心者が最も多く出会うエラーです。このエラーを見たら、問いを切り替えてください。

- 誤った問い：「なぜ `upcase` が使えないのか」
- 正しい問い：「**なぜここで nil になっているのか**。その nil はどこから来たのか」

nil の出どころとしてよくあるのは、次の4つです。

1. Hash に存在しないキーで取り出した（文字列とシンボルの取り違えを含む）
2. 配列の範囲外を取り出した
3. `@` を付け忘れて、インスタンス変数が設定されていなかった（第5章）
4. メソッドの最後の式が nil で、それが戻り値になった（`puts` の戻り値など）

### よく出会うエラーの早見表

| 種類 | よくある原因 | 内容の例 |
|---|---|---|
| NameError | 変数名・クラス名の打ち間違い、定義前に使った | `undefined local variable or method `nmae'` |
| NoMethodError | nil に対して呼んだ、メソッド名の打ち間違い、private を外から呼んだ | `undefined method `upcase' for nil` |
| ArgumentError | 引数の数が違う、値が不正 | `wrong number of arguments (given 2, expected 1)` |
| TypeError | 型の違う値どうしを計算した | `no implicit conversion of Integer into String` |
| ZeroDivisionError | 整数を0で割った | `divided by 0` |
| KeyError | `fetch` で存在しないキーを取り出した | `key not found: "b"` |
| IndexError | `fetch` で配列の範囲外を取り出した | `index 5 outside of array bounds: -2...2` |
| LoadError | `require` するファイルや Gem が見つからない | `cannot load such file -- calculator` |
| Errno::ENOENT | ファイルやフォルダが存在しない | `No such file or directory` |
| SyntaxError | 文法の誤り（`end` の不足など） | `unexpected end-of-input, expecting end` |

全部を暗記する必要はありません。この表は、演習のときに引く辞書として使ってください。何度も見ているうちに、自然に覚えます。

> **Ruby のバージョンによる表示の違い**：この章の出力例には、古い Ruby で実行したものがあります。Ruby 3.1 以降では、エラーの起きた行のコードが表示され、問題の部分に `^^^^` で下線が引かれます。Ruby 3.4 以降では、メソッド名が `'Order#subtotal'` のように「クラス名#メソッド名」で、一重引用符で囲まれて表示されます。表示が少し違っても、「種類・内容・場所」を読むという方法は同じです。

## スタックトレースを読む

実際のプログラムでは、メソッドがメソッドを呼び、その中でエラーが起きます。そのとき Ruby は、「どういう順番で呼ばれて、そこにたどり着いたか」を一覧にして表示します。これを**スタックトレース**（バックトレース）と呼びます。

例を見てみましょう。次の2つのファイルを `~/workspace/ch07-debugging/` に作ります。

```ruby
# lib/order.rb
class Order
  def initialize(items)
    @items = items
  end

  def total
    @items.sum { |item| subtotal(item) }
  end

  private

  def subtotal(item)
    item[:price] * item[:quantity]
  end
end
```

```ruby
# report.rb
require_relative "lib/order"

items = [
  { name: "ノート", price: 150, quantity: 2 },
  { name: "ペン", price: 100 },
]

order = Order.new(items)
puts "合計: #{order.total}円"
```

```console
$ ruby report.rb
/Users/you/workspace/ch07-debugging/lib/order.rb:13:in `*': nil can't be coerced into Integer (TypeError)
	from /Users/you/workspace/ch07-debugging/lib/order.rb:13:in `subtotal'
	from /Users/you/workspace/ch07-debugging/lib/order.rb:7:in `block in total'
	from /Users/you/workspace/ch07-debugging/lib/order.rb:7:in `sum'
	from /Users/you/workspace/ch07-debugging/lib/order.rb:7:in `total'
	from report.rb:9:in `<main>'
```

（`/Users/you/...` の部分は、あなたの環境のパスになります。）

### 上から読むと「どこで倒れたか」、下から読むと「どう呼ばれたか」

スタックトレースは、**一番上が、例外が起きた場所**です。下に行くほど、呼び出しの元をさかのぼります。

下から上へ読むと、次のような流れになります。

1. `report.rb` の9行目（`<main>`）で `total` を呼んだ
2. `order.rb` の7行目、`total` の中で `sum` を呼んだ
3. `sum` がブロックを実行した（`block in total`）
4. ブロックの中で `subtotal` を呼んだ
5. `order.rb` の13行目、`subtotal` の中で `*`（掛け算）をしたところで例外が起きた

スタックトレースは、会社の「指示の伝言リスト」のようなものです。社長が部長に頼み、部長が課長に頼み、課長が担当者に頼み、担当者のところで問題が起きた。一番上が問題の起きた担当者、一番下が最初に指示を出した社長です。

### 内容を読んで、原因を推理する

メッセージは `nil can't be coerced into Integer` です。直訳すると「nil を Integer に変換できない」です。掛け算 `item[:price] * item[:quantity]` の右側が nil だった、ということです。

`item[:quantity]` が nil になる商品はどれでしょうか。データを見ると、「ペン」に `quantity` がありません。原因はデータの側にありました。

ここで大切なことがあります。**例外が起きた場所と、原因がある場所は、同じとは限りません。** 例外が起きたのは `order.rb` の13行目です。しかし原因は、`report.rb` のデータに数量が欠けていたことです。スタックトレースは「どこで倒れたか」を正確に教えてくれますが、「なぜ倒れたか」は自分で推理する必要があります。

### 長いスタックトレースでは「自分のコード」を探す

Gem やフレームワークを使うと、スタックトレースが何十行にもなります。多くは、Gem の内部のファイルです。そのときは、次の順で読みます。

1. 一番上の行で、例外の種類と内容を読む
2. 上から順に見ていき、**最初に出てくる自分のファイルの行**を探す
3. その行のコードを開き、そこで使っている値が何だったかを考える

Gem の内部にバグがあることもありますが、まれです。まずは「自分のコードが、Gem に変な値を渡していないか」を疑うのが近道です。

### テストが失敗したときのスタックトレース

第6章で見たように、Minitest の Error にもスタックトレースが付きます。

```text
  1) Error:
GradeReportTest#test_average:
NoMethodError: undefined method `sum' for nil:NilClass
    lib/grade_report.rb:10:in `average'
    test/grade_report_test.rb:14:in `test_average'
```

読み方は同じです。一番上の `lib/grade_report.rb:10` が例外の起きた場所、一番下がテストの中で呼んだ場所です。

`bundle exec rake test` でテストが失敗すると、最後に次のような表示も出ます。

```text
rake aborted!
Command failed with status (1)
```

これは「テストが失敗したので、rake も失敗として終わった」という報告です。この下に続くスタックトレースは rake 自身のものなので、たいていは読む必要はありません。見るべきなのは、その上にあるテストの失敗の報告です。

## SyntaxError：文法の誤り

ここまでのエラーは、プログラムを実行している途中で起きるものでした。**SyntaxError** は、実行する前の「文法チェック」の段階で起きます。

```ruby
def greet(name)
  if name.empty?
    "名無しさん、こんにちは"
  else
    "#{name}さん、こんにちは"
end

puts greet("花子")
```

```console
$ ruby syntax.rb
syntax.rb:8: syntax error, unexpected end-of-input, expecting end
```

`unexpected end-of-input, expecting end` は、「`end` が来るはずなのに、ファイルが終わってしまった」という意味です。`if` を閉じる `end` が1つ足りません。

ここで注意したいのは、**報告された行番号（8行目）が、間違えた場所ではない**ことです。Ruby はファイルの最後まで読んで初めて、`end` が足りないと気づきます。だから最後の行が報告されます。実際に `end` が抜けているのは6行目の前です。

`end` の不足を見つけるコツは、**インデント（字下げ）を揃えること**です。`def` と `end`、`if` と `end` の位置が縦に揃っていれば、足りない場所が目で見てわかります。エディタの自動整形機能を使うのも有効です。

`ruby -c ファイル名` で、実行せずに文法チェックだけを行えます。

```console
$ ruby -c report.rb
Syntax OK
```

> Ruby 3.4 以降では文法チェックの仕組みが新しくなり、SyntaxError のメッセージがより詳しくなっています。表示は違っても、「報告された行より前に原因があることが多い」という点は同じです。

## デバッグの基本姿勢：仮説を立てて、1つずつ確かめる

**デバッグ**とは、プログラムの誤り（バグ）の原因を見つけて直すことです。デバッグで一番大切なのは、道具よりも進め方です。

うまくいかない進め方は、思いついた修正を手当たり次第に試すことです。ネットで見つけたコードを貼る、あちこちを同時に書き換える、といったやり方です。たまたま動いても、なぜ動いたのかわかりません。別の場所を壊していることもあります。

おすすめの進め方は、次の繰り返しです。

1. **観察する**：エラーメッセージとスタックトレースを読む。何が起きたかを事実として書き出す。
2. **仮説を立てる**：「`item[:quantity]` が nil だからではないか」のように、原因の候補を1つ決める。
3. **確かめる**：その仮説が正しいかを、値を表示するなどして確かめる。
4. **直す・次へ**：正しければ直す。間違っていれば、仮説を立て直す。

ポイントは、**一度に1つのことしか変えない**ことです。2つ同時に変えると、どちらが効いたのかわかりません。

もう1つ大切なことがあります。デバッグ中に考えたことは、メモに残してください。「仮説・確かめ方・結果」を1行ずつでも書いておけば、同じことを二度試さずに済みます。人に質問するときにも、そのまま「試したこと」として使えます。

## p と pp で値を見る

仮説を確かめる一番手軽な道具は、値を表示することです。Ruby では `puts` より `p` を使います。

```ruby
puts nil
puts ""
puts "42"
puts 42
p nil
p ""
p "42"
p 42
x = p("戻り値も返す")
puts x
```

```console
$ ruby p_vs_puts.rb


42
42
nil
""
"42"
42
"戻り値も返す"
戻り値も返す
```

`puts` では、`nil` も空文字 `""` も空行になり、区別できません。文字列の `"42"` と数値の `42` も同じに見えます。`p` なら、`nil`・`""`・`"42"`・`42` がはっきり区別できます。

| | puts | p |
|---|---|---|
| 目的 | 利用者向けの表示 | 開発者向けの確認 |
| nil | 空行 | `nil` |
| 文字列 | 引用符なし | 引用符付き（`"42"`） |
| 戻り値 | nil | 渡した値そのもの |

`p` は渡した値をそのまま返します。そのため、`total = p(calc_total)` のように、既存のコードの途中に差し込んでも動きが変わりません。

### pp で入れ子のデータを見やすくする

入れ子になった Hash や配列は、`p` だと1行に詰まって読みにくくなります。そのときは `pp`（pretty print、整形表示）を使います。

```ruby
data = {
  "users" => [
    { "id" => 1, "name" => "テスト太郎", "roles" => ["admin", "editor"], "email" => "user1@example.com" },
    { "id" => 2, "name" => "テスト花子", "roles" => ["viewer"], "email" => "user2@example.com" },
  ],
}
p data
pp data
```

```console
$ ruby pp_demo.rb
{"users"=>[{"id"=>1, "name"=>"テスト太郎", "roles"=>["admin", "editor"], "email"=>"user1@example.com"}, {"id"=>2, "name"=>"テスト花子", "roles"=>["viewer"], "email"=>"user2@example.com"}]}
{"users"=>
  [{"id"=>1,
    "name"=>"テスト太郎",
    "roles"=>["admin", "editor"],
    "email"=>"user1@example.com"},
   {"id"=>2,
    "name"=>"テスト花子",
    "roles"=>["viewer"],
    "email"=>"user2@example.com"}]}
```

（Ruby 3.4 以降では、Hash の表示が `{"users" => [...]}` のように、`=>` の前後に空白が入る形に変わっています。）

### 表示を使うときのコツ

- **ラベルを付ける**：`p item` を何か所にも書くと、どの出力がどこのものかわからなくなります。`p [:subtotal, item]` のように、目印を一緒に表示します。
- **境界で表示する**：メソッドの入口（引数）と出口（戻り値）で表示すると、問題の範囲を半分ずつ絞り込めます。
- **終わったら必ず消す**：デバッグ用の `p` を残したままコミットしないでください。コミットする前に `git diff` で確認する習慣を付けましょう。

## binding.irb で止めて調べる

`p` は手軽ですが、見たい値が変わるたびにコードを書き換えて、実行し直す必要があります。**binding.irb** を使うと、プログラムをその場で一時停止して、対話的に値を調べられます。

先ほどの `lib/order.rb` の `subtotal` に、1行足します。

```ruby
  def subtotal(item)
    binding.irb
    item[:price] * item[:quantity]
  end
```

実行すると、`binding.irb` の行で止まり、irb（第3章で使った対話環境）が起動します。止まった場所の変数を、自由に調べられます。

```console
$ ruby report.rb

From: /Users/you/workspace/ch07-debugging/lib/order.rb @ line 13 :

     8:   end
     9: 
    10:   private
    11: 
    12:   def subtotal(item)
 => 13:     binding.irb
    14:     item[:price] * item[:quantity]
    15:   end
    16: end

irb(#<Order:0x00007f81ec820a08>):001:0> item
=> {:name=>"ノート", :price=>150, :quantity=>2}
irb(#<Order:0x00007f81ec820a08>):002:0> item[:quantity]
=> 2
irb(#<Order:0x00007f81ec820a08>):003:0> exit

From: /Users/you/workspace/ch07-debugging/lib/order.rb @ line 13 :
（同じ表示が続く）

irb(#<Order:0x00007f81ec820a08>):001:0> item
=> {:name=>"ペン", :price=>100}
irb(#<Order:0x00007f81ec820a08>):002:0> exit!
```

- `=> 13:` の矢印が、今止まっている行です。
- プロンプト（`irb(...)>`）に変数名や式を打つと、その値が表示されます。メソッドを呼ぶこともできます。
- `exit` で irb を抜けると、プログラムが続きから動きます。この例では `subtotal` がもう一度呼ばれるので、2つ目の商品で再び止まりました。
- `exit!` で、プログラムごと終了します。

2回目に止まったときの `item` を見ると、`:quantity` がありません。仮説「ペンの数量が nil だから」が、ここで確かめられました。

（irb のプロンプトの形は版によって違います。新しい irb では `irb(#<Order:0x...>):001>` のように表示されます。）

### 条件付きで止める

ループの中に `binding.irb` を書くと、毎回止まって手間がかかります。怪しいときだけ止めるには、`if` を付けます。

```ruby
binding.irb if item[:quantity].nil?
```

### debug gem（Ruby 3.1 以降）

Ruby 3.1 以降には、**debug** という本格的なデバッガが付属しています。`require "debug"` と書いてから、止めたい場所に `binding.break`（または `debugger`）と書きます。止まった後は、`next`（次の行へ）、`step`（メソッドの中に入る）、`continue`（次に止まる場所まで進む）などのコマンドで、1行ずつ実行を進められます。

`binding.irb` は「止めて調べる」道具、debug gem は「止めて、1行ずつ進めながら調べる」道具です。最初は `binding.irb` で十分です。使えるコマンドは版によって変わるので、使う前に [debug の README](https://github.com/ruby/debug) で確かめてください。

`binding.irb` や `binding.break` も、`p` と同じく**コミットする前に必ず消します**。残したままにすると、テストや本番の処理がそこで止まってしまいます。

## 最小再現を作る

原因がなかなかわからないとき、強力な方法が**最小再現**です。最小再現とは、問題が起きる状況を、できるだけ短いコードに切り出したものです。

先ほどの例なら、最終的にはこの1行まで縮められます。

```console
$ ruby -e 'p 150 * nil'
-e:1:in `*': nil can't be coerced into Integer (TypeError)
	from -e:1:in `<main>'
```

`ruby -e '...'` は、ファイルを作らずに、その場でコードを実行する書き方です。

### 作り方

1. 問題が起きるコードを、別のファイル（または別のフォルダ）にコピーする。
2. 問題に関係なさそうな部分を、**少しずつ**消す。消すたびに実行して、問題がまだ起きるか確かめる。
3. 消したら問題が消えた部分は、原因に関係しています。元に戻して、他の部分を消す。
4. これ以上消せなくなったら、それが最小再現です。

データも同じように減らします。商品が100個あるなら、問題が起きる1個だけにします。

### 最小再現の効果

最小再現を作る途中で、原因に気づくことがよくあります。関係ない部分を取り除くと、本当の問題だけが残るからです。熟練者がデバッグに強いのは、この切り分けが速いからでもあります。

また、人に質問するときにも欠かせません。300行のコードを渡されて「動きません」と言われても、相手は困ります。5行の再現コードなら、相手は自分のPCですぐに試せます。

## 公式ドキュメントを引く

調べ物の基本は、**公式ドキュメント**です。Ruby の公式リファレンスは、日本語で読めます。

- Ruby リファレンスマニュアル（日本語）：https://docs.ruby-lang.org/ja/latest/doc/index.html
- 英語版：https://docs.ruby-lang.org/en/master/

### クラスのページの読み方

たとえば Array の `sum` を調べたいとします。まず https://docs.ruby-lang.org/ja/latest/class/Array.html を開きます。次に、ページ内検索（Mac なら command + F）で `sum` を探します。

クラスのページは、主に次の部分でできています。

- **特異メソッド**：`Array.new` のように、クラスに対して呼ぶメソッド（第5章のクラスメソッドのこと）
- **インスタンスメソッド**：`[1, 2].sum` のように、オブジェクトに対して呼ぶメソッド
- **継承しているクラス・インクルードしているモジュール**：ページの上部に書かれています。Array なら Enumerable が含まれます。

`sum` の項目には、次のような書き方が並んでいます（表記は版により多少違います）。

```text
sum(init = 0) -> object
sum(init = 0) {|e| expr } -> object
```

これはメソッドの**シグネチャ**（使い方の形）です。読み方は次のとおりです。

- `sum(init = 0)`：引数 `init` を1つ取れる。省略すると 0 になる。
- `{|e| expr }`：ブロックを渡せる。ブロックには要素が1つずつ渡される。
- `-> object`：戻り値の種類。

その下に説明文と例が続きます。**例は必ず自分の irb で試してください。** 読むだけより、ずっと記憶に残ります。

目的のメソッドがクラスのページに見つからないときは、ページ上部の「インクルードしているモジュール」も探します。たとえば Array の `each_slice` は、Enumerable のページに書かれています。

### バージョンを合わせる

URL の `latest` の部分は、Ruby のバージョンに置き換えられます。古い記事のコードが動かないときは、使っている Ruby の版と、ドキュメントの版が合っているかを確かめましょう。まず、自分の版を確かめます。

```bash
ruby -v
bundle exec ruby -v       # プロジェクトで実際に使われる版
bundle exec gem list minitest   # Gem の版
```

ドキュメントを開く前に、irb で手早く調べる方法もあります。

```ruby

p 1.5.class

```

- `.methods.grep(/正規表現/)`：名前の一部から、使えるメソッドを探す
- `.class`：その値が何のクラスか調べる。nil や文字列と数値の取り違えに気づける
- `.ancestors`：どのクラスやモジュールのメソッドが使えるかを調べる

### 調べるときの優先順位

情報の信頼度は、出どころによって違います。上から順に頼ってください。

1. **公式ドキュメント**（Ruby のリファレンス、Rails ガイドなど）
2. **Gem の README と CHANGELOG**（変更履歴）。GitHub や rubygems.org にある
3. **GitHub の Issue**：同じ問題が報告されていないか
4. **技術ブログや Q&A サイト**：便利だが、古い・間違っている情報も混ざる

ブログ記事を参考にするときは、**書かれた日付と、対象の版**を必ず確かめてください。5年前の記事の方法は、今の版では動かないことがよくあります。

### エラーメッセージで検索するコツ

エラーメッセージで検索するのは、有効な方法です。ただし、そのまま全部を貼ると、うまく見つかりません。

- 自分のファイル名・パス・変数名・オブジェクトの番号（`0x00007f...`）は取り除く
- 例外の種類と、内容の決まった部分（`can't be coerced into Integer` など）を残す
- Gem の名前を一緒に入れる（例：`minitest assert_equal nil deprecated`）

## 質問の仕方

どんなに調べても、自分だけでは解けないことがあります。そのときに上手に質問できることは、エンジニアにとって大切な技術です。

### いつ質問するか

自分で考える時間を、先に決めておきましょう。たとえば「30分調べて進展がなければ質問する」と決めます。何時間も一人で悩み続けるのは、学習でも仕事でも得策ではありません。逆に、エラーを読む前に質問するのも早すぎます。この章の手順（読む・仮説を立てる・確かめる・調べる）を一通り試してから質問します。

### 質問のテンプレート

元にした研修では、質問に次の情報を添えるよう求めています。「該当Phase・目的・OS/Ruby/Gemの版・実行コマンド・期待結果・実際の結果・試したこと」です。この教材では次のテンプレートを使います。

````markdown
## 該当箇所
第7章 演習7-2

## やりたいこと（目的）
GradeReport#average で、点数の平均を小数で求めたい。

## 環境
- OS: macOS 15.x
- Ruby: ruby 3.4.x（`bundle exec ruby -v` の結果を貼る）
- Gem: minitest 5.x（`bundle exec gem list minitest` の結果を貼る）

## 実行したコマンド
bundle exec rake test

## 期待した結果
4 runs, 4 assertions, 0 failures

## 実際の結果（全文）
```
（エラーメッセージとスタックトレースを、省略せずにそのまま貼る）
```

## 最小再現
```ruby
p [80, 65, 90].sum / 3
# => 78 （78.33... を期待した）
```

## 試したこと
- `p list` で中身を表示し、配列 [80, 65, 90] が入っていることを確認した
- `list.sum` は 235 だった
- docs.ruby-lang.org の Integer#/ を読んだが、小数にする方法がわからなかった
````

（` ```` ` は、中に ` ``` ` を含む文書全体を囲むための書き方です。実際の質問では外側の4つのバッククォートは不要です。）

それぞれの項目が必要な理由も知っておきましょう。

- **目的**：あなたが本当にやりたいことがわかれば、相手は「そもそも別の方法がよい」と提案できます。手段だけを質問すると、遠回りの手段の手伝いをしてしまうことがあります（これを XY 問題と呼びます）。
- **環境**：版によって動きが違うことは、この章で何度も見てきました。
- **実行したコマンドと実際の結果（全文）**：相手が同じことを再現するために必要です。「エラーが出ました」だけでは、何も伝わりません。結果は画像ではなく、テキストで貼ります。テキストなら検索やコピーができます。
- **期待した結果**：「何が問題なのか」は、期待と実際の差でしか表せません。
- **試したこと**：相手が同じ提案を繰り返さずに済みます。また、あなたがどこまで理解しているかも伝わります。

### 質問するときの安全上の注意

質問文には、次のものを絶対に含めないでください。

- パスワード・APIキー・トークン・秘密鍵（`.env` ファイルの中身や、`key.pem` など）
- 実在の人の名前・メールアドレス・住所などの個人情報
- 会社の内部情報（社内のURL、顧客名など）

エラーメッセージやログには、これらが紛れ込んでいることがあります。貼る前に全体を読み、`user1@example.com` のようなダミーに置き換えてください。最小再現を作ると、こうした情報も自然に取り除けます。

### 解決したら

解決したら、何が原因で、どう直したかを返信しましょう。質問に答えてくれた人への礼儀です。同じ問題で困った次の人の助けにもなります。自分の学習メモにも残しておけば、次に同じエラーを見たときに、すぐに思い出せます。

## 実務ではこうなる

実務では、デバッグと調べ物に、コードを書くのと同じくらいの時間を使います。特にジュニアのうちは、その割合がもっと大きくなります。

- **エラー監視**：本番環境で起きた例外は、エラー監視サービスに自動で集められます。そこにはスタックトレースが記録されています。この章の読み方が、そのまま障害調査に使われます（第23章）。
- **他人のコードのデバッグ**：自分が書いていないコードのバグを調べることが多くなります。スタックトレースから「最初に出てくる自社のコード」を探す力が役立ちます。
- **質問の質が評価される**：チームの先輩は、あなたの質問文から、あなたの理解度を読み取ります。必要な情報がそろった質問は、短時間で解決し、信頼にもつながります。
- **調べたことを残す**：解決した問題を、チームの Wiki や Issue に書き残す文化があります。

ジュニアがやりがちな失敗を挙げます。

- エラーメッセージを読まずに、すぐ質問する。または、メッセージの最初の数語だけを見て判断する。
- 「動かないです」とだけ書いて質問する。何をして、何を期待して、何が起きたかがない。
- エラーメッセージを画像で貼る。相手はコピーも検索もできない。
- 動いたからといって、なぜ動いたかを理解しないまま先に進む。同じバグが別の形で再発する。
- デバッグ用の `p` や `binding.irb` を消し忘れてコミットする。
- ログやエラー画面に含まれたトークンや個人情報を、そのまま貼って質問する。

### 演習7-2：バグのあるコードをデバッグで直す

- 次の2つのファイルを、そのまま作ってください。`lib/grade_report.rb` には**3つのバグ**があります。テストファイルは「正しい仕様」です。変更してはいけません。

```ruby
# lib/grade_report.rb
class GradeReport
  PASSING_SCORE = 60

  def initialize(scores)
    @scores = scores
  end

  def average(name)
    list = @scores[name.to_sym]
    list.sum / list.size
  end

  def passed?(name)
    average(name) > PASSING_SCORE
  end

  def top_student
    @scores.keys.max_by { |name| average(name) }
  end
end
```

```ruby
# test/grade_report_test.rb
require_relative "test_helper"
require "grade_report"

class GradeReportTest < Minitest::Test
  def setup
    @report = GradeReport.new(
      "テスト太郎" => [80, 65, 90],
      "テスト花子" => [60, 60, 60],
      "テスト次郎" => [50, 70, 59],
    )
  end

  def test_average
    assert_in_delta 78.33, @report.average("テスト太郎"), 0.01
  end

  def test_passed_when_average_is_exactly_passing_score
    assert @report.passed?("テスト花子")
  end

  def test_not_passed_when_average_is_below_passing_score
    refute @report.passed?("テスト次郎")
  end

  def test_top_student
    assert_equal "テスト太郎", @report.top_student
  end
end
```

- `bundle exec rake test` を実行し、3つのバグを1つずつ直してください。
- バグ1つにつき、`notes.md` に次を書きます。
  - 観察：どのテストが、どんなメッセージで失敗したか
  - 仮説：原因は何だと考えたか
  - 確かめ方：`p` または `binding.irb` で、何を表示して、何がわかったか
  - 修正：何をどう直したか
- 3つのうち少なくとも1つは、`binding.irb` で止めて確かめてください。
- **完了条件**：
  - テストファイルを変えずに、`bundle exec rake test` の結果が `4 runs, 4 assertions, 0 failures, 0 errors, 0 skips` になる。
  - `notes.md` に、3つのバグそれぞれの「観察・仮説・確かめ方・修正」が書かれている。
  - `lib/grade_report.rb` に `p` や `binding.irb` が残っていない。
- ヒント：
  - 最初は4つのテストすべてが Error になります。全部同じ原因かもしれません。スタックトレースの一番上を見比べてください。
  - 1つ直すと、Error が Failure に変わります。これは前進です。
  - `assert_in_delta 期待, 実際, 誤差` は、小数を「誤差の範囲内で等しいか」で比べるアサーションです。小数は計算の誤差が出るので、`assert_equal` では比べにくいのです。
  - `Expected false to be truthy.` は、「真になるはずなのに false だった」という意味です。
  - このコードは、すべてのテストが失敗していてもカバレッジが 100% になります。第6章の「カバレッジは正しさの証明ではない」を、実際に確かめてみてください。

require "json"

class MemberReport

  end

  def names
    @members.map { |member| member[:name] }
  end

  def lines

      "#{number}. #{name.ljust(10)}"
    end
  end
end

**Q6.** 質問するためにエラーログを貼ろうとしたら、`API_TOKEN=abc123...` という行が含まれていました。どうしますか。

### 解答と解説

**A1.** 種類は NoMethodError です。内容は「nil に対して `*`（掛け算）を呼んだが、そのメソッドはない」です。つまり、掛け算の左側が nil でした。場所は `app.rb` の12行目、`price_with_tax` メソッドの中です。次に考えるべきは「なぜその値が nil なのか」です。

**A2.** 一番上は、例外が実際に起きた場所です。一番下は、呼び出しの出発点（多くの場合、最初に実行したファイルの `<main>`）です。下から上へ読むと、どういう順番でメソッドが呼ばれたかがわかります。

**A3.** このエラーは「`end` が足りないまま、ファイルが終わった」という意味です。Ruby はファイルの最後で初めて気づくので、報告される行は最後の行になります。実際の原因は、それより前の `def`・`if`・`do` などに対応する `end` の不足です。インデントを揃えて、始まりと `end` の対応を上から確かめます。

**A4.** 1つ目は、`nil` と空文字、文字列の `"42"` と数値の `42` などを区別して表示できることです。`puts` ではこれらが同じに見えます。2つ目は、`p` が渡した値をそのまま返すので、既存の式の途中に差し込んでも動きが変わらないことです。

**A5.** 例えば次のものが足りません。どの章・演習のことか（該当箇所）。何をしたかったか（目的）。OS・Ruby・Gem の版（環境）。実行したコマンド。期待した結果。実際の結果（エラーメッセージの全文）。試したこと。これでは、答える側は状況を一つも再現できません。

**A6.** その行を削除するか、`API_TOKEN=（伏せ字）` のように置き換えてから貼ります。トークンは秘密の情報なので、質問の場に出してはいけません。もし誤って公開の場に貼ってしまったら、漏えいしたものとして扱い、そのトークンを無効にして作り直します。

## AIの使い方（この章）

エラーの読み方は、AIに「答え」ではなく「読み方」を教わるのに向いた分野です。ただし、AIに丸投げすると、自分でエラーを読む力がいつまでも育ちません。

**推奨する聞き方の例**

- 「次のスタックトレースを、下から上へ、呼び出しの順番として日本語で説明してください。原因の推測や修正方法は書かないでください。（スタックトレースを貼る）」
- 「`nil can't be coerced into Integer` というメッセージの、それぞれの英単語の意味と、Ruby がこのメッセージを出す典型的な状況を教えてください。」
- 「私はこのバグの原因について、次の仮説を立てました。（仮説）。この仮説を確かめるには、どの値を表示すればよいでしょうか。」

**この章でやってはいけない使い方**

- エラーメッセージを貼って「直したコードをください」と頼むこと。直ったとしても、なぜ直ったかがわからなければ、次に同じエラーが出たときにまた困ります。
- 秘密情報や個人情報が含まれたログ・コードを、確認せずに AI に貼ること。人への質問と同じく、貼る前に必ず読み、ダミーに置き換えてください。

## まとめ

エラーメッセージは「種類・内容・場所」の順に読み、スタックトレースは一番上が「倒れた場所」、下が「呼び出しの出発点」です。例外の起きた場所と原因の場所は違うことがあるので、nil などの値の「出どころ」を推理します。デバッグは、仮説を1つ立てて `p`・`pp`・`binding.irb` で確かめることの繰り返しです。調べるときは公式ドキュメントを優先し、質問するときは最小再現とテンプレートの情報をそろえ、秘密情報を取り除きます。

## 用語

| 用語 | 意味 |
|---|---|
| エラーメッセージ | 例外が起きたときに表示される報告。種類・内容・場所が書かれている |
| スタックトレース（バックトレース） | 例外が起きるまでに、どの順番でメソッドが呼ばれたかの一覧 |
| NoMethodError | 存在しないメソッドを呼んだときの例外。nil に対して呼んだ場合が多い |
| SyntaxError | 文法の誤り。実行する前の段階で見つかる |
| デバッグ | バグの原因を見つけて直すこと |
| 仮説と検証 | 原因の候補を1つ決め、それが正しいかを確かめる進め方 |
| p / pp | 値を開発者向けの形で表示するメソッド ／ 入れ子のデータを整形して表示するメソッド |
| binding.irb | プログラムをその場で止め、irb で変数を調べられるようにする命令 |
| デバッガ | プログラムを止めたり1行ずつ進めたりして調べる道具。Ruby 3.1 以降は debug gem が付属する |
| 最小再現 | 問題が起きる状況を、できるだけ短いコードに切り出したもの |
| 公式ドキュメント（リファレンス） | 言語やライブラリの作者側が出している正式な説明書 |
| シグネチャ | メソッドの使い方の形。引数・ブロック・戻り値を表す |
| XY 問題 | 本当の目的（X）ではなく、自分が考えた手段（Y）についてだけ質問してしまうこと |
