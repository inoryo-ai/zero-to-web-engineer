# 第9章 HTML・CSS・JavaScriptの最低限（フォーム中心）

> **この章のゴール**：ブラウザが受け取るHTMLの構造を読み書きでき、フォームがどんなHTTPリクエストになるかを自分の目で確かめて説明できるようになる。
> **目安時間**：読む 3時間 ＋ 演習 4時間
> **前提**：第8章まで

## この章で学ぶこと

- HTMLの要素・属性・入れ子の構造を読み、簡単なページを自分で書ける
- フォームの `action`・`method`・`name` が、送られるHTTPリクエストのどこに現れるかを説明できる
- GETとPOSTの使い分けと、「GETで状態を変えてはいけない」理由を説明できる
- `hidden` の値や入力チェックが「サーバ側では信用できない」理由を説明できる
- CSSのセレクタとボックスモデルの基本を使って、見た目を少し整えられる
- JavaScriptでDOMを操作し、`fetch` でデータを取ってくる最小の流れを説明できる

## ブラウザは何を受け取って、何をしているのか

第8章で、ブラウザがサーバにHTTPリクエストを送り、レスポンスを受け取る流れを学びました。この章では、そのレスポンスの「ボディ」に入っている中身を扱います。

ブラウザが受け取るWebページは、主に3つの言葉でできています。家づくりにたとえると、役割の違いがつかみやすくなります。

| 言葉 | 家でたとえると | 役割 |
| --- | --- | --- |
| HTML | 骨組みと間取り | 「ここは見出し」「ここは入力欄」という構造と意味 |
| CSS | 内装・壁紙・家具の配置 | 色・大きさ・並べ方などの見た目 |
| JavaScript | 電気設備・スイッチ | クリックや入力に反応して、ページを動かす |

ブラウザは、レスポンスの `Content-Type: text/html` を見て「これはHTMLだ」と判断します。そしてHTMLを上から読み、画面を組み立てます。途中で `<link>` や `<script>` を見つけると、CSSやJavaScriptのファイルを取りに、追加のリクエストを送ります。1枚のページを表示するだけで、裏では何回もリクエストが飛んでいるのです。

この教材でHTMLを学ぶ一番の目的は、きれいなページを作ることではありません。**ブラウザとサーバの間で何がやり取りされるかを理解すること**です。第11章では自作サーバからHTMLを返し、第14章ではフォームの値を受け取ります。第10章以降で学ぶXSSやCSRFといった攻撃も、HTMLとフォームの仕組みを知らないと理解できません。この章はその土台です。

## HTMLの基本：タグ・要素・属性

### 最小のHTML文書

まずは、最小限の正しいHTML文書を見てみましょう。

```html
<!DOCTYPE html>
<html lang="ja">
  <head>
    <meta charset="UTF-8">
    <title>はじめてのページ</title>
  </head>
  <body>
    <h1>こんにちは</h1>
    <p>これは<strong>段落</strong>です。</p>
  </body>
</html>
```

1行ずつ見ていきます。

- `<!DOCTYPE html>`：「これは現在のHTMLの書き方で書いた文書です」という宣言です。書かないと、ブラウザが古い互換モードで表示することがあります。
- `<html lang="ja">`：文書全体を包む箱です。`lang="ja"` は「日本語の文書です」という情報で、読み上げソフトなどが使います。
- `<head>`：画面には出ない「文書の情報」を書く場所です。
- `<meta charset="UTF-8">`：文字コードの指定です。文字コードとは、文字をバイト列に変換する規則のことです。これがないと日本語が文字化けすることがあります。
- `<title>`：ブラウザのタブに出る題名です。
- `<body>`：画面に表示される中身を書く場所です。

### タグ・要素・属性

HTMLの部品には名前があります。用語を正確に覚えると、エラーの説明や調べものが楽になります。

```html
<a href="/about" class="nav">会社概要</a>
```

- **タグ**：`<a>` や `</a>` のように、山かっこで囲んだ印です。`<a>` を開始タグ、`</a>` を終了タグといいます。
- **要素**：開始タグから終了タグまでのまとまり全体です。上の例では「`<a ...>会社概要</a>` 全体」が1つのa要素です。
- **属性**：開始タグの中に書く追加情報です。`href="/about"` や `class="nav"` がそうです。`名前="値"` の形で書きます。
- **内容**：開始タグと終了タグの間にあるもの（ここでは「会社概要」）です。

`<meta>` や `<input>`、`<br>` のように、終了タグを持たない要素もあります。これを空要素といいます。

### 入れ子と木構造

要素の中には、さらに要素を入れられます。これを入れ子といいます。

```html
<ul>
  <li>りんご</li>
  <li>みかん</li>
</ul>
```

`ul`（箇条書きの箱）の中に `li`（項目）が2つ入っています。HTML全体は、`html` を根っこにした「木」のような形になります。家系図をイメージしてください。`body` は `html` の子、`ul` は `body` の子、`li` は `ul` の子です。

この木構造は、あとでJavaScriptがページを操作するときの「地図」になります。ブラウザはHTMLを読んで、この木をメモリの中に作ります。これを**DOM**（Document Object Model）といいます。DOMについては後の節で扱います。

入れ子では、閉じる順番が大切です。

```html
<!-- 正しい：後から開いたものを先に閉じる -->
<p>これは<strong>大事</strong>です。</p>

<!-- 間違い：閉じる順番が交差している -->
<p>これは<strong>大事</p></strong>
```

ブラウザは間違ったHTMLでも、できるだけがんばって表示します。そのため、間違いに気づきにくいという難しさがあります。表示が崩れたら、まず閉じ忘れと交差を疑いましょう。

### よく使う要素

最初は、次の要素が読めれば十分です。

| 要素 | 意味 | 例 |
| --- | --- | --- |
| `h1`〜`h6` | 見出し（数字が小さいほど大きな見出し） | `<h1>メモ一覧</h1>` |
| `p` | 段落 | `<p>本文です。</p>` |
| `a` | リンク | `<a href="/memos">一覧へ</a>` |
| `ul` / `ol` / `li` | 箇条書き／番号付きリスト／その項目 | 上の例を参照 |
| `img` | 画像（空要素） | `<img src="/logo.png" alt="ロゴ">` |
| `div` / `span` | 意味を持たない箱（ブロック／行内） | CSSで見た目をつけるときに使う |
| `table` / `tr` / `th` / `td` | 表／行／見出しセル／セル | 一覧画面でよく使う |
| `form` / `input` / `button` | フォームとその部品 | 次の節で詳しく扱う |

`img` の `alt` 属性は、画像が読み込めないときや、目の不自由な人が読み上げソフトを使うときに読まれる代わりの文章です。省略しないようにしましょう。

### リンクとパスの書き方

`href` や `src` に書く場所の指定を**パス**といいます。書き方は3種類あります。

| 書き方 | 例 | 意味 |
| --- | --- | --- |
| 絶対URL | `https://example.com/about` | どこから見ても同じ場所 |
| ルートからのパス | `/about` | 同じサーバの、一番上から数えた場所 |
| 相対パス | `about.html`、`../index.html` | 今いるページの場所から数えた場所 |

`../` は「1つ上のフォルダ」という意味です。第1章のターミナルの `cd ..` と同じ考え方です。この `../` は、第10章と第11章で学ぶ「パストラバーサル」という攻撃で悪用されます。今のうちに意味をしっかり覚えておきましょう。

### 特別な意味を持つ文字

HTMLでは `<` と `>` がタグの印です。では、本文に「1 < 2」と書きたいときはどうするのでしょうか。

```html
<p>1 &lt; 2 であり、A &amp; B です。</p>
```

`&lt;` は `<` を、`&amp;` は `&` を表します。これを**文字参照**といいます。特別な意味を持つ文字を、ただの文字として表示させるための書き方です。

これはセキュリティの話にも直結します。もし利用者が入力した `<script>` という文字列を、そのままHTMLに埋め込んだらどうなるでしょうか。ブラウザはそれを「ただの文字」ではなく「タグ」として扱ってしまいます。これがXSSという攻撃の入口です。第10章で考え方を、第14章で対策の実装を学びます。

### 開発者ツールで中身を見る

ブラウザには、ページの中身を調べる**開発者ツール**がついています。ChromeやEdgeならページ上で右クリックして「検証」、Safariは設定で「開発」メニューを有効にしてから使います。

よく使うタブは3つです。

- **Elements（要素）**：今のDOMの木構造が見られます。その場で書き換えることもできます。
- **Console（コンソール）**：JavaScriptのエラーが表示されます。コードを試しに実行することもできます。
- **Network（ネットワーク）**：ページが送ったリクエストと、返ってきたレスポンスの一覧です。第8章で学んだヘッダもここで見られます。

「表示がおかしい」「ボタンを押しても何も起きない」と思ったら、まず開発者ツールを開く習慣をつけましょう。

## フォーム：ブラウザからサーバへデータを送る仕組み

ここからがこの章の中心です。Webアプリの大部分は「利用者が何かを入力して、サーバに送る」という操作でできています。ログイン、検索、投稿、削除。その入口がフォームです。

### フォームの基本形

```html
<form action="/memos" method="post">
  <label for="title">タイトル</label>
  <input type="text" id="title" name="title">

  <label for="body">本文</label>
  <textarea id="body" name="body"></textarea>

  <button type="submit">保存する</button>
</form>
```

このフォームの「保存する」を押すと、ブラウザは次のことをします。

1. `form` の中にある、`name` 属性を持つ入力欄を集める
2. `name=値` の組を `&` でつないで、1本の文字列にする
3. `method` で指定された方法（ここではPOST）で、`action` で指定された場所（`/memos`）にリクエストを送る

属性の意味を整理します。

| 属性 | どこに書くか | 意味 |
| --- | --- | --- |
| `action` | `form` | 送り先のパス。省略すると今のページのURLに送る |
| `method` | `form` | `get` か `post`。省略すると `get` |
| `name` | 入力欄 | サーバに送るときの「項目名」 |
| `id` | 入力欄 | ページの中での目印。`label` の `for` と結びつける |
| `type` | `input` / `button` | 入力欄の種類やボタンの役割 |

### name属性がないと送られない

ここは初心者がとてもつまずきやすいところです。`id` と `name` は似ていますが、役割がまったく違います。

- `id`：ページの中だけで使う目印です。CSSやJavaScript、`label` が使います。**サーバには送られません。**
- `name`：サーバに送るときの項目名です。**`name` がない入力欄は、送信されません。**

「入力したはずの値がサーバに届かない」という不具合の原因は、たいてい `name` の付け忘れか、つづりの違いです。

### 送信されるデータの形を見る

実際にどんなリクエストが送られるのでしょうか。ここでは「受け取ったものを画面にそのまま出すだけ」の道具で観察します。`nc`（netcat）というコマンドを使います。`nc` は、指定したポートで待ち受けて、届いたバイト列をそのまま表示する道具です。

サーバの代わりに `nc` を、自分のPCの中だけ（`127.0.0.1`）で待ち受けさせます。

```bash
nc -l 127.0.0.1 3000
```

別のターミナルで、待受先を確認します。この確認は第10章で詳しく学ぶ安全ルールの1つです。

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
```

```
COMMAND  PID   USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
nc      5017 you       3u  IPv4 0x3605a6b25444db45      0t0  TCP 127.0.0.1:3000 (LISTEN)
```

`NAME` の列が `127.0.0.1:3000` になっていれば、自分のPCの中からしか接続できません。

この状態で、上のフォームと同じ内容を `curl` で送ってみます。`--data-urlencode` は、フォームと同じ形式に変換して送るオプションです。

```bash
curl --data-urlencode 'title=テスト' --data-urlencode 'body=こんにちは 世界' http://127.0.0.1:3000/memos
```

`nc` の画面には、次のように表示されました。

```
POST /memos HTTP/1.1
Host: 127.0.0.1:3000
User-Agent: curl/8.7.1
Accept: */*
Content-Length: 103
Content-Type: application/x-www-form-urlencoded

title=%E3%83%86%E3%82%B9%E3%83%88&body=%E3%81%93%E3%82%93%E3%81%AB%E3%81%A1%E3%81%AF+%E4%B8%96%E7%95%8C
```

`nc` は返事をしないので、`curl` はしばらく待ってからエラーで終わります。観察が目的なので問題ありません。`nc` 側は `Ctrl-C` で止めます。

読み取れることを整理します。

- 1行目は第8章で学んだ**リクエスト行**です。メソッドがPOST、パスが `/memos` です。
- `Content-Type: application/x-www-form-urlencoded` は「フォームの標準形式で送ります」という意味です。
- 空行のあとが**ボディ**です。`title=...&body=...` の形で、`name` と値が並んでいます。
- 日本語は `%E3%83%86` のような形に変換されています。これを**パーセントエンコーディング**といいます。URLやフォームのデータでは使える文字が限られるので、それ以外の文字をバイトごとに `%` と16進数で表します。
- 空白は `+` になっています。フォームの形式では、空白を `+` で表す決まりです。

Rubyでこの文字列を元に戻すと、次のようになります。

```ruby
require "uri"
p URI.decode_www_form("name=%E3%83%86%E3%82%B9%E3%83%88%E5%A4%AA%E9%83%8E&age=20&memo=a+b%26c")
```

```
[["name", "テスト太郎"], ["age", "20"], ["memo", "a b&c"]]
```

`%26` は `&` です。値の中の `&` は区切りと混ざらないように、変換されて送られます。第14章では、この変換を自分のフレームワークで行います。

ブラウザから送った場合も、形は同じです。ただし `User-Agent` などのヘッダがもっと増えます。演習9-2で、実際にブラウザから送って確かめます。

### GETとPOSTの違い

`method="get"` にすると、同じデータがボディではなくURLの後ろにつきます。

```bash
curl -G --data-urlencode 'q=テスト 太郎' http://127.0.0.1:3000/search
```

```
GET /search?q=%e3%83%86%e3%82%b9%e3%83%88+%e5%a4%aa%e9%83%8e HTTP/1.1
Host: 127.0.0.1:3000
User-Agent: curl/8.7.1
Accept: */*
```

`?` より後ろの部分を**クエリ文字列**といいます。ボディはありません。

zshでは、URLに `?` を含むときは必ずシングルクォートで囲んでください。囲まないと `no matches found` というエラーになります。zshが `?` を「任意の1文字」というファイル名の記号として解釈するためです。

2つの違いをまとめます。

| 観点 | GET | POST |
| --- | --- | --- |
| データの場所 | URLのクエリ文字列 | リクエストのボディ |
| URLに残るか | 残る（履歴・ブックマーク・ログ） | 残らない |
| 用途 | 情報を**読む**（検索・一覧・表示） | 状態を**変える**（作成・更新・削除） |
| 同じリクエストを何度送ってよいか | よい（結果が変わらないのが原則） | 注意が必要（二重投稿など） |

一番大切なルールは、**「GETで状態を変えてはいけない」**です。理由は3つあります。

1. **URLはあちこちに残る**：ブラウザの履歴、サーバのログ、共有したリンクに残ります。パスワードなどを含めると漏れます。
2. **GETは勝手に送られることがある**：ブラウザの先読み機能や、検索エンジンの巡回プログラムはリンクを次々とたどります。`<a href="/memos/1/delete">` のようなリンクがあると、誰もクリックしていないのに削除が起きるかもしれません。
3. **他のサイトから簡単に送らせられる**：`<img src="http://127.0.0.1:3000/memos/1/delete">` と書いたページを開くだけで、ブラウザはそのURLにGETを送ります。これはCSRFという攻撃の一種です。POSTにすれば安全になるわけではありませんが、GETで状態を変えると防ぎようがなくなります。CSRFは第10章で考え方を、第17章で対策の実装を学びます。

### 入力欄の種類

`input` の `type` を変えると、いろいろな入力欄になります。

```html
<input type="text" name="title">
<input type="password" name="password">
<input type="email" name="email">
<input type="number" name="age" min="0">
<input type="checkbox" name="pinned" value="1">
<input type="radio" name="color" value="red"> 赤
<input type="radio" name="color" value="blue"> 青
<select name="category">
  <option value="work">仕事</option>
  <option value="private">個人</option>
</select>
```

ここでつまずきやすい点が2つあります。

- **チェックボックスは、チェックしていないと何も送られません。** `pinned=0` が送られるのではなく、`pinned` という項目そのものがなくなります。サーバ側では「項目がない＝チェックなし」と解釈する必要があります。
- **`type="password"` は画面で隠すだけです。** 暗号化はされません。通信を守るのはHTTPS（第13章）の役目です。

### hidden：見えないけれど、書き換えられる

`type="hidden"` は、画面に表示されない入力欄です。

```html
<form action="/memos/3" method="post">
  <input type="hidden" name="_method" value="delete">
  <button type="submit">削除</button>
</form>
```

画面には「削除」ボタンしか見えません。しかし送信すると、`_method=delete` も一緒に送られます。hiddenは「利用者に入力させる必要はないが、サーバに一緒に送りたい値」に使います。

HTMLのフォームは、GETとPOSTしか送れません。そこで多くのフレームワークは、上の例のように hidden で「本当はDELETEのつもり」と伝える工夫をしています。Railsもこの方法を使います。第14章と第18章で再び出てきます。

**ここで必ず覚えてほしいことがあります。hiddenの値は、利用者が自由に書き換えられます。** 開発者ツールのElementsタブで `value` をダブルクリックすれば、すぐに変えられます。`curl` を使えば、フォームを使わずに好きな値を送ることもできます。

たとえば、次のようなフォームは危険です。

```html
<!-- 悪い例：値段をhiddenで送っている -->
<input type="hidden" name="price" value="1000">
```

利用者が `price` を `1` に書き換えれば、1円で買えてしまいます。サーバは値段を自分のデータベースから調べるべきです。

一般化すると、こうなります。**ブラウザから届いたものは、すべて利用者が自由に作れる。だからサーバは、届いた値を信用せずに確かめる。** この考え方は、この教材のセキュリティの話すべての出発点です。

### ブラウザの入力チェックは「親切」であって「防御」ではない

HTMLには、入力内容をチェックする属性があります。

```html
<input type="text" name="title" required maxlength="50">
```

`required` は「空欄では送信させない」、`maxlength` は「50文字まで」という意味です。ブラウザは条件を満たさないと送信を止めて、メッセージを出します。

これは利用者にとって便利です。しかし、hiddenと同じ理由で防御にはなりません。開発者ツールで属性を消せますし、`curl` ならそもそもチェックを通りません。**入力チェックは、必ずサーバ側でも行います。** ブラウザ側のチェックは「間違いに早く気づかせる親切」と考えてください。サーバ側の入力チェックは第16章で実装します。

### labelと使いやすさ

`label` の `for` 属性に入力欄の `id` を書くと、2つが結びつきます。ラベルの文字をクリックすると入力欄が選ばれ、読み上げソフトも「タイトル、入力欄」と読んでくれます。誰でも使えるページにするための基本なので、フォームには必ずlabelをつけましょう。

## CSSの最低限

この教材ではCSSを深くは扱いません。チームでは、デザイン担当や専用の仕組みがあることが多いからです。ただし、読めないと困る場面は多いので、最低限の文法を押さえます。

### ルールの書き方

```css
/* style.css */
h1 {
  color: #333333;
  font-size: 24px;
}

.error {
  color: #b00020;
}

#title {
  width: 100%;
}
```

CSSは「**どれに**（セレクタ）」「**何を**（プロパティ）」「**どうする**（値）」の組み合わせです。

| セレクタ | 意味 | HTML側の書き方 |
| --- | --- | --- |
| `h1` | すべてのh1要素 | `<h1>` |
| `.error` | `class="error"` を持つ要素 | `<p class="error">` |
| `#title` | `id="title"` の要素 | `<input id="title">` |
| `form input` | form の中にある input | 入れ子の関係 |

実務では、見た目のためには主に `class` を使います。`id` はページに1つしか置けないので、使い回しがききにくいためです。

HTMLからCSSファイルを読み込むには、`head` の中に次のように書きます。

```html
<link rel="stylesheet" href="/style.css">
```

ブラウザはこの行を見つけると、`/style.css` を取りに追加のGETリクエストを送ります。第11章で静的ファイルを配信するサーバを作ると、このリクエストが自分のサーバに届く様子を見られます。

### 同じ要素に複数のルールが当たったら

同じ要素に、矛盾するルールが複数当たることがあります。そのときは、おおむね次の順で強さが決まります。

1. より具体的なセレクタが勝つ（`#id` ＞ `.class` ＞ 要素名）
2. 具体さが同じなら、後に書いたほうが勝つ

「CSSを書いたのに効かない」ときは、開発者ツールのElementsで要素を選んでください。右側のStylesに、当たっているルールと、打ち消されたルール（取り消し線つき）が表示されます。ここを読むのが一番の近道です。

### ボックスモデル

CSSでは、すべての要素を「箱」として扱います。箱は内側から順に4層でできています。

- **content**：中身（文字や画像）
- **padding**：中身と枠線の間の余白（内側の余白）
- **border**：枠線
- **margin**：枠線の外側の余白（隣の箱との距離）

封筒に入れた手紙にたとえると、手紙がcontent、手紙の周りのすき間がpadding、封筒がborder、隣の封筒との間隔がmarginです。開発者ツールのElementsタブの下のほうに、この4層の図が数値つきで表示されます。

### 横に並べる：flexbox

要素を横に並べたいときは、親の箱に `display: flex` を指定するのが基本です。

```css
.form-row {
  display: flex;
  gap: 8px;
  align-items: center;
}
```

`gap` は子どうしの間隔、`align-items: center` は縦方向の中央揃えです。最初はこれだけ覚えれば、フォームの1行を整えるには十分です。

## JavaScriptの最低限：DOMとfetch

JavaScriptは、ブラウザの中で動くプログラミング言語です。Rubyとは別の言語ですが、変数・条件分岐・関数といった考え方は共通です。この章では「ページを書き換える」「サーバからデータを取ってくる」の2つだけを扱います。

### scriptの読み込み

```html
<script src="/app.js" defer></script>
```

`defer` は「HTMLを全部読み終わってから実行する」という指定です。これがないと、まだ存在しない要素を探してエラーになることがあります。

JavaScriptのエラーは画面には出ません。**必ず開発者ツールのConsoleに出ます。** 「何も起きない」と思ったら、まずConsoleを見てください。

### DOMを操作する

先ほど、ブラウザはHTMLを木構造（DOM）にすると説明しました。JavaScriptはこの木を読んだり書き換えたりできます。

```html
<textarea id="body" name="body"></textarea>
<p>残り <span id="remaining">140</span> 文字</p>
<script>
  const body = document.querySelector("#body");
  const remaining = document.querySelector("#remaining");

  body.addEventListener("input", () => {
    remaining.textContent = String(140 - body.value.length);
  });
</script>
```

1行ずつ見ていきます。

- `document.querySelector("#body")`：CSSと同じセレクタで、要素を1つ探します。
- `const`：Rubyの変数のようなものです。`const` は再代入しない変数を作ります。
- `addEventListener("input", ...)`：「入力があるたびに、この処理を実行して」と登録します。クリックなら `"click"`、フォーム送信なら `"submit"` です。このように「何かが起きたら呼ばれる処理」を**イベントハンドラ**といいます。
- `() => { ... }`：JavaScriptの関数の書き方の1つです。Rubyのブロックに近いものです。
- `textContent`：要素の中の文字を書き換えます。

### textContent と innerHTML

要素の中身を書き換える方法には、`textContent` と `innerHTML` があります。

- `textContent`：入れた値を**ただの文字**として表示します。
- `innerHTML`：入れた値を**HTMLとして解釈**します。

利用者が入力した値を表示するときは、必ず `textContent` を使ってください。`innerHTML` に `<img src=x onerror=...>` のような文字列を入れると、それがタグとして解釈され、中のプログラムが動いてしまいます。これは、先ほど文字参照の節で触れたXSSと同じ問題です。「データとして扱うべきものを、命令（HTML）として扱ってしまう」ことが原因です。

### fetchでサーバと通信する

`fetch` は、JavaScriptからHTTPリクエストを送る機能です。ページ全体を読み直さずに、一部だけを更新したいときに使います。

```javascript
async function loadMessage() {
  const response = await fetch("/data.json");
  if (!response.ok) {
    console.error("取得に失敗しました", response.status);
    return;
  }
  const data = await response.json();
  document.querySelector("#message").textContent = data.message;
}

loadMessage();
```

- `fetch("/data.json")`：`/data.json` にGETリクエストを送ります。
- `await`：通信が終わるまで待ちます。通信には時間がかかるので、「待つ」と明示する必要があります。`await` を使う関数には `async` をつけます。ここは最初は難しいところです。「通信の結果を使う前には `await` をつける」とだけ覚えておけば十分です。
- `response.ok`：ステータスコードが200番台なら `true` です。`fetch` は404や500でもエラーにはならないので、自分で確かめる必要があります。
- `response.json()`：ボディをJSONとして解釈します。JSONはデータをやり取りするための書式で、第21章で詳しく扱います。

`fetch` でPOSTを送ることもできます。

```javascript
await fetch("/memos", {
  method: "POST",
  headers: { "Content-Type": "application/x-www-form-urlencoded" },
  body: new URLSearchParams({ title: "テスト", body: "本文" }),
});
```

`URLSearchParams` は、フォームと同じ `title=...&body=...` の形を作ってくれます。つまり、サーバから見ればフォームから送られたものと区別がつきません。ここでも「届いた値はすべて信用しない」が大切です。

### fetchを試すときの注意

`fetch` を使うページは、ファイルをダブルクリックして開く（URLが `file://` で始まる）と、うまく動きません。ブラウザが安全のため、ファイルから開いたページの通信を制限しているからです。

ブラウザには**同一オリジンポリシー**という仕組みがあります。オリジンとは「スキーム（http/https）・ホスト・ポート」の組です。あるオリジンのページから、別のオリジンのデータを自由に読むことは原則できません。この仕組みは第19章と第21章で詳しく扱います。

そのため、`fetch` を試すときは、小さなWebサーバからページを配信します。Rubyには、フォルダの中身をそのまま配信する機能があります。

```bash
ruby -run -e httpd -- --bind-address=127.0.0.1 --port=8000 .
```

`--bind-address=127.0.0.1` は必ずつけてください。省略すると、同じWi-Fiにいる他人からも接続できる状態になることがあります。起動したら、別のターミナルで待受先を確認します。

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

```
COMMAND  PID   USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
ruby    5497 you       9u  IPv4 0x9a08f526a99a1fe6      0t0  TCP 127.0.0.1:8000 (LISTEN)
```

Ruby 3.0以降では、この機能に必要なWEBrickが標準で入っていません。`cannot load such file -- webrick` と出たら、先に `gem install webrick` を実行してください。Windowsの人はWSLのターミナルで同じコマンドを使えます。WSLでは `lsof` の代わりに `ss -ltn` で確認できます。

## 実務ではこうなる

実務では、HTMLを1から手で書くことは減っています。Railsのビュー（第18章）や、ReactなどのJavaScriptの仕組みが、HTMLを組み立ててくれるからです。それでも、この章の知識は毎日のように使います。

- **不具合調査の第一歩は開発者ツール**です。「保存ボタンを押しても保存されない」と言われたら、Networkタブで送信内容を見ます。`name` が違う、値が空、ステータスが422、などがすぐにわかります。
- **フォームの `name` は、サーバ側のコードとの約束**です。Railsでは `memo[title]` のような名前になり、サーバ側でその形を前提に値を取り出します。片方だけ変えると壊れます。
- **セキュリティレビューでよく指摘される点**は、この章の内容そのものです。GETで削除できる、hiddenの値を信用している、`innerHTML` に入力値を入れている、などです。

ジュニアがやりがちな失敗も挙げておきます。

- `id` だけつけて `name` を忘れ、「値が届かない」と半日悩む。
- ブラウザ側の `required` だけで入力チェックを済ませ、`curl` から空の値を送られる。
- 削除リンクを `<a href="/items/1/delete">` で作り、GETで削除してしまう。
- JavaScriptが動かない原因を、Consoleを見ずに推測で探し続ける。

演習は `~/workspace/ch09-html/` で行います。最初に作っておきましょう。

```bash
mkdir -p ~/workspace/ch09-html
cd ~/workspace/ch09-html
```

### 演習9-1：自己紹介ページを書く

- `profile.html` を作り、次を含む自己紹介ページを書きます。名前は実名でなく「テスト太郎」のようなダミーにします。
  - `<!DOCTYPE html>`、`lang="ja"`、`<meta charset="UTF-8">`、`<title>`
  - `h1` を1つ、`h2` を2つ以上
  - `ul` か `ol` のリスト
  - 同じフォルダの別ファイル（`hobby.html`）への相対パスのリンクと、`hobby.html` から戻るリンク
  - 本文のどこかに「1 < 2 & 3 > 2」という文字列を、文字参照を使って正しく表示する
- ブラウザでファイルを開き、表示とリンクの行き来を確かめます。
- **完了条件**：
  - ブラウザで「1 < 2 & 3 > 2」がそのまま表示される
  - [W3CのHTMLチェッカー](https://validator.w3.org/#validate_by_input) の「Validate by Direct Input」に `profile.html` の中身を貼り、Errorが0件になる。Warningは残ってもよい
- ヒント：チェッカーのエラーは、行番号と英語の説明が出ます。第7章のエラーの読み方を思い出してください。

### 演習9-2：フォームが送るリクエストを観察する

- `form.html` に、メモを作るフォームを書きます。`action="http://127.0.0.1:3000/memos"`、`method="post"` とし、`title`（text）、`body`（textarea）、`pinned`（checkbox）を入れます。
- 1つ目のターミナルで `nc -l 127.0.0.1 3000` を起動し、2つ目のターミナルで `lsof -nP -iTCP:3000 -sTCP:LISTEN` を実行して、待受先を確かめます。
- ブラウザで `form.html` を開き、日本語と空白を含む値を入れて送信します。`nc` の画面に出たリクエストを `notes.md` に貼ります。ブラウザ側は応答待ちのままエラーになりますが、それで正常です。
- `method="get"` に変えて、同じことをもう一度行います。
- 観察が終わったら、`nc` を `Ctrl-C` で止めます。
- **完了条件**：
  - `lsof` の出力で `NAME` が `127.0.0.1:3000` だったことを `notes.md` に記録している
  - `notes.md` にPOSTとGETのリクエストが貼られ、「データがどこにあるか」「`Content-Type` があるかないか」「空白が何に変わったか」の3点を自分の言葉で書いている
- ヒント：Linuxや WSL で `nc -l 127.0.0.1 3000` がエラーになる場合は、`nc` の種類が違います。`sudo apt install netcat-openbsd` で入れ直してください。

### 演習9-3：送られないもの・書き換えられるもの

- 演習9-2のフォームを使い、次の3つを試して、それぞれ `nc` に届いた内容を `notes.md` に記録します。
  1. `pinned` のチェックを外して送る
  2. `body` の `textarea` から `name` 属性を消して送る
  3. `<input type="hidden" name="user_id" value="1">` を追加する。開発者ツールのElementsタブで `value` を `999` に書き換えてから送る
- **完了条件**：`notes.md` に3つの結果が貼られ、それぞれについて「サーバ側で何に気をつけるべきか」を1〜2文で書いている
- ヒント：3つ目の結果から、「hiddenの値でログイン中の利用者を判断してよいか」を考えてみてください。

### 演習9-4：CSSで見た目を整える

- `style.css` を作り、`form.html` から `<link>` で読み込みます。
- 次の見た目にします。
  - ラベルと入力欄を `display: flex` で横に並べる（1行ずつ）
  - 入力欄に `padding` を `8px` つける
  - `class="note"` をつけた注意書きの文字色を変える
- **完了条件**：
  - 開発者ツールで入力欄を選ぶと、ボックスモデルの図で padding が上下左右 8 と表示される
  - `.note` のルールが Styles に表示され、取り消し線がついていない
- ヒント：効かないときは、セレクタのつづりと、`<link>` の `href` のパスを確認します。Networkタブで `style.css` が200で読み込まれているかも見ましょう。

### 演習9-5：JavaScriptで残り文字数を表示する

- `form.html` の `body` 欄の下に「残り N 文字」を表示します。上限は100文字とします。

- **完了条件**：
  - 文字を打つたびに表示が変わり、101文字目で赤字になる
  - 開発者ツールのConsoleにエラーが1件も出ていない
  - 表示の書き換えに `innerHTML` を使っていない
- ヒント：`class` の切り替えには `element.classList.toggle("名前", 条件)` が使えます。調べ方は第7章を参考にしてください。

### 演習9-6（発展）：fetchでJSONを読み込む

- `data.json` に `{"message": "こんにちは", "count": 3}` と書きます。
- `fetch.html` を作り、ボタンを押すと `/data.json` を取得して、`message` を画面に表示します。
- `ruby -run -e httpd -- --bind-address=127.0.0.1 --port=8000 .` でフォルダを配信し、`http://127.0.0.1:8000/fetch.html` を開いて確かめます。
- 終わったらサーバを `Ctrl-C` で止め、もう一度 `lsof -nP -iTCP:8000 -sTCP:LISTEN` を実行して、何も表示されないことを確かめます。
- **完了条件**：
  - 起動中の `lsof` の出力が `127.0.0.1:8000` で、停止後は何も表示されない

- ヒント：`response.ok` を確かめる部分を忘れると、3つ目の条件を満たせません。

## 確認クイズ

**Q1.** `<input id="email" type="email">` と書いたフォームを送信したが、サーバに `email` の値が届かない。原因は何か。

**Q2.** 検索フォームをGET、メモの削除フォームをPOSTにした。この使い分けの理由を2つ挙げよ。

**Q3.** 商品の購入フォームで、値段を `<input type="hidden" name="price" value="1000">` で送っている。何が問題か。

**Q4.** 入力欄に `required maxlength="50"` をつけたので、サーバ側で長さを確かめる必要はない。正しいか。

**Q5.** 利用者が入力したニックネームを、JavaScriptで画面に表示したい。`innerHTML` と `textContent` のどちらを使うべきか。理由も答えよ。

### 解答と解説

1. **`name` 属性がないから。** サーバに送られるのは `name` を持つ入力欄だけです。`id` はページの中の目印で、送信には使われません。`name="email"` を追加します。
2. **例：(1) GETはURLが履歴やログに残り、先読みや巡回でも勝手に送られるので、状態を変える操作に向かない。(2) 検索は同じ条件で何度送っても結果が変わらず、URLを共有・ブックマークできると便利だから。** 他のサイトから `<img>` などでGETを送らせられる、という点（CSRF）を挙げても正解です。
3. **利用者がhiddenの値を書き換えられる。** 開発者ツールや `curl` で `price=1` にして送れます。値段のように信用が必要な値は、サーバが自分のデータから決めます。
4. **正しくない。** ブラウザのチェックは開発者ツールで外せますし、`curl` ではそもそも行われません。ブラウザ側のチェックは利用者への親切で、防御はサーバ側で行います。
5. **`textContent`。** `innerHTML` は値をHTMLとして解釈するので、ニックネームに仕込まれたタグやプログラムが動いてしまいます（XSS）。`textContent` は、ただの文字として表示します。

## AIの使い方（この章）

推奨する聞き方の例です。

- 「次のHTMLを、入れ子の構造がわかるように木の形で説明してください。私が書いたものなので、修正案ではなく解説だけをお願いします。」
- 「`nc` で観察したら、空白が `+` になっていました。`%20` になる場合との違いを、初心者向けに説明してください。」
- 「hiddenの値を信用してはいけない理由について、私の理解を書きます。間違いや抜けがあれば指摘してください。」

この章でやってはいけない使い方です。

- 演習のHTML・CSS・JavaScriptを丸ごと書かせること。この章の目的は、自分で書いて、ブラウザでの見え方とリクエストの形を体で覚えることです。
- AIが出したコードを、`innerHTML` かどうかなどを確かめずに貼ること。AIは `innerHTML` を使った例をよく出します。入力値を扱う部分は必ず自分で読んでください。

## まとめ

HTMLは要素の入れ子でできた木構造で、ブラウザはそれをDOMとして持ちます。フォームは `name` のついた入力欄を集め、GETならクエリ文字列に、POSTならボディに入れて送ります。hiddenの値やブラウザの入力チェックは、利用者がいくらでも変えられます。だからサーバは届いた値を信用しません。CSSとJavaScriptは最低限を押さえ、困ったら開発者ツールを開きます。

## 用語

| 用語 | 意味 |
| --- | --- |
| HTML | Webページの構造と意味を書く言葉 |
| 要素 | 開始タグから終了タグまでのまとまり |
| 属性 | 開始タグに書く追加情報。`名前="値"` の形 |
| DOM | ブラウザがHTMLから作る木構造。JavaScriptで操作できる |
| 文字参照 | `&lt;` のように、特別な文字をただの文字として書く方法 |
| 開発者ツール | ブラウザについている、ページの中身や通信を調べる道具 |
| フォーム | 入力欄を集めてサーバに送る仕組み（`form` 要素） |
| name属性 | フォーム送信時の項目名。ないと送られない |
| クエリ文字列 | URLの `?` より後ろの部分。GETフォームの値が入る |
| パーセントエンコーディング | URLやフォームで使えない文字を `%E3` のような形で表す方法 |
| hidden | 画面に出ない入力欄。利用者が書き換えられる |
| CSS | 見た目を指定する言葉 |
| セレクタ | CSSで「どの要素に当てるか」を指定する部分 |
| ボックスモデル | 要素を content・padding・border・margin の箱として扱う考え方 |
| fetch | JavaScriptからHTTPリクエストを送る機能 |
