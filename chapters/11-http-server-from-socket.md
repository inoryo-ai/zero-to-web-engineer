# 第11章 SocketでHTTPサーバを作る（元教材 Phase 1）

> **この章のゴール**：Rubyの標準ライブラリ（Socket）だけで、`127.0.0.1` で待ち受けるHTTPサーバを作り、ブラウザにHTMLを表示する。静的ファイルを配信し、パストラバーサルを拒否するテストを通す。
> **目安時間**：読む 3時間 ＋ 演習 10時間
> **前提**：第10章まで

## この章で学ぶこと

- `TCPServer` で `127.0.0.1` に待ち受け、`lsof` で待受先を確かめられる
- HTTPリクエストをヘッダの終わりまで読み、リクエスト行からメソッドとパスを取り出せる
- CRLF・`Content-Length`・`Connection: close` を使って、ブラウザが表示できるレスポンスを組み立てられる
- パスによって返す内容を変える「ルーティング」の原型を、テスト駆動で作れる
- 公開フォルダのファイルを配信し、パストラバーサル攻撃を拒否するテストを書いて通せる
- 自分のサーバが「HTTPのどの部分を実装していて、どこを実装していないか」を説明できる

## この章で作るもの

これまでの章で、HTTPはテキストの約束ごとだと学びました（第8章）。ブラウザはその約束に従ってリクエストを送り、レスポンスのHTMLを画面にします（第9章）。この章では、その「レスポンスを返す側」を、自分の手で一から作ります。

使うのは、Rubyに最初から入っている `socket` ライブラリだけです。WEBrickやRackのような、HTTPを代わりに処理してくれる部品は使いません。フレームワークを使えば数行で済むことを、あえて自分で書きます。

なぜ遠回りをするのでしょうか。この教材の元になった研修には、「抽象を降りて、また登る」という考え方があります。Railsは便利ですが、中で何が起きているかが見えません。一番下の層まで降りて、自分で組み立てた経験があると、後でRailsを使うときに「この1行の裏で何が起きているか」を想像できるようになります。不具合の原因を追うときに、この差がはっきり出ます。

### 作る範囲を決めておく

HTTP/1.1の仕様はとても大きいものです。この章では、次の範囲に絞ります。

| 実装する | 実装しない |
| --- | --- |
| `127.0.0.1` でのTCP接続の受け付け | 外部への公開、HTTPS（第13章） |
| ヘッダの終わり（空行）までの受信 | リクエストボディの受信（第14章） |
| ボディのないGETリクエスト | POSTなど他のメソッドの本格対応 |
| 長さの決まったレスポンスと `Connection: close` | 接続の再利用（keep-alive）、chunked転送 |
| 1つの接続で1つのリクエスト | 複数の接続の同時処理（第13章） |
| パスによる分岐と404 | 異常な入力の厳密な検証 |
| 公開フォルダからの静的ファイル配信 | 本番で必要な各種の上限・タイムアウト |

これは学習のための**部分的な実装**です。HTTP/1.1の仕様すべてに従うものではなく、本番で使うこともできません。第10章で作った記録用紙の5つの領域は、この章の終わりでもほとんどが「未実装」のままです。それで正しいのです。

### 作業フォルダの構成

この章の作業は `~/workspace/ch11-http-server/` で行います。第13章以降でこのコードを引き継ぐので、Gitで管理してください。最終的に、次のような構成になります。

```
ch11-http-server/
├── .gitignore
├── server.rb            # 起動の入口。ソケットを扱う部分だけを書く
├── lib/
│   ├── mini_http.rb     # リクエスト行の解析、レスポンスの組み立て
│   ├── router.rb        # パスによる分岐
│   └── static_files.rb  # 静的ファイルの場所を決める（パストラバーサル対策）
├── public/              # 配信してよいファイルだけを置く
└── test/
    ├── mini_http_test.rb
    ├── router_test.rb
    └── static_files_test.rb
```

ファイル名やメソッド名は、この章で説明に使う「おすすめの名前」です。自分で変えてもかまいません。ただし、`server.rb` に全部を詰め込むのは避けてください。理由は「テストしやすい形に分ける」の節で説明します。

## 安全の確認：この章で必ず守ること

第10章のルールを、この章に当てはめて確認します。

- サーバは必ず `TCPServer.new("127.0.0.1", 3000)` のように、**ホストを明示して**待ち受けます。ホストを省略したり、`"0.0.0.0"` を書いたりしてはいけません。
- 起動するたびに、別のターミナルで `lsof -nP -iTCP:3000 -sTCP:LISTEN` を実行し、`NAME` が `127.0.0.1:3000` であることを確かめます。WSLでは `ss -ltn` を使います。
- 作業が終わったら `Ctrl-C` でサーバを止め、もう一度 `lsof` を実行して何も表示されないことを確かめます。
- `public/` には、配信してよいダミーのファイルだけを置きます。ソースコード・`.git`・秘密鍵は、必ず `public/` の外に置きます。

## ステップ0：既存のサーバと会話してみる

自分でサーバを作る前に、既存のサーバに自分でリクエストを送ってみます。ブラウザが裏でしていることを、手で再現するのです。この体験が「自分のサーバは何を受け取り、何を返せばよいか」を考える土台になります。

### 観察用のサーバを起動する

観察用のフォルダを作り、その中だけを配信するサーバを起動します。

```bash
cd ~/workspace/ch11-http-server
mkdir -p http-observation
printf '%s' '<h1>Hello HTTP</h1>' > http-observation/index.html
ruby -run -e httpd -- --bind-address=127.0.0.1 --port=3000 http-observation
```

`printf '%s'` を使うのは、ファイルの最後に改行を入れないためです。こうすると本文がちょうど19バイトになり、後で `Content-Length` と見比べやすくなります。Ruby 3.0以降で `webrick` が見つからないと言われたら、`gem install webrick` を先に実行してください。

このターミナルはサーバを動かしたままにします。別のターミナルを開いて、待受先を確認します。

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
```

```
COMMAND  PID   USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
ruby    7138 you       9u  IPv4 0x7468445d70d81891      0t0  TCP 127.0.0.1:3000 (LISTEN)
```

### 自分でリクエストを組み立てて送る

次のコマンドは、Rubyで小さな「クライアント」を作り、HTTPリクエストを1つ送って、返事をそのまま表示するものです。サーバではありません。

```bash
ruby -rsocket -e 'TCPSocket.open("127.0.0.1", 3000) { |socket| socket.write("GET / HTTP/1.1\r\nHost: localhost:3000\r\nConnection: close\r\n\r\n"); print socket.read }'
```

送っている文字列を見やすく書き直すと、次のようになります。

```
GET / HTTP/1.1
Host: localhost:3000
Connection: close

```

ここで大切なのは、目に見えない改行です。HTTP/1.1では、各行の終わりは `\r\n` という2バイトです。これを**CRLF**といいます。CRは「行の先頭に戻る」、LFは「次の行に進む」という、タイプライター時代の名残の文字です。最後のヘッダ行の後に、もう1つ `\r\n` を送ります。この「空行」が「ヘッダはここまで」という合図になります。

`Host` ヘッダは、HTTP/1.1では必須です。`Connection: close` は「この返事が終わったら接続を切ってください」というお願いです。

返ってきたレスポンスは次のとおりです。

```
HTTP/1.1 200 OK
Etag: 65927-13-6abe1afd
Content-Type: text/html
Content-Length: 19
Last-Modified: Thu, 01 Oct 2026 08:34:05 GMT
Server: WEBrick/1.4.4 (Ruby/2.6.10/2022-04-12)
Date: Thu, 01 Oct 2026 08:34:07 GMT
Connection: close

<h1>Hello HTTP</h1>
```

ヘッダの種類や順番は、WEBrickの版によって違います。次の4つの部分を探してください。

- **ステータス行**：`HTTP/1.1 200 OK`。HTTPの版と、処理の結果です。
- **ヘッダ**：本文の種類（`Content-Type`）、本文のバイト数（`Content-Length`）、接続を閉じる指定（`Connection`）などです。
- **空行**：ヘッダの終わりの印です。本文全体の終わりではありません。
- **ボディ**：今回は19バイトのHTMLです。

### いろいろ変えて観察する

上のコマンドの文字列を書き換えて、何度か送ってみましょう。

1. `GET /` を `GET /missing` に変える。作っていないファイルなので、`HTTP/1.1 404 Not Found` が返ります。
2. `Host: localhost:3000\r\n` を消す。HTTP/1.1の仕様では `400 Bad Request` を返すべきですが、この観察用サーバは `200 OK` を返しました。**「動いた」ことと「仕様どおり」であることは別**だと覚えておいてください。
3. 最後の `\r\n\r\n` を `\r\n` 1つに減らす。サーバは「まだヘッダが続く」と思って待ち続けるので、返事が来ません。`Ctrl-C` で止めます。

観察が終わったら、サーバのターミナルで `Ctrl-C` を押して止めます。`lsof` で何も表示されないことを確かめてから、次へ進みます。

## Socketの基本：電話の受付窓口

ここからは、サーバ側を作るための道具を学びます。

**ソケット**は、プログラム同士が通信するための「受話器」のようなものです。サーバ側では、次の3段階で使います。会社の代表電話の受付にたとえて説明します。

| 段階 | 電話でたとえると | Rubyでは |
| --- | --- | --- |
| 1. 待ち受ける | 代表番号の受付窓口を開ける | `TCPServer.new("127.0.0.1", 3000)` |
| 2. 接続を受け付ける | 鳴った電話の受話器を取る | `server.accept` |
| 3. 話して、切る | 用件を聞き、答え、受話器を置く | `client.gets` / `client.write` / `client.close` |

それぞれのメソッドの意味は次のとおりです。

- `TCPServer.new("127.0.0.1", 3000)`：`127.0.0.1` の3000番ポートで待ち受けを始めます。返ってくるのは「窓口」のオブジェクトです。
- `server.accept`：誰かが接続してくるまで、**そこで止まって待ちます**。接続が来ると、その相手と話すための「通話中の受話器」（ソケット）を返します。
- `client.gets`：相手から1行（改行まで）受け取ります。まだ届いていなければ、届くまで待ちます。
- `client.write(文字列)`：相手に文字列を送ります。
- `client.close`：通話を終えます。

窓口（`server`）と受話器（`client`）は別のものです。窓口は開けたまま、電話が来るたびに新しい受話器を取ります。1件の電話が終わったら、また次の電話を待つ。これを繰り返すのがサーバの基本形です。この「繰り返し」をどう書くかは、演習で考えてください。

### つまずきやすいエラー

すでに3000番ポートを使っているプログラムがあると、次のエラーになります。

```
-e:1:in `initialize': Address already in use - bind(2) for "127.0.0.1" port 3000 (Errno::EADDRINUSE)
```

前に起動したサーバを止め忘れていることがほとんどです。`lsof -nP -iTCP:3000` で使っているプログラムの `PID`（プロセス番号）を調べ、そのターミナルで `Ctrl-C` を押すか、`kill PID` で止めます。

## リクエストを受け取る

接続を受け付けたら、リクエストを読みます。実際にブラウザや `curl` から届くリクエストを、1行ずつ表示してみると次のようになります。これは `curl -s 'http://localhost:3000/hello?name=x'` を送ったときに、サーバ側で受け取った行を `p` で表示したものです。

```
"GET /hello?name=x HTTP/1.1\r\n"
"Host: localhost:3000\r\n"
"User-Agent: curl/8.7.1\r\n"
"Accept: */*\r\n"
```

`p` で表示すると、行の終わりの `\r\n` が見えます。最後に `"\r\n"` だけの行（空行）が届いたら、ヘッダは終わりです。

### なぜ `read` ではなく `gets` なのか

ステップ0のクライアントでは、`socket.read` でレスポンスを読みました。`read` は「相手が接続を閉じるまで、全部読む」メソッドです。

サーバ側でリクエストを `read` で読もうとすると、困ったことが起きます。ブラウザや `curl` は、リクエストを送った後も接続を開いたまま、返事を待っています。サーバは「接続が閉じるまで読む」、クライアントは「返事が来るまで待つ」。お互いが相手を待つので、永遠に進みません。

だから、サーバは**空行が来るまで1行ずつ読む**必要があります。HTTPがわざわざ「空行でヘッダの終わりを示す」という約束をしているのは、このためです。

### TCPは「行」を運んでいるわけではない

ここは少し難しい話です。TCPは、バイトの列を順番どおりに届ける仕組みです。「1行」や「1リクエスト」という区切りは知りません。送った側が1回で書いたものが、受け取る側では2回に分かれて届くこともあります。逆に、複数の行がまとめて届くこともあります。

`gets` は、Rubyが内部でバイトをためておき、改行が来た時点で1行として返してくれます。だから、届き方がばらばらでも正しく読めます。区切りを決めるのは、いつも受け取る側の責任です。HTTPではCRLF・空行・`Content-Length` が、その区切りの目印になります。

### 受け取ったら何も返さないとどうなるか

リクエストを読むだけで、何も返さずに接続を閉じると、`curl` は次のように表示して終わります。

```
curl: (52) Empty reply from server
```

「サーバにはつながったが、HTTPの返事がなかった」という意味です。演習11-1で、この状態を一度確かめます。

## リクエスト行を解析する

最初の1行を**リクエスト行**といいます。ここから、メソッド・パス・HTTPの版を取り出します。

```ruby
p "GET /about HTTP/1.1\r\n".chomp.split(" ", 3)
```

```
["GET", "/about", "HTTP/1.1"]
```

`chomp` は行の終わりの改行（`\r\n` を含む）を取り除きます。`split(" ", 3)` は空白で区切り、最大3つに分けます。

パスにクエリ文字列がついていることもあります。

```ruby
p "GET /about?x=1 HTTP/1.1\r\n".split(" ")
```

```
["GET", "/about?x=1", "HTTP/1.1"]
```

ルーティングでは `?` より前の部分（パス）を使い、`?` より後ろ（クエリ文字列）は別に取っておきます。どう分けるかは、演習で考えてください。第9章で学んだ `URI.decode_www_form` を使うと、クエリ文字列を `name` と値の組に戻せます。

### 想定外の行が来たら

リクエスト行は、いつも正しい形で届くとは限りません。空の行、要素が2つしかない行、とても長い行。第10章で学んだとおり、外から来たものは誰でも自由に作れます。

形がおかしいときは、`400 Bad Request` を返すのが基本です。解析するメソッドは、おかしな行を受け取ったら `nil` を返す、と決めておくと扱いやすくなります。この章では厳密な検証は対象外ですが、「おかしな行で例外が起きてサーバが止まる」ことだけは避けましょう。

## レスポンスを組み立てる

ブラウザに「Hello World」と表示させるには、次のレスポンスを返します。

```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 20
Connection: close

<h1>Hello World</h1>
```

表示の都合で普通の改行に見えますが、ステータス行と各ヘッダ行の終わりは、すべて `\r\n` です。最後のヘッダの後にもう1つ `\r\n` を書き、その後に本文を書きます。

### Content-Length はバイト数

`Content-Length` は、本文の長さを**バイト数**で表します。文字数ではありません。

```ruby
s = "こんにちは"
p s.length
p s.bytesize
p "<h1>Hello World</h1>".bytesize
p "<h1>Not Found</h1>".bytesize
```

```
5
15
20
18
```

UTF-8では、日本語の1文字はたいてい3バイトです。`length` は文字数なので、日本語を含む本文で `length` を使うと、`Content-Length` が実際より小さくなります。するとブラウザは、指定されたバイト数だけ読んで残りを捨ててしまい、本文の後ろが切れて表示されます。**Rubyでは必ず `bytesize` を使います。**

逆に `Content-Length` が実際より大きいと、ブラウザは足りない分を待ち続けます。どちらの場合も、エラーが出ずに「なんとなくおかしい」ように見えるので、気づきにくい不具合です。

### 接続を閉じる

`Connection: close` は「この返事が終わったら接続を閉じます」という宣言です。宣言したら、本文を書き終えた後に本当に `close` します。ヘッダに書くだけでは、接続は閉じません。

HTTP/1.1は、本来は1つの接続を何度も使い回す（keep-alive）のが基本です。使い回すには、どこまでが1つのレスポンスかを正確に伝え、次のリクエストを読む処理が必要になります。この章では簡単にするため、1つの接続で1つのリクエストだけを扱います。

### 完成したときの見え方

演習11-2を終えると、`curl -i` の出力は次のようになります。`-i` はヘッダも表示するオプションです。

```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 20
Connection: close

<h1>Hello World</h1>
```

存在しないパスでは、次のようになります。

```
HTTP/1.1 404 Not Found
Content-Type: text/html
Content-Length: 18
Connection: close

<h1>Not Found</h1>
```

## テストしやすい形に分ける

ここで設計の話をします。サーバのコードを `server.rb` 1つに全部書くと、テストがとても書きにくくなります。テストのたびにサーバを起動して、ソケットで接続しなければならないからです。

そこで、コードを2つに分けます。

- **ソケットを扱う部分**（`server.rb`）：待ち受け、受け付け、読む、書く、閉じる。ここは薄く保ちます。
- **文字列を扱う部分**（`lib/` の中）：リクエスト行の解析、ルーティング、レスポンスの組み立て、ファイルの場所の決定。ここは「文字列を受け取って、文字列や値を返す」だけのメソッドにします。

後者はソケットを使わないので、第6章で学んだMinitestで簡単にテストできます。料理にたとえると、ガスコンロ（ソケット）と、レシピ（文字列の処理）を分けるようなものです。レシピは紙の上で確かめられますが、コンロは実際に火をつけないと確かめられません。確かめにくい部分をできるだけ小さくするのが、テストしやすい設計のこつです。

### TDDで進める

この章の実装は、第6章で学んだTDD（テスト駆動開発）で進めます。

1. **RED**：まだ存在しない機能のテストを書き、失敗することを確かめる
2. **GREEN**：テストが通る最小限のコードを書く
3. **REFACTOR**：テストが通ったまま、コードを読みやすく整える

たとえば、リクエスト行の解析なら、最初のテストは次のようになります。

```ruby
# test/mini_http_test.rb
require "minitest/autorun"
require_relative "../lib/mini_http"

class MiniHTTPTest < Minitest::Test
  def test_parses_method_and_path
    result = MiniHTTP.parse_request_line("GET /about HTTP/1.1\r\n")
    assert_equal "GET", result[:method]
    assert_equal "/about", result[:path]
  end
end
```

`lib/mini_http.rb` に空の `module MiniHTTP; end` だけを書いて実行すると、次のように失敗します。これがREDです。

```
  1) Error:
MiniHTTPTest#test_parses_method_and_path:
NoMethodError: undefined method `parse_request_line' for MiniHTTP:Module
    test/mini_http_test.rb:6:in `test_parses_method_and_path'

1 runs, 0 assertions, 0 failures, 1 errors, 0 skips
```

第6章の `test_helper.rb` を使う場合は、1行目の `require "minitest/autorun"` を `require "test_helper"` に置き換えます。

エラーの内容が「まだメソッドがない」という、予想どおりの理由であることを確かめてください。予想と違う理由で失敗しているなら、テストのほうが間違っています。

テストファイルが増えたら、第6章と同じように `Gemfile`・`Rakefile`・`test/test_helper.rb` を用意し、まとめて実行します。第6章の `~/workspace/ch06-testing/` からコピーして使ってかまいません。

```bash
bundle exec rake test
```

Rakefileを用意する前に、とりあえずまとめて動かしたいときは、次のコマンドでも実行できます。

```bash
ruby -e 'Dir["test/*_test.rb"].each { |f| require "./" + f }'
```

## ルーティングの原型

パスによって返す内容を変えることを**ルーティング**といいます。駅の案内係が、行き先を聞いて「何番線へ」と教えるようなものです。

最初は、次の表のとおりに分岐させます。

| パス | ステータス | 本文 |
| --- | --- | --- |
| `/` | 200 OK | `<h1>Hello World</h1>` |
| `/about` | 200 OK | `<h1>About Page</h1>` |
| `/hello?name=Ota` | 200 OK | `<h1>Hello Ota</h1>` |
| その他 | 404 Not Found | `<h1>Not Found</h1>` |

最初は `if` や `case` で書いてかまいません。テストが通ったら、REFACTORの段階で「パスと処理の対応表」をHashにまとめられないか考えてみてください。第14章でフレームワークを作るとき、この対応表が「ルーター」という部品に育ちます。

### クエリの値をHTMLに入れるときの注意

`/hello?name=Ota` で `Hello Ota` と返す機能は、第10章で学んだXSSの入口そのものです。`/hello?name=<script>...</script>` と送られたら、そのままHTMLに埋め込んではいけません。`CGI.escapeHTML` でエスケープしてから埋め込みます。

XSS対策の本格的な実装は第14章で行います。ただ、ここでも「`<` を含む名前を送ると `&lt;` になって返る」テストを1つ書いておきましょう。たった1行の対策ですが、テストがあれば将来うっかり消しても気づけます。

### GET以外のメソッドが来たら

この章のサーバはGETだけを扱います。POSTなどが来たときは、`405 Method Not Allowed` を返すのが仕様に沿った返し方です。余裕があれば、ルーティングのテストに加えてみてください。

## 静的ファイルを配信する

いよいよ、HTMLを文字列で書く代わりに、ファイルから読んで返します。CSSや画像のように、中身が変わらないファイルを**静的ファイル**といいます。第9章で作ったHTMLやCSSを `public/` に置けば、自分のサーバから配信できるようになります。

### 基本の考え方

リクエストのパスが `/css/style.css` なら、`public/css/style.css` を読んで返します。そのとき、次の点に気をつけます。

- **ファイルはバイト列として読む**：画像などは文字ではありません。`File.binread` を使うと、ファイルをそのままのバイト列で読めます。
- **`Content-Type` を拡張子で決める**：ブラウザは `Content-Type` を見て、中身の扱い方を決めます。少なくとも次の表の分は対応しましょう。

| 拡張子 | Content-Type |
| --- | --- |
| `.html` | `text/html; charset=utf-8` |
| `.css` | `text/css; charset=utf-8` |
| `.js` | `text/javascript; charset=utf-8` |
| `.json` | `application/json` |
| `.png` | `image/png` |
| `.jpg` / `.jpeg` | `image/jpeg` |
| それ以外 | `application/octet-stream`（中身のわからないバイト列） |

- **`Content-Length` はバイト数**：`File.binread` で読んだものの `bytesize` を使います。
- **ディレクトリが指定されたら**：`/` や `/docs/` のようにディレクトリが指定されたら、その中の `index.html` を返すのが一般的です。なければ404にします。

## パストラバーサル対策：この章で一番大事なところ

第10章で学んだとおり、静的ファイルの配信には**パストラバーサル**という危険があります。リクエストのパスに `../` を入れて、`public/` の外のファイルを読み出す攻撃です。`public/` の外には、ソースコードも `.git` もあります。読まれてよいものは1つもありません。

ここは正直に言って、難しいところです。「`..` が含まれていたら断る」という単純な対策では、すり抜けられる書き方がたくさんあります。ひとつずつ、なぜ単純な方法ではだめなのかを見ていきましょう。

### 落とし穴1：先頭の `/` と `File.expand_path`

リクエストのパスは、必ず `/` から始まります。`File.expand_path(パス, 基準のフォルダ)` という使い方をすると、先頭が `/` のパスでは基準のフォルダが無視されます。

```ruby
p File.expand_path("/../../etc/passwd", "/Users/you/workspace/public")
p File.expand_path("../../etc/passwd", "/Users/you/workspace/public")
```

```
"/etc/passwd"
"/Users/you/etc/passwd"
```

1つ目は、基準のフォルダを無視して `/etc/passwd` そのものを指しています。公開フォルダとつなげるには、まず `File.join` でつなげてから、`File.expand_path` で `..` を解決します。

```ruby
root = "/Users/you/workspace/public"
joined = File.join(root, "/../../etc/passwd")
p joined
p File.expand_path(joined)
```

```
"/Users/you/workspace/public/../../etc/passwd"
"/Users/you/etc/passwd"
```

これで「最終的にどこを指すか」がわかります。結果は `public` の外なので、断る必要があります。

### 落とし穴2：エンコードされた `../`

第9章で学んだパーセントエンコーディングを使うと、`../` は `%2e%2e%2f` とも書けます。

```ruby
require "uri"
p URI.decode_www_form_component("%2e%2e%2f")
p URI.decode_www_form_component("%252e%252e%252f")
p URI.decode_www_form_component(URI.decode_www_form_component("%252e%252e%252f"))
```

```
"../"
"%2e%2e%2f"
"../"
```

`..` の検査をデコードの**前**に行うと、`%2e%2e%2f` は検査をすり抜け、その後のデコードで `../` に化けます。3つ目のように、2回デコードすると、2重にエンコードした `%252e` も `../` になります。

対策は、**デコードはちょうど1回だけ行い、デコードした後のパスで場所を決めて検査する**ことです。検査した後にもう一度デコードしてはいけません。

また、デコードできない不正な書き方もあります。

```ruby
require "uri"
begin
  URI.decode_www_form_component("%zz")
rescue ArgumentError => e
  p e.message
end
```

```
"invalid %-encoding (%zz)"
```

例外が起きたままにすると、サーバが止まります。不正なエンコーディングは `400 Bad Request` などで断ります。

### 落とし穴3：文字列の前方一致と、似た名前のフォルダ

「最終的なパスが、公開フォルダのパスで始まっていればOK」という検査を考えます。一見よさそうですが、穴があります。

```ruby
p File.expand_path("../public-other/secret.txt", "/Users/you/workspace/public").start_with?("/Users/you/workspace/public")
```

```
true
```

`/Users/you/workspace/public-other/secret.txt` は `public` の外です。しかし、文字列としては `/Users/you/workspace/public` で始まっているので、検査を通ってしまいます。

対策は、**パスの区切りの境界まで含めて確かめる**ことです。「公開フォルダそのものと等しい」か、「公開フォルダのパスの後ろに `/` をつけたもので始まる」かを調べます。

### 落とし穴4：シンボリックリンク

**シンボリックリンク**は、別の場所にあるファイルを指す「ショートカット」です。`public/` の中に、`public/` の外を指すシンボリックリンクがあると、パスの文字列は `public/` の中なのに、実際に読まれるのは外のファイルになります。

`File.expand_path` は、文字列の上で `..` を解決するだけで、シンボリックリンクはたどりません。実際のファイルの場所を知るには `File.realpath` を使います。`File.realpath` は、ファイルが存在しないと例外を起こすので、先に存在を確かめるか、例外を受け止めて404にします。

macOSでは、ここにもう1つ罠があります。

```ruby
p File.realpath("/tmp")
```

```
"/private/tmp"
```

`/tmp` 自体がシンボリックリンクなのです。テストで一時フォルダを公開フォルダにすると、公開フォルダ側は `/var/folders/...`、ファイル側は `/private/var/folders/...` となり、正しいファイルまで「外」と判定されることがあります。**比べる両方を `File.realpath` でそろえる**のがこつです。

### 落とし穴5：特殊な文字

パスに NUL文字（`\0`、`%00`）が入ると、Rubyのファイル操作は例外を起こします。

```
-e:1:in `exist?': path name contains null byte (ArgumentError)
```

また、Windowsでは `\` もパスの区切りとして扱われます。NUL文字や `\` を含むパスは、先に断ってしまうのが安全です。

### 対策の手順をまとめる

コードは自分で書いてほしいので、手順だけを示します。

1. リクエストのパス（クエリ文字列を除いたもの）を、**1回だけ**デコードする。不正なエンコーディングなら断る
2. NUL文字や `\` を含んでいたら断る
3. 公開フォルダを `File.realpath` で実際の場所にしておく
4. 公開フォルダとパスを `File.join` でつなぎ、`File.expand_path` で `..` を解決する
5. その場所にファイルがなければ404にする。あれば `File.realpath` でシンボリックリンクも解決する
6. 結果が「公開フォルダそのもの」か「公開フォルダ + `/` で始まる」場所かを確かめる。違えば断る

この6つの手順を担当するのが `StaticFiles.resolve(root, request_path)` です。範囲内なら実際のファイルのパスを、だめなら `nil` を返す、という形にするとテストしやすくなります。

### 断るときの返し方

断るときは、`403 Forbidden` か `404 Not Found` を返します。どちらを選ぶかは自分で決めてかまいません。ただし、**エラーの本文に実際のパスや例外の内容を入れてはいけません。** `/Users/you/workspace/...` のような本物のパスが見えると、攻撃者にフォルダの構造を教えることになります。

本番のサーバでは、「そもそも存在を教えない」ために404で統一することもよくあります。

### テストで攻撃が失敗することを示す

この章の完了条件は、**攻撃が失敗するテストが通ること**です。テストでは、一時フォルダの中に次のような構成を作ります。本物の大事なファイルは使いません。

```
（一時フォルダ）/
├── public/
│   ├── index.html
│   ├── docs/a.html
│   └── link.txt  → ../secret.txt を指すシンボリックリンク
├── secret.txt         # 中身は "dummy-secret"
└── public-other/x.txt # 似た名前の隣のフォルダ
```

一時フォルダは `require "tmpdir"` して `Dir.mktmpdir` で作れます。テストの `setup` で作り、`teardown` で `FileUtils.remove_entry` を使って消します。シンボリックリンクは `File.symlink(元, リンクの場所)` で作れます。

テストの1つは、たとえば次のようになります。

```ruby
def test_rejects_dot_dot
  assert_nil StaticFiles.resolve(@root, "/../secret.txt")
end
```

演習11-3で、必要なテストの一覧を示します。

### ブラウザや curl は `../` を消してしまう

実際に `curl` で攻撃を試すときには、注意があります。

```bash
curl 'http://127.0.0.1:3000/../secret.txt'
```

このように送っても、`curl` は親切に `../` を解決して、`GET /secret.txt` を送ってしまいます。ブラウザも同じです。`../` をそのまま送るには、`--path-as-is` をつけます。

```bash
curl -i --path-as-is 'http://127.0.0.1:3000/../secret.txt'
```

このとき、実際にサーバに届くリクエスト行は `GET /../secret.txt HTTP/1.1` です。攻撃者はブラウザを使うとは限りません。**「ブラウザでは送れないから大丈夫」は理由になりません。** `%2e%2e/` のようにエンコードしたものは、`curl` もそのまま送ります。

## HTTP/2・HTTP/3との違い

この章で作ったのは、HTTP/1.1の一部です。今のWebでは、HTTP/2やHTTP/3も広く使われています。

| 版 | 通信上の形 |
| --- | --- |
| HTTP/1.1 | 開始行とヘッダがテキスト。TCPの上で直接やり取りする |
| HTTP/2 | TCPの上で、バイナリの「フレーム」でやり取りする |
| HTTP/3 | QUIC（UDPの上で動き、暗号化を組み込んだ仕組み）の上で、バイナリのフレームでやり取りする |

メソッド・ステータス・ヘッダといった「意味」は共通ですが、通信上のバイトの並びはまったく違います。ブラウザの開発者ツールで見えるヘッダの表示は、実際のバイト列そのままではない、ということも覚えておいてください。HTTP全体を「ただのテキスト通信」だと思い込まないことが大切です。

## 実務ではこうなる

実務で、ソケットからHTTPサーバを書くことはまずありません。Pumaなどの実績あるサーバと、Railsのようなフレームワークを使います。それでも、この章の経験は次のような場面で役に立ちます。

- **不具合の切り分け**：「日本語のときだけ表示が切れる」と聞いて、`Content-Length` と `bytesize` を思い浮かべられます。「応答が返ってこない」と聞いて、改行や接続の終わり方を疑えます。
- **ログやエラーを読む力**：`Errno::EADDRINUSE` や `Empty reply from server` のようなメッセージが、何を意味するかがわかります。
- **セキュリティレビュー**：ファイルのダウンロード機能や、画像のアップロード機能のレビューでは、パストラバーサルの観点が必ず出てきます。Railsを使っていても、`params[:filename]` をそのまま `File.read` に渡すようなコードは、この章と同じ問題を起こします。

ジュニアがやりがちな失敗です。

- `Content-Length` に `length` を使い、英語のテストでは動くのに日本語で壊れる。
- `include?("..")` だけで対策したつもりになり、エンコードされたパスですり抜けられる。
- エラーの本文に例外のメッセージをそのまま返し、サーバのフォルダ構成を漏らす。
- サーバを止め忘れ、次に起動したときに `Address already in use` で悩む。

### 演習11-1：TCPサーバを立ち上げ、届いたリクエストを観察する

- 本文の「ステップ0」を行い、観察用サーバとの会話の結果を `notes.md` に記録します。
- `server.rb` を作り、次を満たすプログラムを書きます。

  - 接続を受け付け、ヘッダの終わりの空行まで1行ずつ読み、各行を `p` でターミナルに表示する

  - 停止後の `lsof` が何も表示しない

### 演習11-2：TDDで Hello World・404・ルーティングを作る

- 次のメソッドを、TDD（RED → GREEN → REFACTOR）で作ります。名前は変えてもかまいません。
  - `MiniHTTP.parse_request_line(line)`：メソッド・パス・クエリ文字列・HTTPの版を返す。形のおかしい行には `nil` を返す
  - `MiniHTTP.build_response(status, body, content_type)`：ステータス行・`Content-Type`・`Content-Length`・`Connection: close`・空行・本文をCRLFでつないだ文字列を返す
  - `Router.route(method, path, query)`：本文の「ルーティングの原型」の表のとおりに、ステータスと本文を返す
- 少なくとも、次のテストを書いて通します。
  - `GET /about HTTP/1.1` から、メソッド `GET` とパス `/about` が取れる
  - `GET /hello?name=Ota HTTP/1.1` から、パス `/hello` とクエリ文字列 `name=Ota` が取れる
  - 空文字列や `GET` だけの行では `nil` が返る
  - `build_response` の結果で、ヘッダの各行が `\r\n` で終わり、ヘッダと本文の間が `\r\n\r\n` になっている
  - 本文が `"こんにちは"` のとき、`Content-Length: 15` になる
  - `/` は200と `<h1>Hello World</h1>`、`/about` は200と `<h1>About Page</h1>`、`/nope` は404と `<h1>Not Found</h1>`
  - `/hello` に `name=Ota` で `<h1>Hello Ota</h1>`、`name=<b>x</b>` で本文に `<b>` が含まれず `&lt;b&gt;` が含まれる
- 最後に `server.rb` から3つのメソッドを使い、本物のレスポンスを返すようにします。形のおかしいリクエスト行には400を返します。
- **完了条件**：
  - `bundle exec rake test` が `0 failures, 0 errors` で終わる
  - サーバ起動中の `lsof` が `127.0.0.1:3000` を示す
  - `curl -i http://localhost:3000/` と `curl -i http://localhost:3000/nope` の出力が、本文「完成したときの見え方」と同じ形になる
  - ブラウザで `http://localhost:3000/hello?name=テスト` を開くと「Hello テスト」と表示される
- ヒント：RED のとき、失敗の理由が予想どおりかを毎回確かめてください。`build_response` のテストでは、`assert_includes` や `start_with?` を使うと、ヘッダの順番に縛られないテストが書けます。

### 演習11-3：静的ファイルを配信し、パストラバーサルを拒否する

- `public/` に `index.html`・`style.css`・小さな画像（自分で作ったダミーのPNGなど）を置きます。`index.html` からCSSと画像を読み込みます。
- `StaticFiles.resolve(root, request_path)` をTDDで作ります。範囲内なら実際のファイルの絶対パスを、そうでなければ `nil` を返します。
- テストでは、本文の「テストで攻撃が失敗することを示す」の構成を一時フォルダに作り、少なくとも次のテストを書いて通します。
  - `/docs/a.html` は、`public/docs/a.html` の実際のパスを返す
  - `/../secret.txt` は `nil`
  - `/%2e%2e%2fsecret.txt` は `nil`
  - `/%252e%252e%252fsecret.txt`（2重エンコード）は `nil`
  - `/../public-other/x.txt`（似た名前の隣のフォルダ）は `nil`
  - `/link.txt`（外を指すシンボリックリンク）は `nil`
  - `/%zz`（不正なエンコーディング）は例外を起こさずに `nil`
  - `/missing.html`（存在しないファイル）は `nil`
- 拡張子から `Content-Type` を決めるメソッドもテストつきで作り、`server.rb` に組み込みます。ルーティングの表にないパスは静的ファイルとして探し、見つからなければ404を返します。
- **完了条件**：
  - すべてのテストが `0 failures, 0 errors` で通り、上の8つのテストが含まれている
  - ブラウザで `http://localhost:3000/index.html` を開くと、CSSが効き、画像が表示される。開発者ツールのNetworkタブで、CSSと画像が200で、正しい `Content-Type` で返っている
  - `~/workspace/ch11-http-server/secret.txt` を作って中身を `dummy-secret` にし、`curl -i --path-as-is 'http://127.0.0.1:3000/../secret.txt'` と `curl -i 'http://127.0.0.1:3000/%2e%2e/secret.txt'` を実行する。どちらも403か404が返り、本文に `dummy-secret` も実際のフォルダのパスも含まれない
  - サーバ起動中の `lsof` が `127.0.0.1:3000` を示し、停止後は何も表示しない
- ヒント：`setup` で作った公開フォルダのパスと、`resolve` が返すパスを比べるときは、期待値も `File.realpath` でそろえます。macOSで「正しいファイルなのに `nil` になる」なら、本文の「落とし穴4」を読み直してください。

### 演習11-4（発展）：ディレクトリ一覧と、本物の通信を使うテスト

- `/docs/` のようにディレクトリが指定され、`index.html` がないときに、中のファイルの一覧をHTMLで返します。次を満たしてください。
  - ファイル名はHTMLエスケープして表示する（`<b>.txt` という名前のファイルを作って確かめる）
  - リンクのパスは、パスの要素ごとにURLエンコードする
  - パストラバーサルの対策は、演習11-3と同じ `resolve` を通す
- サーバを起動して本物のソケットで確かめる「結合テスト」を1つ書きます。テストの中でサーバを別のスレッドで起動し、`TCPSocket` で接続して、レスポンスの1行目が `HTTP/1.1 200 OK` であることを確かめます。
- 第10章で作った `security-record.md` を更新し、5つの領域それぞれの状態と根拠を書きます。
- **完了条件**：
  - ディレクトリ一覧のテストで、`<b>.txt` が `&lt;b&gt;.txt` として出力されることを確かめている
  - 結合テストが通り、テストの中でも待受ホストが `127.0.0.1` である
  - `security-record.md` の5つの領域に、「状態」と「根拠」が書かれ、コミットされている
- ヒント：結合テストでは、ポート番号に `0` を指定すると、OSが空いているポートを選んでくれます。選ばれたポートは `server.addr[1]` で取れます。こうすると、開発中のサーバとテストがぶつかりません。

## 確認クイズ

**Q1.** サーバで、リクエストを `client.read` で読もうとしたところ、`curl` もサーバも止まったまま動かなくなった。なぜか。

**Q2.** 本文を `"<h1>こんにちは</h1>"` に変えたら、ブラウザで表示の後ろが切れた。何が原因と考えられるか。

**Q3.** パストラバーサル対策として「デコードした後のパスに `..` が含まれていたら断る」だけにした。どんな問題が残るか。1つ以上挙げよ。

**Q4.** 「最終的なパスが `/Users/you/workspace/public` で始まっているか」を `start_with?` で調べた。何がすり抜けるか。どう直すか。

**Q5.** `curl 'http://127.0.0.1:3000/../secret.txt'` を試したら、秘密のファイルは返ってこなかった。これで対策ができていると言えるか。

### 解答と解説

1. **お互いが相手を待っているから。** `read` は相手が接続を閉じるまで読みます。`curl` はリクエストを送った後も、返事を待って接続を開いたままです。HTTPでは空行がヘッダの終わりの合図なので、`gets` で空行まで読みます。
2. **`Content-Length` を文字数（`length`）で計算している可能性が高い。** 日本語はUTF-8で1文字3バイトほどなので、文字数ではバイト数より小さくなります。ブラウザは `Content-Length` の分だけ読んで残りを捨てます。`bytesize` を使います。
3. **例：シンボリックリンクで外を指すファイルは、`..` を含まずに外を読める。** `..` を含む正当なファイル名（`a..b.txt` など）も誤って断ってしまいます。最終的な場所を求めてから、範囲内かを確かめる方法が確実です。
4. **`/Users/you/workspace/public-other/...` のような、似た名前の隣のフォルダがすり抜ける。** 「公開フォルダと等しい」か「公開フォルダ + `/` で始まる」かを調べ、パスの区切りの境界まで確かめます。
5. **言えない。** `curl` は `../` を自分で解決して、`/secret.txt` を送っています。サーバには攻撃が届いていません。`--path-as-is` をつけるか、`%2e%2e/` のようにエンコードして送り、さらにテストで確かめます。

## AIの使い方（この章）

推奨する聞き方の例です。

- 「`TCPServer#accept` が何を返すのか、`server` と `client` の違いを、電話の受付のたとえで説明してください。コードは書かないでください。」
- 「パストラバーサルのテストとして、次の8つを考えました。抜けている攻撃パターンがあれば、パターンの名前と、なぜ危ないかだけを教えてください。」
- 「次のテストが失敗します。エラーメッセージの意味を説明してください。修正コードではなく、どこを調べればよいかのヒントがほしいです。」

この章でやってはいけない使い方です。

- `server.rb` や `StaticFiles.resolve` をAIに書かせること。この章の価値は、自分で手を動かし、つまずき、理由を理解することにあります。特にパストラバーサル対策は、AIが出すコードにも穴があることがよくあります。自分で理解していないと、その穴に気づけません。
- AIの出したコードに、ホストの指定がない `TCPServer.new(3000)` や `"0.0.0.0"` が含まれていても、そのまま使うこと。待受先は必ず自分で `lsof` で確かめます。

## まとめ

TCPServer で `127.0.0.1` に待ち受け、空行までリクエストを読み、CRLFと `bytesize` で計算した `Content-Length` をつけて返し、接続を閉じる。これがHTTPサーバの最小の形です。ソケットを扱う部分を薄くし、文字列の処理を分けると、TDDで確かめながら作れます。静的ファイル配信では、デコード・正規化・シンボリックリンク・境界の確認を経て、範囲外を断ります。攻撃が失敗するテストがあって初めて、対策ができたと言えます。

さらに深く：元教材の [Phase 1](https://github.com/speee/training-web-app/blob/main/phase-1.md) には、HTTP/1.1のメッセージの区切りについての仕様（RFC 9112）へのリンクがあります。

## 用語

| 用語 | 意味 |
| --- | --- |
| ソケット | プログラム同士が通信するための受話器のようなもの |
| TCPServer | Rubyで、指定したアドレスとポートで待ち受けるためのクラス |
| accept | 待ち受けている窓口に来た接続を受け付けること |
| CRLF | `\r\n`。HTTP/1.1の行の終わりを表す2バイト |
| リクエスト行 | リクエストの1行目。メソッド・パス・HTTPの版が入る |
| ステータス行 | レスポンスの1行目。HTTPの版とステータスコードが入る |
| Content-Length | 本文の長さをバイト数で表すヘッダ |
| bytesize | 文字列のバイト数を返すRubyのメソッド |
| Connection: close | 「この応答の後に接続を閉じる」という宣言 |
| ルーティング | パスやメソッドによって、どの処理をするかを決めること |
| 静的ファイル | CSSや画像など、中身が変わらないファイル |
| Content-Type | 本文の種類を表すヘッダ |
| シンボリックリンク | 別の場所にあるファイルを指すショートカットのようなもの |
| File.realpath | シンボリックリンクなどを解決して、実際の場所を返すメソッド |
| 結合テスト | 部品をつなげた状態で、本物に近い形で動作を確かめるテスト |
