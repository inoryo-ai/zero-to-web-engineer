# 第2章 Git と GitHub

> **この章のゴール**：Git で変更を記録・確認・取り消しでき、秘密情報を履歴に入れない習慣を身につける。GitHub に非公開の作業用リポジトリを作り、push できる。
> **目安時間**：読む 2時間 ＋ 演習 3時間
> **前提**：第1章まで

## この章で学ぶこと

- バージョン管理が何のためにあるかを、具体的な困りごとと結び付けて説明できる
- 作業ツリー・ステージングエリア・コミットの関係を図で説明できる
- `status`・`add`・`commit`・`diff`・`log`・`restore` を使って、変更を記録・確認・取り消しできる
- `.gitignore` を先に用意し、秘密情報や生成物をコミットしない手順を実行できる
- 「一度コミットした秘密は履歴に残る」ことを実演し、漏らしたときの正しい対応を説明できる
- GitHub アカウントと gh CLI の認証を設定し、`~/workspace` を非公開リポジトリとして push できる

## なぜバージョン管理が必要なのか

プログラムを書いていると、次のような場面に必ず出会います。

- さっきまで動いていたのに、何かを変えたら動かなくなった。何を変えたか思い出せない。
- 試しに大きく書き換えたい。でも、失敗したら元に戻せるか不安だ。
- `report_final.txt`、`report_final2.txt`、`report_final_本当に最後.txt` が増えていく。
- 2人で同じファイルを直したら、相手の変更を上書きしてしまった。

これらをまとめて解決するのが、**バージョン管理システム**です。ファイルの変更の歴史を記録し、いつでも過去の状態を見たり、戻したりできるようにします。今、世界で最も使われているのが **Git** です。

ゲームのセーブにたとえると、わかりやすくなります。Git では、好きなタイミングで「セーブ」できます。セーブには「ボスの手前」のようなメモを付けられます。後から、どのセーブでも中身を確かめられ、そこから別の道を試すこともできます。

Git は、チーム開発の土台でもあります。現場では、ほぼすべてのコードが Git で管理されています。「Git が使えない」状態では、コードを1行も提出できません。この章は、エンジニアとして働くための必修科目です。

## Git の基本の考え方

### リポジトリ

Git で履歴を管理しているディレクトリを**リポジトリ**と呼びます。リポジトリの中には、隠しディレクトリ `.git` があります。ここに履歴のすべてが入っています。`.git` を消すと、履歴も消えます。自分で中身をいじることはありません。

### 3つの場所

Git を理解するうえで一番大事なのが、次の3つの場所です。ここは最初は難しく感じる部分です。図と一緒に、ゆっくり読んでください。

```text
 作業ツリー            ステージングエリア        リポジトリ（履歴）
（いま編集中の       （次のコミットに          （コミットの
  ファイル）           入れるもの）              積み重ね）
     │                    │                      │
     │ ── git add ──────> │                      │
     │                    │ ── git commit ─────> │
     │ <───────────── git restore ────────────── │
```

1. **作業ツリー**：普段エディタで編集している、実際のファイルです。
2. **ステージングエリア**（インデックスとも呼びます）：「次のセーブに含めるもの」を集めておく場所です。
3. **リポジトリ**：セーブ（コミット）が積み重なった履歴です。

引っ越しの荷造りにたとえてみます。部屋にある物が作業ツリーです。段ボール箱に詰めた物がステージングエリアです。箱を封をして発送し、記録を残したものがコミットです。部屋の物を全部一度に送る必要はありません。「この箱には本だけ」のように、まとまりごとに送れます。

なぜ、わざわざステージングエリアがあるのでしょうか。それは、**1つのコミットに、1つの意味のある変更だけを入れるため**です。たとえば、バグの修正と、関係ない見た目の調整を同時にしていたとします。ステージングエリアがあれば、バグの修正だけを先にコミットし、見た目の調整は別のコミットにできます。後から履歴を読む人（未来の自分を含む）が、何をなぜ変えたかを追いやすくなります。

### コミット

**コミット**は、ある時点のファイルの状態を記録したものです。コミットには、次の情報が付きます。

- **コミットID（ハッシュ）**：`e623c96a76...` のような、40桁の英数字です。普段は先頭の7桁ほどで呼びます。
- **作者**：名前とメールアドレス
- **日時**
- **コミットメッセージ**：何を、なぜ変えたかの説明
- **親コミット**：1つ前のコミットへの参照

コミットは、親をたどることで一本の歴史になります。そして、**一度作ったコミットは、基本的に書き換えません**。間違いを直すときは、直すためのコミットを新しく積みます。この性質が、後で説明する「秘密は履歴に残る」につながります。

## GitHub とアカウントの準備

### Git と GitHub の違い

**Git** は、自分の PC で動く道具です。インターネットがなくても使えます。**GitHub** は、Git のリポジトリをインターネット上に置いて、共有や共同作業をできるようにするサービスです。

Git が「ノートと筆記用具」なら、GitHub は「ノートを置いておく共有の書庫」です。書庫には、鍵付きの個室（**非公開＝private**）と、誰でも入れる閲覧室（**公開＝public**）があります。この教材の作業用リポジトリは、必ず private にします。

### アカウントを作る

<https://github.com/> にアクセスし、「Sign up」からアカウントを作ります。いくつか注意点があります。

- **ユーザー名は公開されます**。リポジトリの URL やコミットに表示されます。本名を出したくない場合は、ハンドルネームにしてください。後から変えることもできますが、URL も変わるので最初に決めておくのがよいです。
- **2要素認証を設定してください**。2要素認証とは、パスワードに加えて、スマートフォンの認証アプリなど「もう1つの鍵」でログインする仕組みです。GitHub はコードを書く人に2要素認証を求めています。設定時に表示される**リカバリーコード**は、パスワード管理アプリなど安全な場所に保管してください。スマートフォンをなくしたときの最後の鍵です。
- **メールアドレスを非公開にしてください**。後で説明するとおり、コミットにはメールアドレスが記録され、公開リポジトリでは誰でも読めます。

メールアドレスを非公開にする手順です。

1. GitHub の右上のアイコン → Settings → Emails を開きます。
2. 「Keep my email addresses private」にチェックを入れます。
3. その下に表示される `12345678+ユーザー名@users.noreply.github.com` という形のアドレスを控えます。これが、コミットに使う**公開用の代わりのアドレス**です。
4. 「Block command line pushes that expose my email」にもチェックを入れます。うっかり本物のアドレスでコミットしたものを push しようとすると、GitHub が止めてくれます。

## Git の初期設定

ターミナルで、Git にあなたの名前とメールアドレスを教えます。この設定はコミットの「作者」欄に使われます。メールアドレスには、さきほど控えた noreply のアドレスを使ってください。

```console
git config --global user.name "Taro Yamada"
git config --global user.email "12345678+taro@users.noreply.github.com"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"
```

- `--global` は、「この PC のこのユーザーの、すべてのリポジトリで使う設定」という意味です。設定は `~/.gitconfig` に保存されます。
- `init.defaultBranch main` は、新しいリポジトリの最初のブランチ名を `main` にする設定です。GitHub の標準に合わせています。ブランチは後で説明します。
- `core.editor "code --wait"` は、Git がメッセージの入力を求めるときに VS Code を開く設定です。`--wait` は、VS Code でファイルを閉じるまで Git に待ってもらうための指定です。

設定を確かめます。

```console
git config --global --list
```

## 作業用リポジトリを作る

### `~/workspace` を Git の管理下に置く

第1章で作った `~/workspace` を、Git のリポジトリにします。この教材の演習成果は、すべてここに入れていきます。

```console
cd ~/workspace
git init
```

`Initialized empty Git repository in /Users/taro/workspace/.git/` のように表示されれば成功です。`ls -a` で `.git` ができたことを確かめてください。

### コミットする前に `.gitignore` を書く

ここが、この章で一番大事な手順です。**最初のコミットより先に、`.gitignore` を書きます。**

**`.gitignore`** は、「Git で管理しないファイル」の一覧を書いておくファイルです。ここに書いたファイルは、`git status` に出てこなくなり、`git add .` でうっかり追加されることもなくなります。

なぜ「先に」なのでしょうか。Git は、一度コミットしたものを履歴にずっと残します。後から `.gitignore` に書いても、**既にコミットされたファイルには効きません**。秘密の鍵や設定ファイルを作る前に、門番を立てておく必要があるのです。

`~/workspace/.gitignore` を VS Code で作ります。

```console
code ~/workspace/.gitignore
```

中身は次のようにします。`#` で始まる行はコメントです。

```gitignore
# OS やエディタが作るファイル
.DS_Store

# 秘密情報（鍵・トークン・環境変数ファイル）
*.pem
*.key
.env
.env.*
!.env.example

# 生成物
coverage/
tmp/
log/
*.log

# ローカルのデータベース
*.sqlite3
*.sqlite3-*

# 第2章の練習用リポジトリ（中に別の Git リポジトリを作るため）
ch02/sandbox/
```

それぞれの意味を確認しておきます。

- `*` は「何でもよい文字の並び」です。`*.pem` は「名前が `.pem` で終わるすべてのファイル」を表します。
- 末尾の `/` はディレクトリを表します。`coverage/` は、`coverage` というディレクトリの中身を丸ごと除外します。
- 先頭の `!` は「ただし、これは除外しない」という意味です。`.env.example` は、秘密を含まない見本のファイルなので、管理してよいことにしています。
- **秘密情報**の行が最も重要です。`.pem` や `.key` は暗号の鍵、`.env` はパスワードやトークンを書いておく設定ファイルによく使われる名前です。第13章で HTTPS の練習用の鍵 `key.pem` を作ります。そのときに守ってくれるのが、この行です。
- `.sqlite3` は、第15章以降で作るデータベースのファイルです。データは毎回作り直せるようにし、ファイル自体は管理しません。

### 本当に除外されているか確かめる

`.gitignore` は、書いただけで安心してはいけません。**本当に効いているかを確かめる**のが大事です。`git check-ignore` コマンドを使います。

```console
$ touch .env key.pem
$ git check-ignore -v .env key.pem
.gitignore:7:.env	.env
.gitignore:5:*.pem	key.pem
```

各行は「`.gitignore` の何行目のどの規則で、どのファイルが除外されたか」を表しています。何も表示されなければ、そのファイルは除外されていません。確かめたら、試しに作ったファイルは消しておきます。

```console
rm .env key.pem
```

## 変更を記録する：基本のサイクル

Git の毎日の作業は、次のサイクルの繰り返しです。

1. ファイルを編集する
2. `git status` で状態を見る
3. `git diff` で変更内容を確かめる
4. `git add` でステージングエリアに入れる
5. `git diff --staged` でコミットする内容を最終確認する
6. `git commit` で記録する

### status：今の状態を見る

`~/workspace` に `README.md` を作り、`# 学習記録` と1行書いて保存します。そして `git status` を実行します。

```console
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md

nothing added to commit but untracked files present (use "git add" to track)
```

`Untracked files` は「Git がまだ管理していないファイル」です。Git の出力は英語ですが、怖がらずに読んでください。次に何をすればよいか（`use "git add"...`）まで教えてくれています。

`git status` は、迷ったら何度でも打ってよいコマンドです。何も変えずに状態を見るだけなので、壊す心配はありません。

### add と commit：記録する

```console
$ git add README.md
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md

$ git commit -m "READMEを追加"
[main (root-commit) b24cc03] READMEを追加
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
```

`git add` で、`README.md` が `Changes to be committed`（コミットされる予定の変更）に移りました。ステージングエリアに入った状態です。`git commit -m "メッセージ"` で記録します。`b24cc03` が、このコミットの ID です（人によって違います）。

`-m` を付けずに `git commit` とだけ打つと、設定したエディタ（VS Code）が開きます。1行目にメッセージを書き、保存してタブを閉じるとコミットされます。長い説明を書きたいときはこちらを使います。

### diff：何が変わったかを見る

`README.md` に `第1章を読んだ` と1行追記して保存し、`git diff` を実行します。

```console
$ git diff
diff --git a/README.md b/README.md
index aa7645f..d236aeb 100644
--- a/README.md
+++ b/README.md
@@ -1 +1,2 @@
 # 学習記録
+第1章を読んだ
```

`+` で始まる行が追加された行、`-` で始まる行が削除された行です。この形式を**差分（diff）**と呼びます。コードレビューでは、毎日この形式を読むことになります。

注意してほしいのは、`git diff` が見せるのは「作業ツリーと、ステージングエリアの差」だという点です。`git add` した後は、`git diff` には何も出ません。コミットする予定の内容は `git diff --staged` で見ます。

```console
$ git add README.md
$ git diff --staged
diff --git a/README.md b/README.md
index aa7645f..d236aeb 100644
--- a/README.md
+++ b/README.md
@@ -1 +1,2 @@
 # 学習記録
+第1章を読んだ
$ git commit -m "第1章の記録を追加"
```

**コミットの直前に `git diff --staged` を見る**のは、とても良い習慣です。入れるつもりのなかったファイルや、消し忘れたデバッグ用の行、そして秘密の情報に、ここで気付けます。

### log：履歴を見る

```console
$ git log --oneline
e623c96 第1章の記録を追加
b24cc03 READMEを追加
```

`--oneline` を付けると、1コミット1行で表示します。付けないと、作者や日時も表示されます。

```console
$ git log -1
commit e623c96a7632e6316f34c9f13cb755247d6812b4
Author: Taro Yamada <12345678+taro@users.noreply.github.com>
Date:   Thu Oct 1 17:25:55 2026 +0900

    第1章の記録を追加
```

`Author` の行に、設定したメールアドレスが記録されています。リポジトリを公開すれば、これは誰でも読めます。noreply のアドレスを使う理由がここにあります。

`git log -p` とすると、各コミットの差分も一緒に表示します。長い出力は `less` で表示されるので、`q` で抜けてください。

### `git add .` の落とし穴

`git add .` は、今いるディレクトリ以下の変更をすべてステージングエリアに入れます。便利ですが、**入れるつもりのないファイルまで入れてしまう**危険があります。秘密のファイルを作ったのに `.gitignore` を書き忘れていれば、それも入ります。

初心者のうちは、ファイル名を指定して `git add` するか、`git add .` の後に必ず `git status` と `git diff --staged` で確かめてください。

### コミットメッセージの書き方

コミットメッセージは、未来の自分とチームへの手紙です。次の点を意識します。

- **1行目に、何をしたかを短く書く**：「READMEに第1章の記録を追加」のように具体的に書きます。「修正」「更新」「wip」だけでは、後から読んでも何もわかりません。
- **必要なら、空行を1つ空けて理由を書く**：なぜその変更が必要だったか。コードを見ればわかる「何を」より、コードからはわからない「なぜ」が大事です。
- **1つのコミットに1つの話題**：関係ない変更を混ぜないようにします。

チームによって、英語で書く、先頭に種類を付ける（`fix:`、`feat:` など）、といったルールがあります。現場ではそのルールに従ってください。

## 変更を取り消す

失敗しても戻せるのが Git の強みです。ただし、取り消しの操作の中には、**本当に消えてしまうもの**もあります。違いを理解してから使ってください。

| やりたいこと | コマンド | 注意 |
|---|---|---|
| ステージングエリアから外す（変更自体は残す） | `git restore --staged ファイル` | 安全。作業ツリーは変わらない |
| 作業ツリーの変更を捨てて、最後のコミットの状態に戻す | `git restore ファイル` | **コミットしていない変更は消え、戻せない** |
| 直前のコミットのメッセージや内容を直す | `git commit --amend` | **push する前だけ**使う |
| 過去のコミットを打ち消す | `git revert コミットID` | 打ち消すための新しいコミットを作る。安全 |

例を見てみましょう。

```console
$ echo "書きかけ" >> README.md
$ git status --short
 M README.md
$ git restore README.md
$ git status --short
```

`git status --short` は、状態を短く表示するオプションです。`M` は「変更あり（Modified）」です。`git restore` の後は何も表示されず、変更が消えたことがわかります。

`git commit --amend` を push の前だけにするのは、amend が「新しいコミットを作って、古いものと差し替える」操作だからです。既に GitHub に送ったコミットを差し替えると、他の人の手元の履歴と食い違います。チームでは混乱のもとになります。

インターネットで `git reset --hard` という操作を見かけることがあります。これは、作業ツリーとステージングエリアをまとめて巻き戻す強力な操作で、コミットしていない変更はすべて消えます。意味を理解するまでは使わないでください。

## 一度コミットした秘密は履歴に残る

### 消したつもりでも消えていない

ここは、この章で最も伝えたいことです。

パスワードの書かれたファイルを、うっかりコミットしてしまったとします。気付いて、ファイルを消して、「削除」のコミットをしました。これで安全でしょうか。

**安全ではありません。** 実際に確かめてみます。次の例は、練習用の別リポジトリで、**明らかに偽物の値**を使って行っています（演習2-3で同じことをします）。

```console
$ echo 'API_TOKEN=dummy-0000-THIS-IS-FAKE' > config.txt
$ git add config.txt
$ git commit -q -m "設定ファイルを追加"
$ git rm -q config.txt
$ git commit -q -m "設定ファイルを削除"
$ ls
$ git log --oneline
cf5b4d6 設定ファイルを削除
ceae6a0 設定ファイルを追加
```

`ls` では何も表示されず、ファイルは消えたように見えます。しかし、履歴を検索すると、こうなります。

```console
$ git log -p --oneline -S 'API_TOKEN'
cf5b4d6 設定ファイルを削除
diff --git a/config.txt b/config.txt
deleted file mode 100644
index 319c13c..0000000
--- a/config.txt
+++ /dev/null
@@ -1 +0,0 @@
-API_TOKEN=dummy-0000-THIS-IS-FAKE
ceae6a0 設定ファイルを追加
diff --git a/config.txt b/config.txt
new file mode 100644
index 0000000..319c13c
--- /dev/null
+++ b/config.txt
@@ -0,0 +1 @@
+API_TOKEN=dummy-0000-THIS-IS-FAKE
```

`-S 'API_TOKEN'` は、「この文字列が増えたり減ったりしたコミットを探す」というオプションです。秘密の値が、しっかり残っています。`git show ceae6a0:config.txt` とすれば、そのときのファイルの中身をそのまま取り出せます。

なぜこうなるのでしょうか。思い出してください。コミットは「ある時点の状態の記録」で、一度作ったら書き換えません。「削除」のコミットは、「この時点でファイルがなくなった」という新しい記録を積んだだけです。前の記録は、そのまま残っています。ゲームのセーブで言えば、最新のセーブからアイテムを捨てても、古いセーブにはアイテムが残っているのと同じです。

### push した後なら、なおさら

GitHub に push すると、履歴ごとコピーされます。公開リポジトリであれば、世界中の誰でも、いつでも複製できます。秘密の値を自動で探して回るプログラムも存在し、公開から悪用までの時間は非常に短いことがあります。非公開リポジトリでも、共同作業者、連携しているサービス、バックアップなど、見える範囲は自分が思うより広いものです。

### 漏らしてしまったときの正しい対応

秘密の値をコミットしてしまったら、次の順で対応します。

1. **その秘密は漏れたものとして扱い、無効にする**：パスワードなら変更し、トークンなら失効させて新しいものを発行し、鍵なら作り直します。これが最優先です。
2. **関係者に報告する**：チームなら、すぐに先輩やリーダーに伝えます。隠すと被害が広がります。
3. **履歴から取り除くかを検討する**：履歴を書き換える専用の道具（`git filter-repo` など）や、GitHub の「機密データの削除」の手順があります。ただし、これは後始末です。既に誰かが複製していれば、取り戻せません。だから 1 が最優先なのです。

「削除コミットを足したから大丈夫」「`.gitignore` に追加したから大丈夫」は、どちらも間違いです。

### 予防が一番

漏らした後の対応は大変です。予防の手順をまとめておきます。

- **秘密のファイルを作る前に `.gitignore` に書き、`git check-ignore -v` で確かめる。**
- **秘密の値をコードに直接書かない**。設定ファイルや環境変数で渡します（第20章で詳しく扱います）。
- **コミット前に `git status` と `git diff --staged` を見る。**
- **追跡済みのファイルを確かめる**：`git ls-files` で、Git が管理しているファイルの一覧を表示できます。`git ls-files -- '*.pem' '*.key' '*.env'` で何も表示されなければ、それらは管理されていません。
- **演習ではダミーデータだけを使う**：本物の名前、メールアドレス、パスワードは使いません。

もし `.gitignore` に書く前にファイルを `git add` してしまっていたら、`git rm --cached -- ファイル` で管理対象から外せます。`--cached` は「作業ツリーのファイルは消さず、Git の管理からだけ外す」という意味です。ただし、**既にコミットしていたなら、その履歴には残っています**。その場合は上の「漏らしてしまったときの正しい対応」に従います。

## GitHub に送る

### gh CLI で認証する

自分の PC の Git から GitHub にアクセスするには、「あなたが本人であること」を GitHub に証明する必要があります。この教材では、GitHub の公式コマンドラインツール **gh（GitHub CLI）** を使います。

```console
brew install gh
gh --version
```

Windows（WSL）の人は、gh の公式サイト <https://cli.github.com/> の Linux 向け手順に従ってください。

認証を始めます。

```console
gh auth login
```

いくつか質問されるので、次のように選びます。矢印キーで選び、Enter で決定します。

1. `Where do you use GitHub?` → `GitHub.com`
2. `What is your preferred protocol for Git operations on this host?` → `HTTPS`
3. `Authenticate Git with your GitHub credentials?` → `Yes`
4. `How would you like to authenticate GitHub CLI?` → `Login with a web browser`

すると、`XXXX-XXXX` のような**ワンタイムコード**が表示されます。Enter を押すとブラウザが開くので、GitHub にログインし、コードを入力して許可します。ターミナルに戻ると、認証が完了しています。

3番目で `Yes` を選んだことで、`git push` などの Git の操作でも、この認証が使われるようになります。

認証の状態を確かめます。

```console
$ gh auth status
github.com
  ✓ Logged in to github.com account taro (keyring)
  - Active account: true
  - Git operations protocol: https
  - Token: gho_************************************
  - Token scopes: 'gist', 'read:org', 'repo'
```

（表示は gh の版によって少し違います）

### なぜこの方法なのか

GitHub に Git でアクセスするとき、昔はパスワードを使っていました。今は、パスワードの代わりに**トークン**という長い合言葉を使います。トークンは、それを持っていればあなたとして GitHub を操作できる、非常に大事な秘密です。

`gh auth login` のブラウザ方式では、トークンを**自分の目で見ることも、手でコピーすることもありません**。gh が受け取り、macOS のキーチェーン（パスワードを安全に保管する仕組み）にしまいます。上の `gh auth status` の出力でも、トークンは `*` で伏せられています。手で扱わないので、ファイルに書いてしまったり、チャットに貼ってしまったりする事故が起きません。

もし、何かのきっかけでトークンそのものを表示する操作をしても、その出力を人に見せたり、AI に貼ったり、ファイルに保存したりしないでください。漏れたと思ったら、`gh auth logout` してから GitHub の Settings で該当する許可を取り消し、もう一度 `gh auth login` します。

### 非公開リポジトリを作って push する

最初の push の前に、送ろうとしているものを確かめます。

```console
cd ~/workspace
git status
git ls-files
git ls-files -- '*.pem' '*.key' '*.env'
```

`git status` で、コミットしていない変更がないかを見ます。`git ls-files` で、送られるファイルの一覧を見ます。3つ目のコマンドで何も表示されないことを確かめます。

問題がなければ、GitHub にリポジトリを作り、push します。

```console
gh repo create workspace --private --source=. --remote=origin --push
```

それぞれの意味です。

- `workspace`：GitHub 上のリポジトリ名
- `--private`：**非公開**で作る。この教材では必ず付けます
- `--source=.`：今いるディレクトリのリポジトリを元にする
- `--remote=origin`：GitHub のリポジトリを `origin` という名前で登録する
- `--push`：今あるコミットを送る

本当に非公開になっているか、確かめます。

```console
$ gh repo view --json visibility --jq .visibility
PRIVATE
```

`PRIVATE` と表示されれば、非公開です。ブラウザで `https://github.com/ユーザー名/workspace` を開くと、リポジトリ名の横に「Private」と表示されていることも確認できます。

### リモートと push / pull / clone

GitHub 上のリポジトリのように、自分の PC の外にあるリポジトリを**リモート**と呼びます。`origin` は、そのリモートに付けた名前（あだ名）です。

```console
$ git remote -v
origin	https://github.com/taro/workspace.git (fetch)
origin	https://github.com/taro/workspace.git (push)
```

リモートとのやり取りは、主に次の3つです。

| コマンド | 意味 |
|---|---|
| `git push` | 自分のコミットをリモートに送る |
| `git pull` | リモートのコミットを取り込む |
| `git clone URL` | リモートのリポジトリを、履歴ごと手元に複製する |

2回目以降は、コミットした後に `git push` と打つだけで送れます。GitHub はバックアップの役目も果たすので、**区切りのよいところで push する**習慣を付けてください。PC が壊れても、作業が失われません。

`git clone` は、他人のリポジトリを読むときにも使います。第12章では、Ruby の Web サーバ WEBrick のリポジトリを clone して、中身を読みます。

### public と private の使い分け

学習の成果を公開して、転職活動のポートフォリオにしたい人もいるでしょう。それ自体は良いことです。ただし、公開する前に、**履歴全体**を見直す必要があります。最新のファイルに問題がなくても、過去のコミットに個人情報や秘密が残っていることがあるからです。この教材では、第26〜27章で成果物を共有するときの確認方法を扱います。それまでは private のままにしておいてください。

## ブランチの入口

最後に、**ブランチ**を少しだけ紹介します。ブランチは、履歴を枝分かれさせる仕組みです。本流（`main`）を壊さずに、別の枝で新しいことを試せます。

```console
$ git switch -c add-ch02-notes
Switched to a new branch 'add-ch02-notes'
$ echo "第2章を読んだ" >> README.md
$ git commit -qam "第2章の記録を追加"
$ git switch main
Switched to branch 'main'
$ git merge add-ch02-notes
Updating 276f485..843a991
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
```

- `git switch -c 名前`：新しいブランチを作って、そこに移ります。
- `git commit -am`：`-a` は「追跡済みファイルの変更をまとめて add する」という意味です。新しいファイルは含まれません。
- `git merge 名前`：指定したブランチの変更を、今のブランチに取り込みます。

`Fast-forward` は、「`main` が枝分かれしてから何も変わっていなかったので、`main` の先端をそのまま進めた」という意味です。両方の枝で同じ場所が変わっていると、**コンフリクト（衝突）**が起きます。その解決方法や、チームでのブランチの使い方、プルリクエストは、第24章で詳しく学びます。

## 実務ではこうなる

現場での Git の使い方は、この章の内容の延長です。

- **作業は必ずブランチで行う**：`main` に直接コミットすることは、ほぼありません。ブランチで作業し、GitHub の**プルリクエスト**で他の人にレビューしてもらってから、`main` に取り込みます（第24章）。
- **コミットの単位と説明が評価される**：レビューする人は、差分とコミットメッセージを読みます。1つのコミットに無関係な変更が混ざっていると、レビューが大変になります。
- **秘密情報の事故は、本当に起きる**：API のキーやデータベースのパスワードをコミットしてしまう事故は、経験者でも起こします。だから多くの現場では、`.gitignore` の整備に加えて、秘密を自動で検出する仕組みを入れています。GitHub にも、push された秘密を検出する機能があります。それでも、最後の砦は一人ひとりの `git diff --staged` です。

ジュニアがやりがちな失敗も挙げておきます。

- **`git add .` で、関係ないファイルや秘密をまとめてコミットする。**
- **秘密を漏らしたことに気付いても、怒られるのが怖くて黙っている。** 秘密の無効化は早いほど被害が小さくなります。すぐに報告するのが、プロとして正しい行動です。
- **push 済みのコミットを `--amend` や強制 push（`git push --force`）で書き換える。** 他の人の作業を壊すことがあります。
- **「とりあえず」で `git reset --hard` を実行し、未コミットの作業を消す。**
- **コミットメッセージが「修正」だけ。** 半年後の自分が困ります。

## 演習

演習の成果は `~/workspace/` と `~/workspace/ch02/` に置きます。

### 演習2-1：作業用リポジトリを作り、最初のコミットをする

- 本文の手順で、`git config --global` の初期設定をしてください。メールアドレスは GitHub の noreply アドレスにします。
- `~/workspace` を `git init` し、本文の内容で `.gitignore` を作ってください。
- `~/workspace/README.md` を作り、「この教材の学習記録」であることと、第1章を終えた日付を書いてください。
- `.gitignore` と `README.md`、第1章の成果物（`ch01/`）をコミットしてください。コミットは**2つ以上に分けて**ください（たとえば「.gitignore の追加」と「README と第1章の成果の追加」）。
- **完了条件**：
  - `git log --oneline` で2つ以上のコミットが表示される。
  - `git log -1 --format='%ae'` が `users.noreply.github.com` で終わるアドレスを表示する。
  - `git status` が `nothing to commit, working tree clean` を表示する。
- ヒント：分けてコミットするには、`git add` するファイルを指定します。コミットの前に `git diff --staged` を見てください。

### 演習2-2：`.gitignore` の効き目を確かめる

- `~/workspace/ch02/` を作り、その中にダミーのファイル `.env`、`server.key`、`app.log`、`notes.txt` を作ってください。中身は空でも、`DUMMY=1` のような明らかな偽物でも構いません。
- `git status --short` で、どれが表示され、どれが表示されないかを確かめてください。
- `git check-ignore -v` で、除外されたファイルが `.gitignore` のどの規則に当たったかを確かめてください。
- 結果を `~/workspace/ch02/ignore-check.txt` にリダイレクトで保存し、`notes.txt` と一緒にコミットしてください。
- **完了条件**：
  - `git ls-files ch02` の出力が `ch02/ignore-check.txt` と `ch02/notes.txt` の2行だけである。
  - `ignore-check.txt` に、`.env`・`server.key`・`app.log` の3つについて、当たった規則が記録されている。
- ヒント：`git check-ignore -v ch02/.env ch02/server.key ch02/app.log ch02/notes.txt` のように、まとめて調べられます。`notes.txt` は何も表示されないのが正しい結果です。

### 演習2-3：秘密が履歴に残ることを自分で確かめる

- `~/workspace/ch02/sandbox` を作り、その中で `git init` してください。`.gitignore` に `ch02/sandbox/` があるので、外側の `~/workspace` からは無視されます。外側で `git status` を打ち、`sandbox` が出てこないことを先に確かめてください。
- `sandbox` の中で、本文と同じ手順を自分で行ってください。値は必ず **`dummy-` で始まる偽物**にします。
  1. 偽の秘密を書いたファイルを作ってコミットする
  2. そのファイルを `git rm` で削除してコミットする
  3. `ls` でファイルがないことを確かめる
  4. `git log -p -S` で、偽の秘密を履歴から見つける
  5. `git show コミットID:ファイル名` で、当時のファイルの中身を取り出す
- 4 と 5 の出力を `~/workspace/ch02/history-leak.txt` に保存してください（これは `sandbox` の**外**です）。その末尾に、「本物の秘密だったら、どの順番で何をするか」を自分の言葉で3行以上書き、外側のリポジトリにコミットしてください。
- **完了条件**：
  - `history-leak.txt` に、削除済みのはずの偽の値が含まれている。
  - 対応の手順に「無効化（変更・失効・作り直し）が最優先」であることが書かれている。
  - 外側で `git ls-files ch02` を実行しても、`sandbox` の中のファイルは表示されない。
- ヒント：入れ子のリポジトリの中にいるのか外にいるのか、迷ったら `pwd` と `git rev-parse --show-toplevel` で確かめられます。後者は「今いるリポジトリの一番上のディレクトリ」を表示します。

### 演習2-4：GitHub に非公開で push する

- GitHub のアカウントを作り、2要素認証とメールアドレスの非公開設定をしてください。
- gh をインストールし、`gh auth login` で認証してください。
- 本文の確認手順（`git status`、`git ls-files`、秘密のファイルの確認）を行ってから、`gh repo create` で `workspace` を **private** で作り、push してください。
- **完了条件**：
  - `gh auth status` に `Logged in to github.com` と表示される。
  - `gh repo view --json visibility --jq .visibility` が `PRIVATE` を表示する。
  - `git status` に `Your branch is up to date with 'origin/main'.` と表示される。
  - ブラウザで GitHub のリポジトリを開き、`.env` や `*.key` が含まれていないことを目で確かめた。
- ヒント：`gh repo create` で失敗したら、エラーメッセージをよく読んでください。同じ名前のリポジトリが既にある、というのはよくある原因です。

### 演習2-5（発展）：clone して往復する

- `~/workspace` とは別の場所（たとえば `~/clone-test`）に、`gh repo clone ユーザー名/workspace ~/clone-test` で自分のリポジトリを複製してください。
- `~/clone-test` 側で `README.md` に1行追記し、コミットして push してください。
- `~/workspace` 側に戻り、`git pull` でその変更を取り込んでください。
- 最後に、`~/clone-test` を削除してください（削除する前に `pwd` と `ls` で場所を確かめてください）。
- **完了条件**：`~/workspace` で `git log --oneline -3` を実行すると、`~/clone-test` 側で作ったコミットが表示される。`ls ~/clone-test` が「No such file or directory」になる。
- ヒント：この往復は、「2台の PC で作業する」場面や、「チームメンバーの変更を取り込む」場面の練習です。

## 確認クイズ

**Q1.** `git add` と `git commit` は何が違いますか。ステージングエリアという仕組みがあると、何がうれしいですか。

**Q2.** `git diff` を実行しても何も表示されませんが、`git status` には `Changes to be committed` と出ています。変更の内容を見るにはどうしますか。

**Q3.** `key.pem` を既にコミットしてしまっていました。`.gitignore` に `*.pem` を追加すれば、問題は解決しますか。

**Q4.** パスワードを書いたファイルをコミットして push しました。すぐに削除のコミットを作って push しました。これで十分ですか。何をすべきですか。

**Q5.** コミットの作者のメールアドレスに、GitHub の noreply アドレスを使うのはなぜですか。

### 解答と解説

**A1.** `git add` は「次のコミットに入れるもの」をステージングエリアに集める操作です。`git commit` は、ステージングエリアの内容を履歴として記録する操作です。ステージングエリアがあると、作業ツリーにある変更の一部だけを選んでコミットできます。そのため、1つのコミットに1つの意味のある変更だけを入れられ、履歴が読みやすくなります。

**A2.** `git diff --staged` を使います。`git diff` は作業ツリーとステージングエリアの差だけを見せるので、`git add` した後の変更は表示されません。

**A3.** 解決しません。`.gitignore` は、まだ追跡されていないファイルにしか効きません。`git rm --cached -- key.pem` で管理対象から外す必要があります。さらに、過去のコミットには鍵が残っています。共有や push をしていたなら、その鍵は漏れたものとして使うのをやめ、作り直します。

**A4.** 十分ではありません。削除のコミットを作っても、前のコミットにはパスワードが残っています。最優先は、そのパスワードを変更して無効にすることです。チームであれば、すぐに報告します。履歴からの削除は、その後に検討する後始末です。既に複製されていれば取り戻せないからです。

**A5.** コミットには作者のメールアドレスが記録され、リポジトリを公開すると誰でも読めるからです。本物のアドレスを使うと、迷惑メールや個人の特定につながるおそれがあります。noreply のアドレスなら、GitHub 上では自分のコミットとして扱われつつ、本物のアドレスを隠せます。

## AIの使い方（この章）

この章では、AI を「Git の動きを図や言葉で説明してもらう相手」として使います。

推奨する聞き方の例：

- 「`git status` で次の表示が出ました（出力を貼る）。それぞれのファイルが、作業ツリー・ステージングエリア・リポジトリのどこにある状態か、説明してください」
- 「ステージングエリアがなぜ必要なのか、引っ越しの荷造り以外のたとえでも説明してください。私は『コミットに含める変更を選ぶため』と理解していますが、合っていますか」
- 「`git restore`、`git restore --staged`、`git revert` の違いを、それぞれ『何が消えて何が残るか』の観点で表にしてください」

この章でやってはいけない使い方：

- **トークン、`.env` の中身、`gh auth status` 以外の認証情報の出力を AI に貼る。** AI のサービスに送った内容は、自分の PC の外に出ます。エラーの相談をするときも、秘密の部分は必ず伏せてください。
- **AI が提案した `git reset --hard`、`git push --force`、履歴の書き換えのコマンドを、意味を確かめずに実行する。** これらは作業や履歴を消す操作です。まず「このコマンドを実行すると何が消えますか」と聞き返し、自分で納得してから判断してください。

## まとめ

- Git は変更の履歴を記録する道具で、作業ツリー → ステージングエリア → リポジトリの順に変更を記録します。
- 毎日のサイクルは `status` → `diff` → `add` → `diff --staged` → `commit` です。
- `.gitignore` は最初のコミットより前に書き、`git check-ignore -v` で効き目を確かめます。
- 一度コミットした秘密は、削除しても履歴に残ります。漏らしたら、まず無効化して報告します。
- `~/workspace` は gh で認証したうえで、private の GitHub リポジトリに push します。

## 用語

| 用語 | 意味 |
|---|---|
| バージョン管理 | ファイルの変更の歴史を記録し、過去の状態を見たり戻したりできるようにすること |
| Git | 最も広く使われているバージョン管理システム |
| リポジトリ | Git が履歴を管理している場所。実体は `.git` ディレクトリ |
| 作業ツリー | 実際に編集しているファイル |
| ステージングエリア | 次のコミットに入れる変更を集めておく場所。インデックスとも呼ぶ |
| コミット | ある時点のファイルの状態の記録。ID・作者・日時・メッセージを持つ |
| 差分（diff） | 2つの状態の違い。`+` が追加、`-` が削除 |
| `.gitignore` | Git で管理しないファイルの規則を書くファイル |
| GitHub | Git のリポジトリをインターネット上で共有するサービス |
| private / public | 招待した人だけが見られる / 誰でも見られる |
| 2要素認証 | パスワードに加えて、もう1つの手段で本人確認する仕組み |
| トークン | パスワードの代わりに使う長い合言葉。持っていれば本人として操作できる |
| gh（GitHub CLI） | GitHub をターミナルから操作する公式ツール |
| リモート / origin | 手元の外にあるリポジトリ / その標準的な呼び名 |
| push / pull / clone | 送る / 取り込む / 履歴ごと複製する |
| ブランチ | 履歴の枝分かれ。本流を壊さずに作業できる |
