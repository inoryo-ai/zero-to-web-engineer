# 第22章 テスト戦略とCI

> **この章のゴール**：「どのテストを、どれだけ、どう書くか」を自分で判断できるようになります。テストと静的解析を GitHub Actions で毎回自動実行する仕組み（CI）を作ります。
> **目安時間**：読む 2.5時間 ＋ 演習 7時間
> **前提**：第21章まで

## この章で学ぶこと

- テストピラミッドの考え方で、単体・結合・E2E テストの役割と割合を説明できる
- モックとスタブの違いを説明し、使うべき場面と避けるべき場面を判断できる
- fixtures と factory の違いを知り、ダミーデータでテストデータを用意できる
- flaky テストの原因を特定し、再現して直せる
- カバレッジの数字を正しく読み、足りないテストを見つけられる
- GitHub Actions で、テストと RuboCop を毎回自動で実行する CI を設定できる

## テストを「戦略」として考える

第6章で、Minitest と TDD を学びました。RED → GREEN → REFACTOR の流れで、第11章から第21章まで、たくさんのテストを書いてきました。

アプリが大きくなると、新しい悩みが出てきます。

- テストが増えて、全部実行すると何分もかかる
- 小さな変更で、関係なさそうなテストが大量に壊れる
- たまに失敗するテストがあり、もう一度実行すると通る
- テストは全部通るのに、本番で不具合が出る

これらは、テストを1本ずつ見ていても解決しません。「どの種類のテストを、どれくらいの割合で持つか」という全体の設計が必要です。これを **テスト戦略** と呼びます。

もう一つ、チームで開発していると「テストを実行し忘れたまま変更をマージしてしまう」という問題も起きます。人の注意力に頼らず、機械に毎回実行させる仕組みが **CI** です。この章の後半で作ります。

## テストピラミッド

### 3つの層

テストは、確かめる範囲の大きさで3つに分けられます。

- **単体テスト**（ユニットテスト）：1つのクラスやメソッドを、単独で確かめる。Rails ではモデルのテスト（`test/models/`）や、第21章で作った `WeatherClient` のテストがこれにあたります。
- **結合テスト**（インテグレーションテスト）：複数の部品を組み合わせて確かめる。Rails ではルーティング・コントローラ・モデル・DB を通して HTTP リクエストを送る `test/integration/` のテストがこれにあたります。第20章のセキュリティテストや、第21章の API テストもここです。
- **E2E テスト**（End to End）：本物のブラウザを動かし、利用者と同じ操作で最初から最後まで確かめる。Rails では **システムテスト**（`test/system/`）と呼ばれ、Capybara という gem がブラウザを操作します。

この3つを、数の多い順に下から積むと、ピラミッドの形になります。

```text
        /\         E2E（システムテスト）：少し
       /  \        遅い・壊れやすい・でも一番本物に近い
      /----\
     / 結合 \      結合テスト：ほどほど
    /--------\
   /   単体   \    単体テスト：たくさん
  /------------\   速い・原因が分かりやすい・でも部品単位
```

### なぜピラミッドの形がよいのか

3つの層には、それぞれ得意と不得意があります。

| | 単体 | 結合 | E2E |
|---|---|---|---|
| 実行の速さ | とても速い | ふつう | 遅い |
| 失敗したときの原因の分かりやすさ | とても分かりやすい | ふつう | 分かりにくい |
| 「本当に動く」という安心感 | 低い | ふつう | 高い |
| 壊れにくさ | 高い | ふつう | 低い |

単体テストは速く、失敗したときに悪い場所を特定しやすいです。しかし、部品が正しくても、組み合わせ方が間違っていれば見逃します。E2E テストはその逆で、本物に近い安心感がありますが、遅く、ブラウザの動きの揺らぎで失敗することもあります。

たとえるなら、車の検査です。ネジ1本1本の強度検査（単体）はたくさん安くできます。エンジンを組み上げての検査（結合）はそれより手間がかかります。完成した車での試走（E2E）は一番確実ですが、毎回全部の条件で走らせるのは無理です。だから、ネジの検査を厚くし、試走は大事な道だけにします。

逆に、E2E テストばかりで単体テストが少ない形を **アイスクリームコーン** と呼びます。上が重く、下が細い形です。テストが遅く、失敗の原因も探しにくくなります。

### Rails での目安

Rails アプリでの、実用的な目安を挙げます。

- **モデルや独立したクラス**：バリデーション、計算、状態の変化などは単体テストで細かく確かめる。
- **リクエストの流れ**：認証・認可、ステータスコード、リダイレクト、DB の変化は結合テストで確かめる。セキュリティのテストは、ほとんどがここに入ります。
- **画面の操作**：ログインして投稿する、のような「これが壊れたらサービスとして致命的」な流れだけを、システムテストで確かめる。JavaScript が関わる画面も、ここでしか確かめられません。

なお、Rails のバージョンによっては、scaffold などでシステムテストが自動生成されなくなっています。必要なものを意識して書く、という姿勢がますます大切です。

### 何をテストするか

層を選んだ後、「何を確かめるか」も大切です。目安は次のとおりです。

- **実装ではなく振る舞いを確かめる**：「内部でどのメソッドを呼んだか」より「何を入れたら何が返るか、DB がどう変わるか」を確かめます。内部の書き方を変えただけでテストが壊れるなら、テストが実装に縛られすぎています。
- **境界を確かめる**：上限ちょうど、上限プラス1、空、`nil` など。バグは境目に集まります。
- **失敗の道筋も確かめる**：成功のケースだけでなく、入力が間違っているとき、権限がないとき、外部が失敗したときを確かめます。第20章・第21章で書いたテストの多くはこれです。

## モックとスタブ

### なぜ偽物が必要なのか

テストしたい部品が、外部のものに依存していることがあります。

- 外部 API（第21章の天気 API など）
- 現在時刻
- 乱数
- メールの送信

これらを本物のまま使うと、テストが困ったことになります。外部 API が落ちていたらテストが失敗する。時刻によって結果が変わる。乱数で毎回違う結果になる。本物のメールが送られてしまう。

そこで、テストのときだけ、本物の代わりに偽物を使います。テストのための偽物を総称して **テストダブル** と呼びます。映画のスタントマン（ダブル）が由来です。代表的なものが **スタブ** と **モック** です。

### スタブとモックの違い

- **スタブ**：決まった答えを返すだけの偽物。「今は朝9時です」と答える時計など。テストしたい部品に、都合のよい入力を与えるために使います。
- **モック**：「正しく呼ばれたか」を記録して、後で確かめる偽物。「メール送信が、この宛先で1回呼ばれたはず」を確かめるときに使います。

一言で言うと、スタブは「入力を用意する」、モックは「出力（呼び出し）を確かめる」ための道具です。

Minitest での例を見てみます。

```ruby
require "minitest/autorun"
require "minitest/mock"

class Greeting
  def initialize(clock: Time)
    @clock = clock
  end

  def message
    @clock.now.hour < 12 ? "おはようございます" : "こんにちは"
  end
end

class Notifier
  def initialize(mailer)
    @mailer = mailer
  end

  def welcome(email)
    @mailer.deliver(email, "ようこそ")
  end
end

class GreetingTest < Minitest::Test
  def test_morning_with_stub
    morning = Time.new(2026, 4, 1, 9, 0, 0)
    Time.stub(:now, morning) do
      assert_equal "おはようございます", Greeting.new.message
    end
  end

  def test_afternoon_with_injected_clock
    fake_clock = Struct.new(:now).new(Time.new(2026, 4, 1, 15, 0, 0))
    assert_equal "こんにちは", Greeting.new(clock: fake_clock).message
  end
end

class NotifierTest < Minitest::Test
  def test_welcome_sends_mail_with_mock
    mailer = Minitest::Mock.new
    mailer.expect(:deliver, true, ["user1@example.com", "ようこそ"])
    Notifier.new(mailer).welcome("user1@example.com")
    mailer.verify
  end
end
```

```text
$ ruby stub_mock_test.rb --seed 1234
Run options: --seed 1234

# Running:

...

Finished in 0.000848s, 3537.7359 runs/s, 2358.4906 assertions/s.

3 runs, 2 assertions, 0 failures, 0 errors, 0 skips
```

3つのテストを順に見ます。

1. `Time.stub(:now, morning)` は、ブロックの間だけ `Time.now` を「朝9時を返すスタブ」に差し替えます。ブロックを抜けると元に戻ります。
2. 2つ目は、時計を外から渡せるように作っておき（`clock:` 引数）、テストでは偽物の時計を渡しています。このように、依存するものを外から渡す設計を **依存性の注入** と呼びます。差し替えの仕掛けを使わずに済むので、テストが素直になります。
3. `Minitest::Mock` は、`expect` で「`deliver` がこの引数で呼ばれるはず」と予告し、`verify` で本当に呼ばれたか確かめます。

もし `welcome` の中で `deliver` を呼び忘れると、`verify` が次のように失敗します。

```text
  1) Error:
MockFailTest#test_forgot_to_call:
MockExpectationError: expected deliver("user1@example.com", "ようこそ") => true
```

ここで示した出力は、このPCの Minitest 5.11 のものです。Minitest のバージョンによっては、モックの機能が別の gem（minitest-mock）に分かれていて、追加が必要な場合があります。`require "minitest/mock"` でエラーが出たら、まずそれを疑ってください。

### Rails でよく使う差し替えの道具

Rails のテストでは、目的別の道具がそろっています。

- **時刻**：`travel_to Time.zone.local(2026, 4, 1, 9, 0, 0) do ... end` で、ブロックの間の現在時刻を固定できます。Rails のテストでは最初から使えます。
- **メール**：`assert_emails 1 do ... end` で、送信されたメールの数を確かめられます。テスト環境ではメールは実際には送られず、配列に貯まるだけです。
- **ジョブ**：第21章の `assert_enqueued_with` です。
- **外部 HTTP**：**WebMock** という gem がよく使われます。`stub_request(:get, "https://weather.example.com/...").to_return(status: 503)` のように、特定の URL への応答を決められます。さらに `WebMock.disable_net_connect!` を設定すると、スタブしていない外部への通信がすべてエラーになります。うっかり本物の API を呼ぶ事故を防げます。

### モックを使いすぎない

モックやスタブは便利ですが、使いすぎると逆効果です。

- **自分のアプリの部品まで差し替えすぎない**：たとえば Active Record のメソッドをスタブして DB を使わないようにすると、テストは速くなります。しかし、本物の DB で起きる問題（制約違反、SQL の間違い）を見逃します。DB は差し替えずに、テスト用の DB を使うのが Rails の基本です。
- **実装の細部をモックで固めない**：「このメソッドが、この順番で、この引数で呼ばれる」を細かくモックで確かめると、内部を少し書き換えただけでテストが壊れます。リファクタリングを邪魔するテストになります。
- **偽物と本物がずれる**：スタブが返す値が、本物の API の実際の応答と違っていたら、テストは通るのに本番で壊れます。スタブの中身は、相手のドキュメントや実際の応答例をもとに作ります。

目安は「自分では制御できない境界（外部 API、時刻、乱数、メール送信）だけを差し替える」です。

## テストデータ：fixtures と factory

### fixtures

Rails の標準のテストデータの仕組みが **fixtures** です。`test/fixtures/` に、テーブルごとの YAML ファイルを置きます。

```yaml
# test/fixtures/users.yml
alice:
  email: alice@example.com
  password_digest: <%= BCrypt::Password.create("password") %>

bob:
  email: bob@example.com
  password_digest: <%= BCrypt::Password.create("password") %>
```

```yaml
# test/fixtures/posts.yml
alice_first:
  user: alice
  title: アリスの最初の投稿
  body: テスト用の本文です
```

`alice` や `alice_first` は、データに付けた名前（ラベル）です。テストの中では `users(:alice)` のように取り出せます。`user: alice` のように、関連をラベルで書けるのも便利です。YAML の中では ERB が使えるので、パスワードのハッシュも作れます。

fixtures は、テストの実行前に一度だけ DB に入れられます。各テストはトランザクションの中で実行され、終わると巻き戻されます。そのため速く、テスト同士が DB の変更で影響し合いません。

### factory

もう一つの方法が **factory** です。代表的な gem は **factory_bot** で、RSpec という別のテストの仕組みと一緒によく使われます。factory は「データの作り方のひな形」を定義しておき、テストの中で必要なときに、必要な分だけ作ります。

```ruby
# factory_bot の例（雰囲気をつかむためのもの）
user = create(:user, email: "carol@example.com")
post = create(:post, user: user, title: "テスト")
```

### どちらを使うか

| | fixtures | factory |
|---|---|---|
| データを作るタイミング | 実行前に一度 | 各テストの中で |
| 速さ | 速い | 作る量によっては遅くなる |
| データが見える場所 | YAML ファイル | テストの中 |
| 向いている場面 | 共通の基本データ | テストごとに条件を変えたいとき |

どちらにも一長一短があり、現場によって使い分けています。この教材では Rails 標準の fixtures を使います。

どちらを使う場合も、次の点は共通です。

- **ダミーデータだけを使う**：第10章のルールです。メールアドレスは `example.com`、名前は「テスト太郎」などにします。本番のデータをコピーしてテストデータにしてはいけません。
- **テストに必要な最小限にする**：関係ないデータが多いと、テストが何を確かめているのか分かりにくくなります。
- **意味のある名前を付ける**：`user1` より `admin` や `suspended_user` の方が、テストを読んだときに意図が伝わります。

## flaky テスト

### たまに失敗するテスト

コードを何も変えていないのに、通ったり失敗したりするテストを **flaky テスト**（不安定なテスト）と呼びます。flaky は「薄く剥がれやすい」という意味の英語です。

flaky テストは、見た目以上に有害です。「また例のやつか」と失敗を無視する習慣ができ、本物のバグによる失敗まで見逃すようになるからです。オオカミ少年のようなものです。

### よくある原因

- **テストの実行順**：あるテストが変えた状態を、別のテストが前提にしている。
- **時刻**：日付をまたぐ時間帯、月末、タイムゾーンの違いで結果が変わる。
- **乱数**：ランダムな値がたまに境界に当たる。
- **非同期の待ち方**：システムテストで、画面の表示を待たずに確かめている。
- **外部のもの**：ネットワークや外部 API に依存している。
- **並列実行**：同時に動く別のテストと、ファイルや共有の状態を取り合っている。

### 実行順による flaky を再現する

Minitest は、テストの実行順を毎回ランダムにします。順番に依存するテストを見つけ出すためです。その順番を決めているのが **シード**（種）の値で、実行結果の最初に `Run options: --seed 12345` のように表示されます。同じシードを指定すれば、同じ順番を再現できます。

わざと順番に依存するテストを書いてみます。

```ruby
require "minitest/autorun"

# テスト間で共有されてしまう状態（よくない例）
module Settings
  @locale = "ja"
  class << self
    attr_accessor :locale
  end
end

class FlakyOrderTest < Minitest::Test
  def test_switch_to_english
    Settings.locale = "en" # 変えたまま戻さない
    assert_equal "en", Settings.locale
  end

  def test_default_locale
    assert_equal "ja", Settings.locale
  end
end
```

シードを変えながら6回実行すると、次のようになりました。

```text
$ for s in 1 2 3 4 5 6; do echo "seed $s: $(ruby flaky_order_test.rb --seed $s | tail -1)"; done
seed 1: 2 runs, 2 assertions, 0 failures, 0 errors, 0 skips
seed 2: 2 runs, 2 assertions, 1 failures, 0 errors, 0 skips
seed 3: 2 runs, 2 assertions, 0 failures, 0 errors, 0 skips
seed 4: 2 runs, 2 assertions, 0 failures, 0 errors, 0 skips
seed 5: 2 runs, 2 assertions, 0 failures, 0 errors, 0 skips
seed 6: 2 runs, 2 assertions, 1 failures, 0 errors, 0 skips
```

```text
$ ruby flaky_order_test.rb --seed 2
...
  1) Failure:
FlakyOrderTest#test_default_locale [flaky_order_test.rb:18]:
Expected: "ja"
  Actual: "en"
```

`test_switch_to_english` が先に実行されたときだけ、`test_default_locale` が失敗します。どのシードで失敗するかは、Minitest のバージョンによって変わります。

直し方は「テストが変えた状態は、テストの最後に必ず元に戻す」です。Minitest なら `teardown` メソッドに戻す処理を書きます。もっとよいのは、そもそもテスト間で共有される状態（グローバルな設定やクラス変数）を作らない設計にすることです。

### flaky テストに出会ったら

1. **再現する**：失敗したときのシードを記録し、`bin/rails test --seed <その値>` で再実行する。時刻が原因なら、その時刻に `travel_to` して実行する。
2. **原因を絞る**：失敗するテストと、その直前に実行されたテストを組み合わせて実行し、相手を特定する。
3. **直す**：状態を元に戻す、時刻を固定する、外部を差し替える、システムテストでは Capybara の「表示されるまで待つ」仕組みを使う。`sleep` を足すのは、直したのではなく隠しただけです。
4. **すぐ直せないなら、チームに知らせる**：失敗するテストを黙って削除したり、無効にしたりしません。Issue を立て、誰が、いつまでに直すかを決めます。

「CI で失敗したら、もう一度実行すれば通る」という運用は、問題を先送りしているだけです。

## カバレッジの読み方

### カバレッジとは

**カバレッジ**（網羅率）は、テストを実行したときに、アプリのコードのうち何割が実行されたかを表す数字です。Ruby では **SimpleCov** という gem で測るのが一般的です。

```ruby
# test/test_helper.rb の一番上（アプリを読み込む行より前）
require "simplecov"
SimpleCov.start "rails"
```

アプリのコードが読み込まれた後に計測を始めても、正しく測れません。必ず一番上に書きます。テストを実行すると `coverage/index.html` に結果ができます。このフォルダは `.gitignore` に追加しておきます。

Rails のテストは、初期設定で複数のプロセスに分けて並列に実行されます（`test_helper.rb` の `parallelize`）。並列実行のときは、SimpleCov の結果をまとめるための追加の設定が必要です。最初は `PARALLEL_WORKERS=1 bin/rails test` のように並列を止めて測ると、確実です。

### 行カバレッジと分岐カバレッジ

カバレッジにはいくつか種類があります。

- **行カバレッジ**：何行が実行されたか。
- **分岐カバレッジ**：`if` の「真の場合」と「偽の場合」のように、分かれ道のそれぞれを通ったか。

行カバレッジだけだと見逃しが出ます。次の1行は、`if` が真でも偽でも「実行された」と数えられるからです。

```ruby
return "[不正な形式]" if domain.nil?
```

SimpleCov では `enable_coverage :branch` を設定すると、分岐カバレッジも表示されます。

### 数字の使い方

カバレッジは、次のように使うと役に立ちます。

- **赤い（実行されていない）行を見て、大事な所が抜けていないか確かめる**：特に、認可のチェック、エラー処理、お金や個人情報を扱う所。
- **新しく書いたコードがテストされているか確かめる**。

逆に、次の使い方は誤解のもとです。

- **「100%なら安心」と考える**：カバレッジは「実行されたか」しか測りません。実行しただけで何も確かめていない（`assert` がない）テストでも、数字は上がります。
- **数字を上げること自体を目的にする**：意味の薄いテストが増え、保守の手間だけが増えます。

カバレッジは「テストの品質の証明」ではなく、「テストが届いていない場所を探す地図」です。

## 静的解析：RuboCop

**RuboCop** は、Ruby のコードを読んで、書き方の決まり（スタイル）からのずれや、バグになりやすい書き方を指摘する静的解析ツールです。第20章の Brakeman がセキュリティに特化しているのに対し、RuboCop はコード全般の書き方を見ます。

Rails 7.2 以降の `rails new` では、Rails チームの決めたスタイル（rubocop-rails-omakase）で RuboCop が最初から入っています。

```bash
bin/rubocop          # 検査する
bin/rubocop -a       # 安全に直せるものを自動で直す
```

チームの全員が同じ書き方をすると、レビューで「インデントがずれています」のような指摘をしなくて済みます。人間は、設計や振る舞いのような、機械には判断できないことのレビューに集中できます。

ルールを変えたいときは `.rubocop.yml` に書きます。ただし、ルールはチームの合意で決めるものです。自分のコードが指摘されたからといって、勝手にルールを無効にしてはいけません。

## CI：毎回自動で確かめる

### CI とは

**CI**（Continuous Integration、継続的インテグレーション）は、変更をリポジトリに送るたびに、自動でテストや静的解析を実行する仕組みです。

人間は忘れます。「手元でテストを実行してから push する」という決まりがあっても、急いでいると飛ばします。それに、自分のPCでは通るのに、他の人の環境では通らないこともあります。たまたま自分のPCにだけ入っている設定やファイルに依存していると起きる問題です。CI は、毎回まっさらな環境でテストを実行するので、この「自分のPCでは動いた」問題も見つけてくれます。

### GitHub Actions の基本

**GitHub Actions** は、GitHub に組み込まれた CI の仕組みです。リポジトリの `.github/workflows/` に YAML ファイルを置くと、決めたタイミングで処理が実行されます。

用語を整理します。

- **ワークフロー**：1つの YAML ファイルで定義される、自動処理のまとまり。
- **トリガー**（`on`）：いつ実行するか。push されたとき、プルリクエストが作られたとき、など。
- **ジョブ**（`jobs`）：ワークフローの中の作業の単位。ジョブ同士は、初期設定では並行して実行される。
- **ステップ**（`steps`）：ジョブの中で順番に実行される1つ1つの手順。
- **ランナー**（`runs-on`）：ジョブを実行するマシン。GitHub が用意する Linux などの仮想マシンを使える。
- **アクション**（`uses`）：よく使う手順を部品にしたもの。コードの取得や Ruby の準備など。

### 設定ファイルの例

テストと RuboCop を実行する CI の例です。

```yaml
name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - name: コードを取得
        uses: actions/checkout@v4

      - name: Ruby を準備（.ruby-version を読む）
        uses: ruby/setup-ruby@v1
        with:
          bundler-cache: true

      - name: RuboCop
        run: bin/rubocop -f github

  test:
    runs-on: ubuntu-latest
    env:
      RAILS_ENV: test
    steps:
      - name: コードを取得
        uses: actions/checkout@v4

      - name: Ruby を準備（.ruby-version を読む）
        uses: ruby/setup-ruby@v1
        with:
          bundler-cache: true

      - name: テスト用DBを準備
        run: bin/rails db:test:prepare

      - name: テスト
        run: bin/rails test
```

上から順に説明します。

- `on`：プルリクエストのときと、`main` ブランチに push されたときに実行します。
- `permissions: contents: read`：このワークフローに与える権限を「リポジトリの読み取りだけ」に絞っています。CI が乗っ取られても被害を小さくするためです。第20章の「必要最小限」の考え方です。
- `lint` と `test` の2つのジョブ：並行して実行されます。分けておくと、どちらで失敗したかが一目で分かります。
- `actions/checkout`：リポジトリのコードをランナーに取ってきます。
- `ruby/setup-ruby`：Ruby を用意します。バージョンを指定しないと、リポジトリの `.ruby-version` を読みます。`bundler-cache: true` は、`bundle install` を実行し、その結果を次回のためにキャッシュします。
- `bin/rubocop -f github`：`-f github` は、指摘をプルリクエストの該当行に表示する形式で出力する指定です。
- `bin/rails db:test:prepare`：テスト用の DB を、`db/schema.rb` から作ります。SQLite なので、DB サーバは不要です。

`@v4` や `@v1` は、アクションのバージョンです。メジャーバージョンは時々上がるので、使うときは各アクションの公式の README で最新を確認してください。第20章で設定した Dependabot の `github-actions` の項目が、この更新を知らせてくれます。

なお、Rails 7.2 以降の `rails new` では、`.github/workflows/ci.yml` が最初から作られます。中身は上の例に近く、Brakeman などの検査も含まれています。自分のアプリにこのファイルがあれば、上の説明と見比べて、各行の意味を読み解いてみてください。

ちなみに、このファイルを Ruby の YAML ライブラリで読むと、`on` というキーが `true` に変わって表示されます。古い YAML の規則では `on` が真偽値の意味を持つためです。GitHub は正しく `on` として扱うので、心配はいりません。

### CI と秘密情報

CI でも、第20章のルールは同じです。

- **YAML ファイルに秘密情報を書かない**：このファイルはリポジトリにコミットされます。
- **必要なら GitHub の Secrets を使う**：リポジトリの設定画面で登録し、`${{ secrets.名前 }}` で参照します。ログに出力されると、GitHub が自動で伏せ字にしてくれます。ただし、加工した値（一部を切り出したものなど）は伏せ字にならないことがあるので、そもそも出力しないようにします。
- **テストは秘密情報なしで通るように作る**：テストで外部 API を呼ばず（WebMock など）、ダミーの値で動くようにしておけば、CI に本物の秘密情報を渡す必要がありません。これが一番安全です。
- 公開リポジトリでは、フォーク（他人が複製したリポジトリ）からのプルリクエストに対して、Secrets は渡されません。悪意のあるコードに秘密情報を盗まれないための仕組みです。

### CI が赤くなったら

CI が失敗すると、プルリクエストに赤い印が付きます。そのときの手順です。

1. 失敗したジョブとステップを開き、ログを読む。第7章で学んだとおり、エラーメッセージの最初と最後をまず見ます。
2. 手元で同じコマンドを実行して再現する。テストなら、ログに出ているシードを指定します。
3. 手元で再現しないなら、環境の違いを疑う。Ruby のバージョン、タイムゾーン、OS の違い、コミットし忘れたファイルなど。
4. 直して push する。CI が自動でもう一度実行されます。

「CI が赤いけど、たぶん関係ないのでマージします」は、チーム開発で最も嫌われる行動の一つです。

### マージの条件にする

CI を作っても、赤いままマージできてしまっては効果が半分です。GitHub のブランチの保護ルール（branch protection rules や rulesets）で、「CI が通らないと `main` にマージできない」と設定できます。第24章のチーム開発で、プルリクエストの流れと一緒に詳しく扱います。

## 実務ではこうなる

- **テストの実行時間は、チームの生産性に直結する**：全部のテストに30分かかるチームでは、1日に試せる変更の数が減ります。遅いテストを見つけて速くする（不要な E2E を結合テストに置き換える、など）のは立派な仕事です。
- **プルリクエストには、テストを一緒に入れる**：「テストは後で書きます」は、たいてい書かれません。レビューでは「この変更を確かめるテストはどれですか」と必ず聞かれます。
- **flaky テストは、チームで追跡する**：失敗の記録を集め、直す担当を決めます。放置すると、CI 全体が信用されなくなります。
- **CI の設定もコード**：ワークフローの YAML もレビューの対象です。権限を広げる変更や、外部のアクションを追加する変更は、特に慎重に見ます。外部のアクションは、他人が書いたコードを自分のリポジトリの権限で動かすことだからです（第20章の A08）。

ジュニアがやりがちな失敗も挙げておきます。

- テストを通すために、テスト側の期待値を実装に合わせて書き換えてしまう。テストが失敗したら、まず「実装とテストのどちらが正しいか」を考えます。
- モックだらけのテストを書き、全部通るのに本番で動かない。
- flaky テストに `sleep 1` を足して「直った」と報告する。
- CI の失敗を見ずに、レビュー依頼を出す。
- カバレッジを上げるために、`assert` のないテストを増やす。

## 演習

第21章のアプリをコピーして使います。

```bash
cp -R ~/workspace/ch21-api ~/workspace/ch22-ci
cd ~/workspace/ch22-ci
```

テストデータはダミーのみを使います。開発サーバを起動する場合は、これまでどおり `127.0.0.1` で待ち受け、`lsof` で確かめます。

### 演習22-1：テストの棚卸しとカバレッジ

- やること
  1. 今あるテストを、単体（`test/models/` など）・結合（`test/integration/` など）・システム（`test/system/`）に分類し、それぞれの数を数える。`bin/rails test` の実行時間も記録する。
  2. SimpleCov を導入し、分岐カバレッジも有効にする。`coverage/` を `.gitignore` に追加する。
  3. `PARALLEL_WORKERS=1 bin/rails test` でカバレッジを測り、`coverage/index.html` をブラウザで開く。
  4. 実行されていない行や分岐のうち、「壊れたら困る」ものを3つ選ぶ。選んだ理由を `docs/test-strategy.md` に書く。
  5. その3つを確かめるテストを書く。既存のコードに対するテストなので、まずテストを書いて通ることを確かめ、次に実装の該当部分を一時的に壊して、テストが失敗することを確かめる（確認後は元に戻す）。
  6. `docs/test-strategy.md` に、自分のアプリのテストピラミッドの現状（層ごとの数）と、今後どの層を厚くしたいかを書く。
- **完了条件**
  - `coverage/index.html` が生成され、`git status` に `coverage/` が表示されない。
  - 追加した3つのテストが成功し、それぞれ実装を壊すと失敗することを確認した。
  - `docs/test-strategy.md` に、層ごとのテストの数、実行時間、選んだ3か所とその理由が書かれている。
- ヒント
  - カバレッジの数字そのものを目標にしないでください。この演習のゴールは「大事な所の抜けを見つけること」です。
  - 認可のチェック、エラー処理、第21章の Webhook の署名検証の分岐などは、候補になりやすい場所です。

### 演習22-2：外部と時刻を差し替える

- やること
  1. WebMock を `Gemfile` の `test` グループに追加し、`test_helper.rb` で `WebMock.disable_net_connect!(allow_localhost: true)` を設定する。
  2. 第21章の `WeatherClient` のテストを、WebMock を使う形に書き直す（既に WebMock を使っていれば、確認だけでよい）。
  3. わざと、スタブしていない URL にアクセスするテストを1つ書いて実行し、WebMock がエラーにすることを確かめる。確認後はそのテストを消す。
  4. 時刻に依存する小さな機能を TDD で作る。例：投稿から24時間以内の投稿にだけ、一覧で「NEW」と表示する。テストでは `travel_to` で時刻を固定し、「23時間59分後には表示される」「24時間ちょうど（または1秒後）には表示されない」の境界を確かめる。どちらを境界にするかは自分で決め、テスト名に表す。
- **完了条件**
  - `bin/rails test` が成功し、テスト中に外部ネットワークへの通信が発生しない（WebMock の設定により、発生すればエラーになる状態である）。
  - 「NEW」表示のテストが、テストを実行する時刻に関係なく成功する。たとえば `TZ=America/Los_Angeles bin/rails test` のように、タイムゾーンを変えても成功する。
- ヒント
  - `allow_localhost: true` は、システムテストでブラウザが `127.0.0.1` のテスト用サーバにアクセスするために必要です。
  - 「24時間以内か」の判定をどこに書くか（モデル、ヘルパー、ビュー）によって、テストを書く層が変わります。単体テストで境界を細かく確かめ、結合テストでは表示されることだけを確かめる、という分担を考えてみてください。

### 演習22-3：flaky テストを作って、直す

- やること
  1. 自分のアプリに、わざと実行順に依存するテストを2つ作る。たとえば、あるテストでアプリの設定値（クラスに持たせた値や `ENV`）を変えて戻さず、別のテストがその初期値を前提にする。
  2. 次のコマンドで、シードを変えながら20回実行し、失敗するシードを見つける。
     ```bash
     for i in $(seq 1 20); do bin/rails test --seed $i > /dev/null 2>&1 || echo "seed $i failed"; done
     ```
  3. 見つけたシードで `bin/rails test --seed <値>` を実行し、毎回失敗することを確かめる（再現できた）。
  4. `teardown` で状態を元に戻す、または共有の状態を使わない設計に変えて直す。
  5. 原因・再現手順・直し方を `docs/test-strategy.md` に記録する。
- **完了条件**
  - 手順2のループで、20回すべてが成功する（`failed` が1行も表示されない）。
  - `docs/test-strategy.md` に、失敗したシードの値と、原因の説明がある。
- ヒント
  - 失敗が見つからない場合は、ループの回数を増やすか、`PARALLEL_WORKERS=1` を付けて並列実行を止めてみてください。並列実行だと、2つのテストが別のプロセスに分かれて、問題が隠れることがあります。
  - この演習で作った「わざと壊したテスト」は、直した後の形で残してかまいません。直す前の形をコミットに残しておくと、後で見返すときの教材になります。

### 演習22-4：GitHub Actions で CI を動かす

- やること
  1. GitHub に、この章の作業用の **非公開** リポジトリを作り、push する。push の前に `git ls-files -- config/master.key .env '*.pem' '*.key'` を実行し、何も表示されないことを確かめる。
  2. `.github/workflows/ci.yml` を作る（`rails new` で作られたものがあれば、それを読んで理解したうえで使う）。少なくとも、RuboCop のジョブとテストのジョブを含める。
  3. 第20章の Brakeman と bundler-audit を実行するジョブを追加する。
  4. 新しいブランチを作り、わざと RuboCop の指摘が出る変更（インデントを崩すなど）を入れてプルリクエストを作る。CI が赤くなり、どの行が問題か表示されることを確かめる。
  5. 同じプルリクエストで、指摘を直して push する。CI が緑になることを確かめる。
  6. わざとテストが失敗する変更でも同じことを試す。ログから失敗したテストの名前とシードを読み取り、手元で再現する。
  7. 発展：ブランチの保護ルールを設定し、CI が通らないと `main` にマージできないようにする。
- **完了条件**
  - プルリクエストの画面で、RuboCop・テスト・セキュリティ検査のジョブがすべて緑（成功）になっている。
  - わざと壊したときに CI が赤くなったことを、プルリクエストの履歴で確認できる。
  - ワークフローの YAML に、秘密情報が書かれていない。
- ヒント
  - CI で `bundle install` が失敗し、プラットフォーム（`x86_64-linux` など）についてのメッセージが出たら、`Gemfile.lock` に Linux 用のプラットフォームが入っていない可能性があります。`bundle lock --add-platform x86_64-linux` を調べてください。
  - テストが CI だけで失敗するなら、手元との違い（タイムゾーン、ファイルのコミット漏れ、`.gitignore` で除外したファイルへの依存）を疑います。
  - 非公開リポジトリでの GitHub Actions の利用には、アカウントの種類によって使える量の上限があります。上限の詳細は GitHub の公式ドキュメントで確認してください。

## 確認クイズ

**Q1.** E2E テストは「本物に一番近い」のに、なぜ数を少なくするのがよいとされるのか。

**Q2.** スタブとモックの違いを、それぞれ一言で説明せよ。

**Q3.** 外部 API を呼ぶクラスのテストで、Active Record のメソッドもすべてスタブして DB を使わないようにした。何が問題になりうるか。

**Q4.** あるテストが、CI で10回に1回失敗する。もう一度実行すると通る。どう対応すべきか。

**Q5.** カバレッジが100%になった。このアプリにバグはないと言えるか。

**Q6.** CI のワークフローの YAML に、テストで使う外部 API のキーを直接書きたい。問題はあるか。どうすべきか。

### 解答と解説

1. **遅く、壊れやすく、失敗したときに原因が分かりにくいからです。** 本物のブラウザを動かすため実行に時間がかかり、表示の待ち方などで揺らぎが出ます。大事な流れだけを E2E で確かめ、細かい条件は速い単体・結合テストで確かめます。
2. **スタブは「決まった答えを返す偽物」、モックは「正しく呼ばれたかを後で確かめる偽物」です。** スタブはテスト対象への入力を用意し、モックはテスト対象からの呼び出し（出力）を確かめます。
3. **本物の DB で起きる問題を見逃します。** 制約違反、SQL の間違い、関連の設定ミスなどです。差し替えるのは、自分で制御できない境界（外部 API、時刻、乱数など）だけにし、DB はテスト用の本物を使います。
4. **flaky テストとして原因を調べて直します。** 失敗したときのシードを記録して再現し、実行順・時刻・外部・非同期の待ち方などの原因を探します。再実行で通るのを待つ、`sleep` を足す、黙って無効にする、はどれも問題の先送りです。すぐ直せなければ Issue を立てて共有します。
5. **言えません。** カバレッジは「コードが実行されたか」だけを測ります。実行しても結果を確かめていないテストや、仕様そのものの間違いは見つけられません。カバレッジは、テストが届いていない場所を探す地図として使います。
6. **問題があります。** YAML はリポジトリにコミットされるので、キーが漏れます（第20章）。そもそもテストで外部 API を呼ばないように WebMock などで差し替えるのが一番です。どうしても必要なら GitHub の Secrets に登録し、`${{ secrets.名前 }}` で参照します。

## AIの使い方（この章）

推奨する聞き方の例：

- 「次のテストが flaky です。失敗したときのログと、テストのコードを貼ります（ダミーデータのみ）。考えられる原因を可能性の高い順に3つ挙げ、それぞれを確かめる方法を教えてください。直し方は自分で考えます」
- 「自分のアプリのテストの分類と数はこうです（演習22-1の表）。テストピラミッドの観点から、どの層が厚すぎる・薄すぎるか意見をください」
- 「この GitHub Actions のワークフローの各行が何をしているか、自分の理解を書きました。間違っている所を指摘してください」

やってはいけない使い方：

- 「カバレッジが100%になるようにテストを生成して」と依頼し、中身を読まずに取り込む。数字だけが上がり、何も確かめていないテストが増えます。
- CI のログを、そのまま AI に貼り付ける。ログには環境変数やパス、場合によっては秘密情報の断片が含まれます。必要な部分だけを、伏せ字にしてから貼ります。

## まとめ

- テストは、速い単体テストを土台に、結合テストを中ほどに、E2E テストを少しだけ持つピラミッドの形にします。
- モックとスタブは、外部 API・時刻・乱数など、自分で制御できない境界だけに使います。
- flaky テストはシードや時刻の固定で再現してから直し、決して放置しません。
- カバレッジは「テストが届いていない場所」を探すための地図で、品質の証明ではありません。
- CI でテストと静的解析を毎回まっさらな環境で実行し、通らなければマージしない仕組みにします。

## 用語

| 用語 | 意味 |
|---|---|
| テスト戦略 | どの種類のテストを、どれくらいの割合で持つかという全体の設計 |
| テストピラミッド | 単体テストを多く、結合テストを中ほど、E2E テストを少なく持つ考え方 |
| 単体テスト | 1つのクラスやメソッドを単独で確かめるテスト |
| 結合テスト | 複数の部品を組み合わせて確かめるテスト |
| E2E テスト・システムテスト | 本物のブラウザで、利用者と同じ操作を最初から最後まで確かめるテスト |
| テストダブル | テストのために本物の代わりに使う偽物の総称 |
| スタブ | 決まった答えを返す偽物 |
| モック | 正しく呼ばれたかを記録し、後で確かめる偽物 |
| 依存性の注入 | 部品が使うものを、外から渡せるように作る設計 |
| fixtures | Rails 標準の、YAML で書くテストデータ |
| factory | テストの中で、ひな形からデータを作る方法。factory_bot が代表 |
| flaky テスト | コードを変えていないのに、通ったり失敗したりするテスト |
| シード | テストの実行順を決める乱数の種。同じ値で同じ順番を再現できる |
| カバレッジ | テストでコードの何割が実行されたかを表す数字 |
| CI | 変更のたびに、自動でテストや静的解析を実行する仕組み |
