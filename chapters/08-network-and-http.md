# 第8章 ネットワークとHTTP

> **この章のゴール**：URL を開いてからページが表示されるまでに、IP アドレス・ポート・DNS・TCP・HTTP が何をしているかを説明できるようになる。`curl -v` で HTTP のやり取りを観察し、読めるようになる。
> **目安時間**：読む 3時間 ＋ 演習 3時間
> **前提**：第7章まで

## この章で学ぶこと

- URL を、スキーム・ホスト・ポート・パス・クエリに分解できる
- IP アドレス・ポート・DNS の役割を、たとえを使って説明できる
- TCP が「順番どおりに届くバイトの通り道」であることを説明できる
- HTTP のリクエストとレスポンスの形（開始行・ヘッダ・空行・ボディ）を読める
- `curl -v` でやり取りを観察し、ステータスコードの意味を判断できる
- `127.0.0.1` と `0.0.0.0` で待ち受ける違いを説明し、`lsof` で待受先を確かめられる

## URL を開くと何が起きるのか

ブラウザのアドレス欄に `http://example.com/` と入力して Enter を押すと、裏では次のようなことが順番に起きています。

1. **URL を分解する**：どこの、どの窓口に、何を頼むのかを読み取る。
2. **DNS で住所を調べる**：`example.com` という名前から、IP アドレス（ネットワーク上の住所）を調べる。
3. **TCP で接続する**：その住所の、決まった番号の窓口（ポート）に、通り道をつなぐ。
4. **HTTP でお願いを送る**：「`/` のページをください」というリクエストを送る。
5. **HTTP で返事を受け取る**：サーバが、結果と HTML を含むレスポンスを返す。
6. **表示する**：ブラウザが HTML を読み、画面に描く。画像や CSS が必要なら、2〜5をさらに繰り返す。

レストランの出前にたとえると、次のようになります。

| 手順 | 出前でたとえると |
|---|---|
| URL | 「〇〇亭の、出前窓口に、ラーメンを1杯」というメモ |
| DNS | 店の名前から、電話帳で電話番号（住所）を調べる |
| IP アドレス | 店の住所 |
| ポート | 店の中の窓口番号（出前窓口、予約窓口など） |
| TCP | 電話をかけて、つながった状態にする |
| HTTP | 注文の言い方のルール（何を、いくつ、どこへ） |

この章の後半から、第11章では Ruby でこのサーバ側を自分で作ります。そのときに「今どの段階の話をしているのか」がわかるよう、この章で全体の地図を持っておきましょう。

## URL を分解する

**URL** は、「どこの、何を、どうやって」取りに行くかを1行で表した住所書きです。Ruby の `URI` ライブラリで分解してみます。

```ruby
require "uri"

u = URI.parse("http://localhost:3000/search?q=ruby&page=2#result")
p u.scheme
p u.host
p u.port
p u.path
p u.query
p u.fragment
p URI.parse("https://example.com/").port
```

```console
$ ruby url_parts.rb
"http"
"localhost"
3000
"/search"
"q=ruby&page=2"
"result"
443
```

| 部分 | この例では | 意味 |
|---|---|---|
| スキーム | `http` | どの方法（プロトコル）で通信するか。`https` なら暗号化された HTTP |
| ホスト | `localhost` | 相手のコンピュータの名前、または IP アドレス |
| ポート | `3000` | 相手のコンピュータの中の、どの窓口か |
| パス | `/search` | サーバの中の、どの資源（ページやデータ）か |
| クエリ | `q=ruby&page=2` | 追加の条件。`名前=値` を `&` でつなぐ |
| フラグメント | `result` | ページの中の位置。**サーバには送られない** |

ポートを省略すると、スキームごとに決まった番号が使われます。`http` なら80番、`https` なら443番です。最後の行で `https://example.com/` のポートが 443 になったのはこのためです。

フラグメント（`#` の後ろ）は、ブラウザの中だけで使われます。ページを読み込んだ後に、その位置までスクロールするための目印です。HTTP のリクエストには含まれません。

**プロトコル**という言葉が出てきました。プロトコルとは、通信する者どうしの「約束ごと」です。電話で「もしもし」から始め、用件を伝え、「失礼します」で切る、という流れも一種のプロトコルです。HTTP も TCP も、それぞれの約束ごとの名前です。

## IP アドレス：コンピュータの住所

ネットワークにつながったコンピュータには、**IP アドレス**という番号が付いています。データを届けるときの宛先、つまり住所です。

IP アドレスには2つの形式があります。

- **IPv4**：`192.168.1.10` のように、0〜255 の数を4つ、点で区切ったもの。
- **IPv6**：`2606:4700:10::ac42:93f3` のように、16進数をコロンで区切ったもの。IPv4 の数が足りなくなったために作られました。

### 特別な住所：127.0.0.1（ループバック）

`127.0.0.1` は特別な IP アドレスです。意味は「**自分自身のこのコンピュータ**」です。この住所に送ったデータは、ネットワークの外に出ずに、同じコンピュータの中で折り返します。そのため**ループバック**（輪になって戻る）アドレスと呼ばれます。IPv6 では `::1` が同じ意味です。

`localhost` という名前も、ふつうはこのループバックアドレスを指します。家の中の内線電話のようなものです。家の中からはかけられますが、外の人からはかけられません。

この教材の演習で作るサーバは、すべてこの `127.0.0.1` で待ち受けます。理由はこの章の最後で詳しく説明します。

### 家の中の住所と、外向きの住所

自宅やカフェの Wi-Fi につながると、PC には `192.168.x.x` のような住所が割り当てられます。これは**プライベート IP アドレス**と呼ばれ、同じ Wi-Fi の中だけで通じる住所です。マンションの部屋番号のようなもので、同じ建物の中では通じます。

インターネット全体で通じる住所は、**グローバル IP アドレス**と呼ばれます。家の中の機器がインターネットに出るときは、ルーターがグローバル IP アドレスに付け替えます。マンションの住所が、建物全体の代表の住所になるイメージです。

ここで大切なのは、**同じ Wi-Fi にいる他人からは、あなたの PC のプライベート IP アドレスに接続できる場合がある**ことです。カフェで隣に座っている人も、同じ「建物」の住人です。

## ポート：建物の中の窓口番号

1台のコンピュータの中では、たくさんのプログラムが同時に通信しています。ブラウザ、チャットアプリ、自分で作ったサーバなどです。IP アドレスだけでは、どのプログラム宛てのデータなのか区別できません。そこで使うのが**ポート番号**です。

IP アドレスが建物の住所なら、ポート番号はその建物の中の窓口番号です。郵便で言えば、「〇〇ビル（IP アドレス）の、305号室（ポート）」です。

ポート番号は 0〜65535 の整数です。よく使われる番号は、慣習で決まっています。

| ポート | 主な用途 |
|---|---|
| 80 | HTTP |
| 443 | HTTPS |
| 22 | SSH（サーバへのリモート接続） |
| 3000 | Rails などの開発用サーバでよく使われる（慣習） |

1024 番より小さい番号は、多くの OS で特別な権限が必要です。そのため開発中は 3000 番や 8080 番のような大きめの番号を使います。

サーバが特定のアドレスとポートで接続を待つことを、**待ち受ける**（listen する）と言います。窓口を開けて、客を待つ状態です。

### 1つのポートには、1つのプログラムだけ

同じアドレスとポートで、2つのプログラムが同時に待ち受けることはできません。すでに使われているポートで待ち受けようとすると、次のようなエラーになります。

```console
$ ruby -e 'require "socket"; TCPServer.new("127.0.0.1", 3000)'
-e:1:in `initialize': Address already in use - bind(2) for "127.0.0.1" port 3000 (Errno::EADDRINUSE)
	from -e:1:in `new'
	from -e:1:in `<main>'
```

`Address already in use`（アドレスはすでに使われている）は、演習で何度も見るエラーです。多くの場合、前に起動したサーバを止め忘れています。どのプログラムが使っているかは、`lsof` で確かめられます（Linux や WSL では `ss -ltnp`）。

```console
$ lsof -nP -iTCP:3000 -sTCP:LISTEN
COMMAND  PID   USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
ruby    8479 you      9u  IPv4 0xa56d29344307c559      0t0  TCP 127.0.0.1:3000 (LISTEN)
```

- `-iTCP:3000`：TCP の3000番ポートに関係するものを表示する
- `-sTCP:LISTEN`：待ち受け中のものだけに絞る
- `-nP`：名前やポートを、変換せずに数字のまま表示する

`COMMAND` と `PID`（プロセス番号）で、どのプログラムかがわかります。一番右の `NAME` が、実際に待ち受けているアドレスとポートです。この見方は、この章の最後で重要になります。

## DNS：名前から住所を調べる

人間にとって `104.20.23.154` のような数字は覚えにくいものです。そこで、`example.com` のような名前（**ドメイン名**）を使います。名前を IP アドレスに変換する仕組みが **DNS**（Domain Name System）です。

DNS は、インターネットの電話帳です。「〇〇亭」という店名で電話帳を引くと、電話番号がわかります。ブラウザも、まず DNS で名前を引いてから、その住所に接続します。

`dig` コマンドで、DNS を引いてみましょう（Linux や WSL で `dig` がない場合は `nslookup example.com` でも構いません）。

```console
$ dig +short example.com A
172.66.147.243
104.20.23.154
$ dig +short example.com AAAA
2606:4700:10::6814:179a
2606:4700:10::ac42:93f3
```

- `A` は IPv4 のアドレス、`AAAA` は IPv6 のアドレスを問い合わせる指定です。
- 1つの名前に、複数のアドレスが登録されていることがあります。大きなサイトは、複数のサーバで負荷を分けているからです。
- 結果は、時期や場所によって変わります。あなたの結果が上と違っていても問題ありません。

### localhost はどこで引かれるのか

`localhost` は、インターネットの DNS ではなく、PC の中の `/etc/hosts` というファイルで決まっていることが多いです。

```console
$ grep localhost /etc/hosts
127.0.0.1	localhost
::1             localhost
```

`localhost` には、IPv4 の `127.0.0.1` と IPv6 の `::1` の2つが登録されています。Ruby でも確かめられます。

```ruby
require "socket"
p Addrinfo.getaddrinfo("localhost", 3000, nil, :STREAM).map(&:inspect_sockaddr)
```

```console
$ ruby resolve.rb
["127.0.0.1:3000", "[::1]:3000"]
```

（順番は環境によって違います。）

`localhost` が2つの住所を持つことは、後で `curl` の動きを観察するときに出てきます。

## TCP：順番どおりに届く通り道

住所（IP アドレス）と窓口（ポート）がわかったら、実際にデータを送ります。Web の通信では、**TCP**（Transmission Control Protocol）という約束ごとを使います。

TCP の特徴は次の3つです。

1. **最初に接続する**：データを送る前に、相手と「つながった」状態を作ります。電話で、相手が出たことを確かめてから話し始めるのと同じです。
2. **確実に、順番どおりに届ける**：ネットワークの途中でデータが失われたら、TCP が自動で送り直します。届いた順番が入れ替わっても、元の順番に並べ直します。
3. **バイトの流れとして運ぶ**：TCP は、送られたデータを「区切りのないバイトの流れ」として運びます。

3つ目は、とても大事な点です。送る側が「こんにちは」と「さようなら」を別々に送っても、受け取る側では「こんにちはさようなら」とつながって届くことがあります。逆に、1回で送ったものが、2回に分かれて届くこともあります。TCP は「どこからどこまでが1つのメッセージか」を教えてくれません。

ホースで水を送るようなものです。水は確実に、順番どおりに届きます。しかし、コップ何杯分ずつ送ったかは、受け取る側にはわかりません。区切りは、上に乗る約束ごと（HTTP）が自分で決める必要があります。第11章で HTTP サーバを作るとき、この「区切りをどう判断するか」が中心的な課題になります。

### 通信は「層」になっている

ここまでの登場人物を整理すると、通信は次のような層（レイヤー）になっています。

```text
HTTP   … 何を頼み、何を返すか（注文の言い方）
  ↓ の上に乗る
TCP    … 確実に順番どおりに運ぶ（電話の通話）
  ↓ の上に乗る
IP     … 住所を頼りに届ける（電話網）
```

上の層は、下の層の細かいことを気にしなくて済みます。HTTP は「データが確実に届く」ことを TCP に任せています。TCP は「どうやって相手の住所まで運ぶか」を IP に任せています。このように、役割を分けて積み重ねる考え方は、ソフトウェアのあちこちに出てきます。

なお、**UDP** という別の約束ごともあります。UDP は接続を作らず、届いたかの確認もしません。その代わり速いので、動画の配信やオンラインゲームなどに使われます。この教材では TCP だけを扱います。

## HTTP：Web のやり取りの約束ごと

**HTTP**（HyperText Transfer Protocol）は、ブラウザとサーバが「何を頼み、何を返すか」を決めた約束ごとです。基本は、クライアント（頼む側）が**リクエスト**を送り、サーバが**レスポンス**を1つ返す、という往復です。

この章で扱うのは **HTTP/1.1** です。HTTP/1.1 は、リクエストやレスポンスの前半部分を、人間が読める文字で書くのが特徴です。新しい HTTP/2 や HTTP/3 は、同じ意味のやり取りを、機械向けの形式（バイナリ）で送ります。意味は共通なので、まず読める HTTP/1.1 で仕組みを学びます。

### リクエストの形

ブラウザや curl が送るリクエストは、次のような形をしています。

```http
GET /search?q=ruby HTTP/1.1
Host: 127.0.0.1:4000
User-Agent: curl/8.7.1
Accept: */*

```

| 部分 | この例では | 意味 |
|---|---|---|
| リクエスト行 | `GET /search?q=ruby HTTP/1.1` | メソッド・パス（とクエリ）・HTTP のバージョン |
| ヘッダ | `Host: ...` など | 追加情報。`名前: 値` の形で1行に1つ |
| 空行 | （何もない行） | ヘッダの終わりの印 |
| ボディ | （この例ではなし） | 送りたいデータ本体。フォームの入力内容など |

ここで、目に見えない大切な決まりがあります。HTTP/1.1 では、**各行の終わりは CRLF**（`\r\n`）という2文字の改行です。ふだんの Ruby の `"\n"`（LF）だけではありません。ヘッダの終わりは、最後のヘッダ行の CRLF に続けて、もう1つ CRLF を置きます。つまり `\r\n\r\n` が「ヘッダはここまで」の印です。

HTTP/1.1 では `Host` ヘッダが必須です。1つの IP アドレスで、複数のサイト（`a.example` と `b.example` など）を動かしていることがあるからです。`Host` を見れば、サーバはどのサイト宛てのリクエストかを判断できます。

### レスポンスの形

サーバが返すレスポンスは、次のような形です。

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 19
Connection: close

<h1>Hello HTTP</h1>
```

| 部分 | この例では | 意味 |
|---|---|---|
| ステータス行 | `HTTP/1.1 200 OK` | バージョン・ステータスコード・その説明 |
| ヘッダ | `Content-Type: text/html` など | ボディの種類や長さなどの追加情報 |
| 空行 | （何もない行） | ヘッダの終わりの印 |
| ボディ | `<h1>Hello HTTP</h1>` | 返す内容そのもの。HTML、画像、JSON など |

`Content-Length: 19` は、「ボディは19バイトです」という意味です。TCP はメッセージの区切りを教えてくれないので、受け取る側はこの数字を頼りに「どこまでがボディか」を判断します。ここでの単位は**バイト**であって、文字数ではありません。日本語の「テスト」は3文字ですが、UTF-8 では9バイトです。

```console
$ ruby -e 'p "テスト".bytesize, "テスト".length'
9
3
```

### メソッド：何をしてほしいか

リクエスト行の最初の単語は**メソッド**です。サーバに「何をしてほしいか」を表します。

| メソッド | 意味 | 例 |
|---|---|---|
| GET | 資源を取得する | ページを表示する、一覧を見る |
| POST | 新しく作る・処理を依頼する | フォームから投稿する |
| PUT / PATCH | 更新する（全体／一部） | プロフィールを変更する |
| DELETE | 削除する | 投稿を消す |
| HEAD | GET と同じだが、ヘッダだけを返してもらう | 存在や更新日時の確認 |

大切な約束が1つあります。**GET は、サーバの状態を変えてはいけません。** GET は「見るだけ」の操作として扱われます。ブラウザは GET を先読みしたり、何度も送り直したりすることがあるからです。データを変更する操作は POST などで行います。この約束は、第10章と第19章で扱う安全対策（CSRF 対策）の前提にもなります。

### ステータスコード：結果はどうだったか

レスポンスの最初の行にある3桁の数字が、**ステータスコード**です。百の位で、大まかな意味が決まっています。

| 範囲 | 分類 | 主なコード |
|---|---|---|
| 1xx | 情報 | （この教材ではほぼ使わない） |
| 2xx | 成功 | 200 OK（成功）、201 Created（作成した）、204 No Content（成功、返す本文なし） |
| 3xx | 転送 | 301 Moved Permanently（恒久的に移動）、302 Found / 303 See Other（別の場所を見て）、304 Not Modified（前と同じ） |
| 4xx | **クライアント側**の問題 | 400 Bad Request（リクエストがおかしい）、401 Unauthorized（認証が必要）、403 Forbidden（権限がない）、404 Not Found（ない）、405 Method Not Allowed（そのメソッドは使えない）、422 Unprocessable Content（内容を処理できない） |
| 5xx | **サーバ側**の問題 | 500 Internal Server Error（サーバ内部のエラー）、502 Bad Gateway（中継先のエラー）、503 Service Unavailable（一時的に使えない） |

4xx と 5xx の区別は、障害を調べるときにとても役立ちます。4xx なら「送った側のリクエストを見直す」、5xx なら「サーバのログを見る」というように、調べる場所が変わるからです。

3xx のレスポンスには、`Location` ヘッダで「次に行くべき URL」が入っています。ブラウザはそれを見て、自動でそちらにリクエストし直します。これを**リダイレクト**と呼びます。

### よく見るヘッダ

| ヘッダ | 向き | 意味 |
|---|---|---|
| Host | リクエスト | 宛先のホスト名とポート |
| User-Agent | リクエスト | 送り手のソフトウェアの名前（ブラウザや curl） |
| Accept | リクエスト | 受け取れるデータの種類 |
| Content-Type | 両方 | ボディのデータの種類（`text/html`、`application/json` など） |
| Content-Length | 両方 | ボディのバイト数 |
| Location | レスポンス | リダイレクト先の URL |
| Connection | 両方 | 応答の後に接続を閉じるか（`close`）、使い続けるか（`keep-alive`） |
| Set-Cookie / Cookie | レスポンス／リクエスト | ブラウザに情報を覚えさせる仕組み（第19章） |

### HTTP は「毎回はじめまして」

HTTP には、前のリクエストを覚えておく仕組みがありません。1つ1つのリクエストは独立しています。この性質を**ステートレス**と呼びます。

毎回「はじめまして」の受付係のようなものです。さっき来た人が、またやってきても、受付係は覚えていません。ログインしたことを覚えておくには、Cookie という「会員証」を毎回見せてもらう仕組みが必要です。これは第19章で学びます。

## curl -v で HTTP を観察する

ここからは、実際に HTTP のやり取りを観察します。**curl** は、ターミナルから HTTP リクエストを送るコマンドです。`-v`（verbose、詳しく）を付けると、送ったリクエストと受け取ったレスポンスのヘッダを表示します。

### 観察用のサーバを起動する

まず、観察の相手になるサーバを自分の PC で起動します。Ruby の WEBrick という小さな Web サーバを使います。Ruby 3.0 以降は WEBrick が Ruby に含まれていないので、Gemfile で用意します。

```bash
mkdir -p ~/workspace/ch08-network/public
cd ~/workspace/ch08-network
printf '%s' '<h1>Hello HTTP</h1>' > public/index.html
```

`Gemfile` を作ります。

```ruby
source "https://rubygems.org"

gem "webrick"
```

```bash
bundle install
bundle exec ruby -run -e httpd -- --bind-address=127.0.0.1 --port=3000 public
```

```console
[2026-10-01 17:42:42] INFO  WEBrick 1.9.2
[2026-10-01 17:42:42] INFO  ruby 2.6.10 (2022-04-12) [universal.x86_64-darwin23]
[2026-10-01 17:42:42] INFO  WEBrick::HTTPServer#start: pid=8479 port=3000
```

（版や日時の表示は環境によって違います。）

- `ruby -run -e httpd` は、指定したフォルダの中身をそのまま配信する、簡易 Web サーバを起動します。
- `--bind-address=127.0.0.1` で、**ループバックだけで待ち受ける**ように指定しています。この指定は省略しないでください。
- 最後の `public` が、配信するフォルダです。このフォルダの外のファイルは配信されません。

この端末はサーバが動いたままになります。**別の端末（ターミナルのウィンドウやタブ）を開き**、まず待受先を確かめます。

```console
$ lsof -nP -iTCP:3000 -sTCP:LISTEN
COMMAND  PID   USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
ruby    8479 you      9u  IPv4 0xa56d29344307c559      0t0  TCP 127.0.0.1:3000 (LISTEN)
```

`NAME` が `127.0.0.1:3000` になっていれば、ループバックだけで待ち受けています。

### curl -v の出力を読む

同じ別の端末で、curl を実行します。

```console
$ curl -v http://127.0.0.1:3000/
*   Trying 127.0.0.1:3000...
* Connected to 127.0.0.1 (127.0.0.1) port 3000
> GET / HTTP/1.1
> Host: 127.0.0.1:3000
> User-Agent: curl/8.7.1
> Accept: */*
> 
* Request completely sent off
< HTTP/1.1 200 OK
< Etag: 65cbb-13-6abe1d01
< Content-Type: text/html
< Content-Length: 19
< Last-Modified: Thu, 01 Oct 2026 08:42:41 GMT
< Server: WEBrick/1.9.2 (Ruby/2.6.10/2022-04-12)
< Date: Thu, 01 Oct 2026 08:42:45 GMT
< Connection: Keep-Alive
< 
* Connection #0 to host 127.0.0.1 left intact
<h1>Hello HTTP</h1>
```

行の先頭の記号で、何の行かがわかります。

| 先頭 | 意味 |
|---|---|
| `*` | curl 自身のメモ（接続の状況など） |
| `>` | curl が**送った**内容（リクエスト） |
| `<` | curl が**受け取った**内容（レスポンス） |
| 記号なし | レスポンスのボディ |

上から順に、この章で学んだことを当てはめてみましょう。

1. `Trying 127.0.0.1:3000...` と `Connected` で、**TCP の接続**ができました。
2. `>` の行が **HTTP リクエスト**です。リクエスト行、ヘッダ、そして空行（`> ` だけの行）があります。
3. `<` の行が **HTTP レスポンス**です。ステータス行 `200 OK`、ヘッダ、空行と続きます。
4. 最後の行がボディです。`Content-Length: 19` のとおり、19バイトです。

サーバを起動した端末を見ると、アクセスの記録（ログ）が増えています。

```text
127.0.0.1 - - [01/Oct/2026:17:42:54 JST] "GET / HTTP/1.1" 200 19
```

接続元が `127.0.0.1`（自分自身）であること、リクエスト行、ステータスコード、ボディのバイト数が記録されています。

### いろいろなリクエストを送ってみる

curl のオプションを変えると、いろいろなリクエストを送れます。

| コマンド | すること |
|---|---|
| `curl -i URL` | レスポンスのヘッダとボディを表示する（`-v` より簡潔） |
| `curl -I URL` | HEAD メソッドで送り、ヘッダだけを表示する |
| `curl -d 'title=test' URL` | POST メソッドで、ボディにデータを付けて送る |
| `curl -L URL` | リダイレクトされたら、自動で次の URL についていく |
| `curl -H 'X-Name: 値' URL` | 好きなヘッダを追加する |

存在しないパスにアクセスすると、404 が返ります。

```console
$ curl -i http://127.0.0.1:3000/missing
HTTP/1.1 404 Not Found
Content-Type: text/html; charset=ISO-8859-1
Server: WEBrick/1.9.2 (Ruby/2.6.10/2022-04-12)
Date: Thu, 01 Oct 2026 08:42:54 GMT
Content-Length: 278
Connection: close

<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.0//EN">
<HTML>
  <HEAD><TITLE>Not Found</TITLE></HEAD>
  <BODY>
    <H1>Not Found</H1>
    '/missing' not found.
（以下略）
```

この簡易サーバはファイルを配るだけなので、POST には対応していません。POST を送ると、405 が返ります。

```console
$ curl -i -d 'title=test' http://127.0.0.1:3000/
HTTP/1.1 405 Method Not Allowed
Content-Type: text/html; charset=ISO-8859-1
（中略）
    unsupported method 'POST'.
（以下略）
```

`public/docs/index.html` を作り、末尾に `/` を付けずに `/docs` にアクセスすると、リダイレクトが観察できます。

```console
$ mkdir -p public/docs
$ printf '%s' '<p>docs</p>' > public/docs/index.html
$ curl -i http://127.0.0.1:3000/docs
HTTP/1.1 301 Moved Permanently
Location: http://127.0.0.1:3000/docs/
Server: WEBrick/1.9.2 (Ruby/2.6.10/2022-04-12)
Date: Thu, 01 Oct 2026 08:42:54 GMT
Content-Length: 42
Connection: Keep-Alive

<HTML><A HREF="/docs/">/docs/</A>.</HTML>
```

`Location` ヘッダに、次に行くべき URL が入っています。`-L` を付けると、curl がそれについていきます。

```console
$ curl -iL http://127.0.0.1:3000/docs
HTTP/1.1 301 Moved Permanently
Location: http://127.0.0.1:3000/docs/
（中略）
HTTP/1.1 200 OK
（中略）
<p>docs</p>
```

レスポンスが2つ続いていることに注目してください。1回のコマンドで、HTTP の往復が2回行われました。ブラウザも、リダイレクトのたびに同じことをしています。

### localhost で接続したときの動き

今度は `127.0.0.1` ではなく `localhost` で接続してみます。

```console
$ curl -v http://localhost:3000/
* Host localhost:3000 was resolved.
* IPv6: ::1
* IPv4: 127.0.0.1
*   Trying [::1]:3000...
* connect to ::1 port 3000 from ::1 port 53958 failed: Connection refused
*   Trying 127.0.0.1:3000...
* Connected to localhost (127.0.0.1) port 3000
> GET / HTTP/1.1
> Host: localhost:3000
（以下略）
```

（表示は curl の版や OS の設定によって違います。）

curl はまず名前を引き、`::1` と `127.0.0.1` の2つの住所を得ました。最初に IPv6 の `::1` に接続しようとして、`Connection refused`（接続を拒否された）になりました。サーバは IPv4 の `127.0.0.1` だけで待ち受けているからです。そこで curl は、次の `127.0.0.1` を試して接続に成功しています。

`Connection refused` は「その住所のその窓口では、誰も待っていない」という意味です。サーバを起動し忘れたときや、ポート番号を間違えたときにも出ます。

```console
$ curl -v http://127.0.0.1:3001/
*   Trying 127.0.0.1:3001...
* connect to 127.0.0.1 port 3001 from 127.0.0.1 port 53875 failed: Connection refused
* Failed to connect to 127.0.0.1 port 3001 after 0 ms: Couldn't connect to server
* Closing connection
curl: (7) Failed to connect to 127.0.0.1 port 3001 after 0 ms: Couldn't connect to server
```

## 生の HTTP を見る

curl の `-v` の表示は、読みやすいように整えられています。本当にネットワークを流れているバイトを見てみましょう。

### Ruby で HTTP リクエストを手書きして送る

Ruby の `TCPSocket` を使うと、TCP で接続して、好きな文字列を送れます。観察用サーバが動いている状態で、別の端末から実行します。

```bash
ruby -rsocket -e 'TCPSocket.open("127.0.0.1", 3000) { |socket| socket.write("GET / HTTP/1.1\r\nHost: localhost:3000\r\nConnection: close\r\n\r\n"); p socket.read }'
```

```console
"HTTP/1.1 200 OK\r\nEtag: 65cbb-13-6abe1d01\r\nContent-Type: text/html\r\nContent-Length: 19\r\nLast-Modified: Thu, 01 Oct 2026 08:42:41 GMT\r\nServer: WEBrick/1.9.2 (Ruby/2.6.10/2022-04-12)\r\nDate: Thu, 01 Oct 2026 08:42:54 GMT\r\nConnection: close\r\n\r\n<h1>Hello HTTP</h1>"
```

- `-rsocket` は、`require "socket"` と同じ意味のオプションです。
- 送った文字列は、HTTP のリクエストそのものです。各行の終わりは `\r\n`、ヘッダの終わりは `\r\n\r\n` です。
- `Connection: close` で、「返事をしたら接続を閉じてください」と頼んでいます。`socket.read` は、接続が閉じられるまで受け取り続けるからです。
- 結果を `p` で表示したので、`\r\n` がそのまま見えています。HTTP が「決まった形の文字列」でやり取りされていることがわかります。

ブラウザも curl も、裏ではこれと同じことをしています。HTTP は魔法ではなく、決まった形の文字列を TCP で送り合っているだけです。これが、第11章で自分で HTTP サーバを作れる理由です。

観察が終わったら、サーバを起動した端末で `Ctrl-C` を押して止めます。止めた後、`lsof -nP -iTCP:3000 -sTCP:LISTEN` で何も表示されないことを確かめてください。

### nc でサーバ役をやってみる

逆に、自分が「サーバ役」になって、curl から届くリクエストを見ることもできます。**nc**（netcat）は、TCP で文字を送受信する道具です。

1つ目の端末で、127.0.0.1 の4000番で待ち受けます。

```bash
nc -l 127.0.0.1 4000
```

2つ目の端末で、待受先を確かめてから curl を送ります。

```console
$ lsof -nP -iTCP:4000 -sTCP:LISTEN
COMMAND  PID   USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
nc      6859 you      3u  IPv4 0xe96f37a0f533869d      0t0  TCP 127.0.0.1:4000 (LISTEN)
$ curl -v "http://127.0.0.1:4000/search?q=ruby" -H "X-Practice: hello"
```

1つ目の端末に、curl が送ったリクエストがそのまま表示されます。

```text
GET /search?q=ruby HTTP/1.1
Host: 127.0.0.1:4000
User-Agent: curl/8.7.1
Accept: */*
X-Practice: hello

```

curl は、レスポンスが来るのを待って止まっています。サーバ役のあなたが返事をするまで、終わりません。演習8-4で、この返事を手で書いてみます。

`nc` の書き方は、OS や nc の種類によって違います。Linux や WSL では `nc -l 127.0.0.1 4000` で動かない種類もあります。その場合は `man nc` で書き方を確かめてください。**どの書き方でも、待ち受けた直後に `lsof` や `ss -ltn` で `127.0.0.1:4000` になっていることを確かめます。** `*:4000` や `0.0.0.0:4000` と表示されたら、すぐに `Ctrl-C` で止めてください。

## 外のサーバを観察する

自分の PC の外にあるサーバとも、同じやり取りをしています。`example.com` は、説明や例のために予約されたドメインです。ここに1回だけリクエストを送って観察してみましょう。

```console
$ curl -v http://example.com/
* Host example.com:80 was resolved.
* IPv6: 2606:4700:10::ac42:93f3, 2606:4700:10::6814:179a
* IPv4: 104.20.23.154, 172.66.147.243
*   Trying 104.20.23.154:80...
* Connected to example.com (104.20.23.154) port 80
> GET / HTTP/1.1
> Host: example.com
> User-Agent: curl/8.7.1
> Accept: */*
> 
* Request completely sent off
< HTTP/1.1 200 OK
< Date: Thu, 01 Oct 2026 08:30:18 GMT
< Content-Type: text/html; charset=utf-8
< Transfer-Encoding: chunked
< Connection: keep-alive
< Server: cloudflare
（中略）
< 
<!doctype html><html lang=en><head>（以下略）
```

（IP アドレスやヘッダは、時期や場所によって変わります。）

この章で学んだ流れが、すべて見えています。

1. `was resolved` で、**DNS** による名前解決が行われた。
2. スキームが `http` でポートを省略したので、**80番ポート**に接続した。
3. `Connected` で **TCP 接続**ができた。
4. `>` で **HTTP リクエスト**を送り、`<` で **HTTP レスポンス**を受け取った。

自分の PC のサーバと違う点もあります。`Content-Length` がなく、代わりに `Transfer-Encoding: chunked` があります。これは、ボディを「かたまり（チャンク）」ごとに長さを付けて送る方法です。全体の長さが先にわからないときに使われます。HTTP には、ボディの終わりを伝える方法が複数あるのです。この教材で作るサーバでは、わかりやすい `Content-Length` を使います。

**注意**：他人のサーバに、短時間に何度もリクエストを送らないでください。相手の負担になり、迷惑行為とみなされることがあります。観察は、基本的に自分の PC のサーバで行います。

### HTTPS について

`https://` で始まる URL は、**HTTPS** で通信します。HTTPS は、HTTP のやり取りを **TLS** という仕組みで暗号化したものです。HTTP がハガキなら、HTTPS は鍵付きの箱です。途中の人に中身を読まれたり、書き換えられたりするのを防ぎます。また、証明書という仕組みで、相手が本物のサーバかを確かめます。ポートは 443 番を使います。

HTTPS の仕組みは、第13章で自分の PC の中だけで試します。そのときに使う `curl -k` というオプションは、相手が本物かを確かめる仕組みを**止めて**しまいます。第13章の比較の演習以外では使わないでください。

## 127.0.0.1 と 0.0.0.0 の違い

最後に、この教材の安全ルールの中心である「どのアドレスで待ち受けるか」を説明します。

### PC には入口が複数ある

PC には、ネットワークとつながる「入口」（**ネットワークインターフェース**）が複数あります。

- **ループバック**（`127.0.0.1`）：PC の中だけで通じる内線の入口
- **Wi-Fi や有線 LAN**（例：`192.168.1.10`）：同じネットワークの他の機器とつながる外線の入口

サーバを起動するとき、どの入口で待ち受けるかを指定します。

| 待受アドレス | 意味 | 誰が接続できるか |
|---|---|---|
| `127.0.0.1`（`::1`） | ループバックの入口だけ | 同じ PC の中のプログラムだけ |
| `0.0.0.0`（`::`） | **すべての入口** | 同じ PC に加え、同じ Wi-Fi などの他の機器からも |

`0.0.0.0` は「どこか特定の住所」ではなく、「この PC のすべての入口」という特別な意味です。家にたとえると、`127.0.0.1` は内線電話だけに出る状態、`0.0.0.0` は内線にも外線にも出る状態です。

`0.0.0.0` で待ち受けると、カフェや会社の Wi-Fi で、同じネットワークにいる他人があなたのサーバに接続できてしまいます。この教材で作るサーバは、学習のための最小限の作りです。攻撃に耐えるようには作られていません。だから、必ず `127.0.0.1` で待ち受けます。

### 「つながった」ことは、証拠にならない

注意したいのは、**`0.0.0.0` で待ち受けても、`http://localhost:3000/` には問題なくつながる**ことです。すべての入口には、ループバックも含まれるからです。

つまり、「localhost で開けた」ことは、「ループバックだけで待ち受けている」ことの証拠になりません。確かめる方法は、OS に「どの入口で待ち受けているか」を直接聞くことです。それが `lsof`（Linux や WSL では `ss -ltn`）です。

| `lsof` の NAME の表示 | 判定 |
|---|---|
| `127.0.0.1:3000` または `[::1]:3000` | OK。ループバックだけ |
| `*:3000`、`0.0.0.0:3000`、`[::]:3000` | NG。すべての入口で待ち受けている。すぐ止めて設定を直す |

サーバを起動したら、毎回 `lsof` で確かめる習慣を付けてください。第11章以降の演習でも、これを完了条件の1つにします。

### この教材で守るルール

- 自作サーバも、WEBrick も、Rack も、待受アドレスは必ず `127.0.0.1` を明示する。省略しない（省略すると、すべての入口で待ち受けるソフトウェアがある）。
- `0.0.0.0` や `::` で待ち受けない。外部から接続できるようにする公開トンネルやポート転送のサービスも使わない。
- 起動したら `lsof` / `ss` で、実際の待受先を確かめる。

なお、ループバックで待ち受けていても、安全上の問題がすべてなくなるわけではありません。あなたのブラウザは同じ PC の中で動いています。悪意のあるサイトを開くと、そのページからブラウザ経由で `127.0.0.1` にリクエストを送らせることができます。この攻撃（CSRF）と対策は、第10章と第19章で学びます。

## 実務ではこうなる

Web エンジニアの仕事では、HTTP の知識をほぼ毎日使います。

- **ブラウザの開発者ツール**：ブラウザの「ネットワーク」タブで、ページが送ったリクエストとレスポンスを一覧できます。この章で curl で見たものと、同じ情報が表示されます（演習8-5）。
- **API の動作確認**：他のサービスと連携するとき、まず curl でリクエストを送り、レスポンスを確かめます（第21章）。
- **障害調査はステータスコードから**：「画面が真っ白です」という報告を受けたら、まずステータスコードを確かめます。4xx か 5xx かで、調べる場所が変わります。502 や 503 は、アプリの前にある中継サーバが返していることも多いです。
- **本番の待受アドレス**：本番環境では、サーバが外からの接続を受けるために `0.0.0.0` で待ち受けることもあります。ただしその場合は、ファイアウォールや中継サーバなど、何重もの守りの内側に置かれます（第23章）。この教材の演習では、その守りがないので使いません。

ジュニアがやりがちな失敗も挙げておきます。

- **`Address already in use` で慌てる**：前に起動したサーバが残っているだけのことが多いです。`lsof` で PID を確かめ、その端末で `Ctrl-C` を押して止めます。
- **「つながらない」を全部同じ問題だと思う**：DNS で名前が引けないのか、`Connection refused` なのか、4xx・5xx が返っているのかで、原因はまったく違います。`curl -v` で、どの段階で止まっているかを確かめます。
- **「動かないから」と `0.0.0.0` に変える**：スマートフォンから見たい、などの理由で待受先を広げると、同じネットワークの他人にも見えてしまいます。
- **GET でデータを変更する**：`/delete?id=3` のようなリンクで削除できる作りにすると、先読みやリンクの共有で意図せず削除されます。
- **文字数で Content-Length を計算する**：日本語を含むとバイト数とずれて、ボディが途中で切れたり、待ち続けたりします。

## 演習

演習は `~/workspace/ch08-network/` で行います。本文の「観察用のサーバを起動する」の手順で、`Gemfile` と `public/index.html` を用意しておいてください。結果は `notes.md` に書きます。

**すべての演習で、サーバや nc を起動したら、まず `lsof -nP -iTCP:ポート番号 -sTCP:LISTEN`（Linux・WSL は `ss -ltn`）で待受先が `127.0.0.1` であることを確かめてください。** 終わったら `Ctrl-C` で止め、同じコマンドで何も表示されないことを確かめます。

### 演習8-1：URL を分解し、名前を引く

- 次の4つの URL を、`URI.parse` を使って分解する Ruby スクリプト `url_parts.rb` を書いてください。スキーム・ホスト・ポート・パス・クエリ・フラグメントを表示します。
  1. `http://127.0.0.1:3000/`
  2. `https://example.com/docs/index.html?lang=ja`
  3. `http://localhost:4567/items/42?sort=desc&page=3#comments`
  4. `https://example.com`
- 次に、`dig +short example.com A` と `dig +short localhost` を実行してください（`dig` がなければ `nslookup`）。
- **完了条件**：
  - `ruby url_parts.rb` が4つの URL の各部分を表示し、その結果を `notes.md` の表にまとめてある。
  - 4つ目の URL のパスが何になったか、ポートが何になったかを書き、その理由を1文で説明してある。
  - `dig` の結果を貼り、`localhost` の結果がどこで決まっているかを1文で説明してある。
- ヒント：ポートを省略した URL では、`URI` がスキームから既定のポートを補います。値が `nil` のときに `p` と `puts` で表示がどう違うかは、第7章で学びました。

### 演習8-2：自分のサーバとのやり取りを curl で観察する

- 観察用サーバを起動し、`lsof` で待受先を確かめてください。その出力を `notes.md` に貼ります。
- 次の5つのリクエストを送り、それぞれのステータスコードと、気づいたヘッダを `notes.md` に記録します。
  1. `curl -v http://127.0.0.1:3000/`
  2. `curl -i http://127.0.0.1:3000/missing`
  3. `curl -I http://127.0.0.1:3000/`
  4. `curl -i -d 'title=test' http://127.0.0.1:3000/`
  5. `curl -i http://127.0.0.1:3000/docs` と `curl -iL http://127.0.0.1:3000/docs`（`public/docs/index.html` を作ってから）
- `public/index.html` の中身を日本語を含む文章に書き換え、もう一度 `curl -v` を送ります。
- **完了条件**：
  - `lsof` の出力の NAME 欄が `127.0.0.1:3000` である。
  - 5つのリクエストのステータスコードが、200・404・200・405・301（`-L` 付きは 301 の後に 200）として記録されている。
  - 1の出力で、`>` の行と `<` の行がそれぞれリクエスト・レスポンスのどの部分にあたるかを、矢印やコメントで書き込んである。
  - 日本語に書き換えた後の `Content-Length` の値が、`ruby -e 'p File.binread("public/index.html").bytesize'` の結果と一致することを確かめてある。また、`.length`（文字数）とは一致しない理由を説明してある。
  - 最後にサーバを止め、`lsof` で何も表示されないことを確かめた。
- ヒント：3の `-I` は HEAD メソッドです。ボディが表示されないのに `Content-Length` があることに注目してください。2と4では、`Connection` ヘッダの値が1とは違います。なぜそうなるのかも考えてみましょう。

### 演習8-3：HTTP リクエストを手で組み立てる

- 観察用サーバを起動し、本文の「Ruby で HTTP リクエストを手書きして送る」のコマンドを実行してください。
- 次に、送る文字列を変えて、3つの実験をします。1つ変えるたびに、元に戻してから次を試します。
  1. `Host: localhost:3000\r\n` を消す。
  2. `GET /` を `GET /missing` に変える。
  3. `\r\n\r\n`（最後の空行）を `\r\n` だけにする。
- **完了条件**：
  - 3つの実験について、送った文字列・返ってきたステータス行（返ってこなければ、何が起きたか）・その理由の推測を `notes.md` に書いてある。
  - 3の実験で何が起きたかを、「ヘッダの終わり」という言葉を使って説明してある。
- ヒント：
  - 1について。HTTP/1.1 の仕様では、`Host` のないリクエストには 400 を返すべきだと決まっています。しかし、観察用のサーバがそれを守っているとは限りません。「実際の動き」と「仕様の決まり」を区別して書いてください。
  - 3でコマンドが終わらないときは、`Ctrl-C` で止めて構いません。なぜ終わらないのかを考えることが、この実験の目的です。
  - この演習は、第11章の HTTP サーバ作りの準備です。サーバ側から見ると、「どこまで読めばリクエストが終わるのか」が問題になります。

### 演習8-4：サーバ役になって、レスポンスを手で返す

- 1つ目の端末で `nc -l 127.0.0.1 4000` を実行し、2つ目の端末で `lsof` を使って待受先を確かめます。
- 2つ目の端末で `curl -v http://127.0.0.1:4000/hello` を実行します。
- 1つ目の端末に表示されたリクエストを読んだ後、1つ目の端末に次のレスポンスを1行ずつ手で入力します。最後の `hello` の後で Enter を押します。

```text
HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 6

hello
```

- **完了条件**：
  - 2つ目の端末の curl の出力に、`< HTTP/1.1 200 OK` と、ボディの `hello` が表示された。その出力を `notes.md` に貼ってある。
  - `Content-Length` が 6 である理由（`hello` は5文字なのに）を説明してある。
  - `Content-Length` を 3 にして同じことをすると、curl の表示がどう変わるかを試し、記録してある。
  - `lsof` の出力の NAME 欄が `127.0.0.1:4000` だったことを記録してある。
- ヒント：
  - ターミナルで Enter を押して送られる改行は、通常 LF（`\n`）だけです。HTTP/1.1 の正しい形は CRLF ですが、curl は LF だけの行も受け付けてくれます。正しい形ではないことは覚えておいてください。
  - 入力を終えても curl が止まらない場合は、両方の端末で `Ctrl-C` を押して止めます。
  - nc の書き方が OS によって違う点は、本文を参照してください。待受先が `127.0.0.1` 以外になったら、すぐに止めます。

### 演習8-5（発展）：ブラウザの開発者ツールと比べる

- 観察用サーバを起動し、ブラウザで `http://127.0.0.1:3000/` を開きます。
- ブラウザの開発者ツールを開きます。Chrome なら command + option + I で開けます。「ネットワーク」タブを表示してから、ページを再読み込みします。
- **完了条件**：`notes.md` に次を書いてある。
  - ブラウザが送ったリクエストの数と、それぞれのパス・ステータスコード（`index.html` 以外のリクエストが出ていないかに注目する）
  - ブラウザが送ったリクエストヘッダのうち、curl が送らなかったものを3つ以上と、その意味（調べてよい）
  - サーバの端末に表示されたログと、開発者ツールの表示の対応
- ヒント：ブラウザは、ページ本体の他に `/favicon.ico`（タブに表示する小さなアイコン）を自動で取りに行くことがあります。ファイルがないので 404 になっているはずです。ヘッダの意味は、[MDN の HTTP の解説](https://developer.mozilla.org/ja/docs/Web/HTTP/Overview)で調べられます。

## 確認クイズ

**Q1.** `https://example.com/search?q=ruby#top` について、ホスト・ポート・パス・クエリを答えてください。また、`#top` はサーバに送られますか。

**Q2.** TCP が「バイトの流れ」を運ぶ、とはどういう意味ですか。そのために HTTP は何を使ってメッセージの区切りを示していますか。

**Q3.** ステータスコードが 404 のときと 503 のときでは、まずどこを調べるべきですか。

**Q4.** サーバを起動して、ブラウザで `http://localhost:3000/` が開けました。これで「ループバックだけで待ち受けている」と言えますか。どう確かめればよいですか。

**Q5.** レスポンスのボディが `こんにちは` のとき、`Content-Length` に `"こんにちは".length` の値（5）を入れました。何が問題ですか。

**Q6.** サーバを起動しようとしたら `Address already in use` と表示されました。何が起きていて、どう対処しますか。

### 解答と解説

**A1.** ホストは `example.com`、ポートは省略されているので https の既定の 443、パスは `/search`、クエリは `q=ruby` です。`#top` はフラグメントで、ブラウザの中だけで使われるので、サーバには送られません。

**A2.** TCP は、データを「確実に、順番どおりに」届けますが、送る側の区切りは保ちません。2回に分けて送ったものがつながって届いたり、1回で送ったものが分かれて届いたりします。そこで HTTP/1.1 は、CRLF と空行（`\r\n\r\n`）でヘッダの終わりを示し、`Content-Length`（または `Transfer-Encoding: chunked`）でボディの長さを示しています。

**A3.** 404 は 4xx なので、クライアント側の問題です。まず、送った URL やパスが正しいかを見直します。503 は 5xx なので、サーバ側の問題です。サーバのログや、サーバが動いているか、混み合っていないかを調べます。

**A4.** 言えません。`0.0.0.0`（すべての入口）で待ち受けていても、localhost には接続できるからです。`lsof -nP -iTCP:3000 -sTCP:LISTEN`（Linux・WSL は `ss -ltn`）で、待受先が `127.0.0.1:3000` または `[::1]:3000` になっていることを確かめます。`*:3000` や `0.0.0.0:3000` なら、止めて設定を直します。

**A5.** `Content-Length` はバイト数を表します。`こんにちは` は UTF-8 で 15 バイトなので、5 では足りません。受け取る側は最初の 5 バイトだけをボディとして読み、残りは捨てるか、次のメッセージの始まりと誤解します。`bytesize` で数える必要があります。

**A6.** そのアドレスとポートで、すでに別のプログラムが待ち受けています。多くの場合、前に起動したサーバを止め忘れています。`lsof -nP -iTCP:3000 -sTCP:LISTEN` で、どのプログラム（COMMAND と PID）が使っているかを確かめ、そのサーバを起動した端末で `Ctrl-C` を押して止めます。

## AIの使い方（この章）

ネットワークは目に見えないので、AIに図やたとえで説明してもらうのが効果的です。ただし、AIの説明が正しいかを、curl や lsof で自分の目で確かめることを忘れないでください。

**推奨する聞き方の例**

- 「次の `curl -v` の出力を、DNS・TCP・HTTP リクエスト・HTTP レスポンスのどの段階か、行ごとに分類して説明してください。（出力を貼る）」
- 「`127.0.0.1` と `0.0.0.0` で待ち受ける違いについて、私は『〇〇』と理解しました。間違いや足りない点を指摘してください。」
- 「HTTP のステータスコード 301・302・303 の違いを、具体的な Web サイトの場面を例にして説明してください。」

**この章でやってはいけない使い方**

- 「スマートフォンから自分のサーバを見たいので、外からつながる設定を教えて」と頼み、その設定をそのまま使うこと。この教材では、待受先を `127.0.0.1` 以外にすることも、公開トンネルやポート転送を使うことも禁止です。
- 演習8-3・8-4の結果をAIに予想させて、実行せずにメモを書くこと。この章の目的は、自分の目でバイトのやり取りを観察することです。

## まとめ

URL を開くと、DNS で名前から IP アドレスを調べ、TCP でポートに接続し、HTTP でリクエストとレスポンスを1往復させます。TCP は区切りのないバイトの流れなので、HTTP/1.1 は CRLF・空行・Content-Length でメッセージの境界を示します。`curl -v` を使えば、その一部始終を観察できます。演習のサーバは必ず `127.0.0.1` で待ち受け、「つながった」ではなく `lsof` / `ss` の表示で待受先を確かめます。

さらに深く：元の研修では、Phase 1 の最初に、ローカルの WEBrick へ HTTP/1.1 リクエストを手で送って観察します（[Phase 1](https://github.com/speee/training-web-app/blob/main/phase-1.md)）。HTTP の正式な仕様は [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)（意味）と [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html)（HTTP/1.1 の形式）、ステータスコードの一覧は [MDN](https://developer.mozilla.org/ja/docs/Web/HTTP/Status) で確認できます。

## 用語

| 用語 | 意味 |
|---|---|
| URL | 通信の方法・相手・資源の場所を1行で表した住所書き |
| プロトコル | 通信する者どうしの約束ごと。HTTP、TCP、IP など |
| IP アドレス | ネットワーク上のコンピュータの住所。IPv4 と IPv6 がある |
| ループバック（127.0.0.1 / ::1 / localhost） | 自分自身の PC を指す特別な住所。外からは接続できない |
| ポート | 1台の PC の中で、どのプログラム宛てかを区別する番号 |
| 待ち受ける（listen） | サーバが特定のアドレスとポートで接続を待つこと |
| DNS | ドメイン名を IP アドレスに変換する仕組み。インターネットの電話帳 |
| TCP | 接続を作り、バイトの流れを確実に順番どおりに届ける約束ごと |
| HTTP | Web のリクエストとレスポンスの形を決めた約束ごと |
| リクエスト／レスポンス | クライアントからのお願い ／ サーバからの返事 |
| CRLF | HTTP/1.1 の行の終わりに使う2文字（`\r\n`） |
| ヘッダ | リクエストやレスポンスに付ける追加情報。`名前: 値` の形 |
| ステータスコード | レスポンスの結果を表す3桁の数字。2xx 成功、4xx クライアント側、5xx サーバ側 |
| リダイレクト | 3xx と Location ヘッダで、別の URL に行くよう伝えること |
| ステートレス | 前のリクエストを覚えていない性質 |
| 0.0.0.0 | 待受アドレスとして使うと「この PC のすべての入口」を意味する。この教材では使わない |
