# 第10章 安全上の注意とWebセキュリティの基礎

> **この章のゴール**：この教材の演習で必ず守る4つのルールを、理由と確かめ方つきで説明できる。代表的な4つの攻撃が「なぜ起きるか」と「どの章で対策を実装するか」を説明できる。
> **目安時間**：読む 2.5時間 ＋ 演習 2時間
> **前提**：第9章まで

## この章で学ぶこと

- 自作サーバを `127.0.0.1` だけで待ち受ける理由と、`lsof` / `ss` での確かめ方を説明できる
- 秘密鍵・個人情報・認証情報を成果物に混ぜないための手順を実行できる
- パストラバーサル・XSS・CSRF・SQLインジェクションが起きる仕組みを、たとえ話と実際の例の両方で説明できる
- 4つの攻撃に共通する原因（データと命令の取り違え、相手の確認不足）を説明できる
- 「テストが通る」ことと「本番で安全に使える」ことの差を、具体的な領域を挙げて説明できる
- 成果物を共有する前のチェックリストを使える

## なぜ今、セキュリティを学ぶのか

次の第11章から、いよいよ自分でWebサーバを作ります。その後、フレームワーク、ORM、アプリと、Webの部品を1つずつ自作していきます。その前に、この章で「安全に練習するための約束」を確認します。

演習で作るサーバやORMは、仕組みを理解するための**最小構成**です。攻撃に耐えるようには作られていません。たとえるなら、エンジンの仕組みを学ぶために組み立てた模型の車です。構造を学ぶには最高ですが、公道を走らせてはいけません。

Railsのようなフレームワークは、見えないところで多くの仕事をしています。接続数の上限、時間がかかりすぎる通信の打ち切り、HTMLのエスケープ、CSRF対策などです。部品を自作すると、この「見えない仕事」がすべて自分の責任になります。何を守れていて、何が守れていないのか。それを先に知っておくのがこの章の目的です。

もう1つ理由があります。セキュリティの事故は、高度な攻撃よりも、**毎日の小さな作業習慣**から起きることが多いのです。秘密の鍵をうっかりコミットする。練習用のサーバを外から見える状態で動かす。こうした失敗は、知識より習慣で防ぎます。だから最初の実装の前に学びます。

ここで1つ考えてみてください。「テストが全部通った」ことと「本番で安全に動く」ことは、何が違うでしょうか。答えは、この章の後半「テストが通っても本番に出せない理由」の節で確認します。

## 演習で守る4つのルール

この教材のすべての演習で、次の4つのルールを守ります。それぞれ「何をするか」「なぜか」「どう確かめるか」の順に説明します。

### ルール1：ループバックだけで待ち受ける

**何をするか**：自作サーバ・WEBrick・Rackなど、演習で起動するサーバはすべて `127.0.0.1`（IPv6なら `::1`）で待ち受けます。ホスト指定の省略、`0.0.0.0` や `::` での待受、公開トンネル（自分のPCをインターネットに公開するサービス）、ルーターのポート転送は使いません。

**なぜか**：第8章で学んだように、`127.0.0.1` は「自分自身のこのPC」を指す特別な住所です。これを**ループバック**といいます。家の中の内線電話のようなもので、外からはかけられません。

一方、`0.0.0.0` で待ち受けると「このPCのどの入口からでも受け付ける」という意味になります。内線だけでなく外線にも出る状態です。カフェや会社のWi-Fiでは、同じネットワークにいる他人が、あなたの作りかけのサーバに直接つながれてしまいます。

**どう指定するか**：道具ごとに書き方が違います。

| 道具 | 指定のしかた | 出てくる章 |
| --- | --- | --- |
| 自作サーバ（TCPServer） | `TCPServer.new("127.0.0.1", 3000)` | 第11章 |
| WEBrick | `BindAddress: "127.0.0.1"` | 第12章 |
| `ruby -run -e httpd` | `--bind-address=127.0.0.1` | 第9章 |
| rackup | `-o 127.0.0.1` | 第13章 |

注意してほしいのは、**省略したときの動きが道具によって違う**ことです。たとえばWEBrickの設定ファイル（`webrick/config.rb`）には、`BindAddress` の初期値が `nil` で、その意味は `"0.0.0.0" or "::" or nil` だと書かれています。つまり省略すると、すべての入口で待ち受ける可能性があります。だから「省略しない、必ず明示する」をルールにしています。

**どう確かめるか**：起動したら、OSに「今どこで待ち受けているか」を聞きます。macOSでは `lsof`、LinuxやWSLでは `ss` を使います。

```bash
# macOS
lsof -nP -iTCP:3000 -sTCP:LISTEN
# Linux / WSL
ss -ltn
```

`lsof` のオプションの意味は次のとおりです。

- `-n`：IPアドレスを名前に変換しない（表示が速く、正確になる）
- `-P`：ポート番号を名前に変換しない
- `-iTCP:3000`：TCPの3000番ポートに関係するものだけを表示する
- `-sTCP:LISTEN`：待ち受け中のものだけを表示する

正しく待ち受けているときの出力は、たとえば次のようになります。

```
COMMAND  PID   USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
ruby    5094 you       9u  IPv4 0x3605a6b25444db45      0t0  TCP 127.0.0.1:3000 (LISTEN)
```

見るのは最後の `NAME` の列です。判定は次の表のとおりです。

| `NAME` の表示 | 判定 | すること |
| --- | --- | --- |
| `127.0.0.1:3000` | OK | そのまま使う |
| `[::1]:3000` | OK（IPv6のループバック） | そのまま使う |
| `*:3000` | NG（全入口） | すぐ止めて設定を直す |
| `0.0.0.0:3000` / `[::]:3000` | NG（全入口） | すぐ止めて設定を直す |

ここで大事な注意があります。**「`http://localhost:3000` で開けた」ことは、ループバック限定の証拠になりません。** 全入口で待ち受けていても、自分のPCからは当然つながるからです。必ず `lsof` か `ss` で待受先そのものを見てください。

**ループバックでも防げないこと**：ループバック限定にしても、完全に安全になるわけではありません。あなたのブラウザも、同じPCの中で動いているからです。ブラウザで悪意あるページを開くと、そのページがあなたのブラウザを使って `http://127.0.0.1:3000` にリクエストを送らせることができます。同じPCで動く別のプログラムが接続することもできます。後で学ぶCSRF対策が必要なのは、このためです。

### ルール2：ダミーデータだけを使う

**何をするか**：演習のデータベース・ログ・スクリーンショット・発表資料に、本物の個人情報や、実際のサービスのパスワード・トークンを入れません。名前は「テスト太郎」、メールアドレスは `user1@example.com` のように置き換えます。`example.com` は、説明や例のために予約されたドメインで、実在の誰かに届くことはありません。

**なぜか**：演習のアプリには、ログイン機能も、ログの伏せ字処理もありません。入れた情報は、データベースのファイル、Gitの履歴、発表の録画からそのまま漏れます。「どうせ練習だから」と本物のデータを使うのが、一番危ない考え方です。

**どう確かめるか**：コミットや共有の前に、後で紹介する「共有前チェックリスト」で確認します。

### ルール3：秘密情報を共有・コミットしない

**何をするか**：秘密鍵（第13章のHTTPS演習で作る `key.pem` など）、APIトークン、パスワードを書いたファイルは、Gitにコミットせず、人にも渡しません。そのために、**秘密のファイルを作る前に** `.gitignore` に書いておきます。

```gitignore
*.pem
*.key
.env
```

`.env` は、パスワードなどの設定を書いておくファイルによく使われる名前です。第20章以降で使います。

**なぜか**：第2章で学んだように、Gitは「全部のセーブ」を覚えています。秘密のファイルを一度コミットすると、次のコミットで消しても、古いセーブには残ったままです。公開リポジトリにpushしたなら、もう誰かが複製したかもしれません。

だから、**コミットや共有をしてしまった秘密は「漏えいしたもの」として扱い、作り直します。** 鍵なら新しく作り直し、トークンなら発行元で無効にして再発行します。「消したから大丈夫」は通用しません。

**どう確かめるか**：秘密のファイルを作る前に、次の3つのコマンドで確認します。

```bash
git check-ignore -v key.pem cert.pem   # ignore規則が表示されればOK
git ls-files -- key.pem cert.pem       # 何も表示されなければOK
git diff --cached --name-only          # 鍵がコミット予定になければOK
```

実際に試すと、1つ目は次のように表示されます。どのファイルの何行目の規則で無視されるかがわかります。

```
.gitignore:1:*.pem	key.pem
.gitignore:1:*.pem	cert.pem
```

つまずきやすい点が2つあります。

- **`.gitignore` は、すでに追跡しているファイルには効きません。** 先にコミットしてしまったファイルは、`.gitignore` に書いても追跡され続けます。その場合は `git rm --cached -- key.pem` で追跡から外し、さらに鍵そのものを作り直します。
- **ファイルの読み取り権限も絞ります。** 秘密鍵は、`umask 077` を設定したシェルで作り、作った後も `chmod 600 key.pem` で自分だけが読めるようにします。詳しい手順は第13章で扱います。

### ルール4：`curl -k` は比較演習でだけ使う

**何をするか**：`curl -k`（`--insecure`）は、HTTPSの証明書の確認を止めるオプションです。これは第13章のHTTPS演習で「確認あり」と「確認なし」を比べるときだけ使います。

**なぜか**：HTTPSの証明書は、お店の身分証明書のようなものです。`-k` は「身分証を確かめずに信用する」という意味になります。通信相手が本物かどうかを確かめないので、途中で誰かが本物になりすます攻撃（**中間者攻撃**）を防げません。

**どう使い分けるか**：

```bash
# 通常はこちら：自分で作った証明書を「信頼してよい相手」として渡し、確認する
curl --cacert cert.pem https://localhost:3001/   # 証明書の名前（localhost）で接続する
# 第13章の比較でだけ：確認なし
curl -k https://localhost:3001/
```

「エラーが出て動かないから `-k` をつける」のは、火災報知器がうるさいから電池を抜くのと同じです。問題が消えたのではなく、見えなくなっただけです。この癖を実務に持ち込まないことが大切です。

## 攻撃を理解するための共通の考え方

ここからは、Webアプリへの代表的な攻撃を4つ学びます。その前に、すべてに共通する考え方を2つ押さえます。

### 考え方1：外から来たものは、すべて利用者が自由に作れる

第9章で、hiddenの値は書き換えられること、ブラウザの入力チェックは外せることを学びました。さらに言えば、`curl` やプログラムを使えば、ブラウザを通さずに好きなリクエストを送れます。URLのパスも、ヘッダも、ボディも、すべてです。

サーバから見て「ここから先は自分の管理外」という境目を、**信頼境界**といいます。HTTPリクエストとして届くものは、すべて信頼境界の外から来たものです。

### 考え方2：データと命令を混ぜると、データが命令に化ける

4つの攻撃のうち3つは、同じ形をしています。

- 利用者からの「データ」が、
- プログラムの中で「命令」（ファイルのパス、HTML、SQL）の一部として組み立てられ、
- データのつもりだった文字が、命令として解釈されてしまう。

残りの1つ（CSRF）は、「誰からのお願いなのかを確かめずに、本人の操作だと思い込む」ことが原因です。

対策の方向も、大きく3種類に分けられます。

| 対策の種類 | 考え方 | 例 |
| --- | --- | --- |
| 確かめてから使う | 入力が想定の範囲内かを調べ、外れたら断る | パスが公開フォルダの中かを確かめる |
| 出すときに変換する | 特別な意味の文字を、ただの文字に変えてから出す | HTMLのエスケープ |
| 仕組みで分ける | 命令とデータを別々に渡し、混ざらないようにする | SQLのバインド |

では、4つの攻撃を見ていきましょう。どれも図書館を舞台にしたたとえ話から始めます。

## 4つの攻撃：たとえ話と、Webでの実際

### パストラバーサル：立入禁止の書庫に入られる

**たとえ話**：司書さんに「一般の棚の、1つ上の階の、さらに隣の部屋の…」と道順を伝えます。すると司書さんは、言われたとおりに歩いて、立入禁止の書庫の本を持ってきてしまいます。

**Webでは**：第11章で作るサーバは、`public` フォルダの中のファイルを配信します。リクエストのパスが `/index.html` なら、`public/index.html` を返すという具合です。ここで攻撃者は、次のようなパスを送ります。

```
GET /../../etc/passwd HTTP/1.1
```

`../` は「1つ上のフォルダ」です。何も確かめずにパスをつなげると、公開フォルダの外に出てしまいます。Rubyで、パスがどこに行き着くかを確かめてみます。

```ruby
root = "/Users/you/workspace/public"
joined = File.join(root, "/../../etc/passwd")
p joined
p File.expand_path(joined)
```

```
"/Users/you/workspace/public/../../etc/passwd"
"/Users/you/etc/passwd"
```

`File.expand_path` は、`..` などを解決して、最終的な場所を求めるメソッドです。結果は `public` の外を指しています。ソースコードや `.git` フォルダ、秘密鍵などが読まれる危険があります。

攻撃のパターンは `../` だけではありません。`%2e%2e%2f`（`../` をパーセントエンコーディングしたもの）や、2回エンコードしたものもあります。公開フォルダの中に「外を指すショートカット」（シンボリックリンク）を置く方法もあります。

**対策の考え方**：最終的にたどり着く場所を求めてから、**それが公開フォルダの範囲内かを確かめ、外なら断る**。「`..` という文字が含まれていたら断る」のような文字列のチェックだけでは、別の書き方ですり抜けられます。

**この教材では**：第11章の静的ファイル配信で対策を実装し、「公開フォルダの外へのアクセスを拒否するテストが通る」ことを完了条件にします。

### XSS：掲示板の貼り紙が「命令」になる

**たとえ話**：図書館の掲示板に、「これを読んだ人は、自分の利用者カードを入口の箱に入れること」と書いた紙を貼ります。掲示板を読んだ人が、その指示に従ってしまう、という攻撃です。

**Webでは**：掲示板やコメント欄のように、利用者の入力を他の人に表示する機能が狙われます。攻撃者は、本文に次のような文字列を投稿します。

```html
<script>（ここに、閲覧者のブラウザで動かしたいプログラム）</script>
```

サーバがこれをそのままHTMLに埋め込むと、他の人のブラウザはこれを「タグ」と解釈し、プログラムを実行してしまいます。プログラムは、その人としてログインした状態で動くので、勝手に投稿したり、画面の情報を外部に送ったりできます。XSSは Cross-Site Scripting の略です。

**対策の考え方**：利用者の入力をHTMLに埋め込むときは、特別な意味を持つ文字を文字参照に変換します。これを**エスケープ**といいます。第9章で学んだ `&lt;` の仕組みを、自動で行うということです。Rubyには、そのためのメソッドがあります。

```ruby
require "cgi"
puts CGI.escapeHTML(%q(<script>alert("x")</script> & 'quote'))
```

```
&lt;script&gt;alert(&quot;x&quot;)&lt;/script&gt; &amp; &#39;quote&#39;
```

ブラウザはこれを「`<script>...` という文字」として表示するだけで、実行はしません。第9章で学んだ、JavaScriptで `innerHTML` ではなく `textContent` を使うのも、同じ考え方です。

**この教材では**：第14章でHTMLのテンプレートを自作するときに、出力が自動でエスケープされ、入力がHTMLとして実行されないことをテストで確かめます。

### CSRF：知らないうちに申請書に署名させられる

**たとえ話**：悪い人が「蔵書をすべて廃棄します」という申請書を用意します。そして、本物の職員であるあなたに、内容を見せないまま提出させます。受付は、職員が出した申請なので受理してしまいます。

**Webでは**：あなたが自作アプリを開いたまま、別のタブで悪意のあるページを開いたとします。そのページには、次のようなフォームが隠されています。

```html
<form action="http://127.0.0.1:3000/memos/1/delete" method="post">
</form>
<script>document.forms[0].submit();</script>
```

ページを開いた瞬間に、あなたのブラウザから自作アプリへ「削除して」というリクエストが送られます。ブラウザはあなたのPCの中で動いているので、ルール1で `127.0.0.1` に限定していても届いてしまいます。サーバから見ると、あなた自身の操作と区別がつきません。CSRFは Cross-Site Request Forgery（サイトをまたいだリクエストの偽造）の略です。

**対策の考え方**：本物の申請書にだけ、割印のような合言葉（**トークン**）を入れておきます。自分のサイトのフォームにだけ、推測できないトークンを hidden で埋め込みます。そしてサーバは、正しいトークンがないリクエストを断ります。悪意あるページは、そのトークンを知ることができません。第9章で学んだ「GETで状態を変えない」も、CSRF対策の前提です。

**この教材では**：第17章のCRUDアプリで、状態を変更するフォームをトークンで保護します。そして「不正なリクエストではデータベースが変わらない」ことをテストで確かめます。Cookieとの関係は第19章でさらに深めます。

### SQLインジェクション：検索用紙に「命令」を書き足す

**たとえ話**：図書館では、利用者が用紙に書名を書くと、司書さんが台帳を調べてくれます。司書さんは、用紙に書かれたことをそのまま実行する決まりです。そこで書名欄に「山田、または全員」と書くと、司書さんは全員分の貸出記録を渡してしまいます。

**Webでは**：SQLは、データベースに命令するための言葉です（第15章で学びます）。入力された名前で利用者を探すとき、入力を文字列としてSQLに埋め込むと、次のことが起きます。

```ruby
name = "' OR '1'='1"
puts "SELECT * FROM users WHERE name = '#{name}'"
```

```
SELECT * FROM users WHERE name = '' OR '1'='1'
```

入力に含まれた `'` で文字列が閉じられ、`OR '1'='1'`（常に正しい条件）が命令の一部になってしまいました。結果として、全員分のデータが返ります。書き方次第では、データの削除もできてしまいます。

**対策の考え方**：値は、SQLの文章に埋め込まず、**別の通り道で渡します**。これを**バインド**（プレースホルダ）といいます。

```ruby
# NG：入力をSQL文に埋め込む
db.execute("SELECT * FROM users WHERE name = '#{name}'")
# OK：値はプレースホルダ（?）でバインドする
db.execute("SELECT * FROM users WHERE name = ?", [name])
```

この `db` は第15章以降で使うデータベースへの接続です。ここでは形だけ見てください。バインドすると、データベースは `?` の部分を、何があっても「ただの値」として扱います。

ただし、カラム名や並び順（`ORDER BY` の対象）は値ではないので、バインドできません。そこは、許可したカラム名の一覧（**許可リスト**）にあるものだけを受け付けるようにします。

**この教材では**：第16章でORMを自作するときに、値は必ずバインドし、動的なカラム名は許可リストで制限します。攻撃用の入力が条件を書き換えられないことをテストで確かめます。

### 4つの攻撃のまとめ

| 攻撃 | 入口 | 原因 | 対策の考え方 | 実装する章 | 完了条件 |
| --- | --- | --- | --- | --- | --- |
| パストラバーサル | URLのパス | パスをそのまま使う | 最終的な場所が範囲内か確かめる | 第11章 | 公開フォルダ外へのアクセスを拒否するテストが通る |
| XSS | 投稿など表示される入力 | 入力をHTMLに埋め込む | 出力時にエスケープする | 第14章 | 出力がエスケープされ、入力がHTMLとして実行されない |
| CSRF | 他サイトからのフォーム送信 | 誰からのお願いか確かめない | トークンで本物を見分ける | 第17章 | 不正なリクエストでDBが変わらない |
| SQLインジェクション | 検索条件などの入力 | 入力をSQLに埋め込む | 値はバインド、カラム名は許可リスト | 第16章 | 攻撃用の入力で条件が書き換わらない |

どの章でも、「対策を実装した」だけでは完了にしません。**攻撃が失敗することをテストで示す**ところまでを完了条件にします。対策は、書いたつもりで抜けていることが多いからです。テストで確かめれば、後でコードを変えたときに対策が壊れても気づけます。

## テストが通っても本番に出せない理由

冒頭の問い、「テストが全部通った」と「本番で安全」の違いに答えます。

この教材のテストは、**学習範囲の完了条件**だけを確かめます。本番で必要な防御のうち、次の5つの領域は、教材として実装も検証も保証していません。

| 領域 | 放置すると起きること | 状態 | 根拠（コード・テスト） |
| --- | --- | --- | --- |
| 資源の上限（接続数・スレッド数・リクエスト行／ヘッダ／ボディの長さ・メモリ・CPU） | 巨大なリクエストや大量の接続でサーバが落ちる | 未確認 | |
| タイムアウト（読み取り・書き込み・TLSの開始処理、遅いクライアント） | 少しずつしか送ってこない接続に、処理を占有され続ける | 未確認 | |
| 資源の回収（例外や切断時のソケットのclose、スレッド・DB接続） | 接続などが漏れ続け、いずれサーバが止まる | 未確認 | |
| HTTPの厳密な検証（構文・メッセージの区切り・不正な入力の拒否） | 解釈のずれを突かれ、別のリクエストを紛れ込まされる | 未確認 | |
| 運用上の防御（認証・認可、セッション管理、機密を漏らさないログやエラー画面、依存ライブラリの更新） | 誰でも操作でき、エラー画面から内部情報が漏れる | 未確認 | |

この表は、自分の成果物の**記録用紙**として使います。「状態」には「実装済み」「一部」「未実装」「未確認」のどれかを書き、「根拠」にはそれを示すコードやテストを書きます。確かめていないものを「実装済み」にしてはいけません。

演習10-5でこの表を自分のリポジトリに作り、第11章・第13章・第17章・第26章で更新していきます。第12章で読むWEBrickのコードには、たとえば「リクエスト行の長さの上限」がしっかり書かれています。自作との差を見比べると、この表の意味が実感できるはずです。

なお、WEBrickの公式の説明も、用途をテストとローカル開発に限っています。Ruby製の部品でさえそうなのですから、学習用の自作部品を本番に出してはいけないのは当然です。

## 成果物を共有する前のチェックリスト

公開してよいのは、コード・説明資料・録画です。演習サーバそのものを公開することはありません。成果をリモートに保存するときは、自分の演習用リポジトリ（最初は非公開がおすすめ）を使います。push や資料の共有の前に、**毎回**次を確認します。

- [ ] コードだけでなく、Gitの履歴・DBファイル・ログ・スクリーンショット・録画・スライドも見直した
- [ ] 個人情報・社内情報・実サービスの認証情報・トークン・秘密鍵が含まれていない
- [ ] 実名・メールアドレス・実データをダミーに置き換えた
- [ ] `git ls-files -- '*.pem' '*.key'` で何も表示されない
- [ ] 録画・スクリーンショットに、他のタブ、通知、ターミナルの環境変数が映っていない
- [ ] デモは自分のPCのループバックで行い、公開トンネルやポート転送を使っていない

質問をネットに投稿するときや、AIにコードを貼るときも同じです。機密情報を取り除いた、最小の再現例にします。

## 毎回の作業の流れに組み込む

ルールは、毎回の手順に組み込むと忘れません。この教材では、サーバを動かす演習のたびに、次の流れで作業します。

1. **起動**：ホストに `127.0.0.1` を明示して起動する
2. **確認**：別のターミナルで `lsof -nP -iTCP:ポート -sTCP:LISTEN` を実行し、`NAME` が `127.0.0.1:ポート` であることを見る
3. **作業**：ブラウザや `curl` で動作を確かめる
4. **停止**：`Ctrl-C` で止める
5. **再確認**：もう一度 `lsof` を実行し、何も表示されないことを見る

コミットの前には、次の流れを習慣にします。

1. `git status` で、コミットしようとしているファイルを一覧で見る
2. 見覚えのないファイル、`.pem`・`.key`・`.env`・`.sqlite3` などがないかを見る
3. `git diff --cached` で、中身に本物の個人情報や秘密が入っていないかを見る

最初は面倒に感じるはずです。それでも続けてください。第23章や第24章で学ぶ実務の現場では、この確認ができるかどうかが信頼に直結します。

## 実務ではこうなる

実務のチームでは、セキュリティは「専門家だけの仕事」ではありません。ジュニアも含めた全員が、毎日のコードとレビューの中で守ります。

- **フレームワークの安全装置を外さない**：Railsは、XSS・CSRF・SQLインジェクションへの対策を最初から備えています。ところが、`html_safe`（エスケープしない）や `raw`、SQLの文字列埋め込みなどで、自分から外してしまう事故がよくあります。外すときは理由をレビューで説明できる必要があります。
- **秘密情報の置き場所が決まっている**：パスワードやトークンは、リポジトリではなく、環境変数や専用の秘密情報管理の仕組みに置きます（第20章・第23章）。
- **漏えいしたら、すぐ報告する**：秘密をコミットしてしまったら、隠さずにすぐチームに報告します。早ければ早いほど、作り直すだけで被害を防げます。黙って消そうとすると、Gitの履歴に残ったまま被害が広がります。

ジュニアがやりがちな失敗の例です。

- 動作確認用にサーバを `0.0.0.0` で起動し、そのまま忘れる。
- `.env` を作った後に `.gitignore` に追加し、すでに一度コミットしていたことに気づかない。
- 証明書のエラーを `curl -k` や `verify: false` で黙らせ、そのコードが本番に出る。
- 本番データのコピーを手元で使い、スクリーンショットにお客さまの名前が映り込む。

## 演習

演習は `~/workspace/ch10-security/` で行います。

```bash
mkdir -p ~/workspace/ch10-security
cd ~/workspace/ch10-security
```

### 演習10-1：待受先を自分の目で確かめる

- `public` フォルダを作り、その中に `index.html`（中身は `<h1>Hello</h1>` だけでよい）を置きます。
- 次のコマンドで、`public` フォルダだけを配信するサーバを起動します。

```bash
ruby -run -e httpd -- --bind-address=127.0.0.1 --port=3000 public
```

- 別のターミナルで `lsof -nP -iTCP:3000 -sTCP:LISTEN`（WSLなら `ss -ltn`）を実行します。
- `curl -i http://127.0.0.1:3000/` でレスポンスを確かめます。
- `Ctrl-C` でサーバを止め、もう一度 `lsof` を実行します。
- 3つの出力を `notes.md` に貼ります。
- **完了条件**：`notes.md` に、起動中の `lsof` の `NAME` が `127.0.0.1:3000` である出力、`curl` の `HTTP/1.1 200 OK` を含む出力、停止後に何も表示されなかったことの記録がある
- ヒント：Ruby 3.0以降で `webrick` が見つからないと言われたら、`gem install webrick` を先に実行します。`0.0.0.0` での起動は試しません。NGの表示がどうなるかは、本文の表で確認してください。

### 演習10-2：秘密のファイルを作る前に .gitignore を書く

- `~/workspace/ch10-security` で `git init` します。
- `.gitignore` に `*.pem`・`*.key`・`.env` を書き、それだけを先にコミットします。
- 中身が `dummy` だけのテキストファイル `key.pem` を作ります（本物の鍵ではありません）。
- 本文の3つの確認コマンドと、`git status --short` を実行します。
- **完了条件**：
  - `git check-ignore -v key.pem` が `.gitignore:1:*.pem	key.pem` のように規則を表示する
  - `git ls-files -- '*.pem' '*.key'` が何も表示しない
  - `git status --short` に `key.pem` が出てこない
- ヒント：先に `key.pem` を `git add` してしまったら、それこそが練習の機会です。`git rm --cached -- key.pem` で外し、「本物の鍵だったら作り直しが必要」とメモに書いておきましょう。

### 演習10-3：データが命令に化ける瞬間を観察する

- `observe.rb` を作り、次の3つを順に出力するプログラムを書きます。実行する**前に**、それぞれの出力を予想して `notes.md` に書きます。
  1. `File.expand_path(File.join("/tmp/public", パス))` の結果。パスは `"/index.html"`、`"/../secret.txt"`、`"/docs/../../secret.txt"` の3つ
  2. `CGI.escapeHTML` に `"<b>太字</b> & \"引用\""` を渡した結果
  3. `name` に `"テスト太郎"` と `"' OR '1'='1"` を入れて、SQLの文字列を組み立てた結果（`puts` するだけで、データベースには送らない）
- 実行して、予想と比べます。
- **完了条件**：`ruby observe.rb` がエラーなく終わり、`notes.md` に予想・実際の結果・違っていた点の理由が書かれている
- ヒント：`CGI.escapeHTML` を使うには `require "cgi"` が必要です。2つ目は、ブラウザでどう表示されるかも想像してみてください。

### 演習10-4：自分のフォームへの攻撃シナリオを書く

- 第9章の演習で作ったメモのフォームが、サーバにつながった完成アプリだと仮定します（一覧表示・作成・削除ができ、ファイルの配信もする）。
- `threats.md` に、4つの攻撃それぞれについて次の表を埋めます。

| 攻撃 | 攻撃者が送るもの（具体的に） | 対策がないと起きること | 対策の考え方 | この教材で実装する章 |
| --- | --- | --- | --- | --- |

- **完了条件**：4行すべてが埋まり、「攻撃者が送るもの」に、実際のパス・入力値・HTMLのいずれかが書かれている
- ヒント：CSRFの行では、「攻撃者のページに何が書かれているか」を具体的に書きます。ルール1だけでは防げない理由にも触れましょう。

### 演習10-5（発展）：防御の不足の記録用紙を作る

- 本文の「テストが通っても本番に出せない理由」の表を、`security-record.md` として自分のリポジトリに作り、コミットします。
- 各領域の「状態」をすべて「未確認」にし、「いつ見直すか」の列を追加して、第11章・第13章・第17章・第26章のどこで見直すかを自分で割り当てます。
- **完了条件**：`git log --oneline -- security-record.md` でコミットが1件以上表示され、5つの領域すべてに見直す章が書かれている
- ヒント：割り当てに正解はありません。第11章の時点では、ほとんどが「未実装」になるはずです。それでよいのです。

## 確認クイズ

解答を見る前に、自分の言葉で答えを書いてください。

**Q1.** サーバをホスト指定なしで起動し、ブラウザで `http://localhost:3000` を開けた。これでループバック限定だと言えるか。

**Q2.** `key.pem` を誤って公開リポジトリにpushした。次のコミットで削除すれば十分か。

**Q3.** サーバを `127.0.0.1` で待ち受けていれば、CSRF対策は不要か。

**Q4.** HTTPSで接続すると証明書のエラーが出た。`curl -k` をつけて解決してよいか。

**Q5.** 一覧の並び順を、クエリパラメータ `?sort=title` でカラム名ごと切り替えたい。SQLの `?` でバインドすれば安全か。

**Q6.** 全章の演習のテストが通った。社内の小さなツールとして、共有サーバで動かしてよいか。

### 解答と解説

1. **言えない。** 全入口で待ち受けていても、自分のPCからは接続できます。ホストに `127.0.0.1` を明示して起動し、`lsof` や `ss` で `127.0.0.1:3000` と表示されることを確かめます。
2. **不十分。** Gitの履歴に残り、すでに誰かに複製された可能性もあります。漏えいしたものとして使うのをやめ、鍵と証明書を作り直します。以後は、作る前に `.gitignore` を確認します。
3. **必要。** 利用者のブラウザも同じPCで動いています。悪意あるページを開くと、そのページがブラウザに `127.0.0.1` 宛てのリクエストを送らせることができます。
4. **よくない。** `-k` は確認を止めるだけで、原因は解決しません。`--cacert cert.pem` で確認し、失敗するなら証明書のホスト名や有効期限を調べます。`-k` を使うのは第13章の比較だけです。
5. **安全にはならない。** カラム名は値ではないのでバインドできません（文字列の値として扱われ、意図どおりに並び替わりません）。許可リストにあるカラム名だけを受け付けます（第16章）。
6. **動かしてはいけない。** テストは学習範囲の完了条件だけを確かめています。資源の上限・タイムアウト・認証などは保証されていません。社内ネットワークも「信頼できないネットワーク」に含めて考えます。

## AIの使い方（この章）

推奨する聞き方の例です。

- 「パストラバーサルについて、私の理解を書きます。たとえ話と、`File.expand_path` の例が合っているか確かめてください。抜けている攻撃パターンがあれば、名前だけ教えてください。」
- 「この章の確認クイズに、私はこう答えました。採点して、理由が弱いところを指摘してください。」
- 「`lsof` の出力で `*:3000` と表示されました。この意味と、どこを直せばよいかの考え方を教えてください。」（出力を貼るときは、ユーザー名などを伏せてもかまいません）

この章でやってはいけない使い方です。

- 秘密鍵・トークン・パスワード・本物の個人情報を含むファイルやログを、AIに貼ること。AIへの入力も「共有」の一種です。共有前チェックリストと同じ基準で確認してから貼ります。
- 後の章で実装する対策コード（パスの検査、エスケープ、トークン検証、バインド）を、AIに生成させること。対策は「なぜその書き方で防げるのか」を自分で説明できて初めて意味があります。

## まとめ

演習では、ループバックでの待受、ダミーデータ、秘密情報をコミットしないこと、`curl -k` を比較だけに使うこと、の4つを守ります。待受先は「つながった」ではなく `lsof` / `ss` で確かめます。4つの攻撃の多くは、外から来たデータが命令として解釈されることで起きます。対策は第11・14・16・17章で実装し、攻撃が失敗するテストで確かめます。テストが通っても、本番で必要な防御はまだ足りていないことを忘れないでください。

## 用語

| 用語 | 意味 |
| --- | --- |
| ループバック | 自分のPCの中だけで完結する通信。`127.0.0.1` / `::1` |
| `0.0.0.0` | 「このPCのすべての入口」。外からもつながる |
| 待ち受け（listen） | サーバが「この住所とポートで受け付けます」と準備すること |
| 秘密鍵 | 本物であることを証明するための秘密のファイル。他人に渡さない |
| `.gitignore` | Gitで追跡しないファイルを書いておくリスト |
| 中間者攻撃 | 通信の途中に割り込み、本物になりすます攻撃 |
| 信頼境界 | 「ここから先は自分の管理外」という境目 |
| パストラバーサル | `../` などで公開範囲の外のファイルを読む攻撃 |
| XSS | 入力に仕込んだプログラムを、他人のブラウザで動かす攻撃 |
| エスケープ | 特別な意味を持つ文字を、ただの文字に変えること |
| CSRF | 他のサイトから、本人になりすましたリクエストを送らせる攻撃 |
| トークン | 本物のリクエストを見分けるための、推測できない合言葉 |
| SQLインジェクション | 入力でSQLの命令を書き換える攻撃 |
| バインド | SQLに値を、命令と混ざらない別の通り道で渡すこと |
| 許可リスト | 受け付けてよいものだけを並べた一覧。それ以外は断る |
